# 자체 학습모델 vs 관리형 LLM(Bedrock)-only — 아키텍처 근거

## 0. 한 줄 요약

이건 "자체 모델 vs LLM" 둘 중 하나를 고르는 문제가 아니다. **결정론적 조인·사실 정확성·대량 저비용이 필요한 코어는 자체 학습모델**(CRF NER·z-score 이상탐지·LightGBM 랭킹·자체 검색)이, **생성·멀티모달이 필요한 표면은 관리형 LLM**(다듬기·유튜브 추출)이 맡는 **역할 분담**이 정답이다. "Bedrock만"으로 가면 ① 조인 키 부재로 개인화·장보기 로직이 붕괴하고 ② 가격·영양 사실이 환각되며 ③ 대량 실행 비용이 폭발한다.

## 1. 비교 대상 정의

| | 내용 |
|---|---|
| **하이브리드(우리 설계)** | 자체 CRF NER로 재료를 표준 품목코드로 정규화 → 자체 DB(ES·PG) 검색·근거 조립 → LLM은 마지막에 문장만 다듬음(refine-only) |
| **Bedrock-only** | 자체 NER·검색 없이, 질문을 관리형 LLM에 던져 답을 통째로 생성 |

> Bedrock = AWS의 관리형 LLM 호스트(Claude·Nova 등). Gemini는 Bedrock에 없어 현재는 Gemini API 직접, AWS 이전 후 Bedrock의 Nova/Claude로 교체 예정(`chat-assistant-ai.md §3`).

## 2. 자체 학습모델의 확실한 이점

### 2.1 결정론적 조인 키 — 가장 결정적

CRF NER의 진짜 산출물은 "자연스러운 답"이 아니라 **표준 품목코드**(예: 마늘=`ING-0042`)다. 이 코드가 **냉장고 재고 ↔ 레시피 재료 ↔ 마켓 상품가 ↔ 영양 테이블을 잇는 유일한 조인 키**(`ai-spec.md §0`, `design.md §6.3`)다.

- LLM은 확률적이라 "마늘"·"깐마늘"·"다진마늘 한 스푼"을 매번 다른 문자열로 출력 → **안정적 ID가 없어 DB 조인 불가**.
- 앱 데이터 모델 전체가 이 코드 위에 인덱스·조인으로 서 있다. Bedrock-only는 매 호출마다 매핑을 비결정적으로 재추론해야 하고, 그 위에 집계·조인을 못 얹는다.
- **핵심 기능이 성립하려면 필수**: "장보기 목록 = 레시피 재료 − 재고 차감 − 중복 합산", "이 재료 쓰는 레시피 추천", "영수증 품목 → 재고 등록" 전부 안정적 코드가 있어야 동작.

### 2.2 사실 정확성 — 환각 차단

가격·영양·유통기한은 **틀리면 안 되는 사실**이다(유통기한 오류 = 상한 음식 섭취 위험). LLM-only는 파라미터 기억에서 생성 → "대파 2,500원"이 추측일 수 있다. 자체 검색 + 근거 조립이 숫자를 DB에서만 가져오도록 보장한다(가드레일 `check_output_grounded`로 근거 밖 숫자 차단, 실측 검증됨).

> 역설: Bedrock으로 사실을 정확히 답하려면 결국 검색·근거 레이어를 붙여야 한다 → 그 순간 "Bedrock만"이 아니라 RAG가 된다. 즉 자체 검색 레이어는 **회피 불가**.

### 2.3 비용·지연 — 규모에서 갈림

최저가 이상탐지(z-score)·레시피 랭킹(LightGBM)은 **대량·상시 실행**된다(가격 폴링마다, 알림 fan-out 수천 유저마다). LLM 호출로 하면 건당 비용·지연이 규모에 곱해져 경제성이 깨진다. 자체 CPU 모델은 ~0원·수 ms — 학생예산·CPU 전용 제약(`AGENTS.md`)과 정합. 이 영역에서 자체 모델은 "품질 우위"가 아니라 **규모에서 감당 가능한 유일한 방법**이다.

### 2.4 차별화(moat)·통제

- **평가 차별화**: "누구나 ChatGPT에 요리 물어봄" vs "한국 식재료를 표준코드로 정규화하는 자체 모델로 개인 냉장고·예산·시세를 잇는다"(`design.md §4.3`) — 기술 기여도가 다르다.
- **개선 통제**: 자체 모델은 span F1을 측정하고 자체 코퍼스로 재학습해 한국 식재료 특화 오류를 고칠 수 있다. Bedrock-only는 벤더 모델에 종속돼 프롬프트 튜닝만 가능.
- **주권**: 자체 모델은 온프렘 CPU에서 외부 의존·데이터 유출·건당 과금 없이 상시 동작.

## 3. 정직한 균형 — LLM이 오히려 맞는 부분

전부 자체 모델이 낫다는 주장은 과장이다. 다음은 관리형 LLM이 정답:

| 영역 | 이유 |
|---|---|
| 자연스러운 문장 생성(다듬기) | 템플릿 나열보다 LLM 재작성이 우수 → 그래서 Gemini를 붙임 |
| 유튜브 영상 멀티모달 추출 | 자체 구축 불가, Gemini가 정답(승인된 예외) |
| 임의 표현·롱테일 의도 커버리지 | 규칙/CRF보다 LLM이 유연 |

## 4. 결론 — 층별 역할 분담

| 차원 | 자체 학습모델 | Bedrock-only |
|---|---|---|
| 표준 품목코드(조인 키) | ✅ 결정론적·DB 조인 가능 | ❌ 비결정적·조인 불가 |
| 가격·영양 사실 정확성 | ✅ DB 근거·환각 0 | ❌ 환각 위험(검색 붙이면 RAG로 회귀) |
| 대량·상시 실행 비용 | ✅ ~0원·ms(CPU) | ❌ 건당 과금·지연 폭발 |
| 개인화(냉장고·예산 연결) | ✅ 코드 기반 조인으로 성립 | ❌ 조인 키 없어 붕괴 |
| 자연스러운 생성 | △ 템플릿(기본) | ✅ LLM 우위 |
| 멀티모달(영상) | ❌ 불가 | ✅ LLM 필요 |

**정리**: 자체 학습모델 레이어는 Bedrock-only의 세 실패 지점(조인 키 부재·사실 환각·규모 비용)을 정확히 막는다. 반대로 자체 모델만 고집하면 생성 품질·멀티모달에서 지므로, **코어=자체 모델 / 표면=관리형 LLM**의 하이브리드가 각 층에서 최적이다.
