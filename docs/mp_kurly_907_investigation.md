## 2. 컬리 카테고리 페이지의 구조를 확인한다

**왜** — SSR(서버 렌더) 이면 curl 로 그대로 재현할 수 있고, CSR(클라이언트 렌더) 이면
브라우저가 필요하다. 재현 방법 자체가 여기서 갈린다.

**한 것** — 907·908 셸을 curl 로 받고, `_next` 번들 청크 14개를 내려받아 정적 분석.

**결과**

**① CSR 이다.** 셸은 14KB, `<article>` 0개, `/goods/` 링크 0개. 상품은 전부 XHR 로 온다.

**② 상품 XHR 이 세션 게이트에 묶여 있다.**

```js
let f = useSelector(e => e.session.hasSession)
useQuery({ queryKey: paginatedProductList(...), queryFn: ..., enabled: f && p })
```

즉 카드 0개는 **"상품이 없다"가 아니라 "부팅이 안 끝났다"** 와 구분되지 않는다.

**③ 그래서 "907 만 실패"는 카테고리 문제가 아니다.** 907 은
[prototype.py:23](../crawler/kurly/prototype.py#L23) `CATEGORIES` 의 **첫 키**일 뿐이고,
실패 축은 **콜드 컨텍스트의 첫 내비게이션**이다. 반증법 = 순서를 뒤집으면 908 이 실패해야 한다.

**→ 다음** — curl 로는 재현할 수 없다. 브라우저를 띄우기 전에, 사고 시각의 흔적이
어디 남아 있는지부터 뒤진다. 남아 있으면 03:30 을 기다릴 필요가 없다.

## 5. 브라우저 시계 의존 렌더링 가설 — 24시간 전수 스윕

**왜** — 크롤러 컨테이너에 `TZ` 가 없다(`mp-pipeline-env` 키 11개에 TZ 없음). 브라우저는
**UTC 로 돈다.** 03:30 KST 실패는 브라우저가 보기엔 전부 **18:30** 이었다. 그리고 컬리
`moderate.kurly.com/event/config` 에는 **타임존 없는 로컬시각** 창들이 들어 있다:

```
"start":"2026-08-12T20:00:00"  "startReal":"2026-08-12T20:30:00"  "end":"2026-08-12T22:33:00"
"startDateTime":"2026-08-10T10:55:00"   "endDateTime":"2026-08-16T23:59:59"
```

`startDateTime` 이 **08-10** 이고 실패는 **08-11 03:30 부터** 결정적이 됐다. 정황이 겹친다.
그리고 **브라우저 시계는 우리가 정하는 값**이라 지금 전수 검사할 수 있다.

**한 것** — 로컬 docker 로 프로덕션과 동일한 Chromium 확보 후, `Emulation.setTimezoneOverride`
로 UTC-12 ~ UTC+14 를 훑었다. 워밍 컨텍스트 27개 + 콜드 컨텍스트 8개.

> **환경 구축 중 걸린 것 3가지**
> - 로컬 pip playwright 는 chromium 이 `exitCode=127` — 시스템 라이브러리 부재(`install-deps` 가 sudo 요구) → docker 로 전환
> - `docker pull` 을 백그라운드로 돌리면 레이어 시작 직후 프로세스가 죽는다 → **포그라운드로 재시도**해서 해결
> - 컨테이너 기본 브리지 네트워크에서 **DNS 해석 실패** → `--network host` 로 해결

**결과 — 전 구간 96장. 기각.**

```
Etc/GMT+11   200  goto 0.57  Wed Aug 12 2026 18:25:58   96장
UTC          200  goto 0.56  Thu Aug 13 2026 05:26:13   96장
Etc/GMT-14   200  goto 0.49  Thu Aug 13 2026 19:26:33   96장
... 27개 시간대 전부 96장, 콜드 컨텍스트 8회도 전부 96장
```

**→ 다음** — 가설은 죽었지만 **부산물이 하나 나왔다.** 35회 측정에서 정상 셸의 `goto`
(DOMContentLoaded) 가 **한 번도 0.49초 아래로 내려가지 않았다.** 프로덕션 실패의 goto 추정치
(≈0.3초)와 충돌한다. 이걸 정밀하게 판다.

## 6. 15.4초 성분 분해 — 여기서 원인이 잡혔다

**왜** — `goto` 값을 산술적으로 확정하면, 03:30 에 온 문서가 평소의 셸이었는지 아닌지가 갈린다.

**한 것**

1. 상품 API(`api.kurly.com`)만 차단해 **실패를 재현**하고, `_wait_for_cards` 30폴 루프의
   실제 소요를 실측
2. DOM 크기가 다른 문서 5종으로 **지문표**를 만들어 프로덕션 값과 대조

**결과 ①** — 루프는 정상 셸에서 **15.42~15.51초**가 걸린다. 폴마다 `locator("article").count()`
CDP 왕복이 붙어 `30 × 515ms` 가 되기 때문이다. **그런데 프로덕션 총계는 15.386~15.412초로
루프 단독보다도 짧다.** ⇒ 프로덕션에서는 `count()` 가 훨씬 쌌다 ⇒ **DOM 이 작았다.**

**결과 ② — 지문표**

| 문서 (로컬, 동일 Chromium) | goto | 30폴 루프 | **총계** | DOM 노드 |
|---|---|---|---|---|
| 정상 셸 + 상품 API 차단 | 0.79 | 15.51 | **16.30** | 343 |
| 없는 카테고리(9999999) | 0.89 | 15.47 | **16.36** | 355 |
| 컬리 404 페이지 | 0.95 | 15.29 | **16.24** | 220 |
| about:blank | 0.01 | 15.29 | **15.31** | 3 |
| 스크립트 없는 소형 오류문서 | 0.02 | 15.21 | **15.22** | 4 |
| 🔴 **프로덕션 03:30** | ? | ? | **15.386 / 15.401 / 15.412** | ? |

프로덕션 값은 **정상 셸 계열(16.2~16.4)에 전혀 붙지 않고 소형 문서 계열(15.2~15.3)에 붙는다.**

**결과 ③ — goto 의 산술적 상한**

루프는 구조상 최소 `30 × 500ms = 15.0초`다. 총계 15.386초에서 빼면
**goto ≤ 0.386초** — 기계 속도와 무관한 상한이다. 그런데

- 같은 클러스터·같은 노드·같은 이미지의 **정상 콜드 파드 goto = 0.62초**
- 로컬 실측 정상 셸 goto = **35회 전부 0.49~0.95초**

deferred 스크립트 4.7MB 를 **실행까지** 마쳐야 DOMContentLoaded 가 나므로,
**정상 셸은 0.386초 안에 DCL 이 날 수 없다.**

### 결론

**03:30 에 첫 요청이 받은 것은 평소의 카테고리 셸이 아니라, 앱 번들이 붙지 않은 작은 문서다.**
CloudFront·WAF 계열 오류/차단 페이지가 전형적으로 그 모양이다(1KB 안팎·스크립트 0).
그래서 카드는 끝까지 0이었고, 15초 뒤 908 은 정상 문서를 받아 아무 일 없이 돌았다.

> **자기 정정 기록** — 중간에 "curl 로 재보니 셸+스크립트 전송이 0.16~0.23초라 0.29초도
> 가능하다"며 이 논거를 한 번 철회했다. 그건 **원시 전송만** 본 것이고 브라우저의 파싱·실행이
> 빠져 있었다. 실제 브라우저로 재니 하한이 0.49초여서 철회를 **다시 뒤집었다.**

**① [prototype.py:90](../crawler/kurly/prototype.py#L90) — `page.goto()` 의 Response 를 버린다**

```python
await page.goto(url, wait_until="domcontentloaded", timeout=GOTO_TIMEOUT_MS)
return                      # ← Response 객체가 여기서 사라진다
```

Playwright 는 **HTTP 4xx·5xx 에 예외를 던지지 않는다.** 429든 503이든 차단 페이지든 전부
"정상 이동"으로 지나간다. **03:30 에 무슨 응답이 왔는지가 로그에 없는 이유가 이것이다.**

**② [prototype.py:155](../crawler/kurly/prototype.py#L155) — `_wait_for_cards()` 반환값을 버린다**

```python
await _wait_for_cards(page)      # ← 카드 수를 돌려주는데 아무도 안 받는다
```

"0장 렌더"인지 "96장 렌더 후 파싱 0"인지 로그로 못 가른다. 이번 조사는 그걸 **타이밍으로
역산**해야 했다.

**③ 부수 — 컨테이너 TZ 미설정(UTC)**

이번 원인은 아니다(§5 에서 기각). 다만 시각 의존 렌더가 있는 사이트를 UTC 브라우저로 긁는
구조라 별건으로 기록해 둔다.

## 9. 조사 중 하지 않기로 한 것과 그 이유

**① 클러스터 프로브 파드** — 매니페스트까지 작성했으나(`probe-pod.yaml`) **적용하지 않았다.**
`kubectl apply` 가 "클러스터 변경 금지" 지시에 따라 권한 계층에서 차단됐고, 지시를 우회할
사안이 아니었다.

**② 밤샘 관측 파드** — 부하를 계산해 보고 **보류**했다.

| | 클러스터 | 컬리 쪽 |
|---|---|---|
| 로컬 curl 샘플러 | 오브젝트 0 | 14MB (크롤 1회의 9%) |
| 낮 프로브 3분 | Pod 1개 · 3분 | 24MB |
| **밤샘 프로브(원안)** | **Pod 1개 · 17시간** | **470MB = 크롤 3회분** |

결정적이었던 건 트래픽이 아니라 **메모리**다. 크롤러 실사용이 1,676MB 인데, 밤샘 프로브를
그대로 올리면 03:30 에 진짜 잡과 같은 노드에서 **3.3GB** 를 쓴다. worker-a2 는 이미 메모리
request 70% 다. **조사 도구가 관측 대상을 밀어내 진짜 크롤러를 죽일 수 있다** — 그래서 접었다.
(올린다면 상품 이미지 차단 + 간격 확대로 36MB·400MB 수준으로 낮춘 판이어야 한다.)

**③ 대기시간 증량** — 이미 기각된 방향이라 재제안하지 않았다.

## 10. 로컬 재현으로 도달한 한계선

이 조사는 클러스터를 건드리지 않기 위해 **로컬 docker** 로 밀어붙였다. 어디까지 갔고
어디서 멈췄는지를 분명히 남긴다.

### 10.1 로컬로 확정한 것

| 확정 사항 | 근거 |
|---|---|
| 정상 셸의 `goto` 하한 = **0.49초** | 프로덕션과 동일 Chromium 으로 35회 측정, 전부 0.49~0.95초 |
| 프로덕션 `goto` **상한 = 0.386초** | 루프가 구조상 최소 `30 × 500ms` 이므로 총계에서 뺀 산술값 |
| ⇒ **평소의 셸이 아니었다** | 0.386 < 0.49. 정상 셸은 그 시간 안에 DCL 이 날 수 없다 |
| 30폴 루프 상수가 **DOM 크기에 비례** | 정상 셸 15.42~15.51초 vs 소형 문서 15.21~15.29초 |
| ⇒ **DOM 이 작았다** | 프로덕션 총계가 정상 셸의 루프 단독보다도 짧다 |
| 브라우저 시계 의존 렌더 **기각** | 24시간 × 워밍/콜드 전부 96장 |
| 상품 API 지연 **기각** | 무인증·`no-store` → 캐시 불가 ⇒ 그게 원인이면 908 도 죽었어야 함 |
| 907 품절·개편 **기각** | API 직접 호출로 907~910 전부 96건 |

### 10.2 로컬로는 **원리적으로 확정 불가**한 것

**① 실제 HTTP 상태코드** — 그 응답은 **우리 회선·그 시각에만** 온다. 로컬 egress 는
`118.131.22.86`(Tailscale 경유), 클러스터는 집 LAN NAT 로 **서로 다른 IP** 다. CDN·WAF 응답은
클라이언트 IP 와 경로에 따라 갈리므로, 로컬에서 무엇이 오든 그게 그 파드가 받은 것이라는
보장이 없다.

**② 로컬 재현의 음성 결과는 아무것도 증명하지 못한다** — 03:30 에 로컬에서 정상이 나와도
"컬리가 IP 별로 다르게 응답" 인지 "우리 클러스터 경로 문제" 인지 가르지 못한다. 양성이면
컬리 쪽 확정이지만, **음성은 미결**이다.

**③ 우리 쪽 네트워크 계층 요인은 로컬에 존재하지 않는다** — Cilium `toFQDNs` 정책이 새 IP 에
프로그래밍되기 전 SYN 이 드롭되는 경합(재시도 사다리 1·3·7·15초), CoreDNS·Cilium DNS 프록시
경유 해석 등은 **로컬 docker 에 아예 없는 계층**이다. 확인하려면 파드가 필요하다.

**④ 물리 계층은 어느 쪽에서도 확인 불가** — 집 공유기·ISP 회선의 그 시각 거동. §4 의
"우리 코드도 클러스터 설정도 아니다" 논증에서 유일하게 남겨둔 예외가 이것이다.

**⑤ 사후 관측의 해상도** — 로컬과 무관한 한계지만 같이 적어둔다. cAdvisor 스크레이프가
**30초**라 15초짜리 사건을 못 가른다. Istio 사이드카 없음 · Cilium/Hubble 메트릭 미수집이라
요청 단위 기록은 어디에도 남지 않는다.

### 10.3 아직 제거되지 않은 교란요인

**cron 은 항상 `:30:00` 정각에 뜨고, 지금까지 성공한 관측은 한 번도 정각이 아니었다.**
즉 현재 데이터로는 "03:30 이라서"와 "정각이라서"가 분리되지 않는다. 정각에 함께 뜨는 것은
`mp-descheduler`·`mp-bitrot-canary-b1/b2` 뿐이고 셋 다 무해해 보이지만(축출 0건),
**분리 실험은 하지 않았다.**

## 11. 남은 한 칸과 다음 과정

확정되지 않은 것은 **딱 하나, 실제 HTTP 상태코드**다. 예측은 **`!= 200`(502·503 계열 또는
차단 페이지)**.

### 다음 수 — 두 줄 추가 PR

```python
resp = await _goto_with_retry(page, url, code)        # 반환값을 받기만 한다
card_count = await _wait_for_cards(page)              # 반환값을 받기만 한다
raise CrawlTruncatedError(f"... HTTP {resp.status} · 렌더된 카드 {card_count}장 ...")
```

- **지우는 코드가 없다** → C-72(온프렘 동결, 덧셈만) 에 걸리지 않는다
- 오브젝트를 만들지 않고, 크롤 횟수도 그대로다 → **추가 부하 0**
- `pipelines` Application 이 `automated` 라, 머지하면 Jenkins → config `:sha` → ArgoCD 자동
  동기화로 **당일 밤 03:30 런이 이미 계측된 상태로 돈다**
- 재발할 때마다 영구히 증거가 남는다

여기에 실패 시 **미완결 요청 목록 + `page.content()` 앞부분**까지 얹으면(역시 덧셈만) 한 번에
끝난다.

### 판정 기준

| 다음 03:30 로그 | 결론 |
|---|---|
| `HTTP != 200` | **§6 결론 확정.** 컬리/CDN 쪽 응답 문제. 대응은 첫 내비게이션 재시도 |
| `HTTP 200` + 카드 0 | 문서는 정상이었고 부팅(세션·설정 XHR)이 막힌 것. 워터폴 수집으로 한 단계 더 |
