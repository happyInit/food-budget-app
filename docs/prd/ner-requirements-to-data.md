## Part 1. item_master / gazetteer 정리 요구

> ⚠️ **핵심: 이건 "육류 버그" 하나가 아니라 매칭 메커니즘·granularity 정책의 문제다.** 육류만 고치면 아래 다른 클래스가 계속 튀어나와 무한 땜빵이 된다. 그래서 **개별 케이스 수정이 아니라 정책 확립**을 요청한다.

### 1.1 문제 — 체계적 오분류 (실측)

gazetteer(`make_matcher`)는 별칭 **1,055개**(그중 **1~2자 짧은 별칭 323개**)에 exact/**prefix**/**suffix** 매칭을 한다. 이 strip 매칭이 수식어를 무차별로 벗겨 **여러 클래스**에서 오분류한다:

| 클래스 | 실측 예 | 현재 결과 | 심각도 |
|---|---|---|---|
| **prefix 오매칭** | 간장게장 → **간장**(prefix) | 게장(게)이 간장으로 **완전 오분류** | 🔴 |
| 동물·부위 (→ **PR #54에서 처리 중**) | 소갈비·닭갈비 → 갈비 / 돼지갈비 → 돼지고기 | 육류 뭉갬·경로 불일치 | 🔴 |
| 조리형태 | 양념치킨 → 닭고기 (suffix) | 조리 정보 손실 | ⚠️ |
| 품종/원산지 | 대추방울토마토 → 방울토마토 (suffix) | 품종 손실 | ⚠️ |
| 종류 | 볶음김치·열무김치 → 김치 (suffix) | 종류 손실 | ⚠️ |
| 가공상태(대체로 OK) | 냉동새우→새우, 깐마늘→마늘 | 같은 재료라 허용 가능 | ✅ |
| 짧은 별칭(≤2자) | 밥·김·무·파·조·란 등 **323개** | substring/부분매칭 오탐 표면 | ⚠️ |

> 주의: prefix 매칭(간장게장→간장)은 현재 챗봇의 rule 추출기가 exact/suffix만 채택해 직접은 안 걸리지만, **매처 자체가 지원**하므로 다른 소비처(레시피 재료 item_id 정규화 등)에서 활성될 수 있다. 즉 이건 **공유 정규화 계층의 잠재 오류**다.

> **🔗 육류(동물·부위) = PR #54(`docs/proposals/gazetteer-meat-granularity.md`)에서 이미 재현·수식어 가드 프로토타입 진행 중 → 이 문서는 육류를 중복 요청하지 않는다.** #54가 정교화한 사실(반영): (1) 데모의 "갈비→마성의 닭갈비" 뒤섞임은 **매칭 붕괴가 아니라 nori 형태소 검색**(별도 검색 이슈) (2) "소갈비→돼지갈비 누출"은 **품질 게이트가 1192-태그 레시피를 전부 제외해 item_id 경로가 현재 inert** — 게이트 완화·NER 배선·item_id 조회 승격 시 실오답으로 전환되는 잠재 오류. 이 문서는 **육류를 뺀 나머지 정책(prefix·조리형태·품종·종류·짧은 별칭)**에 집중한다.

### 1.2 근본 원인 (per-term 아님)

1. **수식어 정책 부재** — 어떤 수식어는 보존해야 하고(동물·품종·조리·종류) 어떤 건 무시 가능(가공·브랜드·"친환경")인데, strip 매칭이 이를 구분 없이 다 벗긴다.
2. **granularity 일관성 부재** — 어떤 복합어는 별도 품목(닭가슴살·목살), 어떤 건 base로 뭉갬(양념치킨→닭고기). 나눌지/합칠지 기준이 없다.
3. **짧은 별칭 오매칭** — ≤2자 별칭 323개가 부분 매칭 오탐의 표면.
4. **prefix 매칭의 위험** — 앞부분만 잡아 완전 오분류(간장게장).

### 1.3 요구 — 정책 확립 (땜빵 아님)

1. **매칭 정책 정의·문서화**: ① exact/최장 별칭 우선(strip보다) ② **보존해야 할 수식어 클래스 목록**(동물·품종·조리·종류)을 정해 그 접두/접미는 안 벗기게 ③ **prefix strip은 원칙 금지**(오분류 위험) — 재검토.
2. **짧은 별칭(≤2자) 감사**: 323개 검토 → 독립 토큰일 때만 매칭하거나 위험한 것 제거.
3. **granularity 기준**: 복합어를 별도 품목 vs base 뭉갬으로 나누는 일관 규칙.
4. **육류(동물·부위)는 PR #54에서 처리 중** — 재현·수식어 가드 프로토타입(`proto_meat_guard.py`)이 이미 나와 있어 **이 문서에서 중복 요청하지 않는다.** 위 정책(1~3)이 육류를 포함한 전 클래스의 상위 규칙이며, #54의 육류 결정(종 세분화·remap)은 그 정책과 정합되게 진행하면 된다.

> NER 관점: NER은 "문장 어디가 재료명인지"만 뽑고 **표준코드 매핑은 item_master/alias 몫**이라, NER 정확도는 이 정규화 계층의 정확성에 상한이 걸린다. 위 정책이 서면 NER·챗봇·조인 전부가 함께 좋아진다.

## Part 2. NER 학습 데이터 — 합의 항목

> 아래 **1~4는 확정 요청**이다(없으면 CRF 학습이 깨지거나 재현이 안 됨). **학습전용 테이블(구 §5)은 요청하지 않기로 확정** — 학습 코퍼스·라벨·모델을 **AI-side 아티팩트(git → 추후 S3, `ai-spec.md §1`)**로 두는 **모델 X**를 채택(§2.3). 태현 쪽 테이블 작업 없음.

### 2.1 합의 필요 (택일/확인)

| # | 항목 | 요청 | 결정 |
|---|---|---|---|
| 1 | **원문 보존** | `recipe_ingredient.ingredient_raw`(COOKRCP01 자유텍스트)를 **정규화·축약 없이 원형 유지**. CRF가 문자 오프셋으로 라벨을 정렬하므로 다듬으면 학습이 깨짐 | 유지 확약 |
| 2 | **삭제·덮어쓰기 금지** | COOKRCP01·EPIS 행을 재적재/정리 시 **삭제하지 않기**. 서빙이 이미 격리하므로 앱엔 영향 없음 | 유지 확약 |
| 3 | **재적재 안전성** | 재적재 시 `ner_status='RAW'/'LABELED'` 행이 유실 안 되게 **레시피 단위 upsert**. 향후 사람이 검수한 라벨 보호용 컬럼(`labeled_at`,`labeled_by`) 여지 | 방식 합의 |
| 4 | **읽기 방식 = 스냅샷 export 확정** | 학습은 **1회 벌크 export**(CSV/JSONL, `source != '10K'`)로 스냅샷을 떠서 **오프라인 학습** — PG에 반복 쿼리 안 함. ⚠️ "학습이 OLTP에 라이브 쿼리를 많이 날려 부하"라는 우려는 이 방식으로 해소(수 MB 1회). 태현은 "언제·어떻게 한 번 떠줄지"만 정하면 됨. 재현성 위해 export 시점 타임스탬프 포함 | **ⓑ 확정** |
| ~~5~~ | ~~학습전용 테이블 분리~~ | **철회 — 요청 안 함.** 코퍼스·라벨을 AI-side 아티팩트로 둠(모델 X, §2.3) | 해당 없음 |

> **1~4가 요청의 전부다.** 최소한으로 1·2·4만 확약돼도 건우가 NER 착수 가능(3은 학습 중 재적재 없으면 후순위 가능).

### 2.2 건우 몫 (태현 작업 아님 — 공유용)

- EPIS와 COOKRCP01은 **서로 다른 소스라 `RECIPE_ID`로 조인 안 됨**(EPIS=정형 gold, COOKRCP01=자유텍스트, 별개 레시피). → 건우가 **EPIS 재료명을 사전으로 COOKRCP01 텍스트에 문자열 매칭해 약지도(weak supervision) BIO 라벨 자동 생성**. 이건 AI 쪽에서 진행하므로 태현에게 요청 없음.
- 10K(만개) 텍스트는 **학습 코퍼스로 사용 금지**(robots `ai-train=no`, `data-validation §2.2`) — 학습 추출 쿼리에서 `source != '10K'` 고정.

### 2.3 라벨·모델 저장 = 모델 X (AI-side 아티팩트) — 확정

- **결정(2026-07-15)**: 약지도 라벨 코퍼스 + 학습된 CRF 모델을 **AI-side 아티팩트**로 둔다 — 1차는 **git 버전관리**(CRF 모델 KB~MB·코퍼스 수 MB로 소형), 추후 AWS 이전 시 **S3/MLflow**로 승격(`ai-spec.md §1` 설계 그대로). **공유 PG에 라벨을 쓰지 않는다.**
- **읽기 = 1회 스냅샷 export → 오프라인 학습**(Part 2.1 #4 ⓑ). 학습이 OLTP에 라이브 반복 쿼리를 안 날리므로 **DB 부하 우려 없음**(태현 지적 대응). ⚠️ 참고: **같은 PG에 학습전용 테이블을 둬도 워크로드 격리는 안 됨**(같은 인스턴스) — 부하 관점에선 X+스냅샷이 오히려 유리.
- **근거**: ① 서빙 성능 무관(학습 코퍼스는 서빙 때 안 읽음 — 서빙은 학습된 모델+gazetteer만) → X·Y 성능 동일 ② 앱 OLTP 결합·재적재 위험 회피 ③ Swarm→k8s→AWS 이전 안전(아티팩트를 git/S3 등 **포터블 저장소**에 두므로 오케스트레이터 무관; 컨테이너 로컬파일만 금지) ④ 태현 의존 0.
- **설계 방어**: "OLTP에서 시점 스냅샷 1회 export → 오프라인 학습, 모델·라벨은 버전 아티팩트(git→S3/MLflow)"는 표준적인 ML 데이터 분리 — OLTP를 학습 루프에서 뺀 깨끗한 구성.
- **함의**: 태현은 학습 데이터용 **새 테이블·스키마 변경 불필요**. Part 2.1의 1~4(원문 보존·유지 + #4 스냅샷 export)만 지키면 됨.

## Part 3. 우선순위 · 순서

1. **Part 2.1** (원문 보존·삭제금지·읽기=스냅샷) 확약 — 이게 있으면 건우 NER 착수 가능(데이터 이미 적재됨).
2. **Part 1 — item_master 매칭 정책 확립(§1.3)** — 육류 단건이 아니라 정책(①exact 우선 ②보존 수식어 클래스 ③prefix strip 금지 ④짧은 별칭 감사 ⑤granularity 기준)이 요청의 본체. **NER 조인 정확도 상한을 결정**하므로 빠를수록 좋음. **육류는 PR #54에서 별도 진행** — 여기선 그 정책 프레임만 요청.
3. 위 회신 확정 후 건우가 약지도 라벨링 → CRF 학습 착수.

> **회신 요청**: (1) **Part 1.3 매칭 정책** 방향(①~⑤) — 육류는 #54로 다룸, (2) Part 2.1 표(#1·2·4)의 각 결정. 짧게라도 정해주면 그 전제로 진행.
