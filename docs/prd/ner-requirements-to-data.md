## Part 1. item_master / gazetteer 정리 요구

> ⚠️ **핵심: 이건 "육류 버그" 하나가 아니라 매칭 메커니즘·granularity 정책의 문제다.** 육류만 고치면 아래 다른 클래스가 계속 튀어나와 무한 땜빵이 된다. 그래서 **개별 케이스 수정이 아니라 정책 확립**을 요청한다.

### 1.1 문제 — 체계적 오분류 (실측)

gazetteer(`make_matcher`)는 별칭 **1,055개**(그중 **1~2자 짧은 별칭 323개**)에 exact/**prefix**/**suffix** 매칭을 한다. 이 strip 매칭이 수식어를 무차별로 벗겨 **여러 클래스**에서 오분류한다:

| 클래스 | 실측 예 | 현재 결과 | 심각도 |
|---|---|---|---|
| **prefix 오매칭** | 간장게장 → **간장**(prefix) | 게장(게)이 간장으로 **완전 오분류** | 🔴 |
| 동물·부위 | 소갈비·닭갈비 → 갈비 / 돼지갈비 → 돼지고기 | 육류 뭉갬·경로 불일치 | 🔴 |
| 조리형태 | 양념치킨 → 닭고기 (suffix) | 조리 정보 손실 | ⚠️ |
| 품종/원산지 | 대추방울토마토 → 방울토마토 (suffix) | 품종 손실 | ⚠️ |
| 종류 | 볶음김치·열무김치 → 김치 (suffix) | 종류 손실 | ⚠️ |
| 가공상태(대체로 OK) | 냉동새우→새우, 깐마늘→마늘 | 같은 재료라 허용 가능 | ✅ |
| 짧은 별칭(≤2자) | 밥·김·무·파·조·란 등 **323개** | substring/부분매칭 오탐 표면 | ⚠️ |

> 주의: prefix 매칭(간장게장→간장)은 현재 챗봇의 rule 추출기가 exact/suffix만 채택해 직접은 안 걸리지만, **매처 자체가 지원**하므로 다른 소비처(레시피 재료 item_id 정규화 등)에서 활성될 수 있다. 즉 이건 **공유 정규화 계층의 잠재 오류**다.

### 1.2 근본 원인 (per-term 아님)

1. **수식어 정책 부재** — 어떤 수식어는 보존해야 하고(동물·품종·조리·종류) 어떤 건 무시 가능(가공·브랜드·"친환경")인데, strip 매칭이 이를 구분 없이 다 벗긴다.
2. **granularity 일관성 부재** — 어떤 복합어는 별도 품목(닭가슴살·목살), 어떤 건 base로 뭉갬(양념치킨→닭고기). 나눌지/합칠지 기준이 없다.
3. **짧은 별칭 오매칭** — ≤2자 별칭 323개가 부분 매칭 오탐의 표면.
4. **prefix 매칭의 위험** — 앞부분만 잡아 완전 오분류(간장게장).

### 1.3 요구 — 정책 확립 (땜빵 아님)

1. **매칭 정책 정의·문서화**: ① exact/최장 별칭 우선(strip보다) ② **보존해야 할 수식어 클래스 목록**(동물·품종·조리·종류)을 정해 그 접두/접미는 안 벗기게 ③ **prefix strip은 원칙 금지**(오분류 위험) — 재검토.
2. **짧은 별칭(≤2자) 감사**: 323개 검토 → 독립 토큰일 때만 매칭하거나 위험한 것 제거.
3. **granularity 기준**: 복합어를 별도 품목 vs base 뭉갬으로 나누는 일관 규칙.
4. **육류는 대표 케이스로 우선 처리**(당장 챗봇에 노출): 소/닭/돼지갈비가 서로 안 섞이게 + exact 우선 + 경로 일관. (세부 옵션 A=별도품목 / B=2축 / C=alias+매처예외 중 택일)

> NER 관점: NER은 "문장 어디가 재료명인지"만 뽑고 **표준코드 매핑은 item_master/alias 몫**이라, NER 정확도는 이 정규화 계층의 정확성에 상한이 걸린다. 위 정책이 서면 NER·챗봇·조인 전부가 함께 좋아진다.

## Part 2. NER 학습 데이터 — 합의 항목

> **"요구할 게 없다"가 아니다.** 배경 변화(COOKRCP01/EPIS 적재됨 + 서빙이 이미 `source='10K'`만(#46) → 앱 노출·삭제 우려 해소)로 **"새 물리 테이블 분리(#5)"만 덜 급해졌을 뿐**, 아래 **1~4는 확정 요청**이다. 이게 없으면 CRF 학습이 깨지거나 재현이 안 된다.

### 2.1 합의 필요 (택일/확인)

| # | 항목 | 요청 | 결정 |
|---|---|---|---|
| 1 | **원문 보존** | `recipe_ingredient.ingredient_raw`(COOKRCP01 자유텍스트)를 **정규화·축약 없이 원형 유지**. CRF가 문자 오프셋으로 라벨을 정렬하므로 다듬으면 학습이 깨짐 | 유지 확약 |
| 2 | **삭제·덮어쓰기 금지** | COOKRCP01·EPIS 행을 재적재/정리 시 **삭제하지 않기**. 서빙이 이미 격리하므로 앱엔 영향 없음 | 유지 확약 |
| 3 | **재적재 안전성** | 재적재 시 `ner_status='RAW'/'LABELED'` 행이 유실 안 되게 **레시피 단위 upsert**. 향후 사람이 검수한 라벨 보호용 컬럼(`labeled_at`,`labeled_by`) 여지 | 방식 합의 |
| 4 | **읽기 인터페이스** | 건우가 학습 시 데이터를 어떻게 받나 — ⓐ PG 직접 쿼리 ⓑ 시점 스냅샷(CSV/JSONL) export. 재현성 위해 **학습 시점 스냅샷 구분 장치**(타임스탬프 등) | ⓐ/ⓑ 선택 |
| 5 (선택) | **학습전용 테이블 분리** | 지금은 서빙 격리로 **급하지 않음**. 단 HITL 검수 라벨을 쌓을 계획이면 별도 테이블 or 위 3의 보호 컬럼이 깔끔 | 필요/불필요 |

> **1~4는 필수 확정, 5만 선택.** 최소한으로는 1·2·4만 확약돼도 건우가 NER 착수 가능(3은 학습 중 재적재 없으면 후순위 가능).

### 2.2 건우 몫 (태현 작업 아님 — 공유용)

- EPIS와 COOKRCP01은 **서로 다른 소스라 `RECIPE_ID`로 조인 안 됨**(EPIS=정형 gold, COOKRCP01=자유텍스트, 별개 레시피). → 건우가 **EPIS 재료명을 사전으로 COOKRCP01 텍스트에 문자열 매칭해 약지도(weak supervision) BIO 라벨 자동 생성**. 이건 AI 쪽에서 진행하므로 태현에게 요청 없음.
- 10K(만개) 텍스트는 **학습 코퍼스로 사용 금지**(robots `ai-train=no`, `data-validation §2.2`) — 학습 추출 쿼리에서 `source != '10K'` 고정.

## Part 3. 우선순위 · 순서

1. **Part 2.1** (원문 보존·삭제금지·읽기 인터페이스) 확약 — 이게 있으면 건우 NER 착수 가능(데이터 이미 적재됨).
2. **Part 1** (item_master 육류 정리) — NER과 병행 가능하나, **NER의 조인 정확도 상한을 결정**하므로 빠를수록 좋음. 옵션 A/B/C 택일 회신 요망.
3. 위 회신 확정 후 건우가 약지도 라벨링 → CRF 학습 착수.

> 회신 요청: Part 1.2 옵션(A/B/C), Part 2.1 표의 각 결정. 짧게라도 정해주면 그 전제로 진행.
