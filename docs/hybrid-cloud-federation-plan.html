"저희 AI 기능을 쿠버네티스로 이전하면서, 모델이 사는 클라우드를 따라 하이브리드로 구성합니다 — 챗봇은 AWS Bedrock, 영수증 OCR·영상 분석은 GCP Vertex AI를 씁니다. 억지로 나눈 게 아니라 모델 가용성이 자연히 가른 것이고, 실측으로도 AWS의 Nova는 한글 영수증을 못 읽고 GCP의 Gemini는 읽는다는 근거가 있습니다. 핵심 기술은 크로스클라우드 인증 연합입니다 — 쿠버네티스 워크로드 신원 하나로 두 클라우드에서 임시 자격을 받아 장기 비밀번호(정적 키)를 아예 두지 않습니다. 키 유출 표면이 사라지는 보안 이점과, 실무에서 가장 까다로운 멀티클라우드 인증을 직접 구현하는 학습·포트폴리오 가치가 큽니다. 진행은 PoC로 안전하게 — 기존 경로를 폴백으로 남기고 타임박스·비용 상한을 둬 되돌릴 수 있게 합니다."

3.5 k8s 마이그레이션 정합 — GCP가 이전에 편입된다 ★

기존 이전은 온프렘 Proxmox k8s → EKS 이식성(AWS 중심). 이 계획으로 GCP가 3번째 기질로 편입 → 마이그레이션이 "온프렘→EKS(AWS) + GCP"로 확장. 이전 계획에 추가되는 것:

영역기존(AWS 중심)GCP 편입 추가

GitOps(ArgoCD)k8s 매니페스트external_account config·SA·federated 워크로드

빌링·거버넌스AWS 크레딧GCP 프로젝트 빌링·예산알림·quota
신원AWS IRSA(계획)동일 OIDC issuer를 GCP WIF도 소비(재사용)
🔴 OIDC issuer = 두 클라우드 공유 임계 의존(신규 SPOF) — 이전 단계와 직결. 온프렘 유지 시 API서버 OIDC discovery(issuer+JWKS)를 공개 노출해야(MetalLB LB+TLS 또는 JWKS 정적 호스팅) → P0 선행 난제. EKS 이관 시 관리형 issuer 하나가 AWS IRSA + GCP WIF 둘 다의 앵커 → 턴키. ⇒ 연합 난이도가 k8s 이전 단계에 직결(온프렘=어려움/EKS=쉬움). issuer 다운 = 두 클라우드 인증 동시 마비 → HA·degraded fallback 필수.
