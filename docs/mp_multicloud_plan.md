## 4. 🔴 12번(DB 동기화)이 경첩이다

구 문서 §10.3 이 이미 경고했다 — *"PG 는 roll-forward 를 전제로 한다. **양방향 쓰기를 허용하면 되돌릴 수 없다.**"*

| 안 | 구조 | 쓰기 | 난이도 | 발표 서사 |
|---|---|---|---|---|
| **A. 단방향 복제** | 온프렘 primary → AWS **읽기 전용** replica | 한 곳 | 낮음 | "데이터가 흐른다" |
| **B. 액티브-패시브(DR)** | 평시 한쪽만 서비스 · 장애 시 승격 | 한 곳 | 중간 | 🟢 **"온프렘이 죽으면 AWS 가 받는다"** — 시연 가능 |
| **C. 양방향(멀티마스터)** | 양쪽 쓰기 · 충돌 해결 필요 | 양쪽 | 🔴 높음 | 강하지만 캡스톤 범위 밖 |

**B 를 권고한다** *(권고 — 팀 승인 대상)*:
- 우리는 이미 **CNPG 페일오버를 실증**했다(pg-1→pg-2 승격, 200 연속). 같은 서사의 확장이다
- 쓰기가 한 곳이라 §10.3 의 "되돌릴 수 없음" 함정을 밟지 않는다
- **RTT 문제가 사라진다** — 평시엔 서비스하는 쪽이 자기 로컬 DB만 본다

### 4.1 다른 데이터 컴포넌트

| | 처리 | 근거 |
|---|---|---|
| **ES** | **재파생** (동기화 안 함) | 재색인 **7초** 실측 (P2) |
| **Redis** | **재생성** | P2 결정 그대로 |
| **Kafka** | MirrorMaker2 or 단일 사이트 | 🔴 미정 — 12번에 종속 |
| **오브젝트** | S3 단일 (온프렘 MinIO 폐기) | 구 §11 |

## 5. 트랙 분리 — 무엇이 무엇에 묶이나

**서버리스는 거의 따로 논다.** 트랙별 결합도를 명시한다.

| 트랙 | 내용 | 선행 조건 | 다른 트랙 의존 |
|---|---|---|---|
| **T0 · 선행** | 구 §10.1 A0 (request 리사이즈 · priorityClass · SC 하드코딩 · 오버레이 실물화) | 없음 — **AWS 계정 없이 가능** | 없음 |
| **T1 · 인프라 이전** | VPC · EKS · 노드그룹 · 데이터 컷오버 | T0 | — |
| **T2 · CI 교체** | GitLab · 레지스트리 · ArgoCD 재배선 | 없음 | 🟡 약함 — 레지스트리 주소만 T1 과 맞물림 |
| **T3 · 멀티클라우드** | Tailscale · DB 동기화 · 라우팅 | **T1 완료 후** | 🔴 강함 |
| **T4 · 서버리스** | Lambda 등 | AWS 계정만 | 🟢 **거의 없음** |

### 5.1 서버리스(T4)가 따로 놀 수 있는 이유 — 그리고 결합점 3개

**EKS 이전과 시점이 독립**이다. 온프렘에 있든 EKS 로 갔든 Lambda 는 따로 만들 수 있다. **AWS 계정만 있으면 지금 당장 시작 가능**하고, EKS 를 기다릴 필요가 없다.

단 결합점이 셋 있다:

| 결합점 | 언제 문제되나 | 회피법 |
|---|---|---|
| 🔴 **VPC 접근** | Lambda 가 **PG 에 붙어야 하면** VPC Lambda 가 되고 서브넷·ENI·보안그룹이 T1 과 엮인다 | **외부 API 호출·오브젝트 처리만 하는 워크로드**를 고르면 완전 독립 |
| **CI 파이프라인** | GitLab 이 빌드·배포해야 함 | 별도 잡이라 T2 와 느슨하게 결합 |
| **IAM** | 역할·정책 발급 필요 | 독립적으로 가능 |

⇒ **VPC 접근이 없는 워크로드를 고르면 T4 는 완전히 독립 트랙이 된다.**

### 5.2 서버리스 후보 *(제안 — 결정 아님)*

| 후보 | VPC 필요? | 적합성 |
|---|---|---|
| **최저가 알림 fan-out** | 🟡 (알림 대상 조회) | 멘토 피드백의 **다자간 트래픽**과 직결 · 버스티 |
| **YouTube 영상 추출** | ❌ 불필요 | 온디맨드 · 외부 API(Gemini) 호출만 · **가장 독립적** |
| **영수증 OCR** | 🟡 (결과 저장) | 온디맨드 · 버스티 |
| 크롤 스케줄 트리거 | ❌ | 단순 |

## 7. 🔴 알려진 함정

### 7.1 구 §10.2 의 우려 3개 — 재평가

| 구 문서의 우려 | Tailscale 로 해결되나 |
|---|---|
| Site-to-Site VPN 상시 비용 | ✅ **완화** — Tailscale 이 훨씬 저렴 |
| 인터넷 송신 `$0.126/GB` | ❌ **그대로** — 어떤 터널을 써도 AWS 밖으로 나가는 바이트는 과금 |
| 앱→PG 왕복 9회 × 인터넷 RTT | ⚠️ **12번에 종속** — B(액티브-패시브)면 평시 로컬 DB 만 봐서 **소멸** |

### 7.2 🔴 WireGuard 캡슐화 3겹 — MTU

`mp_k8s_infra_migration_plan.md` 에 이미 계산이 있다:

```
VXLAN + Cilium WireGuard   →  오버헤드 ~110B  →  MTU ~1390
+ Tailscale(WireGuard)     →  ~60B 더         →  MTU ~1330
```

Tailscale 도 WireGuard 기반이라 **세 겹**이 된다. 동작은 하지만 **MTU 를 안 맞추면 큰 패킷만 간헐적으로 죽는** 최악의 증상이 나온다. **A5 착수 전에 계산·설정할 것.**

### 7.3 CI 전환 — 규칙 충돌

`CLAUDE.md §CI/CD 구조` 가 **"🔴 CI 는 Jenkins 다 … 새로 만들거나 다른 도구로 옮기지 말 것"** 이라고 명시한다. GitLab 전환은 이 규칙의 **정면 변경**이다.
⇒ **ADR 로 기록하고 `CLAUDE.md` 를 함께 갱신**해야 한다. 안 그러면 다음 세션이 옛 규칙을 따른다.

또한 호스트 C 의 **디스크 함정**(단일 98GB · 여유 27.9GB 에 Harbor 블롭 + JENKINS_HOME)이 EC2 에서 재현되지 않도록 **볼륨 사이징을 처음부터** 잡을 것.

### 7.4 "상시 vs 온디맨드"(구 §0-2)의 성격 변화

온프렘 존치가 확정되면서 이 결정의 의미가 바뀐다:
- **온프렘이 상시 서비스**를 맡으면 → AWS 는 **데모·DR 용 온디맨드**로 충분 → 회당 $2 급
- **AWS 가 상시**면 → 온프렘과 **이중 비용**

⇒ 12·13번(무엇을 어디에 두는가)과 **같이 결정해야 한다.**

### 7.5 이식 준비 실태 — 절반만 진짜

구 §9 의 지적이 **2026-08-05 현재도 유효**하다(실측):
- `services/*/overlays/eks/` 는 **placeholder** — `PLACEHOLDER.dkr.ecr…` · `newTag: "1.1.9"`(죽은 태그)
- **Jenkins 가 `overlays/onprem` 만 갱신**해서 eks 오버레이가 구조적으로 stale
- `platform/`·`pipelines/`·`monitoring/` 은 **오버레이 자체가 없음** → 실제 작업량이 여기 있음
- SC 이름 하드코딩 **5곳**

🔴 **GitLab 전환이 이 문제를 다시 연다** — 새 CI 가 두 오버레이를 어떻게 다룰지 T2 에서 같이 설계해야 한다.
