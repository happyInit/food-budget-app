## 1. 출발점 — 지금 무엇을 옮기는가 (2026-08-02 실측)

이전 계획의 첫 숫자는 "무엇을 옮기느냐"다. AWS 는 **요청량이 아니라 노드 수로 과금**하지만, **노드 수를 정하는 것은 요청량**이다.

### 1.1 컴퓨트

| 노드 | allocatable mem | **요청** mem | **실사용** mem | 실사용 CPU |
|---|---|---|---|---|
| `k8s-master` | 4,702Mi | — | 3,531Mi (75%) | 200m (12%) |
| `k8s-worker-a1` | 10,736Mi | 7,202Mi (67%) | 7,114Mi (66%) | 247m (4%) |
| `k8s-worker-a2` | 9,728Mi | 5,651Mi (58%) | 3,860Mi (39%) | 176m (3%) |
| `k8s-worker-b1` | 9,728Mi | 8,248Mi (84%) | 5,760Mi (59%) | 227m (4%) |
| `k8s-worker-b2` | 9,728Mi | 7,152Mi (73%) | 7,173Mi (73%) | 289m (5%) |
| **워커 합** | **39,920Mi** | **28,253Mi (27.6GiB)** | **23,907Mi (23.3GiB)** | **939m** |

🔴 **읽는 법 세 가지**

1. **메모리가 제약이고 CPU 는 유휴다.** 워커 CPU 사용률이 **3~5%** 다. 그런데 앱 파드 request 는 `mp-account` 500m · `mp-recipe` 300m 인데 실사용이 **3~4m**(SSOT §7.3-4). 온프렘에선 스케줄링 헤드룸만 낭비했지만, **AWS 에서는 request 가 곧 노드 수이고 노드 수가 곧 청구서**다.
2. **master 3,531Mi 는 그냥 사라진다.** EKS 컨트롤플레인은 관리형이고 `$0.10/hr` 정액이다. 노드 용량에서 4.6GiB 가 회수되고, SSOT §1.0 의 "master 하드 파워오프" 걱정도 함께 소멸한다.
3. **요청(27.6GiB) vs 실사용(23.3GiB) 격차는 메모리에선 크지 않다.** 데이터 티어(ES 3 JVM · Kafka 3 JVM · PG 2×2Gi req=lim · Prometheus)가 메모리를 *실제로* 쓴다. ⇒ **메모리 절감은 리사이즈가 아니라 replica 수 결정(§0-5)에서만 나온다.**

### 1.2 스토리지 — PVC 21개 / 합 351Gi

| 용도 | 용량 | AWS 에서 |
|---|---|---|
| kubecost (`aggregator-db` 64 + `local-store` 32 + `configs` 1) | **97Gi** | 판단 필요 — AWS 에서 더 유용하지만 볼륨이 최대 소비자다 |
| Kafka ×3 | 60Gi | gp3 (또는 MSK) |
| PG ×2 (data 20 + wal 10) | 60Gi | gp3. **실사용은 data 257Mi · WAL 1.1Gi** — 과대 프로비저닝 |
| MinIO | **50Gi** | 🔴 **삭제 → S3**(§9) |
| Prometheus | 30Gi | gp3 (또는 retention 단축) |
| ES ×3 | 30Gi | gp3. **인덱스 실사용 15MB** |
| Loki·Tempo·Alertmanager | 22Gi | 로컬 PV 부분만 — 백엔드는 이미 오브젝트 스토리지 |
| pipeline (crawl-state·chat-reports) | 2Gi | gp3 |

**gp3 로 그대로 옮기면** 351Gi × $0.0912 = **$32.01/월**. MinIO(50) + kubecost(97) 정리 시 204Gi = **$18.60/월**. 스토리지는 이 규모에서 지배적 비용이 아니다 — **하지만 EBS 는 AZ 에 고정**돼서 §5 의 HA 설계를 지배한다.

### 1.3 워크로드 — 총 105개 (Deployment/STS/CronJob/DaemonSet)

`app` 16 · `pipeline` 22 · `kube-system` 10 · `data` 9 · `observability` 9 · `argocd` 8 · `cost` 4 · 오퍼레이터·플랫폼 나머지.
이 중 **AWS 에서 소멸**: `metallb-system` 2 · `openebs` 2 · MinIO 1 · 하이퍼바이저 감시 계열(§9).

## 3. 비용 — 네 시나리오

> 🔴 전부 **§0 판단에 종속**된다. 산식을 노출했으니 판단이 정해지면 숫자를 다시 계산할 것.
> Spot 할인은 **65% 가정(미검증)**, ALB $16/월 **가정**. 두 값은 §2.4 참조.

### 3.1 S0 — 데모 온디맨드 (`apply` → 발표 → `destroy`)

**전부 IaC 이기 때문에 가능한 시나리오**이고, 학생 예산 제약에 가장 정직한 답이다.

```
회당 4시간 =  EKS          0.10 × 4  = $0.40
              노드 3× r7g.large 0.3876 × 4 = $1.55
              NAT GW       0.059 × 4 = $0.24
              gp3 204Gi    204 × 0.0912 × 4/730 = $0.10
                                        ─────────
                                          ≈ $2.29 / 회
```
+ 상시 유지분: Route53 호스팅존 $0.50/월 · S3(시드·백업·LGTM) ≈ $2/월 · ECR ≈ $1/월 ⇒ **월 $3.5 + 회당 $2.3**

**20회 리허설·발표 = 약 $50.** 온프렘 클러스터는 그대로 두고 AWS 는 "필요할 때 켜는 두 번째 리전"이 된다.

🔴 **대가**: ① 포트폴리오 URL 이 상시 살아 있지 않다 ② 크롤 CronJob(일·수 05:00)이 안 돈다 ③ Prometheus 시계열이 매번 끊긴다 ④ **`apply`→ArgoCD sync→시드 복원**이 몇 분 안에 재현 가능해야 한다(= 그 자체가 검증 과제이고, 사실 좋은 캡스톤 데모다).

## 4. 청구서를 결정하는 것은 인스턴스가 아니다 — 숨은 3대 비용

온프렘에서 **공짜였던 것**이 AWS 에서 유료가 되는 지점이다. 여기가 이 계획의 실질이다.

### 4.1 NAT Gateway — 고정비의 함정

$0.059/hr(**$43.07/월**) **+ $0.059/GB**. AZ 당 하나 두는 것이 정석이니 3-AZ 면 $129/월이 아무 트래픽 없이 나간다. S1 총액($371)의 12%, "가장 싼 구성"에서는 비중이 더 커진다.

**우리 egress 는 무엇인가** — 크롤러(마켓컬리·오아시스·만개레시피) · Gemini/Vertex · Bedrock · `mp-operations` 의 제3자 PG(`211.46.52.152`) · Harbor/ECR pull · apt·pip. 크롤러가 주 소비자이고 **주 1회 레시피 크롤 + 일 1~2회 가격 폴링**이라 GB 단위는 작다. ⇒ **문제는 처리량이 아니라 base $43 다.**

**선택지 (권고 아님 — 트레이드오프 나열)**

| 안 | 월 비용 | 대가 |
|---|---|---|
| NAT GW ×AZ | $43 × AZ | 정석·관리 불필요 |
| NAT GW ×1 (전 AZ 공유) | $43 | 🔴 그 AZ 죽으면 전 클러스터 egress 사망 + **AZ간 전송료가 egress 에 붙는다** |
| NAT 인스턴스(`t4g.nano` 자체 관리) | ~$4 | 직접 관리·SPOF·대역 제한. 학습 가치는 있음 |
| **NAT 없음** — 노드를 public subnet 에, inbound SG 전면 차단 | **$0** | 🔴 노드에 공인 IP. IMDSv2 강제·SG 엄격·SSM 접속 전제. **보안 리뷰 필요** |
| S3/ECR 만 **Gateway/Interface 엔드포인트**로 우회 | S3 Gateway **무료** / Interface $9.49 각 | ECR 은 Interface 3개(api·dkr·s3) 필요 → $28 이면 NAT 보다 **비싸다**. 🔴 "엔드포인트가 항상 싸다"는 통념은 소규모에서 틀리다 |

> 🔴 **결정됨 (2026-08-11) — 이 표는 판단 재료로만 남는다. 실제 선택은 아래다.**

> | | 결정 | 근거 |

> | NAT | **NAT GW 1대**(AZ-a · 2AZ 공유) | **C-47** — 위 표의 2행. 그 대가(AZ-a 사망 시 두 AZ 아웃바운드 사망)를 **온프렘 페일오버로 받는다** |

> **비용으로는 지금도 맞다** — 우리는 **순증 $56.94** 를 내고 있고 NAT 절감은 ≈$0 이다. 그래서 **ECR 은 실제로 기각**했다(레이어가 S3 Gateway 로 빠져 볼륨이 안 나온다 — 위 표의 지적 그대로다).

### 4.2 AZ간 전송 — 우리 아키텍처와 정면충돌하는 항목

$0.01/GB **양방향** = 왕복 **$0.02/GB**. 그리고 **우리 앱은 chatty 하다**:

- `GET /api/recipes/{id}` = **PG 왕복 9회**, 캐시 0 (SSOT §7.4-1)
- `GET /api/recipes/shared/{token}` = **PG 왕복 5회**, 캐시 0 (SSOT §7.4-2)
- Kafka RF=3 → 프로듀스 1바이트가 **AZ 경계를 2번** 넘는다
- PG 스트리밍 복제 + PGSync CDC + ES replica
- Prometheus 가 **모든 파드를 30초마다** 스크레이프 (타깃 수백 개)

**금액은 아직 산정 못 한다**(정상 상태 바이트를 측정하지 않았다 — P2 리허설 최대 59.7MB/s 는 일회성 벌크였다). **하지만 지연은 지금 계산할 수 있다**: AZ간 RTT ≈ 1~2ms × 왕복 9회 = **요청당 +9~18ms**. 온프렘 LAN(0.1~0.3ms)에서는 안 보였던 비용이다.

🔴 **설계 함의 — 여기서 두 갈래가 갈린다**

| 안 | 결과 |
|---|---|
| **AZ 어피니티**(앱과 PG primary 를 같은 AZ 로) | 전송료·지연 최소. 대가 = **AZ 장애 시 그 AZ 통째 손실** = HA 서사 약화. Istio **locality-aware LB** 로 앱↔앱은 자동 완화 가능 |
| **AZ 분산 우선** | HA 서사 유지. 대가 = 왕복 9회가 전부 유료·유선 |
| 🔴 **캐시를 먼저 넣는다** | **양쪽을 동시에 푼다.** Stage3 1차가 이미 처방으로 "결과 캐시·왕복 배칭"을 지목했다(SSOT §7.4-1·2). **AWS 이전은 그 부채의 가격표를 보이게 만들 뿐이다** |

⇒ **권고: §7.4-1·2 (캐시·왕복 배칭)를 AWS 이전의 *선행조건*으로 볼 것.** 안 고치고 옮기면 아키텍처 결함이 월 청구서로 전환된다.

### 4.3 과대 request — 온프렘에선 무해, AWS 에선 즉시 돈

`mp-account` request 500m vs 실사용 4m(**125배**), `mp-recipe` 300m vs 3~4m. 워커 CPU 사용률 3~5%.

- 온프렘: 스케줄링 헤드룸만 낭비 → **무해**
- AWS: request 가 노드 수를 정하고 **노드 수 = 청구서** → 즉시 손해

⇒ **권고: 이전 전에 CPU request 리사이즈.** 다만 SSOT §7.3-4 의 지적대로 **HPA 타깃도 함께 재설계**해야 한다(request 를 낮추면 70% 타깃이 이제 *발화한다* — 즉 이 작업은 비용 절감이면서 동시에 §7.3-4 부채 해소다). 메모리는 데이터 티어가 실제로 쓰므로 **replica 결정(§0-5) 없이는 안 줄어든다.**

### 5.1 공짜로 좋아지는 것

| 지금 | AWS 에서 |
|---|---|
| master 단일 · etcd WAL 파손 사건 2건(SSOT §1.0.2·§1.0.3) · 스냅샷 복원 런북 | **컨트롤플레인 관리형·멀티AZ.** etcd 백업·복원·버전 스큐 걱정이 통째로 사라진다. `$73/월`에 이걸 산다 |
| 노드 상실 시 수동 대응 · **host-a 상실을 b1·b2 가 수용 못 함**(§7.3-5, 여유 4.0GiB vs 상주 12.6GiB) | **Cluster Autoscaler / Karpenter** 가 노드를 새로 띄운다. 🔴 단 헤드룸은 여전히 유료 |
| Harbor 가 죽으면 **배포 전면 실패** · 백업 타이머 미설치(§7.1-6) · 호스트 C 디스크 여유 27.9GB | **ECR** — 관리형·백업 불요·디스크 압박 소멸. `CLAUDE.md` 의 "호스트 C 는 디스크가 제약" 함정 전체가 사라진다 |
| MinIO **단일 replica·B 고정**(문서화된 예외) | **S3** — 11 nines. 예외 자체가 없어진다 |
| 하이퍼바이저 무흔적 급사 3회 · 온도 감시 4알람 | 물리 계층이 AWS 책임. 🔴 단 **온도 알람 4종은 죽고 대체물이 없다**(§9) |

### 5.2 비싸지거나 어려워지는 것

| 항목 | 왜 |
|---|---|
| 🔴 **Spot + stateful 은 비양립** | Spot 은 **2분 통보** 후 회수. 현행 스토리지는 OpenEBS **LocalPV** — 노드와 생사를 공유하고 이미 §7.3-5 의 원인이다. ⇒ **stateful 은 On-Demand 고정, stateless 만 Spot.** S1·S2 가 그렇게 짜여 있다 |
| **EBS 는 AZ 에 고정** | 파드가 **같은 AZ 안에서만** 재스케줄 가능. LocalPV 의 "노드 고정"이 "AZ 고정"으로 완화될 뿐 **본질은 같다**. §7.1-2(`recipes` 단일 사본이 b2 종속)가 **AZ 단위로 그대로 재현**된다 → replica 를 올리는 게 답이고 그건 돈이다 |
| **quorum 3 = AZ 3 = 전송료** | Kafka RF=3 · Sentinel 3. 3-AZ 로 펴면 HA 는 진짜가 되고 §4.2 비용이 최대가 된다 |
| Spot 회수 처리 | AWS Node Termination Handler 또는 Karpenter 내장 처리 **추가 구축 필요**. §5.6 descheduler CronJob 은 그대로 쓰되 Spot 이면 **더** 필요해진다 |
| 우선순위 클래스 | §7.3-3(app 파드 전부 priority 0)이 **Spot 환경에서 훨씬 위험**해진다 — 회수 시 축출 순서를 아무도 통제하지 않는다 |

### 5.3 🟢 그대로 옮겨가는 HA 자산 — 이건 잘 해둔 것

**§5.5 의 분산 보장이 무수정 이식된다.** hard `topologySpreadConstraints` 2계층(hostname + zone) + `nodeTaintsPolicy: Honor` + `matchLabelKeys: [pod-template-hash]` + PDB.

온프렘 zone 라벨을 `host-a`/`host-b` 로 붙인 것이(플랜 §2.4) **진짜 AZ 로 그대로 매핑**된다. 그리고 §5.7 의 **drain 실검증**이 곧 Spot 회수 리허설이었다 — 의도한 것보다 더 값진 자산이다.

🔴 **다만 §5-1 잔여부채가 여기서 청구된다**: `nodeTaintsPolicy: Honor` 는 **미검증**이고(값을 하는 국면 = host-a 통째 상실), AWS 에서 그 국면이 **AZ 장애 = 실제로 일어나는 일**이 된다.

## 7. 성능 — AWS 에서 **뒤집히는 결정**들

이전 계획에서 가장 놓치기 쉬운 부분: *"온프렘 제약 때문에 내린 결정"이 제약이 사라지면 틀린 결정이 된다.*

### 7.1 🔴 Cilium 라우팅 모드 — 락의 근거가 소멸한다

SSOT §1.0.1: **VXLAN 확정·락**. 근거는 *"CPU 천장 2.25Gbps > 물리 1GbE 라 선이 먼저 찬다"* — **예상이던 native 를 실측으로 뒤집은** 결정이었다.

**AWS 에서 그 전제가 사라진다.** ENA 는 인스턴스 등급에 따라 수~수십 Gbps 다. "선이 먼저 찬다"가 성립하지 않으므로 **VXLAN vs native(ENI) 는 재결정 대상**이다. 그리고 이건 단순 성능 문제가 아니다:

| 안 | 결과 |
|---|---|
| **Cilium 유지 (ENI 모드)** | `CiliumNetworkPolicy` **10개 보존** · `kubeProxyReplacement` 유지. 🔴 대가 = **K8s 버전 상한이 Cilium 이 정한다**(현재 1.34). EKS 버전 정책과 교집합을 매번 확인해야 하고, 어긋나면 §2.1 의 **extended support $365/월** 함정으로 간다 |
| **VPC CNI 로 교체** | 버전 상한 해제 · AWS 지원 · **SG for Pods** 사용 가능. 대가 = **CNP 10개 재작성**(표준 NetworkPolicy 로) + `kubeProxyReplacement` 포기 + 파드 IP 가 VPC IP 라 **서브넷 IP 소진 설계** 필요 |

플랜 §8 은 *"Cilium 은 ENI 모드로 설치, 정책 CRD 는 그대로"* 로 **전자를 이미 가정**해뒀다. 하지만 그건 버전 상한 비용을 계산하기 전의 서술이다 → **재확인 권고.**

### 7.2 스토리지 — gp3 로 충분하다 (숫자로)

| 축 | 온프렘 LocalPV(로컬 SSD) | gp3 | 판정 |
|---|---|---|---|
| IOPS | 로컬 NVMe/SSD | **3,000 기본 포함** | PG data **257Mi** · WAL **1.1Gi** · ES 인덱스 **15MB** — 데이터가 극히 작다. **여유 충분** |
| 처리량 | 로컬 | **125MiB/s 기본** | P2 리허설 최대 59.7MB/s(벌크) — 여유 있음 |
| fsync 지연 | ~0.1ms | ~0.5~1ms | 🔴 유일한 실질 열화. PG 커밋 지연에 직결. **io2 는 이 규모에 불필요**, 필요하면 gp3 IOPS 증설($0.0057/IOPS) |

⇒ **권고: gp3 로 간다.** 플랜 §5.3 이 *"동작 의미가 일대일 대응 → SC 이름 교체로 끝"* 이라 적은 게 이 규모에서는 맞다. **단 §9 의 SC 하드코딩 5곳을 먼저 고쳐야 "이름 교체로 끝"이 성립한다.**

### 7.3 Graviton(ARM64) — 가장 큰 성능/$ 레버이자 가장 구체적인 리스크

§2.2 에서 `r7g` 가 $/GiB 최저다. 하지만:

| 리스크 | 왜 |
|---|---|
| 🔴 **`python-crfsuite`(한식 재료 NER)** | CRF 는 **절대제약(AI 전부 CPU)의 핵심 모델**이다. aarch64 휠이 없으면 소스 컴파일이고, 컴파일되더라도 **성능 재측정**이 필요하다 |
| XGBoost · LightGBM | aarch64 휠은 통상 제공. **버전 확인 필요** |
| **Playwright(`mp-poller-kurly`)** | ARM64 브라우저 바이너리 존재. 단 §7.6(`readOnlyRootFilesystem`) 작업과 **동시에 건드리면 원인 분리가 안 된다** |
| 멀티아치 빌드 | Jenkinsfile 에 `buildx` + QEMU 또는 ARM 빌더 필요. **CI 변경 = §0-6 과 묶인다** |

⇒ **권고: Graviton 은 "가면 좋은 것"이지 전제가 아니다.** 1차 이전은 x86(`m6i`)로 하고 Graviton 은 별건으로 두면 실패 원인이 분리된다. 대가 = §2.2 기준 **15~35% 더 비쌈**. (트레이드오프, 결정 아님)

### 7.4 앱 지연 — AZ 경계가 왕복 9회를 곱한다

§4.2 참조. **Istio locality-aware LB** 로 앱↔앱은 자동 완화되지만 **앱→PG 는 아니다**(PG primary 는 한 AZ 에만 있다). ⇒ Pooler 를 AZ 별로 두고 **읽기를 같은 AZ replica 로 라우팅**하는 것이 정공법이고, 이건 **Stage3 가 이미 처방한 것**과 같은 작업이다(`pg-2` 가 부하 중 idle — SSOT §7.4-2).

### 10.2 🔴 하이브리드 기간을 피하는 이유

A2 에서 "앱은 AWS · 데이터는 온프렘"을 오래 유지하면:
- **Site-to-Site VPN** 상시 비용(+ 터널 시간당) + **인터넷 송신 $0.126/GB**
- 앱→PG 왕복 **9회 × 인터넷 RTT** = 요청당 수백 ms
- §7.4-1 의 캐시 부재가 여기서 치명적이 된다

⇒ **권고: A2·A3 를 짧은 단일 전환창으로 붙인다.** P2 를 그렇게 했고(열화 ~25분) 성공했다. 그때의 함정 목록이 런북에 그대로 있다.

## 12. 미확인 목록 (이 계획의 신뢰 한계)

1. **Spot 실할인율** — IAM 권한 부족. §3 의 65% 가정이 틀리면 S1·S2 총액이 흔들린다
2. **ALB/NLB/WAF/RDS/MSK/OpenSearch/CloudWatch 요율** — 미조회
3. **AZ간 전송 실측 바이트** — 정상 상태를 측정하지 않았다. §4.2 의 금액이 비어 있는 이유
4. 🔴 **EKS 제공 K8s 버전 ∩ Cilium 1.19.6 상한(1.34)** — 어긋나면 §7.1 의 두 갈래 판단이 강제된다
5. **ARM64 실행 가능성** — `python-crfsuite` 등. §7.3
6. **`cloudflared` eks 오버레이 부재가 의도인지**
7. **온프렘 클러스터 존치 여부** — 존치하면 비용이 합산이 아니라 **병렬**이다(전기·하드웨어는 이미 매몰)

## 13. 다음 스텝 (권고)

1. **§0 의 7건을 팀 회의에 올린다.** 특히 2번(상시 vs 데모 온디맨드)이 나머지 전부를 규정한다

3. **§12-1·4 를 먼저 닫는다** — Spot 요율과 버전 교집합은 계획의 뼈대를 바꾼다
