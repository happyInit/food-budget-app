# 단계별 리소스 · 성능 검증 계획

> 배포 단계(Docker → K8s → AWS)별로 무엇을 측정·튜닝하는지 정리한다.
> 핵심 원칙: **Docker에서는 "얼마 쓰는지 측정", K8s에서는 "실부하로 조이기", AWS에서는 "돈으로 조이기(FinOps)".**
> dev 부하로 리소스 제한을 완벽히 맞추려는 것은 조기 최적화다. 실제 사이징 기준은 피크(design.md §8.1: 11-12·17-18) + 최저가 fan-out 버스트(§8.2)이며, 이는 실부하를 재현할 수 있는 K8s 단계에서 튜닝한다.

## 1. 단계별 역할 요약

| 단계 | 목표 | 리소스 작업 | 성격 |
|---|---|---|---|
| Docker (compose) | 기능이 통합돼 돌아가나 | sane 리소스 제한 + **베이스라인 프로파일링** | 실측 시작점 |
| Kubernetes | 실부하에서 견디나·스케일되나 | requests/limits 정밀화 + HPA/KEDA 튜닝 + 부하테스트 | 실부하 튜닝 |
| AWS | 비용 대비 효율적인가 | 노드 사이징 · Spot · 오토스케일 · 비용 배분 | FinOps |

각 단계의 숫자는 다음 단계에서 더 현실적인 부하로 재보정된다. Docker 베이스라인 → K8s requests → AWS 노드 사이징으로 정밀도가 올라가는 파이프라인이다.

---

## 2. Docker (compose) 단계

첫 구현. 목적은 성능 최적화가 아니라 **기능 통합 확인 + 사용량 실측**이다.

### 2.1 한다

| 항목 | 내용 | 판정/기준 |
|---|---|---|
| 기능·통합 테스트 | 핵심 루프 E2E(추천→장보기→식비 기록), 인증(JWT), DB 마이그레이션, 서비스 간 호출 | 시나리오 통과 |
| 스모크 부하 | 적당한 동시 요청(예: 수십 RPS)에 죽지 않나 | 에러율·응답 정상 |
| 베이스라인 프로파일링 | 각 서비스의 idle / 평상 / 가벼운 부하 시 CPU·메모리 실측 | 서비스별 수치 기록 |
| sane 리소스 제한 | 한 컨테이너가 호스트를 독점하지 않도록 limit 설정 | 호스트 OOM 방지 (§8.4) |
| 구성 검증 | 헬스체크, restart 정책, 시크릿 주입, 네트워크 세그먼트 | 정상 동작 |

베이스라인 측정 도구: 이미 배포된 관측 스택(cAdvisor로 컨테이너 메트릭, Prometheus 수집, Grafana 확인). 서비스별로 다음을 기록한다.

- CPU: idle, 평상, 가벼운 부하 시 사용률
- 메모리: 기동 직후, 정상 운영, 피크 근사
- (해당 시) 스타트업 시간, JVM heap(ES/Kafka) 실사용

이 베이스라인이 K8s requests/limits의 출발점이 되는 핵심 산출물이다.

### 2.2 하지 않는다 (뒤로 미룸)

- 프로덕션 규모 부하 테스트
- HPA/KEDA 임계값 튜닝
- dev 부하 기준의 정밀 right-sizing (잘못된 프로파일에 맞추는 조기 최적화)
- 멀티노드 페일오버

### 2.3 주의

- 리소스 제한을 걸어두는 것은 맞다. 그러나 dev 부하로 그 수치를 "최적값"으로 확정하려 하지 않는다. 실제 사이징은 피크·버스트 부하에서 나온다.
- plain compose의 내부 LB는 DNS 라운드로빈(약함)이다. 부하 분산 검증은 이 단계의 목표가 아니다. 진짜 LB·오토스케일은 K8s 단계에서 얻는다.

## 3. Kubernetes 단계

실부하를 재현하고 자동 스케일을 튜닝하는 단계. Docker 베이스라인을 시작값으로 사용한다.

### 3.1 requests / limits 정밀화

- **requests**: 관측된 평상 사용량 기준(스케줄링 기준값). 너무 높으면 노드 낭비, 너무 낮으면 과밀·경합.
- **limits**: 피크 + 헤드룸. 메모리 limit 초과 시 OOMKill 되므로 메모리는 여유 있게.
- Docker 베이스라인 → 초기값 설정 → 실부하 관측 → 조정 반복.
- (선택) VPA를 recommendation 모드로 돌려 권고치 참고.

### 3.2 오토스케일 튜닝

| 티어 | 스케일 방식 | 튜닝 포인트 |
|---|---|---|
| 요청 서비스 (Gateway·User·Pantry·Recipe·Price·MealPlan·Expense·Notification) | HPA (CPU/RPS) | 목표 사용률(예: CPU 60~70%), min/max replica, 피크 대응 |
| 워커 (NER·이상탐지·OCR·추출) | KEDA (Kafka lag/큐) | 스케일 트리거 임계값, idle→0, 콜드스타트 |
| 수집 (크롤러·폴러) | 고정 1 replica | 수평 확장 금지(크롤 예의·중복). CronJob/KEDA cron |
| AI 서빙 (ML Serving) | HPA (CPU) | CPU-bound 특성, 병목 시 분리 검토 |
| 저장소 (PG·ES·Redis·Kafka) | 오토스케일 아님 | 하이브리드로 K8s 밖(§8.4). 읽기 복제·샤딩 등 별도 |

### 3.3 부하 테스트

- 도구: k6 / Locust 등으로 시나리오 부하 생성.
- 재현할 프로파일:
  - 일일 피크(11-12·17-18): 레시피 검색 + 가격 조회 집중 (§8.1)
  - 최저가 알림 fan-out: 이상탐지 감지 → N명 동시 조회 버스트 (§8.2)
- 관측: p50/p95/p99 지연, 에러율, HPA·KEDA 반응(scale-out 속도, scale-to-zero), 저장소 병목.
- 결과로 requests/limits·HPA 임계값·replica 범위를 확정.

## 4. AWS 단계 (FinOps)

돈을 지불하는 단계이므로 비용 최적화가 실질적 의미를 갖는다. K8s에서 확정한 사용량을 노드·인스턴스·비용으로 환산·최적화한다.

| 항목 | 내용 |
|---|---|
| 노드 사이징 | 워크로드 사용량에 맞는 인스턴스 타입 선택. 과대 프로비저닝 회피 |
| Spot 활용 | 무상태 서비스·워커는 Spot(중단 허용). 상태 저장/중요는 On-Demand |
| 클러스터 오토스케일 | 노드 오토스케일러 / Karpenter로 수요 따라 노드 증감 (design.md §6.1) |
| bin-packing 효율 | requests 정확도가 노드당 밀도를 좌우 → 노드 수·비용 직결 |
| 비용 가시성 | 태깅·비용 배분(서비스별/팀별). 필요 시 Kubecost 등으로 워크로드별 비용 파악 |
| 상시 최적화 | 미사용 리소스 회수, 요청/한계 재조정, retention 정책 비용 점검 |

주의: 온프렘(Proxmox) 단계에서는 "돈" 최적화가 아니라 물리 자원 한도 내 용량 관리(예: 32GB 호스트 안에 배치, §8.4)까지가 유효하다. FinOps($ 최적화)는 AWS로 이전한 뒤 의미를 갖는다.

---

## 5. 무엇을 측정하나 (공통 지표)

서비스·단계 공통으로 다음을 관측한다(LGTM 스택 활용).

- 리소스: 컨테이너/Pod별 CPU·메모리 사용률, 스로틀링 여부
- 처리량/지연: RPS, p50/p95/p99 응답시간, 에러율
- 비동기: Kafka consumer lag, 워커 처리량, 큐 적체
- 저장소: PG 커넥션·쿼리 지연, ES 검색 지연, Redis 히트율
- 스케일 동작: HPA/KEDA replica 변화, scale-out/in 지연, scale-to-zero

---

## 6. 요약

- **Docker**: 기능·통합·스모크 + 베이스라인 실측. 정밀 최적화·부하테스트는 하지 않는다. 리소스 제한은 호스트 보호 목적으로 유지.
- **K8s**: 실부하(피크·fan-out) 재현으로 requests/limits·HPA/KEDA를 조인다. 부하 테스트가 여기서 이뤄진다.
- **AWS**: K8s에서 확정한 사용량을 노드·Spot·오토스케일·비용으로 최적화한다(FinOps).
- 리소스 사이징은 단계마다 더 현실적인 부하로 재보정되는 파이프라인이며, dev 부하 기준의 조기 확정은 피한다.
