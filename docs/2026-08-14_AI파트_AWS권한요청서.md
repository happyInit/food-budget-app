## 0. 왜 지금 요청하는가

현재 제 계정으로 되는 것은 **`ec2:DescribeVpcs` · `DescribeSubnets` · `DescribeSecurityGroups` · `iam:ListRoles` · `bedrock:List*`** 뿐입니다.
**`eks:ListClusters` · `lambda:ListFunctions` · `s3:ListAllMyBuckets` · `sqs:ListQueues` · `logs:DescribeLogGroups` 는 전부 거부**됩니다.

그래서 **설계 검증조차 불가능**합니다 — PG·ES 가 클러스터 위 어떤 주소로 떠 있는지, ElastiCache 엔드포인트가 무엇인지 확인할 수 없어
함수의 접속 대상을 정하지 못합니다. 코드 작업(G1)은 권한 없이 진행 중이지만, **배포·검증(G2~G4)은 여기서 막힙니다.**

## 2. 권한별 사유 — 무엇을 하려고 필요한가

### ① 읽기 (`ReadOnlyAccess`)

| 서비스 | 왜 필요한가 |
|---|---|
| `eks:Describe*` `List*` | **PG·ES·Pooler 가 어떤 주소·포트로 떠 있는지** 확인. 함수의 접속 대상이 여기서 정해집니다 |
| `elasticache:Describe*` | **Valkey 엔드포인트 주소**. 함수 6개가 이걸 씁니다 |
| `ec2:Describe*` (전체) | **VPC 엔드포인트·NAT·라우팅** 확인. 지금 3개만 되고 나머지가 막혀 네트워크 경로를 검증할 수 없습니다 |
| `s3:List*` `Get*` | **모델 아티팩트 버킷** 확인. 함수 4개가 모델을 읽습니다 |
| `secretsmanager:List*` `Describe*` | 자격증명이 이미 등록됐는지 확인 (값은 안 봅니다) |
| `logs:Describe*` | 기존 로그 그룹 구조 파악 |
| `sqs:List*` `GetQueueAttributes` | 기존 큐(크롤용)와 이름이 겹치지 않는지 확인 |
| `elbv2:Describe*` | ALB 리스너·타겟그룹 현황. 함수를 어디에 붙일지 판단 |

> **`ReadOnlyAccess` 하나로 위가 전부 해결됩니다.** 개별로 나열할 필요가 없습니다.

### ② 쓰기 (`mp-*` / `mp-ai-*` 한정 — 항목별로 다릅니다, 근거는 §4-1)

| 권한 | 왜 필요한가 | 대상 |
|---|---|---|
| `lambda:*` | **함수 12개 생성·코드 갱신·버전·별칭·동시성 설정** | `function:mp-ai-*` |
| `sqs:*` | **워커큐·알림큐 + DLQ 4개** 생성·설정 | `mp-ai-*` |
| `scheduler:*` | **배치 5종의 실행 시각 등록**(EventBridge Scheduler) | `schedule/*/mp-ai-*` |
| `logs:*` | **로그 그룹 생성 + 보존기간 설정 + 조회.** 🔴 수동 실행 2종은 DLQ 가 없어 **로그가 유일한 실패 확인 수단**입니다 | `/aws/lambda/mp-ai-*` |
| `bedrock:InvokeModel` | 모델을 호출합니다 | nova-micro (§4 주석 참조) |
| `s3:GetObject/PutObject` | **랭킹·NER 모델 파일 읽기/쓰기** | 🔴 **버킷 미지정 — §5 참조** |
| `secretsmanager:Get/Describe` | **기존 자격증명 재사용.** ESO 가 쓰는 `mp/prod/*` 4종이 정본이고 Lambda 도 **같은 값을 읽습니다** — 복사하면 갈라집니다(§5-2) | `secret:mp/prod/*` **읽기만** |
| `secretsmanager:Create/Put/…` | **AI 함수에만 있는 새 값**(Lambda 용 GCP 연동 설정 등). 🔴 **기존 자격증명을 여기 복사하지 않습니다** | `secret:mp-ai/*` **쓰기** |
| `ecr:*` | 함수를 **컨테이너 이미지로 패키징할 경우**의 저장소. zip 으로 가면 안 씁니다 | `repository/mp-ai-*` |
| `iam:PassRole` | **함수에 실행 역할을 붙일 때 필수.** 이게 없으면 함수 생성 자체가 실패합니다 | `role/mp-ai-*` |

### ③ EKS kubectl 접근

`eks:DescribeCluster` 만으로는 **kubectl 이 돌지 않습니다.** EKS 는 IAM 과 별개로 **액세스 항목(access entry)** 을 봅니다(C-80 = public + IAM).
→ §6 의 명령 한 줄이 필요합니다.

## 3. 🔴 실행 역할(IAM Role)은 두 가지 방식이 있습니다 — **A 를 권합니다**

함수에는 "이 함수가 무엇을 할 수 있는가"를 정하는 **실행 역할**이 필요합니다. 누가 만들 것인가의 문제입니다.

| | 방식 | 제게 필요한 IAM 권한 | 관리자 작업량 |
|---|---|---|---|
| **A (권장)** | **관리자가 역할 3개를 미리 만들어 줌** — `mp-ai-batch` · `mp-ai-worker` · `mp-ai-api` | **`iam:PassRole` 만** (IAM 쓰기 0) | 역할 3개 생성 (§7 에 내용 첨부) |
| B | 제가 `mp-ai-*` 경로에 역할을 직접 생성 | `iam:CreateRole` 등 — **권한 상승 경로가 열립니다** | 권한 경계(boundary) 정책 1개 추가 생성 |

**A 를 권하는 이유** — IAM 쓰기 권한은 *"내가 나에게 더 큰 권한을 주는"* 경로가 될 수 있어 가장 민감합니다.
역할 3개는 한 번만 만들면 되고, **함수 12개가 성격별로 셋 중 하나를 씁니다.** 3일 일정에는 이쪽이 빠르고 안전합니다.

### 4-1. 어디를 왜 여유 있게 잡았는지 — **13곳, 전부 이유가 있습니다**

**최소권한을 일부러 느슨하게 한 곳만** 골라 적습니다. 나머지는 전부 계정·리전·이름으로 조여 있습니다.

| 여유를 준 곳 | 좁게 잡으면 무슨 일이 나나 |
|---|---|
| **`function:mp-ai-*` → `mp-*`** | 함수 이름을 `mp-ocr-worker` 로 지으면 **그 순간 거부**됩니다. 이름 규칙은 만들면서 바뀌고, 그때마다 권한을 다시 받는 건 비쌉니다. 🟢 **계정에 Lambda 가 0개**라 실질 범위는 우리 것뿐입니다 |
| **Bedrock `nova-micro` → `*nova*`** | `apac.amazon.nova-micro-v1:0` 은 **교차리전 추론 프로파일**이라 **프로파일 ARN 과 기반 모델 ARN 을 둘 다** 허용해야 통과합니다. 게다가 요약·감정은 nova-lite 로 올라갈 수 있어 **모델 하나로 못박으면 실험이 막힙니다** |
| **S3 `MODEL_BUCKET` → `mp-*/models/*`** | **버킷 이름이 아직 안 정해졌습니다**(§5). 프리픽스로 열어두면 어느 이름으로 정해져도 통과하고, **`models/`·`lambda/` 두 경로 밖은 여전히 막힙니다** |
| 🔴 **`kms:Decrypt` (신설)** | **이게 빠지면 실제로 막힙니다.** Secrets Manager 는 기본이 KMS 암호화라 **읽기 권한이 있어도 복호를 못 해 실패**합니다. `kms:ViaService` 조건으로 **S3·Secrets·SQS·Lambda 를 거칠 때만** 쓰도록 묶어 뒀습니다 |
| **CloudWatch 알람 (신설)** | 설계상 **알람이 실패 감지의 유일한 경로**입니다(DLQ 없는 함수 2종). 알람을 못 만들면 «정상동작 확인»이 성립하지 않습니다. 알람 이름은 `mp-ai-*` 로 조여 뒀습니다 |
| **SNS (신설)** | 알람이 Slack 까지 가려면 SNS 를 거칩니다(제약 4). `mp-ai-*` 한정 |
| **X-Ray·태그 (신설)** | 함수가 느릴 때 **어디서 느린지 볼 수단**입니다. 읽기 위주라 위험이 없습니다 |
| **로그 읽기 `*`** | 로그 조회는 리소스 한정이 잘 안 걸립니다. **읽기뿐이고 쓰기는 `/aws/lambda/mp-*` 로 조여** 뒀습니다 |
| **SQS 는 `mp-ai-*` 유지** | 🔴 **일부러 안 넓혔습니다** — 크롤 레인이 이미 자체 큐를 갖고 있어(`infra/terraform/aws/sqs.tf`) `mp-*` 로 넓히면 **남의 큐를 지울 수 있습니다.** 조회만 전체 허용 |
| **IAM 은 `PassRole` 만 유지** | 🔴 **여기는 절대 안 넓힙니다.** 역할 생성 권한은 «내가 나에게 더 큰 권한을 주는» 경로입니다 |

### 4-2. 기한 — **2026-08-31 까지만 필요합니다**

이 정책은 **이전 작업 기간용**입니다. 8/31 이후에는 **실사용 로그(CloudTrail) 기반으로 최소권한을 다시 써서** 교체하는 것을 제안드립니다.
지금 좁게 잡아 여러 번 되돌아오는 것보다, **넓게 열고 기한을 걸어 한 번에 회수**하는 편이 관리 비용이 낮습니다.
불안하시면 정책에 아래 한 줄을 더해 **자동 만료**를 걸 수 있습니다.

```json
{ "Sid": "Expiry", "Effect": "Deny", "Action": "*", "Resource": "*",
  "Condition": { "DateGreaterThan": { "aws:CurrentTime": "2026-09-01T00:00:00Z" } } }
```
> ⚠️ 이 `Deny` 는 **이 사용자의 모든 권한**에 걸립니다(`ReadOnlyAccess` 포함). 조회까지 같이 끊겨도 되는지 확인 후 넣어 주세요.

## 5. 🔴 함께 정해야 할 것 하나 — 모델 아티팩트 버킷

확정된 S3 버킷 6종(`mp-crawl-ap2` · `mp-backup-ap2` · `mp-pg-dump-ap2` · `mp-observability-ap2` · `mp-source-backup-ap2` · `mp-cloudtrail-ap2`)
중에 **모델 파일을 둘 자리가 없습니다.** 랭킹·NER·감정 모델을 함수 4개가 읽어야 합니다.

**선택지 둘** — ① **`mp-model-ap2` 신설** ② **`mp-backup-ap2` 에 `models/` 프리픽스로 동거**.
②가 버킷을 안 늘려 간단하지만, 백업 버킷의 라이프사이클(C-79 계층 전환·만료)이 **모델 파일에도 걸립니다** — 모델이 Glacier 로 내려가면 함수가 못 읽습니다.
**→ ①을 권하나 인프라 소관이라 결정을 요청드립니다.**

## 5-1. 프론트엔드 — **새 AWS 권한이 거의 필요 없습니다**

config 레포와 프론트 소스를 실측했습니다.

| 확인한 것 | 결과 |
|---|---|
| 프론트가 API 를 부르는 방식 | **상대경로** — `fetch('/api/auth/refresh')` · `fetch('/api/pantry/ocr')` |
| 그래서 CORS 는 | 🟢 **문제 없습니다.** 같은 오리진이라 애초에 발생하지 않습니다 |
| 프론트 배포 경로 | nginx 컨테이너(8080) → **ArgoCD(GitOps)** — AWS 직접 권한 불요 |
| 필요한 AWS 권한 | **읽기만** (`elbv2:Describe*` · `ecr:Describe*`) — **`ReadOnlyAccess` 에 포함** |

**→ 프론트엔드 작업 때문에 추가로 요청드릴 쓰기 권한은 없습니다.**

### 🔴 대신 조정이 필요한 것 3건 (권한이 아니라 결정 사항)

**① 경로 규칙 15개를 ALB 로 옮겨야 합니다 — 그리고 순서가 함정입니다**

현행 라우팅 실측 결과입니다.

```
/                        → frontend        /api/pantry            → pantry
/api/auth                → account         /api/pantry/ocr        → ocr
/api/users               → account         /api/prices            → price
/api/mealplan            → mealplan        /api/recipes           → recipe
/api/mealplan/assistant  → chat            /api/recipes/book      → recipebook
/api/expenses            → mealplan        /api/recipes/mine      → recipebook
/api/notifications       → notify          /api/recipes/shared    → recipebook
                                           /api/recipes/extract   → video
```

🔴 **Gateway API 는 «더 긴 경로가 이긴다»를 규격이 보장하지만, ALB 리스너 규칙은 우선순위를 사람이 번호로 매깁니다.**
번호를 잘못 주면 `/api/recipes/book` 요청이 `recipe` 로 가버립니다. **자동 정렬이 없습니다.**
→ **인프라와 함께 우선순위 표를 만들어야 합니다.** (짧은 경로일수록 큰 번호 = 나중에 평가)

**② `/api/auth` 는 이미 별도 경로입니다**
제가 제안한 `api-auth` 분리는 **경로를 새로 쪼개는 게 아니라, 이미 갈려 있는 경로를 다른 함수로 보내는 것**입니다.
ALB 리스너 규칙 하나면 되고, **프론트 코드는 한 줄도 안 바뀝니다.**

**③ UI 작업 중 실제 API 를 부를 방법이 없습니다**
dev/staging 환경이 없어(계정 1개 · C-57) **프론트 개발 중 붙을 대상이 프로덕션뿐**입니다.
→ 선택지 = ⓐ 프론트 로컬 + ALB 프로덕션 API ⓑ ALB 에 미리보기 경로 추가(인프라 소관) ⓒ 목 데이터로만 개발.
**ⓐ 를 쓰려면 ALB DNS 이름과 테스트 계정이 필요합니다.**

## 5-2. 데이터 연결 — **자격증명 체계는 이미 있습니다. 새로 만들지 않습니다**

config 레포 `bootstrap/eso/overlays/eks/clustersecretstore.yaml` 을 읽고 **초안을 정정했습니다.**
초안은 `mp-ai/*` 에 시크릿을 **새로 만들겠다**고 썼는데, **틀렸습니다.** 이미 체계가 서 있습니다.

| Secrets Manager 시크릿 | 담는 것 | AI 함수가 쓰는 키 |
|---|---|---|
| **`mp/prod/pipeline-secrets`** | 배치용 (5엔트리) | `PGPASSWORD` · `DATA_GO_KR_SERVICE_KEY` · `REPORT_GEMINI_API_KEY` · `AWS_ACCESS_KEY_ID/SECRET` |
| **`mp/prod/data-secrets`** | 데이터 티어 (14엔트리) | `ES_PIPELINE_WRITER_PASSWORD` · `ES_RECIPE_READER_PASSWORD` |
| **`mp/prod/app-secrets`** | 앱용 (33엔트리) | `PGPASSWORD` · `JWT_SECRET` · `CHAT_GEMINI_API_KEY` |

**값의 형상 = 시크릿 1개가 JSON 번들 1개**이고, 그 안의 필드를 이름으로 꺼냅니다.

**→ 그래서 요청을 둘로 나눕니다.**

| 경로 | 권한 | 무엇을 담나 |
|---|---|---|
| **`mp/prod/*`** | **읽기만** | 🔴 **기존 값을 그대로 읽습니다.** 복사하지 않습니다 — DB 비밀번호를 바꿀 때 **한쪽만 바뀌면 함수가 조용히 죽습니다** |
| **`mp-ai/*`** | **쓰기** | AI 함수에만 있는 **새 값**(Lambda 용 GCP 연동 설정 등). 있으면 여기 만듭니다 |

⚠️ **`mp/prod/*` 가 AWS 에 실제로 등록됐는지는 아직 확인 못 했습니다.** 근거가 된 파일이
*"🔴 정본은 이 파일이 아니다 … 여기 있는 것은 **목표 상태의 기록**"* 이라고 스스로 밝히고 있습니다.
**`secretsmanager:ListSecrets` 로 먼저 확인**해야 하며, 없으면 등록이 선행됩니다(다른 레인 소관).

### 🔴 다만 코드는 바뀝니다 — 그리고 이건 조회 없이는 알 수 없었습니다

현행 파드는 **ESO 가 K8s Secret 으로 풀어 주고 `envFrom` 으로 환경변수로 받습니다.**
**Lambda 에는 ESO 도 `envFrom` 도 없습니다.** 함수가 **직접 Secrets Manager 를 호출해 JSON 을 받아 필드를 꺼내야** 합니다.
인증도 다릅니다 — 파드는 **IRSA**, Lambda 는 **실행 역할**입니다.

| 나머지 확인 대기 항목 | 왜 코드에 영향을 주나 | 필요한 권한 |
|---|---|---|
| **PG·Pooler 주소·포트·TLS** | 접속 문자열과 TLS 옵션이 코드에 들어갑니다 | **§6-3 EKS 액세스** |
| **ES 의 TLS 켬/끔** | 온프렘은 «인증 켬 · HTTP TLS 끔»(C-15)인데 AWS 도 같은지 미확인 | **§6-3 EKS 액세스** |
| **Valkey 엔드포인트·TLS·클러스터 모드** | 클라이언트 초기화 코드가 갈립니다 | `ReadOnlyAccess` |
| **Lambda 아키텍처(arm64 여부)** | Graviton(C-29)이면 **의존성 휠을 arm64 로 빌드**해야 합니다 | 팀 결정 |

## 6. 부여 방법 — 3단계

### 1단계 · 읽기 (1분)
```
IAM 콘솔 → 사용자 → geonu → 권한 추가 → 직접 정책 연결
→ "ReadOnlyAccess" 검색·체크 → 권한 추가
```

### 2단계 · 쓰기 정책 (3분)
```
IAM 콘솔 → 정책 → 정책 생성 → JSON 탭
→ §4 를 붙여넣고 MODEL_BUCKET 을 실제 이름으로 치환
→ 이름 "mp-ai-serverless-deploy" 로 생성
→ 사용자 geonu 에 연결
```
CLI 로 하시려면:
```bash
aws iam create-policy --policy-name mp-ai-serverless-deploy \
  --policy-document file://mp-ai-serverless-deploy.json
aws iam attach-user-policy --user-name geonu \
  --policy-arn arn:aws:iam::689192361171:policy/mp-ai-serverless-deploy
```

### 3단계 · EKS 접근 (2분) — **IAM 과 별개입니다**
```bash
aws eks create-access-entry --cluster-name mp-eks \
  --principal-arn arn:aws:iam::689192361171:user/geonu --region ap-northeast-2

aws eks associate-access-policy --cluster-name mp-eks \
  --principal-arn arn:aws:iam::689192361171:user/geonu \
  --access-scope type=cluster \
  --policy-arn arn:aws:eks::aws:cluster-access-policy/AmazonEKSViewPolicy \
  --region ap-northeast-2
```
> **`AmazonEKSViewPolicy` = 읽기 전용**입니다. 클러스터를 변경할 수 없습니다.
> 이것만 있으면 PG·ES·Pooler 주소를 확인할 수 있고, **그게 함수 설계의 마지막 빈칸**입니다.

## 7. 안 A 를 고르실 경우 — 만들어 주셔야 할 실행 역할 3개

셋 다 **신뢰 주체 = `lambda.amazonaws.com`** 입니다.

| 역할 이름 | 쓰는 함수 | 붙일 정책 |
|---|---|---|
| **`mp-ai-batch`** | 배치 5종 (요약·감정·소비기한·NER·가격이상) | `AWSLambdaVPCAccessExecutionRole` + Bedrock 호출 + S3 `models/*` + Secrets Manager `mp-ai/*` 읽기 |
| **`mp-ai-worker`** | 워커 2종 + 알림 컨슈머 (OCR·영상·알림) | `AWSLambdaVPCAccessExecutionRole` + `AWSLambdaSQSQueueExecutionRole` + Secrets Manager `mp-ai/*` 읽기 |
| **`mp-ai-api`** | 동기·접수 4종 (챗봇·랭킹·OCR 접수·영상 접수) | `AWSLambdaVPCAccessExecutionRole` + SQS `SendMessage` + Secrets Manager `mp-ai/*` 읽기 |

> **`AWSLambdaVPCAccessExecutionRole` 이 셋 다에 들어가는 이유** — 함수가 VPC 안에서 돌아야 PG·ES·Valkey 에 닿습니다.
> 이 관리형 정책이 네트워크 인터페이스 생성 권한(`ec2:CreateNetworkInterface` 등)을 담고 있고, **없으면 함수가 VPC 에 붙지 못합니다.**
