# 백엔드 성능 테스트 결과 및 개선 후보 전달서

> 작성일: 2026-07-19
>
> 대상: Food Budget App 백엔드 개발팀
>
> 목적: 서비스별 부하 테스트와 혼합 사용자 시나리오에서 확인된 성능 저하 지점을 공유하고, 백엔드 개선 및 재검증 대상을 정리한다.

## 1. 요약

이번 테스트에서는 다음 세 가지를 확인했다.

1. API를 분리해서 호출했을 때 어느 서비스부터 처리량이 포화되는가
2. 여러 서비스를 동시에 호출했을 때 새로운 자원 경합이 발생하는가
3. 실제 사용자 행동을 가정한 혼합 트래픽에서 서버가 어디까지 안정적으로 동작하는가

핵심 결론은 다음과 같다.

- `fb-app-ai` VM 자체의 CPU·메모리 부족이나 서버 다운은 발생하지 않았다.
- 4단계 혼합 계단식 테스트에서는 약 **200 VUser 전후부터 포화 구간에 진입**했다.
- 가장 우선적으로 확인해야 할 경로는 Price의 `GET /api/prices/{item_id}`와 `GET /api/prices/hotdeals`다.
- Login과 MealPlan도 개별 테스트에서 병목 후보가 확인됐다.
- Chat 지연은 Chat 자체뿐 아니라 Price·PostgreSQL·Elasticsearch 하위 호출의 영향도 함께 분석해야 한다.
- Pantry와 Notify는 최대 연속 호출에서 CPU 제한에 도달했지만 오류율과 응답시간은 상대적으로 양호해 우선순위가 낮다.
- Recipe는 200 VUser까지 처리량이 계속 증가해 현재 기준으로 가장 안정적이었다.

현재 개선 우선순위는 다음과 같다.

```text
Price → Login / MealPlan → Chat → Pantry / Notify → Recipe
```

## 2. 테스트 환경

### 2.1 대상 환경

| 구분 | 값 |
|---|---|
| 테스트 대상 Gateway | `http://192.168.0.9` |
| 부하 발생 도구 | nGrinder `3.5.9-p1` |
| Controller·Agent | 개발자 로컬 Docker 컨테이너 |
| 애플리케이션 환경 | Docker Compose 기반 `fb-app-ai` VM |
| 관측 도구 | Grafana, Prometheus, Loki, Tempo |
| 서버 상태 확인 | `GET /healthz` |

### 2.2 함께 관찰한 지표

- nGrinder: VUser, TPS, Peak TPS, 평균 응답시간, 실행 건수, 오류 수
- Prometheus·Grafana: VM CPU·메모리·디스크, OOM, 컨테이너 재시작, 서비스 요청량
- Tempo: 서비스 및 DB·Elasticsearch 하위 Span
- Loki: 애플리케이션 오류 로그
- Gateway: `/healthz` 응답 코드와 응답시간

### 2.3 서버 보호 조건

테스트 중 다음 조건 중 하나라도 발생하면 즉시 중단하도록 감시했다.

- `fb-app-ai` VM CPU 80% 이상 지속
- VM 메모리 80% 이상 지속
- OOM 또는 컨테이너 반복 재시작
- `/healthz`가 HTTP 200이 아니거나 3초 안에 응답하지 않음
- SSH 또는 Docker 명령이 현저히 느려지거나 응답하지 않음

실제 테스트에서는 보호 조건이 발생하지 않았다.

## 3. 테스트 방법과 해석 기준

### 3.1 API 단독 탐색 테스트

각 서비스를 분리해 VUser를 단계적으로 증가시키며 처리량과 응답시간 변화를 비교했다. 인증이 필요한 Pantry·Notify·MealPlan은 로그인 병목이 결과에 섞이지 않도록 미리 발급한 공유 토큰을 사용했다.

병목 후보는 단순히 응답시간 한 값만으로 정하지 않고 다음 조건을 함께 확인했다.

1. VUser를 30% 이상 증가시켜도 TPS 증가가 10% 미만
2. 응답시간이 이전 단계보다 약 2배 이상 증가
3. 오류율 또는 timeout 증가
4. CPU throttling, DB 풀 고갈 또는 내부 대기 증가
5. 테스트 종료 후 회복이 지연됨

### 3.2 혼합 부하 테스트

여러 서비스를 동시에 호출하여 개별 테스트에서는 나타나지 않았던 VM 공유자원·DB·네트워크 경합이 생기는지 확인했다.

### 3.3 일반 피크 사용자 시나리오

현재 운영 트래픽 자료가 충분하지 않으므로 아래 비율은 확정된 운영 분포가 아니라 기능 중요도와 예상 사용자 행동을 기반으로 한 가설이다.

| 사용자 흐름 | 비율 | 주요 호출 |
|---|---:|---|
| 레시피 탐색·가격 조회 | 50% | 검색, 상세, 현재가, 레시피북 |
| 식단·냉장고·지출 조회 | 25% | 예산, 냉장고, 장바구니, 지출 |
| 핫딜·알림 조회 | 15% | 핫딜, 알림 |
| Chat 요청 | 10% | 식재료·식단 질의 |

테스트 스크립트는 요청마다 새 TCP 연결을 만들지 않고 실제 브라우저와 유사하게 HTTP keep-alive를 사용했다.

```text
connectionReset=false
think time=1~3초
```

## 4. 3단계: API 단독 탐색 결과

### 4.1 전체 요약

| 서비스 | 주요 결과 | 현재 판단 |
|---|---|---|
| Login | 30 VUser 평균 약 3.5초, 오류 약 1.4% | 병목 확인 |
| MealPlan | 100 VUser 평균 약 2.3초 | DB 연결 풀 병목 후보 |
| Price | 150 VUser부터 TPS 정체, 응답시간 급증 | 명확한 포화 |
| Chat | 150 VUser 이후 TPS 증가 둔화와 지연 증가 | 포화 진입 |
| Pantry | 약 310 TPS에서 정체, CPU throttling 관찰 | 최대 연속 호출 한계 |
| Notify | 약 290~310 TPS에서 정체, CPU throttling 관찰 | 최대 연속 호출 한계 |
| Recipe | 200 VUser까지 TPS 계속 증가 | 상대적으로 정상 |

### 4.2 Login

| VUser | 평균 응답시간 | 관찰 내용 |
|---:|---:|---|
| 15 | 약 804ms | 지연 증가 시작 |
| 30 | 약 3,493ms | 오류 약 1.4%, 처리량 증가 둔화 |

판정:

- 30 VUser에서 사용자 체감 지연과 오류가 함께 나타났다.
- bcrypt 검증과 FastAPI 이벤트 루프·worker·CPU 사용 방식이 우선 조사 대상이다.
- bcrypt 비용 인자를 낮춰 보안을 약화하는 방식은 개선안으로 사용하지 않는다.

개선 후보:

- 동기 bcrypt 검증이 이벤트 루프를 막는지 확인
- 필요하면 thread pool로 분리
- worker 수와 컨테이너 CPU limit 검토
- 로그인 SQL과 사용자 조회 인덱스 확인
- 인증 실패·성공 로그와 Login Trace를 동일 시간대에서 비교

### 4.3 Price

| VUser | TPS | 평균 응답시간 | 오류 |
|---:|---:|---:|---:|
| 100 | 48.8 | 42ms | 0 |
| 150 | 58.3 | 488ms | 0 |
| 200 | 58.2 | 1,407ms | 0 |

판정:

- 150→200 VUser에서 부하는 약 33% 증가했지만 TPS는 증가하지 않았다.
- 평균 응답시간은 약 188% 증가했다.
- 요청은 실패하지 않았지만 더 처리되지 못하고 내부 대기시간이 늘어나는 전형적인 포화 형태다.

개선 후보:

- `GET /api/prices/{item_id}`와 `GET /api/prices/hotdeals` SQL에 `EXPLAIN (ANALYZE, BUFFERS)` 수행
- 최신 가격 조회와 핫딜 필터 조건의 인덱스 사용 여부 확인
- 불필요한 전체 스캔·정렬·LATERAL/서브쿼리 반복 여부 확인
- PostgreSQL 연결 풀 크기, 대기시간, connection 반환 여부 확인
- 현재가·핫딜처럼 읽기 비중이 높은 결과의 Redis 캐싱 검토
- Price 컨테이너의 worker·CPU limit 및 DB 동시성 제한 확인

### 4.4 MealPlan

| VUser | 평균 응답시간 | 관찰 내용 |
|---:|---:|---|
| 100 | 약 2,314ms | DB 연결 풀 대기 후보 |

판정:

- 단순 조회 서비스보다 지연이 컸다.
- 테스트 중 관찰된 정황상 PostgreSQL 연결 풀과 집계 SQL을 먼저 확인해야 한다.

개선 후보:

- 연결을 요청 종료 시 확실히 반환하는지 확인
- 트랜잭션 범위를 필요한 구간으로 제한
- 장바구니·지출 집계 SQL 실행 계획 확인
- pool size, max overflow, timeout과 실제 worker 수의 관계 검토
- 동일 요청 Trace에서 DB Span 비중 확인

## 5. 4단계: 혼합 부하 결과

### 5.1 실행 방식

4단계에서는 여러 서비스를 동시에 호출하면서 VUser를 100→200→300으로 높였다. 각 유효 테스트는 2분 동안 실행했다.

최종 결과에는 정상 종료된 다음 테스트만 사용했다.

| nGrinder 테스트 | VUser | 상태 | 결과 사용 여부 |
|---|---:|---|---|
| `stage4-mixed-100vu` | 100 | FINISHED | 사용 |
| `stage4-mixed-200vu` | 200 | CANCELED | 제외 |
| `stage4-mixed-200vu-rerun` | 200 | FINISHED | 사용 |
| `stage4-mixed-300vu` | 300 | FINISHED | 사용 |
| `stage4-mixed-400vu` | 400 | CANCELED | 제외 |

### 5.4 처리량 포화 판정

| Recipe | 28 |
| MealPlan | 22 |

Loki에서는 테스트 시간대 애플리케이션 `ERROR`·`CRITICAL` 및 Gateway 4xx·5xx가 확인되지 않았다.

300 VUser의 오류 4건은 다음과 같다.

- Recipe 검색: 1건
- Account 예산: 2건
- Chat: 1건

Agent 로그의 HTTP 응답은 모두 200이었으므로 서버 5xx보다는 응답 본문 assertion 또는 테스트 클라이언트 측 오류일 가능성이 있다. 정확한 분류를 위해 후속 스크립트에는 assertion 실패 사유와 실제 응답 상태를 함께 기록해야 한다.

### 5.7 4단계 판정

- 서버·VM 자원: 정상, 충분한 여유
- 혼합 트래픽 처리량: 약 200 VUser 전후부터 포화
- 1차 병목: Price 현재가·핫딜 조회
- 2차 지연 후보: Recipe 상세
- MealPlan: 컨테이너 CPU 사용량은 가장 높지만 응답시간은 Price보다 안정적
- Kafka: Consumer Lag 0, 이상 없음
- 서버 다운·OOM·재시작: 없음

결론적으로 서버 다운 위험 때문에 중단할 상황은 아니었지만, 200→300 VUser에서 TPS가 거의 증가하지 않았다. 4단계의 목적은 더 높은 숫자까지 무조건 올리는 것이 아니라 혼합 환경의 포화 지점과 원인 후보를 찾는 것이므로, Price 쿼리·DB 인덱스·연결 풀·캐시를 우선 개선 후보로 전달한다.

## 6. 일반 피크 사용자 시나리오 결과

### 6.1 전체 결과

유효한 keep-alive 테스트만 최종 결과에 사용했다.

| VUser | 실행 시간 | 요청 수 | 오류 수 | 오류율 | 평균 응답시간 | TPS | Peak TPS |
|---:|---:|---:|---:|---:|---:|---:|---:|
| 50 | 3분 | 40,951 | 0 | 0% | 6.25ms | 237.83 | 377 |
| 100 | 5분 | 95,871 | 0 | 0% | 103.07ms | 329.10 | 480 |
| 300 | 5분 | 96,788 | 7 | 0.007% | 675.60ms | 331.13 | 571 |
| 500 | 3분 | 58,514 | 26 | 0.044% | 1,130.40ms | 339.79 | 744 |

### 6.2 포화 판정 근거

100→300 VUser:

- VUser: 3배 증가
- TPS: 329.10→331.13, 약 0.6% 증가
- 평균 응답시간: 103.07→675.60ms, 약 6.6배 증가

300→500 VUser:

- VUser: 약 66.7% 증가
- TPS: 331.13→339.79, 약 2.6% 증가
- 평균 응답시간: 675.60→1,130.40ms, 약 67% 증가

따라서 676ms와 1.13초라는 평균값 자체만 보면 즉시 장애라고 할 수 없지만, VUser가 크게 증가해도 처리량은 거의 증가하지 않고 대기시간만 늘었다. 이는 서버 다운이 아니라 **애플리케이션 처리량 포화**로 해석해야 한다.

### 6.3 500 VUser 상세 관찰

nGrinder 초 단위 상세 리포트에서 다음 Price 요청이 후반 구간에 약 19~20초까지 지연된 시점이 확인됐다.

- `price-current`: `GET /api/prices/{item_id}`
- `price-hotdeals`: `GET /api/prices/hotdeals`

같은 구간에서도 Account·Pantry·Notify 등은 대체로 수~수백 ms 범위였다. 따라서 VM 전체 자원 부족보다 Price 내부 DB 처리·연결 풀·쿼리 구조가 우선 조사 대상이다.

## 7. 서버 안정성 결과

| 항목 | 최대 또는 최종 관찰값 | 결과 |
|---|---:|---|
| `fb-app-ai` VM CPU | 약 19% | 보호 기준 미도달 |
| VM 메모리 | 약 24% | 보호 기준 미도달 |
| OOM | 0건 | 정상 |
| 컨테이너 반복 재시작 | 관찰되지 않음 | 정상 |
| Gateway `/healthz` | 전 구간 HTTP 200 | 정상 |
| 테스트 종료 후 health 응답 | 약 1ms | 즉시 회복 |

결론:

- 500 VUser에서도 VM이나 Gateway가 다운되지는 않았다.
- VM이 여유롭다고 애플리케이션도 여유로운 것은 아니다.
- 일부 컨테이너 CPU limit, DB 연결 풀, 쿼리 처리량이 먼저 병목이 되어 VM CPU가 낮은 상태에서도 요청 대기가 발생할 수 있다.

## 8. 백엔드 개선 요청 우선순위

### P0: Price

대상:

```text
GET /api/prices/{item_id}
GET /api/prices/hotdeals
```

확인 요청:

1. 실제 운영 데이터로 SQL `EXPLAIN (ANALYZE, BUFFERS)` 결과 공유
2. 최신 가격·핫딜 조건 인덱스 사용 여부 확인
3. PostgreSQL pool 대기시간·사용 중 연결 수·timeout 확인
4. Redis 캐시 적용 가능성과 데이터 갱신 전략 검토
5. 동일 부하에서 Price DB Span의 P95·P99 확인

### P1: Login

확인 요청:

1. bcrypt 처리 위치와 이벤트 루프 블로킹 여부
2. thread pool 분리 및 worker 수 검토
3. 사용자 조회 SQL과 인덱스 확인
4. 보안 강도는 유지한 채 처리 구조 개선

### P1: MealPlan

확인 요청:

1. DB connection 반환 누락 여부
2. pool size·timeout과 worker 수의 관계
3. 장바구니·지출 집계 SQL 실행 계획
4. 긴 트랜잭션 또는 불필요한 다중 쿼리 여부

### P1: Chat

확인 요청:

1. `chat.search` 하위 ES·PG Span별 지연 비교
2. Price·DB 병목 전파 여부
3. timeout·동시성 제한·캐싱 검토

### P2: Pantry·Notify

확인 요청:

1. 컨테이너 CPU limit과 throttling 확인
2. 목표 처리량이 약 300 TPS 이상일 경우 worker·CPU limit 조정 검토
3. 조회 인덱스·정렬·페이지네이션 확인

### 관찰 유지: Recipe

- 현재 긴급 수정 대상은 아니다.
- 향후 P95·P99와 Elasticsearch 부하만 재검증한다.

## 9. 재검증 기준

개선 전후를 같은 조건으로 비교하기 위해 다음 기준을 제안한다. 이는 팀 승인 전의 제안값이며 공식 SLO는 아니다.

| 서비스 유형 | 제안 P95 목표 |
|---|---:|
| 단순 조회: Pantry·Notify·Recipe | 500ms 이하 |
| 검색·집계: Price·MealPlan | 1초 이하 |
| Login | 1초 이하 |
| Chat | 2초 이하 |
| 공통 오류율 | 1% 미만 |

재검증 시 필수 비교값:

- TPS 또는 RPS
- P50·P95·P99
- 오류율과 timeout 수
- 컨테이너 CPU throttling
- PostgreSQL pool 사용량과 대기시간
- 느린 요청의 Tempo Trace
- 테스트 종료 후 정상 응답으로 돌아오는 시간

## 10. 결과 해석 시 주의사항

1. nGrinder 요약 화면의 응답시간은 P95가 아니라 평균값이다.
2. 최종 합격·불합격은 개선 대상 경로를 더 긴 고정 부하로 실행해 P95·P99를 확인해야 한다.
3. 50·100·300·500 VUser와 사용자 흐름 비율은 운영 로그 기반 확정값이 아니라 탐색용 가설이다.
4. Pantry·Notify의 단독 테스트는 실제 사용자의 think time 없이 최대 연속 호출한 결과다.
5. 일반 피크 시나리오는 읽기 중심이며, Kafka Deal Ingestion Spike는 포함하지 않는다.
6. 500 VUser의 오류 26건은 전체 오류율로는 낮지만, 오류 유형과 해당 요청은 상세 로그로 추가 분류해야 한다.
7. 잘못 설정된 `connectionReset=true` 사전 실행과 설정값이 무시된 테스트는 최종 결과에서 제외했다.
