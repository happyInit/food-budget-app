## 1. 구상·설계
Tesseract / Gemini Vision / CNN+RNN+LSTM 비교 → **Vision 단독** 채택(팀장: 비용보다 단순성·정확도). 방식이 바뀌어도 뒷단 불변하게 **교체가능 `OcrBackend` 계약**으로 캡슐화. 상세: `ocr-method-comparison.md`, `ocr-service-design.md`.

## 2. 구현
`OcrBackend.parse(image)->ParsedReceipt` 계약 + `VisionBackend`(Gemini) + 공통 파이프라인(parse→NER stub) + FastAPI 비동기 job(`POST/GET /api/pantry/ocr`) + 데모 UI(`GET /`). 챗봇 동형 → 백엔드는 프록시로 붙임.

## 3. 동작 검증 (목 백엔드, 비용 0)
임포트·genai API 표면·파싱/타입 엣지·HTTP 종단(POST→job→GET·404·400) 전부 통과.
- 🐛 **검수 중 발견**: `is_food="false"`(문자열) → `bool()`이 True로 오판. → `_to_bool` 방어 픽스.

## 4. 실측 1차 — ❌ 실패
**증상**: 실물 영수증 업로드 → 데모가 `분석 실패: 알 수 없음`.
**원인 추적**:
1. 서비스 로그에 예외 traceback 없음 → 예외를 job `reason`에만 담고 로그를 안 남긴 게 문제(진단 불가).
2. 실패 job 조회 → `reason=''`(빈 문자열). **빈 str 예외 = `asyncio.TimeoutError`**.
3. 모델ID 의심 → Gemini 모델목록 조회 → `gemini-flash-latest` **유효**(54개 중 존재). 모델·키 문제 아님.

**근본원인**: 비전 호출이 **40.9초** 소요(실측) > **20초 타임아웃** → TimeoutError. + 빈-reason 버그가 원인을 "알 수 없음"으로 가림.

## 5. 개선 1차
- 타임아웃 **20→60초**(비전 실측 ~40s 반영)
- **빈 reason 버그 픽스**: `str(exc) or type(exc).__name__` + Timeout은 친근 메시지 + **traceback 로깅**(다신 "알 수 없음" 안 나오게)
- 큰 사진 **다운스케일**(Pillow, 최장 1600px) — 실물 폰 사진 대비 속도·비용↓
- `is_food` 문자열 방어(3단계 검수 픽스 반영)

## 6. 실측 2차 — ❌ 다른 실패(하지만 진전)
- 합성 영수증으로 재현하려다 **기본 PIL 폰트에 한글 글리프 없음** 발견 → 이름이 □(두부)로 렌더 → Gemini가 이름 못 읽음(name=None). **합성 이미지 결함이지 코드 버그 아님.** → Noto Sans KR로 교체(+ 실측엔 **어떤 합성 이미지인지 반드시 첨부/명시**).
- 재실측 → **503 UNAVAILABLE**(Gemini 일시 과부하). **단 이번엔 reason이 명확** → 1차 픽스(빈-reason) 효과 확인.

**교훈**: 단발 503으로 분석이 통째 실패하면 안 됨(사용자 관점 "이렇게 실패하면 안돼").

## 7. 개선 2차
- 일시 오류(**503/429/overloaded**) **자동 재시도** 최대 2회(백오프). 타임아웃은 재시도 안 함(대기 2배 방지).

## 8. 실측 3차 — ✅ 성공
합성 한국 영수증(Noto Sans KR, GS25 5품목) 데모 API 종단:
- **18초, DONE** · 매장 `GS25 역삼점` · 일시 `2026-07-16 19:32` · 합계 `16,300`
- 삼겹살(500g·8,900)·대파(1단·2,400)·두부(1모·1,500) **식재료** / 종량제봉투(20L·3,500) **비식품** — 이름·수량·가격·구분 **전부 정확**
- `item_id=None`(NER stub — 설계상)

→ 키·모델·프롬프트·파싱·is_food·타임아웃·재시도 **전부 실검증**.

## 9. 실측 4차 — 실물 영수증(2026-07-16) ❌→✅

데모에 **실물 마트 영수증** 투입. 합성으로는 안 보이던 것들이 드러남.

### 9.1 quantity int 버그 (❌→✅)
Gemini가 실물에서 `quantity`를 **정수(`1`)** 로 반환 → `OcrItemOut`(str) **ValidationError** → job 실패("분석 실패: ...string_type").
→ **픽스**: `_str_or_none`로 `name`·`quantity`·`store` 강제 str 변환. 재실측 통과.
**교훈**: **합성 성공만 보고 커밋/PR한 건 성급** — 실물이 버그를 잡음. **PR #87 회수**(실물통과+승인 후 재오픈). 이후 실물통과 확인.

### 9.2 중량 판매 → 수량에 'g' 섞임 (과제, 대기)
`1등급돈생삼겹살 992g 12,890` = **중량 판매**(g당단가×무게, 개수 없음). 영수증에 실제 `992g`이 그 자리에 찍혀 OCR은 정확하나, **`quantity`에 개수(1)와 중량(992g)이 섞임**.
→ **방안**: 낱개(count) vs 중량/용량(measure) **필드 분리** + 코드 정규화기(단위 g/kg/ml/L 감지·환산, 안전망). 중량은 재고 양매칭에 유용 → 살림. (구현 대기)

### 9.3 비재료 식품 다수 → 2축 라우팅 (과제, 팀 제안)
실물엔 **가공·즉석·간식·음료**(고래밥·예감오리·미닛메이드·알탕·해물탕)가 다수 = `is_food`지만 **재료 아님**. 마트 구매의 상당수가 "깨끗한 재료"가 아님.
→ **재프레이밍**: 앱은 2축 — **식비축(모든 식품 계상 + 카테고리)** / **재고·레시피축(재료만)**. 비재료는 식비로 살리고 재고엔 안 넣음(미매칭=정상). 상세·결정은 [`ocr-nonfood-handling-proposal.md`](ocr-nonfood-handling-proposal.md)(팀 제안).

## 10. 방식 선택 근거 — 실측 비교 (Vision vs Tesseract)
왜 Tesseract·타 OCR이 아니라 Gemini Vision인지 **자체 실측**(합성 깨끗/저품질 2종) → `ocr-method-comparison.md §5`.
- **저품질에서 Tesseract 0/12(완전 실패) vs Vision 11/12** — 감열지 도메인 결정적 근거.

## 11. 실측 발견 — thinking 오버헤드 (❌→✅ 최적화)
유료 전환 후 실토큰 측정 중 발견:
- 모델 `gemini-flash-latest`=**`gemini-3.5-flash`**(thinking 모델). 기본값이 **thoughts 828토큰**(출력요율 과금) 소비 → **지연 24~41초 · 4.55원/장**.
- **원인=추론 오버헤드.** OCR은 인식·추출이라 추론 불필요 → **`thinking_budget=0`(OFF)** 적용.
- 결과: **지연 ~2.5초(16배↓) · 1.70원/장(63%↓) · 정확도 동일(실측).** 내가 §9.11에 걱정했던 "40초 지연"이 통째로 이거였음.
- (참고) 무료 티어 20건/일 상한에 걸려 429 → **유료 전환**으로 해소.
