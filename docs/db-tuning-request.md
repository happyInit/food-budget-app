# DB 튜닝 요청서

> 작성일: 2026-07-20
>
> 대상: DB 담당자
>
> 목적: 부하테스트 재검증에서 나온 DB 관련 문제를 정리한다(Chat·MealPlan 2건 + DB 문제가 아닌 것으로 확인된 Login 참고사항). 상세 테스트 데이터는 `perf-loadtest-report.md` 참고.

## 1. 먼저 알아야 할 것 — 커넥션 예산은 이미 빠듯하다

PostgreSQL `max_connections`는 기본값(100) 그대로 쓰고 있는데, 앱 서비스들이 이미 이만큼 쓰고 있다.

| 서비스 | pool_max |
|---|---:|
| account | 10 |
| mealplan | 10 |
| pantry | 10 |
| recipe | 10 |
| chat | 5 |
| notify | 5 |
| price | 5 |
| recipebook | 5 |
| **합계** | **60** |

여기에 파이프라인 컨슈머 4개(retail-refiner·deal-notifier·recipe-refiner·deal-pruner) + PGSync 복제 슬롯 + postgres-exporter까지 더하면 **100개 한도에 이미 근접**한다.

**그래서 아래 요청들에 "그냥 풀 크기 늘려주세요"라고 답하면 안 된다.** 서비스 하나만 보고 숫자를 정하면 다른 서비스나 파이프라인 몫을 갉아먹을 수 있다. 전체 예산을 보고 배분해야 한다.

## 2. Chat — 인덱스 추가 (예산과 무관, 바로 처리 가능)

**문제**: 레시피 이름 검색 쿼리가 `WHERE name ILIKE '%단어%'`(양쪽 와일드카드)라 인덱스를 못 쓰고 매번 전체 테이블을 훑는다. 부하테스트에서 이 쿼리 하나가 응답시간의 91%를 차지했다(2,387ms 중 2,179ms).

**위치**: `services/chat/app/pipeline/search.py`의 `PgRecipeNameSource` 클래스

**요청**:
```sql
CREATE EXTENSION IF NOT EXISTS pg_trgm;
CREATE INDEX ON recipe USING gin (name gin_trgm_ops);
```
위와 같은 형태로 `recipe.name`에 트라이그램 GIN 인덱스 적용 검토 부탁드립니다. 이건 커넥션 예산과 무관한 순수 쿼리 최적화라 다른 요청과 별개로 바로 진행 가능합니다.

## 3. MealPlan — 커넥션 풀 확장 (예산 배분 필요)

**문제**: `services/mealplan/app/db.py`에 풀이 `min_size=1, max_size=10`으로 하드코딩되어 있다. 50명 동시접속부터 이미 포화 상태(처리량은 안 늘고 응답시간만 계속 늘어남 — 50명 427ms → 200명 1,887ms).

**판단**: MealPlan은 로그인과 달리 앱을 켤 때마다 반복 호출되는 핵심 기능이라, 피크타임(11-12시·17-18시)에 실제로 동시 접근이 몰릴 수 있습니다. **풀 확장 방향 자체는 타당하다고 봅니다.**

**요청**:
1. 위 커넥션 예산(60/100) 안에서 mealplan에 얼마나 배정할 수 있을지 산정 부탁드립니다
2. 산정된 값을 알려주시면 백엔드가 코드(현재 하드코딩 → env 조정 가능하게)에 반영하겠습니다
3. 여유가 되시면 PgBouncer 같은 커넥션 풀러 도입도 대안으로 검토 부탁드립니다(앱 풀 크기와 실제 PG 커넥션 수를 분리해서 예산 압박 자체를 줄이는 방법)

## 4. Login — DB 문제 아님으로 확인됨 (참고용)

**처음엔 DB 풀 부족으로 추정했으나, 런타임 증거로 확인한 결과 DB 문제가 아니었습니다.**

100명 동시 로그인부터 성공보다 오류가 30배 이상 많아지는 건 사실입니다(100VU: 성공 17건 vs 오류 528건). 그래서 처음엔 커넥션 풀 부족일 거라 추정했는데, 실제로 그 구간의 Prometheus 메트릭을 직접 확인해보니:

- account 컨테이너 CPU: 최대 **195.8%**(한도 2.0코어=200%의 98%, 완전 포화)
- PG `active`(쿼리 실행 중) 커넥션: **0건**

**즉 DB는 전혀 안 바쁘고, 순수 CPU(bcrypt 연산) 문제입니다.** 그래서 이 건은 **DB담당자 요청에서 제외**합니다 — 커넥션 풀·인덱스와 무관하니 조치하실 필요 없습니다. (백엔드/인프라 쪽에서 CPU 증설 또는 로그인 rate limiting으로 대응 예정 — 상세는 재검증 문서 §3.1·§6 참고)
