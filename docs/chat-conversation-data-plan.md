## 1. 구성요소별 설계

### 1.1 멀티턴 맥락 (P0 — 즉효·저위험)
- **무엇**: "그거 말고 다른 거", "그럼 가격은?", "아까 그 레시피 재료" 같은 팔로우업 처리. 현재 무상태라 불가.
- **어떻게**: `ChatRequest`에 `session_id` 추가 → **세션 내 최근 N턴**(예 6~10턴)을 **Redis 단기 TTL**(예 30분~수시간)로 유지 → `extract`/`generate` 컨텍스트에 주입.
- **범위**: 영속 저장 없이 세션 캐시만 → **프라이버시 노출 최소**. 기존 Redis 인프라 재사용.

### 1.2 개인화 (P1 — 영속·동의 전제)
- **입력**: 영속 대화 로그에서 유저 신호 추출 — 선호 재료·자주 만드는 요리·예산 민감도·**비선호("돼지고기 빼고")·알레르기**.
- **활용 (a) 랭킹 피처**: 개인화 레시피 랭킹(P1 LightGBM)의 유저 행동 피처에 대화 유래 신호 편입(`ai-spec §3`).
- **활용 (b) 응답 개인화**: 챗봇이 비선호·알레르기 재료 회피, 예산 맥락 반영해 답.

### 1.3 제품 분석 — AI 일일 레포트 (時간 기반)
- **무엇**: 매일 그날 대화를 **AI가 집계 분석** → **개선방향** 도출: 유저가 뭘 묻나·미응답 패턴(예 "마라탕 없음")·트렌드 품목·**카탈로그/레시피 커버리지 갭** → **데이터 담당자에게 리포트**.
- **어떻게**: 일일 스케줄 배치(cron) → 오프라인 Gemini로 요약·분석 → 리포트 생성 → 전달(채널 TBD: Slack DM/GitHub 이슈/파일).

### 1.4 로그 임계 트리거 분석 (건수 기반)
- **무엇**: `(질문·응답·미응답·근거)` 로그가 **설정 건수(1000·10000 등 config)** 쌓일 때마다 AI가 **① 요약 ② 분석 정보 ③ 문제점 발견 시 추천 해결방안 몇 가지**를 담당자에게 제안.
- **1.3과의 차이**: 1.3=시간(매일)·제품 개선방향 / 1.4=건수 임계·**품질·문제·해결안**. 둘 다 AI 생성 리포트.
- **어떻게**: 로그 카운터가 임계 도달 → 배치 트리거 → 오프라인 Gemini 분석 → 리포트.

## 2. 데이터 모델 / 저장

`chat` 스키마 `chat_message`(schema-per-service 컨벤션):
```sql
CREATE TABLE chat.chat_message (
  id          bigserial PRIMARY KEY,
  user_id     bigint,                          -- ▶account.app_user 논리참조(동의 유저만)
  session_id  uuid NOT NULL,                    -- 멀티턴 묶음
  role        text NOT NULL CHECK (role IN ('user','bot')),
  text        text NOT NULL,                    -- 발화 내용
  intent      text,                             -- recommend/price/nutrition/unknown
  item_ids    bigint[],                         -- 추출 품목(있으면)
  unanswered  boolean,                          -- bot 미응답 여부(품질 분석용)
  basis       jsonb,                            -- 근거 태그(레시피·가격·영양)
  created_at  timestamptz NOT NULL DEFAULT now()
);
CREATE INDEX ON chat.chat_message (session_id, created_at);
CREATE INDEX ON chat.chat_message (created_at);
```
- 대안: Kafka `events.user.activity`에 chat 이벤트 편입(`user-behavior-data-request`의 인프라 재사용).
- **보존정책**: 원문 단기(90~180일 협의) → 이후 집계·익명화.

## 3. AI 분석 파이프라인 (1.3·1.4 공통)
- **오프라인 배치 Gemini** — 런타임(챗봇 응답)과 분리. 집계 로그를 넣어 요약·분석·해결안 생성.
- **비용 bounded**: 일일 1회 + 임계 트리거만(주기 호출 아님). OCR 오프라인 사전·refine 캐시와 같은 "오프라인 1회성" 원칙.
- **트리거**: 일일(cron) + 카운터 임계(config `report_every_n = 1000|10000`).
- ⚠️ 유료 API + 대화 데이터 → **집계/익명화 후 전송**(원문 최소화) + 팀 승인.

## 4. 프라이버시·거버넌스 (민감정보라 강하게)
- **수집 동의** + **user_id 스코프** + **PII 최소화** + **유저 삭제권**(내 대화 삭제) + 보존 한도.
- 알레르기·예산·건강 = **특별 취급**. Gemini 백엔드/분석이면 **외부 전송 고지**.
- **팀 승인**(클릭스트림 P0와 동일 절차 — `user-behavior-data-request`와 묶어 하나의 "유저 데이터 수집" 트랙).

## 5. 단계 로드맵
1. **P0**: 멀티턴 맥락(Redis 세션, 영속 X) — UX 즉효·저위험.
2. **P1**: 영속 `chat_message`(동의) → 개인화(랭킹 피처·응답) + 로그 축적.
3. **리포트**: 일일 제품분석(1.3) + 임계 트리거 품질/해결안(1.4).

## 7. 미결/질문
1. 리포트 **전달 채널**(Slack/GitHub 이슈/파일) 합의.
2. `report_every_n` 초기값(1000? 10000?) + 일일 리포트 시각.
3. `chat_message` vs Kafka 이벤트 방식 · 보존기간.
4. 수집 **동의·팀 승인**(behavior-request와 묶음).
5. AI 분석 시 **원문 vs 집계/익명화** 수준.

## 8. 담당별 전달 요구사항 (실행용)

> 아래는 챗봇 추가구현(멀티턴·개인화·리포트·가드레일)을 위해 **인프라·데이터 담당이 준비해야 할 것**. AI(건우)는 이 위에서 파이프라인을 구현한다.

### 8.1 인프라 담당
| # | 요구사항 | 상세 | 어떤 기능 | 우선 |
|---|---|---|---|---|
| I-1 | **Redis 멀티턴 세션 키공간** | 키 `chat:sess:{session_id}` → 최근 N턴(6~10) 리스트, **단기 TTL(30분~수시간)**. 챗봇이 이미 refine 캐시로 Redis 사용 중 → **접속 재사용**, 세션용 키공간·TTL 정책만 확정 | 멀티턴 맥락 | **P0** |
| I-2 | **Redis 레이트리밋 카운터** | `chat:rate:{user_id}:{yyyymmdd}` INCR + TTL 24h. 유저별 일일 요청 상한 | 가드레일(#9) | P2 |
| I-3 | **배치 스케줄러(cron)** | ① **일일 1회**(시각 협의) ② **카운터 임계 트리거**(`report_every_n`). 오프라인 Gemini 배치 잡 **실행 환경**(챗 런타임과 분리). 잡 → PG(`chat_message` 읽기)·Gemini(유료키) 접속 | AI 리포트(1.3·1.4) | P2 |
| I-4 | **(선택) Kafka 토픽·컨슈머** | chat 이벤트를 `events.user.activity`에 편입 시(§2 대안). `chat_message` 테이블 방식이면 **불필요** | 이벤트 적재 | 조건부 |
| I-5 | **Gemini 배치 비용 상한·모니터링** | 리포트 배치는 유료 API → OCR과 동일 거버넌스(상한·추적) | 비용 관리 | P2 |

### 8.2 데이터 담당
| # | 요구사항 | 상세 | 어떤 기능 | 우선 |
|---|---|---|---|---|
| D-1 | **`chat_message` 스키마 생성** | §2 DDL(`chat` 스키마) + 인덱스 2개. `user_id`=account 논리참조(FK 아님, 스키마-퍼-서비스) | 영속·개인화·리포트 | P1 |
| D-2 | **동의 게이팅** | 미동의 유저 대화는 **저장 안 함**(무상태 유지). 클릭스트림과 **동일 동의 절차**(`user-behavior-data-request`와 하나의 트랙) | 프라이버시 전제 | **개인화 前 필수** |
| D-3 | **보존·익명화 정책** | 원문 단기(90~180일 협의) → 이후 **집계·익명화**. **유저 삭제권**(내 대화 삭제) 반영 | 거버넌스 | P1 |
| D-4 | **민감정보 특별취급** | 알레르기·예산·건강 = 외부(Gemini 분석) 전송 시 **집계/익명화 후**, 외부전송 고지 | 거버넌스 | P1 |
| D-5 | **item_master 읽기 보장** | 개인화·추출 조인용(이미 존재 — 확인만) | 개인화 | 확인 |

### 8.3 선행 협의 필요 (미결 §7과 동일)
- 리포트 **전달 채널**(Slack/이슈/파일) · `report_every_n` 초기값·일일 시각 · `chat_message` vs Kafka · **원문 vs 집계** 수준.
- **개인화·영속(D-1~4)은 D-2 동의 확보가 전제** — 동의 트랙 승인 전엔 **멀티턴(P0, 영속 X)만** 선행 가능.
