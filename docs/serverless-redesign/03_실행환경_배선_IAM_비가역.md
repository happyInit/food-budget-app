## 축④ 이벤트 배선 (실물 기준 — 계획의 S3 이벤트 전제는 무효, D-11)

### 4-1. 배치 2종 (#4·#8) — EventBridge Scheduler 치환

- 스케줄: #8 매일 07:00 KST → **전일 22:00 UTC** / #4 일·수 08:00 KST → **전일(토·화) 23:00 UTC**. 현행은 CronJob `spec.timeZone: Asia/Seoul` + **컨테이너 프로세스 TZ=UTC 혼재** [출처: FACTS/02 D-17]. Scheduler 의 타임존 지정 지원 여부는 [미확인 — 웹 0회 규율] → **UTC 환산 크론을 정본으로 쓰고 KST 를 주석으로** 두면 지원 여부와 무관하게 안전하다. 단 증분 쿼리의 날짜 로직이 프로세스 로컬/DB 세션 의존으로 혼재(D-17)이므로, **8/9 런타임 고정 목록에 'TZ=UTC 명시 + 날짜 경계 KST 명시 변환' 항목을 추가**한다(자정 경계에서 증분 누락/중복이 나는 전형 지점).
- 정기 증분: **Scheduler → Lambda 단발 호출** — 증분 규모(NULL/template 재포착·신규분)는 수십~수백 건 [추정: 증분 쿼리 구조상 전량 재처리 없음, summarize_reviews.py:90]으로 15분 내 완주 방향 — Distributed Map 불필요.
- 대량 백필(PF-05 판정 반영 — 'ItemReader 는 S3 만' = 거짓):
  - 요약 전량 6,873건: ID 배열 ≈62KB < 256KiB → **DM 에 JSON 배열 직접 입력, S3 내보내기 불필요** [출처: agent-PF-resume PF-05].
  - 감정 백필 14만 건: ID 배열 ≈1.26MB [추정: 9B×140,000] > 256KiB → **이 경우만 S3 ItemReader(CSV/JSON) 또는 구간 분할 필요**. 부모 워크플로는 Standard 필수 [출처: PF-05].
  - 8/8 에 A(그대로 이식)를 고르면 백필도 단발 Lambda 반복 실행으로 대체 — DM 자체가 소멸.

### 4-2. 동기 2종 (#1·#2) — 202+폴링 유지, 내부만 분리

- **결정: 프론트 계약(POST 202 + GET 폴링) 유지.** 큐 기반 전환(웹훅·SSE 등)은 재설계라 이관/재설계 분리 원칙(00 §4) 위반 + 프론트 동시 수정을 마감 창에 강요.
- 단 내부 구현은 그대로 이식 불가 — 실물은 응답 후 **인프로세스 asyncio 태스크**가 처리를 잇는데(D-03), Lambda 는 핸들러 응답 후 실행환경이 동결되어 백그라운드 연속 실행이 보장되지 않는다(플랫폼 일반 동작 — 상세 문구 인용은 PF 재개 시). → **접수 Lambda(202+잡 기록) / 처리 Lambda 분리, 연결은 SQS 표준 큐 + DLQ**. Lambda 비동기 직접 호출 대안은 재시도 제어가 암묵적 — 트리거별 재시도 시맨틱이 **PF-08 미판정**이므로 명시 제어가 되는 SQS 를 보수적 기본값으로 둔다.
- **폴링 상태 저장소** — 실물: #1 = Redis(미설정 시 인메모리 폴백, job TTL) [출처: services/ocr/app/store.py:26-43], #2 = **Redis 전용**(job TTL + 30일 캐시 TTL + 단일비행 락 nx) [출처: services/video/app/store.py:28-61]. 온프렘 Redis 는 이전 후 못 쓴다(경로·지연) → **대체: DynamoDB 단일 테이블(mp-ai-jobs) + TTL** — job 상태(TTL=현 job_ttl_s 승계)·#2 의 30일 캐시·락(조건부 쓰기 = SETNX 대응)을 한 테이블로 통합. ElastiCache 기각: VPC 필수 자원이라 축② 고정비를 재소환. 캐시 제거 기각: 동일 URL 재요청마다 Gemini 재호출(교차유저 캐시 이점·120s 소실). **C안일 때**: GCP 측 대응물(Firestore TTL 등)은 [미확인] — C 확정 후 별도 결정.
- **반증 조건**: ① "202+폴링 유지" — 폴링 주기(1s/2s)×콜드스타트로 첫 DONE 체감이 현행 대비 유의미 악화(측정)되면 큐+푸시 재검토. ② "SQS 경유" — PF-08 판정 재개 결과 비동기 직접 호출의 재시도·DLQ 제어가 충분하면 큐 한 단을 제거(비용·지연 절감). ③ "DynamoDB TTL" — 락·캐시의 강한 일관성 요구가 실측에서 확인되면(중복 추출 관측) 조건부 쓰기 설계를 재검증.

### 4-3. 스케줄 미기동 감지 (데드맨) — 필수 포함

1. 각 배치 종료 시 **성공 하트비트 발행**(CloudWatch 커스텀 메트릭 `mp-ai-batch-heartbeat`, 차원=job). 실물 ingest 배치는 print 뿐·메트릭 0 [출처: FACTS/02 §1 관측 행] — 하트비트 발행 코드가 이전 시 신규 추가 항목이다.
2. 알람 = "기대 주기 + 2h 내 하트비트 미수신 시 발화". **결측 데이터 처리(treatMissingData)가 이 알람의 성패인데 PF-11 미판정** — 값 확정은 판정 재개 후. 잘못 두면 '미기동인데 침묵'이라는 원 지적 그대로 재현된다.
3. 알람 평가·크론은 UTC 정본(4-1 환산표) — KST 로 읽는 사람을 위해 주석 병기.
4. Scheduler 호출 실패 측도 잡는다: 대상 호출 실패 시 재시도·DLQ 설정(값은 배선 구현 시 확정).
- **반증 조건**: 정상 기동인데 하트비트 알람이 오발하면 주기 산정(크론·TZ 환산·+2h 여유) 오류다 — 환산표(4-1)부터 재검증.

### 4-4. #6 가격 체인 — 분할 경계 (1단계 정정 2026-08-07: 탐지 배치는 이전 대상)

- **Phase 1 경계: 탐지 배치(발행 포함)까지 이전, 절단면 = Kafka 프로듀스 직후** — 이전분 = CronJob 탐지(04:40, 무상태 z-score 재계산 + PG 상태 3종 RW + `price.anomaly.detected` 발행) / 잔존분 = 상시 컨슈머 + KEDA + DLQ [출처: FACTS/02 D-09·§2 #6, 01_이전대상_7R §2 정정판]. 컨슈머 쪽은 손대지 않으므로 경로 절단 없음.
- **선행 조건**: Lambda→온프렘 **Kafka 인바운드 + PG 경로**(H축, 02_레지던시 §1-3) — **D-3 의 Tunnel 검증 항목에 PG TCP 와 함께 Kafka TCP 를 병합**해 한 번에 검증한다. 경로 성립 전 착수 금지(구판 "이전 없음" 결론은 이 조건이 미해결이던 시점의 보수 판정 — 조건부 이전으로 대체).
- **반증 조건**: Tunnel/VPN 어느 쪽으로도 Kafka 인바운드가 성립하지 않으면 #6 은 자동으로 구판 결론(전 구간 잔존)으로 복귀한다 — 그 관측이 곧 복귀 트리거다.
