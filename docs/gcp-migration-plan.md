## 2. 왜 지금(온프렘)이 아니라 EKS 이후인가 — 가장 중요한 판단

### 2.1 온프렘에서는 WIF가 **구조적으로 막힌다**

클러스터 실측(2026-07-29, `192.168.0.17`):

```
issuer   : https://kubernetes.default.svc.cluster.local   ← 클러스터 내부 전용 이름
jwks_uri : https://192.168.0.17:6443/openid/v1/jwks       ← 사설 IP
```

Workload Identity Federation은 **Google이 인터넷에서 issuer의 JWKS를 가져와 토큰 서명을 검증**한다.
지금 issuer는 내부 DNS·사설 IP라 **Google에서 도달 불가 → WIF 등록 자체가 실패**한다.

해결하려면 셋 중 하나인데 전부 클러스터 인증 근간을 건드린다:
1. `--service-account-issuer`를 공개 HTTPS로 변경 + JWKS 공개 게시 → **API 서버 재시작·기존 토큰 무효화 위험**
2. OIDC 프록시 외부 노출 → 공인 IP·도메인·TLS 필요
3. 서비스계정 **키 파일** 사용 → 간단하지만 **"키리스"라는 목적이 사라짐**

### 2.2 EKS에서는 **공짜로 해결된다**

EKS는 **공개 OIDC issuer**(`https://oidc.eks.ap-northeast-2.amazonaws.com/id/…`)를 AWS가 제공한다.
Google이 JWKS를 가져올 수 있으므로 **WIF가 그대로 동작**한다.

| 시점 | AWS 인증 | GCP 인증 |
|---|---|---|
| 온프렘 k8s(~8/5) | ESO 정적 키(**IRSA 불가** — EKS 전용) | **WIF 불가**(사설 issuer) |
| **EKS(~8/26)** | **IRSA** ✅ | **WIF** ✅ |

### 2.3 결론

온프렘에서 issuer를 바꾸는 작업은 **수명 3주짜리**이고, 8/26 EKS 이전 시 **통째로 버려진다**.
인프라 정본의 원칙 *"이식성 > 온프렘 최적화"*(§migration_plan L15)와 정면으로 어긋난다.

> **→ GCP 이전은 EKS 이전과 같은 단계에서 수행한다.** 그때 IRSA(AWS) + WIF(GCP)가 동시에 성립해
> **"정적 키 없는 크로스클라우드 인증"** 이라는 목표가 온전히 달성된다.

## ⚠️ 2.4 위 §2.3 의 **순서 결정은 대체되었다** (2026-07-30, 팀 승인)

**Vertex 전환을 EKS 까지 미루지 않고 지금 수행하기로 결정**했다(같은 날 리전 결정
`GCP_LOCATION=global` 과 한 묶음). 따라서 §2.3 의 *"EKS 이전과 같은 단계에서 수행한다"* 는
**더 이상 유효하지 않다.** 아래는 그 결정이 인증 방식에 남긴 결과다.

### 무엇이 유효하고 무엇이 대체되었나

| 조항 | 상태 |
|---|---|
| §2.1 온프렘 issuer 는 사설 → **URL 기반 WIF 등록 불가** | ✅ **유효**(실측 재확인 2026-07-30) |
| §2.3 온프렘 issuer 변경은 **수명 3주짜리** · 이식성 원칙 위반 | ✅ **유효** — 온프렘 WIF 를 택하지 않는 근거 |
| §2.3 결론 *"GCP 이전은 EKS 단계에서"* | 🔴 **대체됨**(2026-07-30 팀 승인) |
| **키리스가 최종 목표** | ✅ **유효** — 포기한 것이 아니라 **연기**다 |

### 그래서 온프렘 구간의 인증은 — **한시적 정적 키(브리지)**

셋 중 실제로 가능한 것만 남기면:

| | 방식 | 판정 |
|---|---|---|
| A | EKS 까지 전환 연기 | ❌ **팀 결정과 배치** |
| B | 온프렘 WIF(JWKS 업로드) | ❌ §2.3 근거 그대로 — apiserver 수술의 **수명이 3주**다 |
| **C** | **정적 SA 키 + 만료 계획** | ✅ 채택 |

> JWKS **업로드** 방식(`--jwk-json-path`)을 쓰면 Google 이 issuer 에 도달할 필요는 없다 —
> 즉 §2.1 의 "등록 자체가 실패" 는 **URL 기반 등록에 한정**된다(실측: `/openid/v1/jwks` 조회 가능).
> 그래도 B 를 택하지 않는 이유는 **도달성이 아니라 수명**이다. 고유 issuer 로 바꾸는
> apiserver 변경 + 서명키 회전 시 JWKS 재업로드가 **8/26 에 통째로 버려진다.**

### 🔴 브리지 키의 조건 — 이걸 지켜야 "포기"가 아니라 "연기"다

1. **최소 권한**: `roles/aiplatform.user` 만. 프로젝트 편집자 금지.
2. **만료 명시**: **EKS 이전(~2026-08-26) 시 키 삭제 + WIF 전환**. 그때 버리는 것을 전제로 만든다.
3. **코드는 이미 양쪽을 지원한다** — `genai_client.make_client` 는 `sa_key_json` 이 비면
   **ADC 자동탐색**으로 간다. WIF 는 external_account credential config 를 통해 ADC 경로로
   그대로 동작하므로, **전환 시 코드 변경이 없다.** 키 경로는 fallback 으로만 남는다.
4. **키를 파일이 아니라 env 로 받는다** — `app` ns 가 PodSecurity restricted +
   `readOnlyRootFilesystem` 이라 볼륨 마운트는 Deployment 수정을 부른다.
   env 는 `envFrom: secretRef` 가 이미 걸려 있어 **ExternalSecret 한 줄**로 끝난다.

## 3. 코드 변경 — 생각보다 작다

`google-genai`는 **통합 SDK**로 두 백엔드를 모두 지원한다. 전환은 **클라이언트 생성 한 줄**이다.

```python
# 현재 (Google AI API · 개인 키)
client = genai.Client(api_key=KEY)

# Vertex AI (팀 GCP · ADC)
client = genai.Client(vertexai=True, project=PROJECT_ID, location=LOCATION)
```

`generate_content` · `types.Part` · `FileData` · 프롬프트는 **전부 그대로**다.

### 3.1 백엔드 토글 방식 (롤백 가능하게)

`OCR_BACKEND`·`GENERATOR_BACKEND`와 동일한 **팩토리 + env 토글** 패턴을 쓴다.
**현행 Google AI API 경로를 지우지 않는다** — 되돌아올 수 없는 마이그레이션을 만들지 않기 위해서다.

| 서비스 | 신규 env | 값 |
|---|---|---|
| OCR | `GEMINI_BACKEND` | `api_key`(기본) \| `vertex` |
| video | `VIDEO_GEMINI_BACKEND` | `api_key`(기본) \| `vertex` |
| 공통 | `GCP_PROJECT_ID` · `GCP_LOCATION` | Vertex 모드에서만 사용 |

### 3.2 호환성 확인이 필요한 파라미터 ⚠️

OCR은 아래를 쓴다(`vision.py:157`) — **Vertex에서 동일 동작인지 PoC로 확인해야 한다**:

| 파라미터 | 확인 포인트 |
|---|---|
| `response_mime_type="application/json"` | Vertex에서도 JSON 강제가 되는가 |
| `system_instruction` | 지원 형식 동일한가 |
| `thinking_config(thinking_budget)` | **가장 위험** — 이 인자 거부로 OCR이 전량 실패한 사고 이력이 있다(PR #272). Vertex에서 인자명·허용값이 다를 수 있음 |
| `temperature=0.0` | 동일 |

video는 `FileData(file_uri=youtube_url)`를 쓴다 — **Vertex도 YouTube URL을 지원**하나 제약이 있다(§4.2).

## 4. 제약·리스크 (빠짐없이)

### 4.1 비용 — 절감 없음, 오히려 증가 가능

| 구성 | 요율 |
|---|---|
| 현행 Google AI API | 기준 |
| Vertex **글로벌** 엔드포인트 | **동일** |
| Vertex **리전**(서울 등) | **약 +10%**(2026-07-01부터) |

- **GCP 크레딧 없음** → 팀 실비 결제
- OCR·video는 AI 비용의 **79.4%**(MAU 50만 기준 월 363만원) → 10% 할증이면 **월 +36만원**
- **→ 레지던시가 요구사항이 아니면 글로벌 엔드포인트를 쓴다**(할증 회피)

### 4.2 YouTube URL 제약 (video 전용)

Vertex 공식 제약:
- **공개 영상이거나 요청 계정 소유** — 비공개·연령제한 영상은 실패
- **요청당 YouTube URL 1개** — 현 파이프라인은 1건씩이라 무관
- 파일 크기·프레임 샘플링(1fps) 제약 존재

→ 현행 Google AI API와 유사하나, **거부 사유·에러 코드가 다를 수 있어** 폴백 문구 검증 필요.

**✅ PoC 완료 2026-07-29 — 지원되나 요청 형태가 더 엄격하다.**

| 조건 | api_key | vertex | 실측 오류 |
|---|---|---|---|
| `Content(role=...)` | 생략 가능 | **필수** | `400 Please use a valid role: user, model.` |
| `FileData(mime_type=...)` | 생략 가능 | **필수** | `400 empty mimeType parameter in fileData` |

두 백엔드가 **같은 형태를 모두 받으므로** 분기 없이 공통(`role="user"` + `mime_type="video/*"`)으로
배선했다(`extract.py`) — api_key 회귀 없음 확인. 정상 영상 추출 결과도 동등(재료 10/10).

⚠️ **에러 코드는 실제로 달랐다**(§4.2가 우려한 대로). 삭제된 영상(oEmbed 404)에서:

| | 결과 |
|---|---|
| api_key | `is_recipe=false` 를 1초 만에 반환 — **"요리 영상이 아님"으로 오안내** |
| vertex | `500 INTERNAL` (3/3 재현) — 잡 실패 |

**둘 다 옳지 않다.** 유저는 삭제·비공개 URL 을 반드시 붙여넣으므로 "영상에 접근할 수 없다"는
별도 사유가 필요하다 → 미해결(`ai-verification-backlog.md` §1.10).

### 4.3 서울 리전 quota/403 리스크

2026-05 기준 **Vertex 서울(`asia-northeast3`)에서 간헐적 403/quota-capacity 오류** 보고가 있고 미해결이다(유료 계정·정상 IAM에도 발생).
- 레지던시가 필요 없으면 **글로벌 엔드포인트**가 오히려 안정적(Google이 리전 용량을 내부 흡수)
- 레지던시가 필요하면 서울을 쓰되 **폴백 순서(서울 → 도쿄 → 글로벌)** 를 설계해야 함
- ⚠️ 도쿄 폴백은 **데이터가 일본으로 나간다** — 레지던시 명분과 자기모순이므로 팀 합의 필요

### 4.4 인증 경로가 하나 더 늘어난다

| 경로 | 온프렘 | EKS |
|---|---|---|
| AWS(Bedrock) | ESO 정적 키 | **IRSA** |
| **GCP(Vertex)** | (미실시) | **WIF** |

- ESO가 **멀티백엔드**(AWS Secrets Manager + GCP Secret Manager)가 되어 관리 대상이 늘어남
- Cilium FQDN egress에 **Vertex 엔드포인트 추가** 필요
  - 🔴 **`generativelanguage.googleapis.com`을 제거하면 안 된다** — 오프라인 도구(#5·#6)와 폴백 경로가 죽는다

### 4.5 3-클라우드 운영 부담

온프렘 + AWS + GCP. 청구·IAM·관측이 셋으로 갈린다.
**5인 캡스톤 기준으로는 실제 부담**이며, 이를 감수하는 근거는 **학습 가치**다(§0 명분 ②).

### 4.6 품질 재검증 필요

모델은 같지만 **엔드포인트가 다르면 동작이 미세하게 다를 수 있다**.
OCR은 실물 13장 벤치마크가 있으므로 **동일 세트로 재측정**해 회귀 여부를 확인한다(§5.2).

**✅ 재측정 완료 2026-07-29 (실물 13장 · location=global)**

| | api_key | vertex |
|---|---|---|
| 성공 | 13/13 | 13/13 |
| 합계 정합 | 13/13 | **13/13** |
| 품목 총합 | 85 | 84 |
| 평균 지연 | 2,993ms | 3,520ms (+18%) |

지연 +18%는 OCR이 비동기 잡(202 접수 → 폴링)이라 체감에 영향 없다.

🔴 **그러나 "합계 일치"가 결함을 덮고 있었다.** 유일한 불일치였던 `receipt_0008`(맥도날드
할인 영수증)을 파고들자 **합계는 맞는데 품목 단가가 서로 달랐다** — 재고·식비에 직접 들어가는
값이라 합계로 상쇄되지 않는다. 상세는 §4.7.

### 4.7 🔴 같은 모델·같은 입력인데 결과가 다르다 (실측 2026-07-29)

`receipt_0008` 을 **같은 이미지·temperature=0** 으로 백엔드별 5~8회 반복했다.

**(1) 백엔드 간 차이가 아니라 실행 간 분산이다.**

| 경로 | 8회 결과 |
|---|---|
| api_key | 스낵랩 1,800원 ×3 · 3,000원 ×2 (품목명은 안정, **가격이 흔들림**) |
| vertex | 품목 2개 ×3 · 3개 ×2 (**같은 백엔드 안에서 갈림**) |

temperature=0 은 결정성을 보장하지 않는다 — 서빙이 동적 배칭이라 배치 구성에 따라 GPU
리덕션 순서가 바뀌고, 부동소수점 비결합성 때문에 근소한 토큰 확률차에서 argmax 가 뒤집힌다.
**vertex 가 이 입력에서 더 불안정했고, api_key 는 품목 구성이 안정적이었다.**

> ⚠️ 첫 측정에서 "api_key 5/5 동일"로 적었던 것은 **품목명만 비교**한 결과다.
> 가격까지 보면 api_key 도 흔들린다. 비교 지표를 좁게 잡으면 분산이 숨는다.

**(2) 버전 핀을 Vertex 에서 강제할 수단이 없다.**

```
api_key  version = 3.5-flash-lite-07-2026     ← 날짜 빌드 노출
vertex   version = default                    ← 가려짐
```

`-latest` 별칭 드리프트로 OCR 이 전량 실패한 사고(PR #272) 이후 **버전 핀은 팀 규칙**인데,
Vertex 는 서빙 빌드를 알려주지 않아 두 백엔드가 같은 빌드인지 **증명할 수 없다**.
→ 미해결 위험(`ai-verification-backlog.md` §1.11).

**(3) 정답은 어느 쪽도 아니었다.** 원본 영수증:

```
1 해피-치킨모짜스낵랩      3,000      ← 식품 정가
  맥도날드 앱 쿠폰        -1,200      ← 할인
  Subtotal                1,800      ← 3,000 - 1,200 ✓
```

말려 찍힌 사진이라 좌측 품목줄과 우측 금액열이 세로로 어긋났고, 두 백엔드가 **금액을 서로
다른 줄에 붙였다**(api_key: 스낵랩=1,800 / vertex: 스낵랩=-1,200). 백엔드 문제가 아니라
**할인 영수증 공통 결함**이며, 이런 건은 `realign_prices` + HITL 플래그가 처리 대상으로 잡는다.

**(4) 이 과정에서 실제 버그를 하나 찾아 고쳤다 → §4.8**

### 4.8 ✅ 복구 로직이 안전망을 지우던 버그 (수정 완료)

`realign_prices`(§7.3.5)는 "조정=음수·품목=양수" 불변을 어긴 쌍이 정확히 하나일 때 두 가격을
스왑한다. 그런데 **엔진은 음수를 근거로 `is_food=false` 까지 함께 붙인다**("음수=할인이겠지").
가격만 되돌리면:

| | 스낵랩 처리 |
|---|---|
| 스왑 **전** | `price<0` → 티어-1 → `needs_review=True` → **HITL 이 잡음** |
| 스왑 **후**(수정 전) | `price>0` 이라 티어-1 통과 → 티어1 `is_food=false` → `needs_review=False` → **식비에서 조용히 증발** |

**복구가 오히려 플래그를 지우는 역전**이었다. 음수가 오배치였다고 방금 판정했으면
`is_food=false` 의 전제도 사라지므로, 스왑과 함께 플래그도 되돌려 **이름 캐스케이드에 판정을
환송**하도록 고쳤다(true 로 단정하는 게 아니다 — 진짜 비식품은 티어1.5 `_NONFOOD_KW` 가 걸러낸다).

**실측 검증** — 동일 입력 8회, 수정 전/후 비교(지표 = 식비에도 없고 플래그도 없는 "조용한 누락"):

| 경로 | 수정 전 | 수정 후 |
|---|---|---|
| api_key | 정상 7 · 플래그 1 | 정상 7 · 플래그 1 (**회귀 없음**) |
| vertex | 🔴 **조용한 누락 6** · 플래그 1 · 정상 1 | **조용한 누락 0** · 정상 7 · 플래그 1 |

회귀 테스트 2건 추가(`test_realign_prices_restores_is_food` · `_keeps_nonfood_by_name`).
전 서비스 **276 passed**.

> 이 버그는 Vertex 가 만든 것이 아니라 **Vertex 가 드러낸 것**이다. api_key 에서도 엔진이
> 음수를 오배치하는 순간 같은 경로로 증발한다 — 빈도가 낮아 안 보였을 뿐이다.

## 7. 결정 기록 · 결정 대기 항목

### 7-1. ✅ **결정: 리전 = `global`** (2026-07-30, 팀 승인)

**결정 내용**: OCR·영상의 Vertex 호출은 **글로벌 엔드포인트(`GCP_LOCATION=global`)** 를 쓴다.
즉 **영수증 이미지가 국내 리전 밖에서 처리되는 것을 수용**한다.

**결정 사유 — 선택의 여지가 없었다.** 레지던시를 포기해서가 아니라 **채택 모델이 리전
엔드포인트에 아직 배치되지 않았기 때문**이다. 실측(2026-07-30):

| 엔드포인트 | `gemini-3.5-flash-lite` |
|---|---|
| `asia-northeast3` (서울) | ❌ **404** |
| 도쿄 · `us-central1` 등 리전 | ❌ **404** |
| `global` | ✅ **유일하게 응답** |

모델이 없는 것이 아니다 — `models.get()` 으로 **존재는 확인**되고 api_key 경로에서도 정상
동작한다. **리전 엔드포인트에서 서브되지 않는 상태**다(2026-07-21 출시분).

**그래서 서울 고정은 "비용 +10%" 문제가 아니라 "모델을 바꿔야 하는" 문제다.** 구세대로 내리면
채택 근거(실물 13장 · 성공률 92% · 0.45원/장)가 통째로 무효가 되어 **재벤치마크가 선행**된다.

**검토한 대안 3개**

| 안 | 내용 | 판정 |
|---|---|---|
| **A** | `global` 수용 | ✅ **채택** — 모델·품질·단가 근거를 그대로 유지 |
| B | 서울 고정 + 구세대 모델 | ❌ 채택 근거 전면 재작성 필요. 비용이 이전 이익을 넘는다 |
| C | api_key 유지(전환 포기) | ❌ 전환 목적(개인 키·개인 과금 탈출) 자체를 버린다 |

> ⚠️ **도쿄 폴백은 검토 대상이 아니다** — 데이터가 일본으로 나가는 것은 레지던시 명분과
> 자기모순인데(§4.3), 애초에 도쿄에도 모델이 없다.

**재검토 조건(트리거)** — 서울 리전에 모델이 배치되면 다시 판단한다. 확인은 1회 호출이면 된다:

```python
genai.Client(vertexai=True, project=..., location="asia-northeast3") \
     .models.get(model="gemini-3.5-flash-lite")     # 200 이면 재검토 가능
```

배치되면 `GCP_LOCATION` 한 줄만 바꾸면 된다(코드 변경 없음). 다만 **리전은 약 10% 할증**이고
quota 403 리스크가 있으니(§4.3) 그때 다시 비교한다.

**부수 효과 — 이 결정이 §7-2(1번 질문)를 대체한다.** "레지던시가 요구사항인가"를 묻기 전에
**요구사항이어도 지금은 충족할 수 없다**는 것이 확인됐다. 요구사항으로 확정된다면 그때는
Vertex 전환 자체를 보류하고 api_key 를 유지하는 것이 맞다(C안).

**운영 반영**
- 코드에 `GCP_LOCATION` **기본값을 두지 않았다** — 리전이 레지던시를 결정하므로 누군가 조용히
  아무 리전에 붙이는 일이 없어야 한다(미지정이면 기동 실패).
- 매니페스트: `deploy/k8s/patch-mp-ocr-vertex.yaml` · `deploy/k8s/video-route.yaml`
- 개인정보 처리방침에 **국외 이전 고지**가 필요한지는 별도 확인 사항이다(법무·심사 영역).
