## 4. 이날의 발견 3가지

### 4.1 🔴 ResourceQuota 가 오토스케일링을 통째로 무력화하고 있었다

`app` ns 의 `mp-app-quota`(`requests.memory: 6Gi`)가 평시에 이미 **84%**.

```
Error creating: pods "mp-account-…" is forbidden: exceeded quota: mp-app-quota,
  requested: requests.memory=384Mi, used: 6080Mi, limited: 6Gi
```

**쿼터 초과는 `Pending` 이 아니라 admission 거부다** — 파드가 아예 안 만들어진다(`ReplicaSet: FailedCreate`).
Pending 이 없으면 **Karpenter 는 반응할 대상이 없다.** HPA 는 "늘렸다"는 이벤트만 남기고 조용히 죽는다.
BG green 세트도 같은 벽에 막힌다.

⇒ **원칙: 쿼터는 노드 용량보다 느슨해야 한다.** 쿼터의 일은 용량 계획이 아니라 폭주 차단이다.
값·산출 = config 레포 `platform/cluster-baseline/overlays/eks/quotas.yaml §"② 검산 완료"` (6→18Gi · 6→16).
감시 = `monitoring/overlays/eks/rules-quota.yaml` (기본 `KubeQuotaAlmostFull` 은 `for: 15m`·`info` 라 9.5분 사고를 못 잡고,
`KubeQuotaExceeded` 는 **원리상 안 뜬다** — 쿼터는 초과가 안 되니까).

### 4.2 🔴 price 의 5xx 는 용량이 아니라 **캐시 스탬피드**였다

핫딜은 캐시 키가 **하나**(`price:hotdeals:20`), TTL 120초, **히트 34ms / 미스 1,360ms**.
초당 526건 상태에서 만료되면 그 1.36초 동안 **약 715건이 같은 쿼리를 동시 실행** → PG 커넥션 고갈.

지표가 **양봉**(p50 42ms / p99 1.74s / max 45.19s)이라 평균만 보면 건강해 보인다.

🔴 **HPA 로는 못 고치고 오히려 나빠진다** — replica 를 늘리면 만료 순간 PG 를 때리는 주체가 그 배수만큼 늘어난다.
⇒ **stale-while-revalidate + single-flight** 로 수정(앱 레포 MR !70).

실측 검증(같은 조건 · price 코드만 다름):
```
hotdeals 실패   1,783건 → 2건
전체 실패       0.19%  → 0.0012%
만료 순간 서버시간  46ms   (진짜 콜드 쿼리 412ms 대비 8배 빠름)
동시 30건 콜드    쿼리 1회 (구 코드였다면 30회)
```

⚠️ 증폭 요인은 **별건으로 남았다** — hotdeals 는 matview 가 없고 `JOIN LATERAL` 이 상품마다 돈다
(EXPLAIN `loops=5867` → 유효 딜 65건). 여기서 고친 것은 **동시성**이지 쿼리가 아니다.

### 4.3 🔴 ArgoCD sync 은 push 직후에 치면 **옛 커밋을 본다**

config 레포 push 직후 `patch … sync` 를 쳤는데 **5분** 뒤에야 반영됐다(20:52 push → 20:57 반응).
레포 캐시가 안 갱신된 상태라 sync 가 옛 리비전으로 돈다. **명령은 성공인데 아무 일도 안 일어난 것처럼 보인다.**

```bash
git push origin main
kubectl -n argocd annotate application <앱> argocd.argoproj.io/refresh=hard --overwrite
sleep 8
kubectl -n argocd patch application <앱> --type merge -p '{"operation":{"sync":{"revision":"HEAD"}}}'
```
hard refresh 를 끼우면 **5분 → 20초**. 이 5분 때문에 촬영 테이크 하나를 통째로 버렸다.

## 5. 운영상 확인된 것

### 5.1 Karpenter 는 왜 6대나 띄웠나 — 대수가 아니라 vCPU×시간이 값이다

베이스 노드(m7g.xlarge)가 **평시에 이미 CPU 87% / 메모리 93%** 다. 노드 2대 합쳐 여유 CPU 약 960m.

| | 파드당(앱+사이드카) | 증가 | CPU |
|---|---|---|---|
| account | 350m + 30m = 380m | +4 | 1,520m |
| recipe | 200m + 30m = 230m | +6 | 1,380m |
| price | 150m + 30m = 180m | +6 | 1,080m |
| **BG green**(account 한 벌 더) | 380m | +6 | 2,280m |
| | | **+22 파드** | **6,260m** |

버스트 1대(m7g.large)가 담는 양 = 할당가능 1,930m − DaemonSet 260m = **1,670m**(파드 약 4개).
`(6,260 − 960) ÷ 1,670 ≈ 3.2` → **최소 4대**, AZ 분산·자투리로 실제 **6대**.

🔵 **대수는 청구서와 무관하다** — m7g 가격은 선형이라 `large` 6대 = `xlarge` 3대 = 같은 값이다.

### 5.2 이날 총 비용 ≈ **$7 (약 1만원)** — EC2 는 10%뿐

| 항목 | 근거 | 비용 | 비중 |
|---|---|---|---|
| WAF 요청 | ≈4.9M × $0.0000006 | $2.94 | 41% |
| 데이터 전송 out | ≈23.6 GB × $0.126 | $2.97 | 42% |
| ALB LCU | 처리 바이트 | $0.53 | 7% |
| **EC2 버스트** | 6.9 node-시간 × $0.1003 | **$0.69** | **10%** |

단가는 Price List API 실조회(2026-08-17 · 서울). 사용량은 4회차만 실측이고 나머지는 처리량 비례 추정.
⚠️ **Cost Explorer 가 SCP 로 막혀 있어 실제 청구액과 대조하지 못했다.**

🔴 돈은 **부하 발생기가 온프렘에 있어서** 나갔다 — 응답 23.6 GB 가 전부 인터넷으로 egress 했다.
대규모로 다시 돌릴 일이 있으면 **같은 VPC 안 EC2 에서** 돌리는 것이 정답이다(전송비가 거의 0이 된다).

### 5.3 ⚠️ 시험 직후 5분간 공개 URL 이 **403** 이다

WAF 레이트룰을 2000/5분/IP 로 원복하는 순간, **직전 5분 창에 시험 트래픽이 남아** 정상 요청까지 막힌다.
실측 18:40:44 → 18:45:32(약 5분) 뒤 자동 회복. **고장이 아니다.**
🔴 시험 직후 데모·촬영을 이어서 하면 여기서 넘어진다. 감시 스크립트도 이때 `http=403 release=-` 를 찍는다.

### 5.4 ⚠️ 버스트 노드는 스스로 안 걷힌다

`consolidationPolicy: WhenEmpty` 라 파드가 하나라도 남으면 노드가 유지된다.
이날 세 번 손으로 `kubectl delete nodeclaim` 했다. 잊으면 240원짜리가 **월 10만원**이 된다.
→ `WhenEmptyOrUnderutilized` 검토 후보(별건).
