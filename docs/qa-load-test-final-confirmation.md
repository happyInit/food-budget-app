# 최종 확인 — Chat·MealPlan·Account 병목 재현 (전체 서비스, 로그인 측정 포함)

> 작성일: 2026-07-21
>
> 배경: 오늘 하루 여러 차례 재실행에서도 결과가 들쭉날쭉했던 문제를, ①원본과 동일 조건(5분·1프로세스) 고정 ②Tempo 쿼리 버그 수정(반복 재조회로 정확한 값 확보) ③로그인을 실제로 측정에 포함(기존엔 전부 제외) 세 가지를 다 반영해서 마지막으로 재확인한 결과. 이번엔 25→50→100→200→300→500VU 계단식으로 6단계 전부 깨끗하게 우상향하는 패턴이 나와, 오늘 나온 결과 중 가장 신뢰할 수 있다.

## 1. 실행 조건

| 항목 | 값 |
|---|---|
| 스크립트 | `full-service-journey.groovy` — OCR 제외(실비용 이슈로 뺌), 로그인은 VUser(스레드)당 1회 **측정 포함**(기존엔 `@BeforeProcess`에서 측정 제외였음) |
| 서비스 커버리지 | Recipe·Price·Recipebook·Account(로그인+예산)·Pantry·MealPlan·Notify·Chat — 8개 |
| 비율 | 레시피 탐색 50% / 식단·장바구니 25% / 핫딜·가격 15% / Chat 10% (로그인은 저니 확률과 별개로 스레드당 1회) |
| duration | 5분(300,000ms) — 전 단계 동일 |
| 프로세스 구성 | 1프로세스 × N스레드(N=VU수) |
| ramp-up | 초기 20명, 3초 간격 20명씩 증가 |
| 단계 | 25 → 50 → 100 → 200 → 300 → 500VU, 이전 단계 안전 확인 후 다음 단계 진행 |

## 3. 서비스별 P50/P95/P99 (Tempo, 반복 재조회로 정확도 확보)

| 25 | 2ms | 5ms | **2,486ms** | 2,700ms | 8.7% |
| 50 | 2ms | 3,091ms | **5,120ms** | 5,297ms | 14.9% |
| 100 | 1ms | 3ms | 5ms | 6ms | 31.1% |
| 200 | 2ms | 1,569ms | **5,137ms** | 5,512ms | 54.4% |
| 300 | 2ms | 1,208ms | **12,173ms** | 13,401ms | 121.5% |
| 500 | **21,374ms** | 30,571ms | **30,912ms** | 31,451ms | **200.0%** |

500VU에서는 **중앙값(P50)조차 21.4초**다. 컨테이너 CPU가 정확히 한도(200%)에 도달했다 — bcrypt 해시 연산이 CPU를 다 써버려서 요청이 줄줄이 대기하는 전형적인 CPU 포화 패턴. 100VU 구간만 유독 낮게 나온 건 표본 수(483건)가 적어 우연히 느린 요청을 못 잡았을 가능성이 있다.

100VU부터 P99가 2초 근처로 올라간 뒤 500VU까지 거의 고정된다(2,031→2,077ms) — CPU는 최대 13.2%로 전혀 안 바쁨. CPU가 아니라 DB 쿼리(미인덱스 `ILIKE` 풀스캔, 기존 코드 확인 사실)가 원인이라는 진단과 일치.

|---:|---:|---:|---:|---:|---:|

| 50 | 14.9% | 4.7% | 5.7% | 3.0% | 6.6% |
| 100 | 31.1% | 7.3% | 8.4% | 4.3% | 9.1% |
| 200 | 54.4% | 8.2% | 10.1% | 5.0% | 11.2% |

## 5. 최종 결론

이번 6단계는 25→500VU까지 **깔끔하게 우상향하는 계단식 패턴**이 나와, 오늘 실행한 테스트 중 가장 신뢰도가 높다.

| 서비스 | 병목 시작 지점 | 원인 | 근거 |
|---|---|---|---|
| **Account(로그인)** | 300VU부터 급격히, 500VU에서 CPU 100% 포화 | CPU 포화(bcrypt 해시) | 컨테이너 CPU가 정확히 한도(200%)에 도달 — 직접 증거 |
| **Chat** | 100VU부터 이미 심각, 이후 고정 | DB 쿼리(미인덱스 `ILIKE` 풀스캔) | CPU 여유(최대 13.2%) + 코드 확인 사실 |
| **MealPlan** | 300VU 임계점부터 폭발 | DB 커넥션 풀 고갈 | CPU 여유(최대 18.3%) + span 다크타임으로 메커니즘 증명(기존) |
| Pantry·Recipebook·Price·Recipe·Notify | 없음 | - | 전 구간 P99 40ms 이하, CPU 여유 |

**우선순위**: Account(로그인)가 가장 심각하다(500VU에서 P50조차 21초, CPU 완전 포화) — 지금까지 로그인을 측정 제외해서 놓치고 있었던 가장 큰 병목이다. Chat·MealPlan은 기존 진단대로 확정, 나머지 5개 서비스는 문제없음이 이번에도 재확인됐다.
