# 최종 확인 — Account(로그인) 장애가 Chat·MealPlan에 전파되는 구조 (전체 서비스, 로그인 정상화)

> 작성일: 2026-07-21
>
> 배경: 오늘 하루 여러 차례 재실행에서도 결과가 들쭉날쭉했던 문제를, ①원본과 동일 조건(5분·1프로세스) 고정 ②로그인을 실제로 측정에 포함(기존엔 전부 제외) ③로그인이 VUser당 정확히 1회만 일어나도록 캐싱 버그 수정 ④**측정 방법을 Tempo 트레이스 길이에서 nGrinder 원본 응답시간으로 교체**(아래 §0 참고) 네 가지를 다 반영해서 최종 재확인한 결과.

## 0. 방법론 정정 — 왜 Tempo 트레이스 길이를 버렸는가

이전 버전 문서는 Tempo가 계산하는 "트레이스 전체 길이"로 P50/P95/P99를 산출했다. 그런데 크로스서비스 호출이 있는 엔드포인트(MealPlan의 cart·expense-summary가 Account를 호출하는 경우 등)에서, **클라이언트(MealPlan)가 이미 타임아웃으로 응답을 끝낸 뒤에도 서버(Account)가 그 요청을 백그라운드로 계속 붙들고 있으면, 그 시간까지 트레이스 길이에 다 포함된다**는 게 실제 트레이스 span 타임라인 분석으로 드러났다.

**직접 증거** — MealPlan `GET /api/mealplan/cart` 트레이스 하나를 열어보면:
- MealPlan 쪽 root span: **3,009.4ms**에서 끝남 (BudgetProvider의 3.0초 타임아웃 설정과 정확히 일치)
- 그 안에 포함된 Account 쪽 span(`GET /api/users/budget`): **20,077.2ms**까지 계속됨 — MealPlan은 이미 포기했는데 Account는 계속 처리 중이었다

즉 Tempo 기준 "20초"는 사용자가 실제로 기다린 시간이 아니다. **이후 모든 수치는 nGrinder가 직접 측정한 응답시간(클라이언트가 실제로 기다린 시간)을 기준으로 한다** — `output.csv`의 GTest별 2초 구간 `Mean_Test_Time` 중 구간 최댓값.

```json
{"method":"GET","route":"/api/users/excluded-items","error_type":"PoolTimeout","retryable":false}
```

### 3.1.1 로그인 자체의 다크타임 — DB가 아니라 이벤트 루프 블로킹

500VU 구간에서 가장 느렸던 로그인 트레이스(30.9초) 하나를 span 단위로 열어보면:

```
0.5ms                             요청 접수
0.5ms  ~ 29,993ms (약 30초, 97%)   완전한 다크타임 — 아무 작업도 안 잡힘
29,993ms ~ 30,064ms (68ms)         DB 쿼리(사용자 조회, select)
30,064ms ~ 30,899ms (834ms)        또 다크타임(bcrypt 비밀번호 검증으로 추정)
```

**DB 쿼리 자체는 68ms로 빠르다 — DB는 원인이 아니다.** 진짜 문제는 요청이 도착한 뒤 DB 쿼리가 시작되기까지 30초 가까이 아무것도 못 하고 대기했다는 것이다. 이건 **다른 로그인 요청들의 bcrypt 연산(동기·CPU 집약)이 서버의 이벤트 루프를 계속 막고 있어서, 이 요청은 자기 차례가 올 때까지 핸들러 코드 실행 자체를 시작도 못 한 것**으로 해석된다. CLAUDE.md에 이미 기록된 진단("bcrypt는 CPU 집약, `cpus: 2.0` 상한에서 대기")과 정확히 일치하며, 로그인이 대량으로 몰리면 CPU 200% 한도로도 감당이 안 된다는 게 이번에 트레이스로 직접 증명됐다.

### 3.4 나머지 서비스(Pantry·Recipebook·Price·Recipe·Notify) — 안정

Account에 의존하지 않는 나머지 5개 서비스는 이번에도 500VU까지 안정적이었다(P99 대부분 50ms 이하, 오늘 앞선 재검증에서 두 차례 독립 재조회로 이미 확인됨 — `docs/qa-load-test-stage4-flow-dbqa.md` 참고).

## 4. 왜 "로그인 반복 호출 때문"이 아닌가

이 문서 작성 전, "로그인이 스레드당 여러 번 반복 호출돼서 Account 수치가 부풀려진 것 아니냐"는 의심이 있었다(§0 이전 버전에서 실제로 발견된 버그). 그래서 캐싱을 수정해 로그인을 거의 1:1로 정상화한 뒤 **똑같은 6단계를 다시 돌렸다**(§2.1). 결과는:

- Account의 최대 응답시간·CPU가 **거의 그대로이거나 오히려 더 나쁘다**(300VU CPU: 이전 121.5% → 이번 103.6%로 비슷, 500VU 응답시간: 이전 계열과 이번 14,112ms로 대등)
- MealPlan·Chat도 여전히 300VU 이후 심각하게 나빠진다

**즉 로그인 반복 호출은 원인이 아니었다.** 로그인 빈도를 실제 서비스처럼(1인 1회) 맞춰도 Account는 진짜로 무너진다.

## 4.1 왜 오늘 이전 테스트들에선 MealPlan·Chat이 이렇게까지 심각해 보이지 않았는가

오늘 초반 테스트(`peak-journey-scenario1.groovy`, 로그인이 프로세스당 딱 1번뿐 — 사실상 "이미 다 로그인한 평상시 트래픽" 상황)의 nGrinder 원본 응답시간을 같은 방식으로 다시 뽑아 비교하면:

| | 로그인 거의 없음(원본) 300VU | 원본 500VU | 로그인 정상화(오늘 최종) 300VU | 오늘 최종 500VU |
|---|---:|---:|---:|---:|
| Account(budget) | 567ms | 411ms | **13,309ms** | **14,112ms** |
| MealPlan(cart) | 118ms | 431ms | **4,219ms** | **8,120ms** |
| MealPlan(expense) | 168ms | 360ms | **1,168ms** | **4,098ms** |
| Chat | 98ms | 343ms | 456ms | 373ms |

**로그인이 거의 없을 때는 Account도, MealPlan·Chat도 전부 수백ms대로 양호하다.** 즉 두 테스트는 서로 다른 트래픽 패턴을 재현한 것이다 — 원본은 "이미 로그인된 사용자들의 평상시 사용", 오늘 최종은 "많은 사용자가 동시에 로그인부터 시작하는 순간"(예: 점심·저녁 피크타임에 다 같이 앱을 켤 때). **MealPlan·Chat이 오늘 갑자기 더 나빠진 게 아니라, 로그인 몰림이라는 숨은 변수가 이번에 처음 활성화되면서 진짜 크기가 드러난 것이다.**

## 5. 최종 결론

| 서비스 | 원인 | 근거 |
|---|---|---|
| **Account** | CPU 포화(bcrypt 로그인 해싱) + 자체 DB 커넥션 풀 고갈 | 컨테이너 CPU가 500VU에서 175.6%(한도 200%)까지 도달, 응답시간·오류 둘 다 VU에 비례해 계속 악화 |
| **MealPlan** | **자체 문제가 아니라 Account 장애 전파** — `cart`·`expense-summary`가 Account 예산 API를 부르다 3초 타임아웃 | 코드(`asyncio.gather` + `BudgetProvider(timeout=3.0)`) + 실측 응답시간이 타임아웃 값과 정확히 일치 |
| **Chat** | **자체 문제가 아니라 Account 장애 전파** — 제외재료 API를 부르다 2초 타임아웃, 실패 시 `PoolTimeout` | 코드(`account_client.py`, `timeout=2.0`) + 실제 Account 로그의 `PoolTimeout` 에러 |
| Pantry·Recipebook·Price·Recipe·Notify | 없음 | Account에 의존하지 않음, 전 구간 안정 |

**우선순위 1순위는 Account입니다.** Account만 고치면(로그인 CPU 부하 완화 또는 DB 풀 확대) Chat과 MealPlan의 문제도 대부분 같이 해소될 가능성이 높습니다 — 셋이 별개의 3개 병목이 아니라 **Account 하나가 근원이고 나머지 둘은 그 증상**이라는 게 이번 재검증의 핵심 결론입니다.

기존에 알려졌던 "Chat=미인덱스 쿼리", "MealPlan=자체 DB 풀 고갈"은 코드상 실재하는 별개의 문제이지만, 이번 결합 부하 테스트에서 관찰된 심각한 지연의 주된 원인은 그게 아니라 Account 장애 전파였다.

## 7. 개발자 전달용 최종 결론 및 요청사항

**한 줄 요약**: 오늘 관찰된 심각한 지연(초 단위)의 근본 원인은 **Account 하나**다. MealPlan·Chat은 별개의 병목이 아니라 Account 장애가 크로스서비스 호출을 통해 전파된 증상이다. Account만 고쳐도 오늘 본 심각한 증상은 대부분 사라진다.

### 1순위 — 지금 고쳐야 함: Account(로그인)

- **원인**: 로그인 다수 동시 요청 시 bcrypt(동기·CPU 집약) 연산이 이벤트 루프를 막아, 요청이 핸들러 실행 자체를 시작 못 하고 대기(§3.1.1 트레이스로 확인 — DB 쿼리는 68ms로 빠름, DB는 원인 아님). 500VU에서 컨테이너 CPU가 175.6%(한도 200%)까지 도달.
- **요청**: bcrypt cost 하향 조정, 또는 해싱을 별도 워커/스레드풀로 오프로드해 이벤트 루프 블로킹 자체를 없애는 방향 검토 요청. (CPU 쿼터를 더 올리는 건 이미 2.0으로 상향된 상태라 근본 해결이 아닐 가능성 — 연산 자체를 비동기화하는 게 우선일 것으로 보임, 다만 이건 추천이지 결정 아님)

### 2순위 — 여유 될 때: MealPlan·Chat 자체 결함(로그인과 무관하게 실재)

- **MealPlan**: `services/mealplan/app/context.py`의 DB 커넥션 풀이 `max_size=10`으로 고정. 로그인 부하 없는 상황에서도 500VU에서 431ms까지 늘어남(경미하지만 실재).
- **Chat**: `services/chat/app/pipeline/search.py`의 `PgRecipeNameSource` 쿼리가 미인덱스 `ILIKE '%키워드%'`(leading wildcard라 인덱스 활용 불가). 로그인 부하 없는 상황에서도 500VU에서 343ms까지 늘어남.

### 3순위 — 설계 개선(강력 추천, 급하진 않음): 크로스서비스 호출 취약성

- MealPlan(`BudgetProvider`, 3.0초)·Chat(`account_client.py`, 2.0초)이 Account를 부를 때 타임아웃이 너무 길다. Account가 조금만 느려져도 그 시간을 통째로 날린다.
- 타임아웃을 훨씬 짧게(예: 300~500ms) 줄이거나, 캐싱/서킷브레이커를 도입하면 Account에 다시 문제가 생겨도 MealPlan·Chat이 지금처럼 통째로 끌려가지 않는다.
