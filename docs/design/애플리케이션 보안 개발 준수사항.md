# 애플리케이션 보안 개발 준수사항

## 1. 문서 목적

OWASP Top 10은 웹 애플리케이션에서 자주 발생하고 보안 영향이 큰 취약점을 정리한 문서다. 우리 서비스는 사용자 계정, 냉장고 재고, 식단, 식비, 영수증 정보를 처리하고 PostgreSQL·Elasticsearch·Redis·Kafka 및 외부 API를 사용하므로, OWASP Top 10:2025 중 서비스 구조와 직접 관련된 다음 6개 항목을 우선 적용한다.

| 항목 | 무엇을 막는가 | 우리 서비스의 적용 이유 |
|---|---|---|
| A01 접근 제어 실패 | 권한 없는 데이터·기능 접근 | 다른 사용자의 냉장고·식단·지출 접근 방지 |
| A02 보안 설정 오류 | 개발 설정·내부 시스템의 운영 노출 | 셀프호스트 인프라와 운영 설정 보호 |
| A03 소프트웨어 공급망 실패 | 취약하거나 악성인 외부 구성요소 | Python 패키지·Docker 이미지 보호 |
| A04 암호화 실패 | 비밀번호·Secret 노출 | API Key·토큰·개인정보 보호 |
| A05 인젝션 | 입력값의 명령·쿼리 실행 | SQL·Elasticsearch·서버 명령 조작 방지 |
| A07 인증 실패 | 로그인 위조·토큰 악용 | 사용자 계정과 로그인 상태 보호 |

### 적용 원칙

- **필수:** 해당 기능을 개발하거나 배포할 때 반드시 준수한다.
- **조건부:** 관련 기능 또는 운영 조건이 생겼을 때 적용한다.
- **향후 검토:** 현재 규모에서는 도입하지 않지만 서비스 확대 시 재검토한다.
- 예외가 필요하면 미적용 이유·위험·보완책·재검토 시점을 기록하고 팀 리뷰를 받는다.

## 2. A01 — Broken Access Control (접근 제어 실패)

**무엇인가?** 로그인하지 않았거나 권한이 없는 사용자가 다른 사용자의 정보 또는 관리자 기능에 접근하는 문제다.

**도입 목적:** 다른 사용자의 냉장고·지출·레시피북 등 개인정보에 접근하는 것을 방지한다.

### 준수사항

- 보호 API는 로그인된 사용자만 호출할 수 있어야 한다.
- 요청으로 받은 `user_id`를 믿지 않고 JWT의 사용자 ID를 사용한다.
- 사용자 데이터 조회·수정·삭제 시 소유자를 확인한다.
- 미인증 및 다른 사용자 접근을 거부하는 테스트를 작성한다.

## 3. A02 — Security Misconfiguration (보안 설정 오류)

**무엇인가?** 개발 편의를 위해 사용한 설정, 기본 계정 또는 열린 포트가 운영 환경에도 남아 시스템이 노출되는 문제다.

**도입 목적:** 개발용 설정이나 관리자 기능이 운영 환경에 노출되는 것을 방지한다.

### 준수사항

- 운영에서 debug와 상세 오류 출력을 끈다.
- CORS는 승인된 프론트엔드 주소만 허용한다.
- 관리자·내부 API와 DB·Grafana 등을 인터넷에 직접 공개하지 않는다.
- 개발과 운영의 Secret 및 설정을 분리한다.

## 4. A03 — Software Supply Chain Failures (소프트웨어 공급망 실패)

**무엇인가?** 설치한 Python 라이브러리, GitHub Actions 또는 Docker 이미지에 알려진 취약점이나 악성 코드가 포함되는 문제다.

**도입 목적:** 취약하거나 출처가 불분명한 패키지와 Docker 이미지 사용을 방지한다.

### 준수사항

- 공식 또는 팀에서 승인한 패키지와 이미지만 사용한다.
- 의존성 버전을 `requirements.txt` 등의 파일로 관리한다.
- Docker 이미지는 CI에서 Trivy로 검사한다.
- 심각한 취약점을 수정하지 못하면 사유와 대응 계획을 기록한다.

## 5. A04 — Cryptographic Failures (암호화 실패)

**무엇인가?** 비밀번호, API Key, 로그인 토큰 또는 개인정보가 평문으로 저장·전송되거나 잘못된 암호화로 노출되는 문제다.

**도입 목적:** 비밀번호·API Key·토큰이 코드나 로그를 통해 유출되는 것을 방지한다.

### 준수사항

- 비밀번호·API Key·JWT Key를 코드와 Git에 저장하지 않는다.
- 비밀번호는 Argon2id 등 검증된 비밀번호 해시로 저장한다.
- 외부 공개 서비스는 HTTPS를 사용한다.
- 비밀번호·토큰·API Key·영수증 개인정보를 로그에 남기지 않는다.

## 6. A05 — Injection (인젝션)

**무엇인가?** 사용자가 입력한 내용이 단순 데이터가 아니라 SQL, Elasticsearch 검색 문법 또는 서버 명령으로 실행되는 문제다.

**도입 목적:** 사용자 입력이 SQL·검색 쿼리·서버 명령으로 실행되는 것을 방지한다.

### 준수사항

- 사용자 입력을 SQL·Elasticsearch·OS 명령 문자열에 직접 붙이지 않는다.
- SQL은 파라미터 바인딩을 사용한다.
- API 입력은 Pydantic으로 타입·길이·범위를 검증한다.
- OCR 파일은 형식과 크기를 검사하고 YouTube URL은 허용된 주소만 받는다.

## 7. A07 — Authentication Failures (인증 실패)

**무엇인가?** 서버가 공격자를 정상 사용자로 잘못 인식하거나 탈취·변조·만료된 로그인 토큰을 받아들이는 문제다.

**도입 목적:** 공격자가 다른 사용자로 로그인하거나 탈취한 토큰을 계속 사용하는 것을 방지한다.

### 준수사항

- 비밀번호는 평문이나 일반 해시로 저장하지 않는다.
- JWT의 서명과 만료시간을 서버에서 검증한다.
- 로그인 요청에 횟수 제한을 적용한다.
- 로그아웃·비밀번호 변경 시 Refresh Token을 폐기할 수 있어야 한다.
- Kakao 로그인을 도입하는 경우 `state`와 PKCE를 적용한다.

## 8. 개발자 PR 확인사항

개발자는 자신의 변경과 관련된 항목만 확인한다.

- [ ] 보호 API에서 로그인과 소유권을 확인했는가?
- [ ] 사용자 입력을 SQL·검색·명령 문자열에 직접 붙이지 않았는가?
- [ ] API 입력에 길이와 범위 제한이 있는가?
- [ ] Secret이나 개인정보를 코드·Git·로그에 넣지 않았는가?
- [ ] 새 패키지와 이미지는 공식 출처인가?
- [ ] 관련된 권한 실패 테스트를 작성했는가?
