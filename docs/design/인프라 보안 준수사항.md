# 인프라 보안 준수사항

## 1. 문서 목적

- 컨테이너 런타임·네트워크·CI/CD·메시징 계층에서 지켜야 할 최소 보안 기준을 통일한다.
- `dockerfile 보안 공통 명세서.md`(Dockerfile단), `애플리케이션 보안 개발 준수사항.md`(애플리케이션단)와 함께 3계층 보안 문서의 마지막 축(인프라단)이다.
- 항목을 필수·조건부 필수·선택으로 구분한다.
- 설정 적용이 어려운 경우 PR 또는 인프라 변경 기록에 사유를 남긴다.

## 2. 한눈에 보는 적용 기준

| 번호 | 항목 | 적용 | 핵심 기준 |
|---|---|---|---|
| 1 | 네트워크 티어 분리 및 최소 포트 노출 | 필수 | edge/app/data 망 분리, DB·Kafka 등은 호스트 포트 비노출 |
| 2 | 컨테이너 런타임 읽기 전용 마운트 | 조건부 필수 | 주요 애플리케이션 디렉토리 `read_only` + 필요한 경로만 tmpfs |
| 3 | CI/CD 시크릿 관리 | 필수 | GitHub Actions Secrets로 관리, 코드·YAML 하드코딩 금지 |
| 4 | 메시징 계층(Kafka) 인증·암호화 | 필수 | SASL/SCRAM 또는 TLS 적용, PLAINTEXT 통신 금지 |

## 3. 항목별 적용 방법

### 3.1 네트워크 티어 분리 및 최소 포트 노출

**도입 이유:** 단일 브릿지 네트워크에 모든 컨테이너를 묶으면 프론트엔드 컨테이너 하나만 침해돼도 같은 네트워크 안의 DB·Kafka·내부 API에 바로 접근할 수 있다. 외부에 노출할 필요가 없는 서비스까지 호스트 포트로 열려 있으면 공격 표면이 커진다.

**적용 방법:** 네트워크를 최소 2~3개 티어로 나눈다. 외부와 직접 통신하는 `edge`(프론트엔드·게이트웨이), 서비스 간 통신용 `app`, DB·Kafka 전용 `data`(가능하면 `internal: true`)로 구분하고, 각 서비스는 필요한 네트워크에만 연결한다. `ports:`는 실제로 외부 접근이 필요한 서비스(프론트엔드 등)에만 선언한다.

**확인·예외:** `docker network inspect <network>`로 실제로 그 네트워크에 속한 컨테이너 목록을 확인한다. VM 간(App 서버 ↔ Data 서버) 통신은 compose bridge로 묶이지 않으므로 IP:포트 직접 연결로 처리하고, 하나의 가상 네트워크로 묶어야 하면 Swarm overlay나 K8s CNI로 승격이 필요하다는 점을 예외로 남긴다.

```yaml
networks:
  edge:
    driver: bridge
  app:
    driver: bridge
  data:
    driver: bridge
    internal: true      # data 티어는 외부 아웃바운드 차단

services:
  frontend:
    networks: [edge]
    ports: ["80:80"]    # 외부 노출은 프론트엔드만

  account:
    networks: [edge, app]

  postgres:
    networks: [app, data]
    # ports 선언 없음 → 호스트에 직접 노출되지 않음
```

### 3.2 컨테이너 런타임 읽기 전용 마운트

**도입 이유:** 컨테이너가 악성 코드에 오염되거나 취약점으로 침해되더라도, 애플리케이션 소스·설정 디렉토리 자체가 변조되면 피해가 지속·확산된다. 런타임에 실제로 쓰기가 필요한 경로는 극히 일부(캐시, 임시파일, 업로드 등)뿐이다.

**적용 방법:** 서비스 컨테이너에 `read_only: true`를 지정하고, 런타임에 쓰기가 꼭 필요한 경로만 `tmpfs` 또는 별도 볼륨으로 예외 처리한다. 함께 `cap_drop: [ALL]`로 불필요한 리눅스 커널 권한을 제거하고, `security_opt: [no-new-privileges:true]`로 컨테이너 내부에서의 권한 상승을 차단한다.

**확인·예외:** `docker inspect --format '{{.HostConfig.ReadonlyRootfs}}' <container>`로 실제 적용 여부를 확인한다. 빌드 산출물을 런타임에 직접 써야 하는 서비스(예: 파일 업로드·OCR 임시 저장)는 해당 경로만 tmpfs/볼륨으로 열어두고 나머지는 읽기 전용을 유지한다.

```yaml
services:
  recipe:
    read_only: true
    tmpfs:
      - /tmp
    cap_drop: [ALL]
    security_opt:
      - no-new-privileges:true
    restart: unless-stopped
```

### 3.3 CI/CD 시크릿 관리

**도입 이유:** DB 비밀번호, Harbor 계정, 배포용 SSH 키, AWS Access Key 등이 워크플로 YAML이나 소스 코드에 평문으로 남으면 저장소 접근 권한만으로 운영 인프라 전체가 노출된다. Dockerfile 단계에서 이미지에 시크릿을 굽지 않는 것과는 별개로, **CI 파이프라인 자체**가 시크릿을 다루는 방식도 관리 대상이다.

**적용 방법:** 모든 자격 증명은 GitHub Actions Repository Secrets(`Settings → Secrets and variables → Actions`)에 등록하고, 워크플로에서는 `${{ secrets.NAME }}` 형태로만 참조한다. 컨테이너 기동 시 필요한 값은 이미지에 포함하지 않고 배포 대상 서버의 `.env`(gitignored) 또는 워크플로 SSH 단계에서 주입한다.

**확인·예외:** 워크플로 로그에 시크릿 값이 그대로 출력되지 않는지 확인한다(GitHub Actions는 등록된 Secrets 값을 로그에서 자동 마스킹하지만, 값을 가공해 출력하면 마스킹이 깨질 수 있으므로 주의). 레포지토리에 `git log -p`로 과거 커밋에 시크릿이 남아있지 않은지 주기적으로 점검한다.

```yaml
# .github/workflows/build-push-app.yml 실사용 예시
- name: Harbor 로그인
  run: echo "${{ secrets.HARBOR_PASSWORD }}" | docker login "$REGISTRY" -u "${{ secrets.HARBOR_USERNAME }}" --password-stdin

- name: 배포 SSH 키 준비
  run: |
    echo "${{ secrets.DEPLOY_SSH_KEY }}" > ~/.ssh/cd_deploy_key
    chmod 600 ~/.ssh/cd_deploy_key
```

> ⏳ **위 두 번째 예시(`DEPLOY_SSH_KEY`)는 2026-07-31 에 삭제된 코드다.** GH Actions → ssh `.9` 배포
> 경로가 폐기되면서 `deploy` 잡·`cd_deploy_key` 롤·키 파일이 함께 사라졌다(러너 은퇴 · `.9` 파괴 ·
> CD 정본 = ArgoCD 단독). **원칙(시크릿은 GitHub Secrets/서버 `.env` 로만, 파일로 떨궜으면 `if: always()`
> 로 지운다)은 그대로 유효**하므로 패턴 예시로만 읽는다. 현행 CI 시크릿 취급의 실물은 레포 루트
> `Jenkinsfile`(Jenkins 크리덴셜 스토어)과 ESO(인클러스터)다. 🔴 레포 시크릿 `DEPLOY_SSH_KEY` 자체는
> **삭제 대상**이다 — 코드가 사라졌다고 시크릿이 무효화되지는 않는다.

### 3.4 메시징 계층(Kafka) 인증·암호화

**도입 이유:** Kafka 브로커와 클라이언트가 PLAINTEXT로 통신하면, 같은 네트워크에 접근 가능한 누구나 토픽을 구독·발행할 수 있다. 딜 알림·레시피 정제 등 파이프라인 메시지에 임의로 끼어들거나 위조 메시지를 주입할 수 있는 위험이 생긴다.

**적용 방법:** 브로커·클라이언트 간 통신에 SASL/SCRAM(또는 SSL/TLS 상호 인증)을 적용해 PLAINTEXT 리스너를 제거한다. 각 컨슈머/프로듀서(retail-refiner, deal-notifier, recipe-refiner, deal-pruner 등)에 별도 자격 증명을 부여하고, 자격 증명은 §3.3과 동일하게 GitHub Secrets/서버 `.env`로 관리한다.

**확인·예외:** 현재는 내부 VLAN(단일 VM 내부망)으로 격리되어 있어 외부 직접 접근은 차단된 상태이며, 이를 근거로 SASL/SCRAM 적용은 P1(향후 검토)로 낮춰두었다. K8s 전환 또는 다자간(multi-party) 접근이 늘어나는 시점에는 필수로 재검토한다. 같은 이유로 Elasticsearch/Redis 인증(`xpack.security.enabled`, `requirepass`)도 함께 검토 대상이다.

```properties
# Kafka 브로커 설정 예시(server.properties)
listener.security.protocol.map=INTERNAL:SASL_SSL
sasl.enabled.mechanisms=SCRAM-SHA-512
sasl.mechanism.inter.broker.protocol=SCRAM-SHA-512
```

## 4. PR·배포 전 체크리스트

- [ ] 새로 추가하는 서비스가 필요한 네트워크 티어에만 연결되어 있는가?
- [ ] DB·Kafka·캐시 등에 불필요한 `ports:` 노출이 없는가?
- [ ] 쓰기가 필요 없는 서비스는 `read_only: true`로 지정했는가?
- [ ] 새 시크릿(API Key, 비밀번호 등)을 GitHub Secrets에 등록하고 코드·YAML에 하드코딩하지 않았는가?
- [ ] 워크플로 로그에 시크릿이 평문으로 노출되지 않는가?
- [ ] Kafka/ES/Redis에 인증 없이 새 접근 경로를 추가하지 않았는가?
- [ ] 적용할 수 없는 항목은 사유·재검토 시점을 기록했는가?

완료 기준은 설정 작성에 그치지 않고 `docker network inspect`, `docker inspect`, GitHub Actions Secrets 목록, Kafka 리스너 설정 등으로 실제 적용 여부까지 확인하는 것이다.
