# food-budget-app 백업·복구 전략

> 작성일: 2026-07-17
> 상태: 계획안 — 현재 Docker 운영 상태와 향후 2노드 Kubernetes 전환 방향을 구분해 작성
> 범위: 서비스 중요도, RPO/RTO, 운영 볼륨과 백업 볼륨, 장애 복구 순서
> 제외: 별도 문서로 분리한 사본 배치 원칙

## 1. 결론

우리 서비스의 핵심은 사용자가 직접 만든 다음 데이터다.

- 회원과 로그인 상태
- 월 식비 예산과 지출
- 냉장고 재고와 소비기한
- 식단과 장바구니
- 사용자가 저장·작성·추출한 레시피북

이 데이터는 다시 크롤링하거나 자동 생성할 수 없다. 따라서 PostgreSQL의 사용자
데이터를 가장 먼저 복구하고, 검색·수집·모니터링 계층은 그다음에 복구한다.

목표는 다음과 같이 정한다.

| 대상 | 목표 RPO | 목표 RTO | 결정 이유 |
|---|---:|---:|---|
| PostgreSQL 사용자 데이터 | 15분 | 30분 | 재생성할 수 없는 핵심 데이터 |
| 사용자 API·프론트엔드 | 커밋된 최신 배포본 | 15분 | DB가 살아 있어도 앱이 열리지 않으면 서비스 불가 |
| 전체 서비스 영속 볼륨 | 1시간 | 1시간 | 볼륨 손상 시 최근 증분본으로 빠르게 복원 |
| Elasticsearch 검색 | 1시간 | 1시간 | PG에서 재색인할 수 있지만 검색 공백 최소화 필요 |
| Kafka 수집 파이프라인 | 마지막 PG 적재 지점 또는 1시간 | 1시간 | 원천 재수집 가능, PG 적재 결과가 우선 |
| Redis PGSync | 1시간 | 30분 | PG 기준 전체 재동기화 가능 |
| Redis 캐시 | 적용 안 함 | 10분 | 삭제 후 자동 재생성 가능 |
| Harbor·모니터링 | 최근 설정·배포본 | 2시간 | 핵심 사용자 흐름보다 후순위 |

이 수치는 현재 달성 완료된 SLA가 아니라 **구축할 백업·복구 체계의 목표**다. 현재는
독립 백업 볼륨과 자동 복원 절차가 없어 일부 목표를 보장할 수 없다.

## 2. RPO/RTO를 이렇게 정한 이유

### 2.1 RPO는 허용 가능한 데이터 손실량이다

RPO가 24시간이면 “하루마다 백업하니 안전하다”는 뜻이 아니다. 매일 01시에 백업하고
다음 날 00시 59분에 볼륨이 손상되면 **거의 하루치 데이터가 사라질 수 있다**는 뜻이다.

우리 서비스에서는 하루 동안 예산·지출·냉장고·식단 데이터가 계속 쌓일 수 있다.
하루치 사용자 데이터를 잃는 것은 허용하기 어렵기 때문에 다음처럼 줄인다.

- PostgreSQL: WAL을 지속 보관하여 최대 손실을 15분으로 제한
- 일반 영속 볼륨: 1시간 단위 증분 snapshot으로 최대 손실을 1시간으로 제한
- Redis 캐시: 원본에서 재생성하므로 RPO를 적용하지 않음

### 2.2 RTO는 백업 계산 시간이 아니라 서비스 중단 시간이다

RTO는 장애를 알아챈 순간부터 사용자가 다시 정상적으로 서비스를 쓸 때까지 걸리는
전체 시간이다. 장애 확인, 복원본 선택, 데이터 복구, 서비스 재기동과 검증이 모두 포함된다.

기존의 4시간 목표는 핵심 서비스 기준으로 너무 길다. 사용자 API가 4시간 중단되면
예산·냉장고·식단 기능을 모두 사용할 수 없으므로 핵심 경로는 15~30분을 목표로 한다.

다만 서버가 갑자기 멈췄다고 항상 백업부터 복원하지는 않는다.

1. 프로세스나 컨테이너만 멈춤: 재시작
2. VM만 멈춤: VM과 Compose 재기동
3. 한 K8s 노드가 멈춤: 다른 노드의 Pod로 전환
4. 운영 볼륨이 손상됨: 이때 백업 볼륨에서 복원
5. 물리 호스트 전체가 손상됨: 다른 컴퓨팅 노드 또는 재구성한 서버에서 복원

즉, **빠른 재시작·장애 전환은 가용성 전략이고, 손상된 데이터를 되돌리는 것은 백업
전략**이다. 둘을 같이 준비해야 실제 RTO가 짧아진다.

### 2.3 우리 서비스에 맞춘 RTO 결정 사유

모든 구성요소에 같은 RTO를 적용하지 않는다. 사용자가 지금 당장 쓰는 기능인지,
잠시 늦어져도 기존 데이터로 서비스를 계속할 수 있는지를 기준으로 정한다.

#### PostgreSQL 사용자 데이터 — RTO 30분

PostgreSQL에는 회원, 예산, 지출, 냉장고, 식단과 레시피북이 들어 있다. 이 DB가
중단되면 로그인 이후의 핵심 기능이 거의 모두 멈춘다. 사용자가 장을 본 직후 지출과
재고를 기록할 수 없고, 남은 예산과 맞춤 추천도 계산할 수 없다.

따라서 2~4시간 복구는 우리 서비스에 너무 길다. 다만 손상된 DB는 전체/차등본 복원,
WAL 재생과 데이터 검증이 필요하므로 15분보다 짧은 목표도 현재 장비에는 비현실적이다.
자동화된 복원 절차를 전제로 30분을 목표로 정한다.

#### 사용자 API·프론트엔드 — RTO 15분

API와 프론트엔드는 사용자 진입점이지만 상태의 정본은 PostgreSQL에 있다. 이미지와
코드는 GitHub·Harbor에서 다시 배포할 수 있어 데이터 복원보다 빠르게 재기동할 수 있다.
Compose 재기동, healthcheck와 핵심 화면 확인 시간을 포함해 15분으로 정한다.

#### 전체 서비스 영속 볼륨 — RTO 1시간

볼륨 손상은 단순 컨테이너 재시작과 다르다. 새 볼륨 생성, snapshot 복원, 소유권과
mount 확인, 각 데이터 서비스 정합성 검사까지 필요하다. 여러 볼륨을 한꺼번에 복원하고
검증하는 시간을 고려해 1시간으로 정한다. 기존 4시간보다 짧지만 자동화 없이 달성할 수
있는 값은 아니므로 실제 복원 시험으로 검증한다.

#### Elasticsearch — RTO 1시간

Elasticsearch가 중단되면 레시피·상품 검색 품질이 떨어지지만 사용자 예산·지출·재고
원본은 PostgreSQL에 남아 있다. 현재 코드에는 PG 폴백과 전체 재색인 경로가 있으므로
핵심 DB보다 후순위로 복구할 수 있다. snapshot 복원 또는 재색인 시간을 포함해 1시간을
목표로 한다.

#### Kafka·크롤링/폴링 — RTO 1시간

Kafka가 중단되면 신규 레시피와 가격 갱신이 지연되지만 이미 PostgreSQL·Redis에 저장된
데이터로 사용자는 서비스를 계속 이용할 수 있다. 마지막 PG 적재 지점 이후를 다시
수집할 수 있으므로 즉시 전체 서비스를 중단할 필요는 없다. 다만 가격 정보의 신선도가
서비스 특장점이므로 1시간 안에 수집을 재개하는 것을 목표로 한다.

#### Redis PGSync — RTO 30분

PGSync 체크포인트가 사라져도 PostgreSQL이 정본이므로 전체 동기화를 다시 실행할 수
있다. 사용자 원본은 손실되지 않지만 검색 반영이 지연되므로 PG 복구와 병행해 30분을
목표로 한다.

#### Redis 캐시 — RTO 10분

현재가·추출 캐시는 원본 데이터가 아니어서 복원하지 않고 빈 Redis로 시작할 수 있다.
컨테이너 재기동과 연결 확인만 하면 되므로 10분으로 정한다. 초기 요청은 캐시 미스로
조금 느릴 수 있지만 서비스 기능은 유지된다.

#### Harbor·모니터링 — RTO 2시간

Harbor와 모니터링이 중단되어도 이미 실행 중인 앱과 사용자 데이터 조회는 계속된다.
Harbor는 신규 배포가, 모니터링은 장애 관찰이 제한되므로 방치할 수는 없지만 사용자
핵심 경로보다 후순위다. 핵심 서비스 복구 후 2시간 안에 정상화하는 것으로 정한다.

## 3. 서비스 구조와 데이터 중요도

### 3.1 현재 Docker 구조

현재는 물리 Proxmox 호스트 1대 안에 VM 4대를 운영한다.

| VM | 주소 | 역할 |
|---|---|---|
| fb-data | 192.168.0.8 | PostgreSQL, Elasticsearch, Redis, Kafka |
| fb-app-ai | 192.168.0.9 | FastAPI 8개, React, 크롤러·폴러 |
| fb-ci-harbor | 192.168.0.10 | Harbor, GitHub Actions runner |
| fb-monitoring | 192.168.0.11 | Prometheus, Loki, Tempo, Grafana |

VM은 네 대지만 물리 서버는 한 대다. 따라서 VM을 나눠 놓은 것은 역할과 자원 격리에는
도움이 되지만 물리 서버 고장에 대한 이중화는 아니다.

### 3.2 데이터 정본과 재생성 가능 여부

| 계층 | 데이터 | 복구 기준 |
|---|---|---|
| PostgreSQL `foodbudget` | 사용자·예산·지출·재고·식단·레시피북 | 최종 정본, 반드시 백업 |
| PostgreSQL `terraform_state` | 현재 인프라 상태 | PG 백업에 함께 포함 |
| Elasticsearch | 레시피·상품 검색 인덱스 | snapshot 또는 PG에서 재색인 |
| Kafka | 크롤링·폴링 중간 이벤트 | 마지막 PG 적재 지점 이후 재수집 |
| Redis 6380 | PGSync 체크포인트 | AOF 복원 또는 전체 재동기화 |
| Redis 6379 | 현재가·추출 캐시 | 비운 상태로 시작 후 재생성 |
| GitHub·Harbor | 코드·설정·이미지 | Git 재배포 또는 이미지 재사용 |
| Prometheus·Loki·Tempo | 메트릭·로그·트레이스 | 설정 재배포 후 새로 수집 |

복구 우선순위는 `PostgreSQL 사용자 데이터 → 핵심 API → 검색·수집 → 운영 보조 계층`이다.

## 4. 장애 유형별 목표

| 장애 유형 | 데이터 상태 | 대응 | 목표 RPO | 목표 RTO |
|---|---|---|---:|---:|
| 앱 컨테이너 중단 | PG 정상 | Docker 재시작 | 0 | 5분 |
| fb-app-ai VM 중단 | fb-data 정상 | VM·Compose 재기동 | 0 | 15분 |

| 일반 영속 볼륨 손상 | 운영 볼륨 손상 | 최근 증분 snapshot 복원 | 1시간 | 1시간 |
| Elasticsearch 손상 | PG 정상 | snapshot 복원 또는 재색인 | 1시간 | 1시간 |
| Kafka 손상 | PG 적재분 정상 | 토픽 재생성·원천 재수집 | 1시간 | 1시간 |
| Proxmox 물리 호스트 손상 | VM 전체 중단 | 서버 재구성·볼륨 복원 | 현재 보장 불가 | 현재 4시간 이상 가능 |

마지막 항목은 백업 설정만으로 줄일 수 없다. 현재 물리 서버가 한 대이므로 대체 컴퓨팅
자원이 없기 때문이다. 향후 2노드 K8s 계획의 목적은 이 단일 장애 지점을 줄이는 데 있다.

## 5. 볼륨과 백업 스토리지 계획

### 5.1 운영 볼륨과 백업 볼륨은 다르다

서비스에 Docker volume 또는 K8s PersistentVolume을 연결하면 컨테이너가 삭제되어도
데이터는 남는다. 하지만 같은 디스크의 볼륨이 손상되면 함께 사라지므로 이것만으로는
백업이 아니다.

필요한 저장 역할은 다음과 같다.

1. **운영 볼륨**: 서비스가 실시간으로 읽고 쓰는 데이터
2. **백업 저장소 볼륨**: 운영 볼륨의 snapshot, PG 전체·차등본과 WAL을 보관
3. **복제 볼륨**: 향후 두 번째 K8s 노드에서 장애 전환에 사용하는 데이터 사본

현재 Docker 단계에서는 1번이 일부 구성되어 있고 2번은 아직 없다. K8s 단계에서는
1번과 3번이 노드 간 가용성을 담당하고, 2번은 두 노드와 별개로 복구를 담당해야 한다.

### 5.2 현재 Docker에서 필요한 볼륨

현재 데이터 티어의 주요 운영 볼륨은 다음과 같다.

- `tfstate_pg`: `foodbudget`과 `terraform_state` PostgreSQL 데이터
- `es_data`: Elasticsearch 인덱스
- `kafka_data`: Kafka KRaft 로그
- `redis_pgsync_data`: PGSync Redis AOF
- Harbor와 모니터링의 서비스별 named volume

추가로 **백업 저장소 볼륨 1개**가 필요하다. 서비스마다 백업 디스크를 하나씩 만드는
것이 아니라, 별도 저장소 볼륨 하나에 서비스별 경로를 나눠 보관한다.

```text
backup-repository/
├── postgres/base
├── postgres/wal
├── elasticsearch/snapshots
├── redis-pgsync
├── kafka/metadata
├── harbor
└── volume-snapshots
```

백업 저장소는 운영 `/var/lib/docker`와 같은 볼륨에 만들면 안 된다. 현재 미사용 `sda`
250GB는 후보일 뿐이며, 사용 여부와 실제 백업 저장소 위치는 아직 팀 결정 사항이다.

### 5.3 전체 볼륨 백업과 DB 전용 백업을 같이 쓰는 이유

- 전체 볼륨 snapshot: 여러 서비스의 실행 상태를 빠르게 되돌려 RTO를 줄임
- PostgreSQL 전체·차등·WAL: DB 정합성과 15분 RPO, 특정 시점 복구를 보장
- Elasticsearch snapshot: 라이브 파일 복사보다 안전하게 검색 인덱스를 복구
- Kafka: 라이브 로그 복사보다 토픽 설정과 PG watermark 기반 재수집을 우선

실행 중인 데이터 볼륨을 단순 파일 복사하면 쓰기 중간 상태가 담길 수 있다. 따라서
전체 볼륨 snapshot만 믿지 않고 각 데이터 서비스가 지원하는 백업 방식도 함께 사용한다.

## 6. 현재 Docker 단계에서 한 것과 할 것

### 6.1 현재 완료된 것

- VM 4대에 `/var/lib/docker` 전용 디스크 연결
- PostgreSQL·Elasticsearch·Kafka·PGSync Redis named volume 영속화
- Docker Compose `restart`와 healthcheck 적용
- GitHub → CI → Harbor → fb-app-ai 배포 경로 구축
- Terraform·Ansible·Compose로 서버와 서비스를 재현할 코드 확보
- Prometheus·Alertmanager로 데이터 계층과 디스크 상태 감시

### 6.2 아직 하지 않은 것

- 독립 백업 저장소 볼륨 연결
- 전체 영속 볼륨의 1시간 단위 증분 snapshot
- PostgreSQL 전체·차등·WAL 자동 백업
- Elasticsearch snapshot repository
- Kafka 적재 watermark 기록과 재수집 자동화
- 실제 복원 시간 측정과 RPO/RTO 검증

### 6.3 Docker 단계 실행 계획

1. 백업 저장소 볼륨 위치와 용량 확정
2. PostgreSQL WAL을 최대 15분 간격으로 보관
3. PostgreSQL 주간 전체 + 일일 차등 백업 구성
4. 전체 영속 볼륨 1시간 단위 증분 snapshot 구성
5. Elasticsearch snapshot과 Kafka watermark 기록 구성
6. 임시 볼륨에 복원하여 30분·1시간 목표 실측
7. 백업 성공 시각, 실패 횟수와 저장소 용량을 Alertmanager에 연결

백업 담당자는 본인이며 대체 담당자는 없다.

## 7. 향후 2노드 Kubernetes 계획

이 단계는 현재 구현이 아니라 향후 계획이다. 설계 정본에 따라 동일 사양 물리 컴퓨터를
한 대 추가해 2노드 클러스터를 구성하는 상황을 가정한다.

### 7.1 배치 방향

- 앱·AI·Kafka·ArgoCD: K8s 내부
- PostgreSQL·Elasticsearch·Redis: 우선 K8s 외부 데이터 티어 유지
- 사용자 API: 두 노드에 최소 2개 replica 배치
- Pod anti-affinity로 같은 서비스 replica가 한 노드에 몰리지 않도록 계획
- readiness/liveness probe로 장애 Pod를 트래픽에서 제외
- HPA/KEDA로 요청량과 Kafka lag에 따라 확장

CNI, Gateway API 구현체와 스토리지 구현체는 아직 확정하지 않는다.

### 7.2 두 노드에서 기대하는 복구 목표

| 상황 | 목표 동작 | 목표 RPO | 목표 RTO |
|---|---|---:|---:|
| 앱 Pod 중단 | 같은 노드 또는 다른 노드에서 자동 재기동 | 0 | 2분 |
| K8s 노드 1대 중단 | 생존 노드의 replica로 트래픽 전환 | 0 | 5분 |
| Kafka Pod/볼륨 장애 | 다른 replica 사용 또는 snapshot 복구 | 15분 | 30분 |
| 외부 PG 장애 | WAL/백업 복구, 추후 standby 검토 | 15분 | 30분 목표 |
| 운영 볼륨 손상 | 독립 백업 저장소에서 복원 | 1시간 | 1시간 |

### 7.3 두 대만으로 해결되지 않는 것

컴퓨터가 두 대라고 해서 모든 데이터가 자동으로 안전해지는 것은 아니다.

- 두 노드 모두 같은 전원·네트워크·스토리지에 의존하면 함께 중단될 수 있다.
- K8s replica는 삭제나 데이터 손상도 복제할 수 있으므로 백업을 대신하지 않는다.
- PostgreSQL·Elasticsearch·Redis를 외부 단일 데이터 티어에 유지하면 앱은 살아도
  데이터 티어 장애 시 핵심 기능은 중단된다.
- 두 노드만으로 control-plane과 데이터 quorum을 완전하게 구성하기 어렵다.

따라서 2노드 전환의 1차 목표는 **앱 가용성 개선**이다. 데이터 계층은 독립 백업
저장소를 먼저 구축하고, 사용량과 장비가 늘면 PostgreSQL standby 또는 별도 데이터
노드를 추가하는 순서로 확장한다.

### 7.4 K8s 볼륨 계획

향후 필요한 저장 역할은 최소 세 가지다.

1. 노드 A의 운영 PersistentVolume
2. 노드 B의 복제 PersistentVolume
3. 두 노드 장애와 별개로 복원할 독립 백업 저장소 볼륨

K8s에서는 스토리지 구현체가 확정된 뒤 CSI `VolumeSnapshot` 또는 동등한 기능으로
증분 snapshot을 자동화한다. snapshot 스케줄, 보관 기간과 복원 절차는 실제 데이터
크기를 측정한 뒤 확정한다.

## 8. 복구 순서

### 8.1 데이터가 손상되지 않은 장애

1. healthcheck와 Alertmanager로 장애 확인
2. 컨테이너·Pod 또는 VM 재시작
3. PostgreSQL·ES·Redis·Kafka 연결 확인
4. 로그인 → 냉장고 → 예산/지출 → 레시피 검색 순서로 smoke test
5. 목표 RTO를 넘겼는지 기록

### 8.2 볼륨 또는 데이터가 손상된 장애

1. 앱·크롤러·폴러의 쓰기 중지
2. 손상 시각과 마지막 정상 WAL/snapshot 확인
3. 새 임시 볼륨에 백업 복원
4. PostgreSQL은 전체/차등본 복원 후 목표 시점까지 WAL 재생
5. Elasticsearch 재색인, PGSync 전체 동기화, Kafka watermark 이후 재수집
6. 핵심 사용자 흐름 검증 후 운영 볼륨으로 전환
7. 실제 데이터 손실 시간과 복구 시간을 기록

## 9. 검증 기준

목표를 문서에 적는 것만으로는 달성한 것이 아니다. 다음 시험에서 시간을 측정해야 한다.

- 매일: 마지막 WAL·snapshot 시간이 RPO 이내인지 자동 검사
- 매주: 임시 PostgreSQL에 최근 백업 복원
- 매월: 빈 볼륨에서 PG → ES → 앱 순서의 전체 복구 시험
- K8s 전환 후: 노드 1대 강제 중단 후 5분 이내 앱 전환 확인

성공 조건:

- PostgreSQL 복구 시 최대 데이터 손실 15분 이하
- 핵심 사용자 데이터 복원 30분 이하
- 일반 영속 볼륨 복원 1시간 이하
- 앱 컨테이너 장애 복구 5분 이하
- 로그인·냉장고·예산/지출·레시피 검색 smoke test 전부 통과

실측 결과가 목표를 넘으면 RTO를 늘려 문서를 맞추는 것이 아니라, snapshot 주기,
복원 자동화, 이미지 준비와 장애 전환 절차를 개선해 목표 안으로 줄인다.
