# 밀플래닝 서비스 백업 전략

## 1. RPO/RTO 전략

- **PostgreSQL: RPO 12시간 / RTO 40분**
  - 오후 2시·새벽 2시에 `foodbudget`, `terraform_state`와 DB role을 dump한다.
  - 새 PG 컨테이너 생성·복원 20분, 로그인·예산·냉장고·식단 확인 20분으로 복구한다.
- **핵심 운영 데이터: RPO 12시간 / RTO 1시간**
  - PG 복원 후 Harbor 설정·배포 이미지와 앱 설정을 복원하고 서비스를 순서대로 기동한다.
  - PG → Redis → API·프론트 순으로 healthcheck를 통과하면 핵심 서비스 복구로 판단한다.
- **Elasticsearch·Kafka: RPO 12시간 / RTO 2시간**
  - ES는 오후 2시·새벽 2시에 snapshot을 만들고, 장애 시 snapshot 또는 PG 재색인을 쓴다.
  - Kafka는 토픽 설정과 마지막 수집 위치를 저장하고, 토픽 재생성 후 누락분을 재수집한다.
- **Redis 캐시: 재생성 / RTO 10분**
  - 빈 Redis 컨테이너를 기동하고 PGSync를 PostgreSQL에서 다시 동기화한다.
- **API·프론트엔드: 재배포 / RTO 15분**
  - Harbor에서 현재 이미지를 pull하고 Docker Compose로 기동한 뒤 healthcheck를 확인한다.
- **물리 서버 손상: 대체 장비 확보 후 RTO 4시간 / 자동화 후 RTO 3시간**
  - 대체 장비에 Proxmox를 설치하고 Terraform·Ansible로 VM 4대를 재생성한다.
  - `fb-data` → `fb-ci-harbor` → `fb-app-ai` → `fb-monitoring` 순서로 복원한다.
  - 초기에는 장비·네트워크 1시간, VM 생성 1시간, 데이터·앱 복원 1시간 30분,
    기능 확인 30분으로 잡고 자동화 후 VM 생성·복원 시간을 1시간 줄인다.

### 우리 서비스 특장점과 선정 이유

우리 서비스는 20~30대 1인 가구가 월 식비 예산 안에서 식단을 계획하는 밀플래닝
서비스다. 레시피에서 재료를 추출하고 마켓컬리·오아시스 가격을 비교해 식단·장바구니·
지출을 연결하는 것이 핵심이다.

회원·예산·지출·냉장고·식단·레시피북은 사용자가 직접 만든 데이터이며 PostgreSQL에
저장된다. 외부에서 다시 만들 수 없으므로 하루 두 번 백업하고 RPO를 12시간으로 정했다.

Elasticsearch 검색 인덱스는 PostgreSQL에서 재색인할 수 있고, Kafka 수집 데이터는
원본을 다시 수집할 수 있으며, Redis 캐시는 재생성할 수 있다. 따라서 이 데이터들은
PostgreSQL보다 복구 순위가 낮다.

현재 데이터량이 크지 않아 PostgreSQL 복원 20분과 로그인·예산·냉장고·식단 확인
20분을 합쳐 RTO를 40분으로 정했다. ES·Kafka는 재색인·재수집 시간이 추가되므로
RTO를 2시간으로 정했다.

## 2. 현재 Docker 전략

현재 물리 컴퓨터 1대 안에서 VM 4대를 사용한다.

### 백업 시간

- 오후 2시: 점심 이용 후 PostgreSQL을 먼저 백업하고 나머지 데이터 순차 백업
- 새벽 2시: 저녁 이용 후 PostgreSQL을 먼저 백업하고 나머지 데이터 순차 백업

우리 서비스는 월 식비 예산을 기준으로 레시피·재료·냉장고 데이터를 연결해 식단을 계획하는
밀플래닝 서비스다. 사용자가 점심과 저녁 전후에 식단과 관련 정보를 저장할 것으로 예상해
두 시간대가 지난 뒤 백업하고 12시간 간격을 유지한다.

## 3. 향후 Kubernetes 전략

물리 컴퓨터 2대로 2노드 Kubernetes를 구성한다.

- API·프론트엔드는 두 노드에 분산한다.
- PG·ES·Redis는 우선 K8s 외부에 유지하고 같은 주기로 백업한다.
- 노드 한 대 중단 시 다른 노드로 전환하는 RTO는 5분을 목표로 한다.

API·프론트엔드는 데이터를 직접 저장하지 않아 다른 노드에서 바로 다시 실행할 수 있다.
PG·ES·Redis를 외부에 유지하는 이유는 초기 데이터 이전 위험을 줄이기 위해서다.

볼륨 구성과 용량은 [07_volume_strategy.md](./07_volume_strategy.md)에서 별도로 관리한다.

백업 담당자는 본인이며 대체 담당자는 없다.
