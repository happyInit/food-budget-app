# 애플리케이션 아키텍처 설명

> 애플리케이션 설계도(`docs/설계도/architecture.drawio`)를 이해·재작성하기 위한 설명 문서.
> **기능(서브시스템) 그룹**을 기준으로 정리한다. 이 그룹 구조는 배포 방식(Docker → K8s → AWS)이 바뀌어도 유지된다 — 바뀌는 건 "각 그룹을 어떻게 호스팅하나"뿐이다.
> 여기 담긴 서비스 분리는 **제안 설계(검토용)**이며 팀 확정 사항이 아니다. 일부 분리는 P0에서 모듈로 시작해 나중에 서비스로 승격해도 된다(각 항목에 표기).

---

## 1. 큰 그림 — 7개 기능 그룹

| 그룹 | 색 | 역할 | 스케일 방식 |
|---|---|---|---|
| 엣지 / 클라이언트 | 회색 | 웹·PWA, 정적 서빙 | CDN/정적 |
| 운영 서비스 (API) | 파랑 | 요청을 받아 처리하는 상시 서비스 | HPA (요청량) |
| AI 서빙 | 보라 | ML 추론 (CPU) | HPA (CPU) |
| 데이터 파이프라인 (비동기) | 주황 | 수집 → Kafka → 워커 → 적재 | KEDA / Cron |
| 저장소 | 초록 | 상태를 보관하는 데이터 스토어 | 오토스케일 아님 |
| 관측 / 모니터링 | 청록 | 메트릭·로그·트레이스·알림 | 고정 |
| 외부 연동 | 회색 | 우리가 통제 못 하는 외부 시스템 | 해당 없음 |

핵심 원칙:
- **화살표(통신)는 애플리케이션 아키텍처에 들어가고, 네트워크 구현(세그먼트·overlay·포트)은 안 들어간다.** 후자는 Docker 배포도로 뺀다.
- **한 그림은 한 축.** 이 그림은 "기능 그룹 + 논리 흐름"만. 스케일 티어는 6장에서 요약하되 상세는 별도 스케일링 뷰로.

## 2. 운영 서비스 (API 그룹) — 8개

요청을 처리하는 무상태(stateless) 서비스. 무상태여야 HPA로 복제(scale-out)가 된다(세션은 JWT, 로컬 상태 금지).

| 서비스 | 역할 | 읽기 | 쓰기 | 외부/AI 호출 | 비고 |
|---|---|---|---|---|---|
| Gateway | 인증 관문·JWT 검증·라우팅 | — | — | — | 자체 비즈니스 API 없음 |
| User | 로그인(Kakao+이메일)·JWT 발급·월예산 | PG | PG | Kakao OAuth | |
| Pantry | 재고·유통기한·재고 CRUD | PG | PG | — | **OCR은 워커로 위임** |
| Recipe | 레시피 검색·레시피북·공유 | ES, PG | PG | ML(랭킹[P1]) | **YouTube추출은 워커로 위임** |
| Price | 마켓컬리 현재가 조회·가격이력·시세추천 | Redis, PG | — | 마켓컬리(온디맨드) | 폴링/최저가 감지는 파이프라인 |
| MealPlan | 밀플래닝·추천 조합·장바구니·장보기 목록 | PG | PG | Pantry·Recipe·Price(조합), Gemini(어시스턴트[P1]) | 오케스트레이터 |
| Expense | 식비 캘린더·외식비·성과지표 | PG | PG | — | **MealPlan에서 분리(권장). P0는 모듈로 시작 가능** |
| Notification | 알림함(목록·읽음)·Push fan-out | PG | PG | Push/FCM | **횡단 알림 통합(권장). P0는 모듈로 시작 가능** |

분리 이유 요약:
- **OCR / YouTube추출을 서비스에서 떼어 워커로**: 둘 다 무겁고(CPU·Gemini) 느린 작업이라, 같은 pod에 두면 점심 피크의 가벼운 조회를 잡아먹는다(noisy neighbor). 워커로 빼면 각자 다른 정책으로 스케일한다.
- **Expense를 MealPlan에서 분리**: "추천·장보기"(피크성 읽기)와 "식비 가계부"(잔잔·다른 도메인)는 부하·성격이 다르다.
- **Notification 신설**: 최저가·유통기한 알림이 여러 서비스에 흩어져 있어, 알림함·발송을 한 곳으로 모은다. 멘토가 강조한 fan-out(다자간) 서사도 선명해진다.

## 3. 데이터 파이프라인 (비동기 그룹)

유저 요청과 분리된, 시스템이 트리거하는 비동기 처리. **아래에서 위로 한 방향 흐름**(수집 → Kafka → 워커 → 저장소)이라 얽히지 않는다.

### 3.1 수집 (Cron · 고정 1 replica)
절대 수평 확장하지 않는다 — 여러 개가 동시에 크롤/폴링하면 대상 사이트를 때리고 중복 수집된다.

- 레시피 크롤러 — 만개의레시피·냉부, 주 1회
- 마켓컬리 폴러 — 핵심 SKU, 일 1~2회
- 지마켓 핫딜 폴러 [P1] — 일 2회(11시/저녁)

### 3.2 Kafka (이벤트 버스)
수집·이벤트를 받아 워커로 분배하는 허브. 서비스끼리 직접 부르지 않고 여기 경유.

### 3.3 워커 (KEDA · 큐/lag 기반, idle→0)
부하가 있을 때만 뜨고 없으면 0으로 줄인다.

- NER 워커 — 레시피·OCR 텍스트 → 재료 추출(ML 호출) → ES 인덱스
- 이상탐지 워커 — 마켓컬리 가격 z-score → 최저가 감지 → 알림 이벤트 발행
- OCR 워커 — 영수증 이미지 → 텍스트(Tesseract) → NER (신규 분리)
- YouTube추출 워커 [P1] — URL → Gemini 멀티모달 추출 → NER → 레시피북 저장 (신규 분리)

## 4. 나머지 그룹

- **AI 서빙**: ML Serving(CPU 단일 통합 pod) — CRF NER·최저가 이상탐지·신선도[P1]·랭킹[P1]. 운영 서비스와 워커가 함께 호출.
- **저장소**: PostgreSQL(계정·재고·식단·식비·경량 가격이력) · Elasticsearch(레시피·상품 검색, nori) · Redis(현재가·추출 캐시). 오토스케일 대상이 아니며, 하이브리드 배포 시 K8s 밖에 둔다(design.md §8.4).
- **관측/모니터링**: Prometheus·Loki·Tempo·Grafana·Alertmanager(LGTM). 에이전트(node-exporter·cAdvisor·Alloy)가 전 컨테이너에서 메트릭·로그·트레이스 수집. 요청 경로 밖의 횡단 그룹.
- **외부 연동**: Kakao OAuth · 마켓컬리(현재가) · Gemini API[P1] · Push/FCM. (Tesseract는 라이브러리라 OCR 워커 내부 — 외부 아님)

## 5. 주요 흐름 (단계별)

### 5.1 핵심 루프 — 추천에서 식비 기록까지 (동기)
1. 클라이언트 → Gateway(JWT 검증) → MealPlan
2. MealPlan이 Pantry(재고)·Recipe(레시피 후보)·Price(가격)를 조합 호출
3. 추천 결과에서 레시피 담기 → 장바구니(부족재료·현재가·예산 대비)
4. 예산 초과 시 경고 표시(조정 기능 없음, A안) → 장보기 목록 확정
5. 구매 후 영수증 등록 → Expense가 식비 기록·예산 갱신

### 5.2 냉장고 채우기 — 영수증 OCR (동기 접수 + 비동기 처리)
1. 클라이언트 → Pantry: 영수증 이미지 업로드(접수만)
2. Pantry가 Kafka에 OCR 작업 이벤트 발행
3. OCR 워커: 이미지 → 텍스트 → NER(ML) → 표준 품목코드
4. 결과가 Pantry 재고(PG)에 반영

### 5.3 최저가 알림 fan-out (비동기 · 시스템 트리거)
1. 마켓컬리 폴러 → Kafka → 이상탐지 워커
2. 평균 대비 급락 감지 → 알림 이벤트 발행
3. Notification이 이벤트 수신 → 관심 등록 유저에 Push fan-out(KEDA로 버스트 흡수)
4. 유저가 알림함 확인 → 장바구니로 딥링크

### 5.4 YouTube 레시피 추출 [P1] (비동기)
1. 클라이언트 → Recipe: URL 제출(접수 + 사전필터)
2. Recipe가 추출 작업 이벤트 발행
3. YouTube추출 워커: 캐시 조회(Redis) → (미스 시) Gemini 추출 → NER → ES 매핑
4. 개인 레시피북(PG) 저장. 결과는 마이 > 레시피북에 표시

## 6. 스케일링 관점 요약 (상세는 스케일링 뷰에서)

| 티어 | 구성 | 오토스케일 |
|---|---|---|
| 요청 (stateless) | Gateway·User·Pantry·Recipe·Price·MealPlan·Expense·Notification | HPA (요청량, 11-12·17-18 피크) |
| 워커 | NER·이상탐지·OCR·추출 | KEDA (큐/lag, idle→0) |
| 수집 | 크롤러·폴러 3종 | 고정 1 replica (Cron) |
| AI | ML Serving | HPA (CPU) |
| 저장소 | PG·ES·Redis·Kafka | 오토스케일 아님 (읽기 복제·샤딩 등 별도) |

주의:
- 수집(폴러/크롤러)은 수평 확장 금지 — 크롤 예의·중복 수집 문제.
- 저장소는 pod처럼 오토스케일하지 않는다. 하이브리드 배포에서 K8s 밖으로.

## 7. 이전 로드맵에서 무엇이 바뀌고 무엇이 유지되나

이 문서의 **기능 그룹·서비스·흐름은 Docker/K8s/AWS 전부에서 동일**하다. 바뀌는 것은 배포 방식뿐이다.

| | Docker (현재) | K8s (이전 후) | AWS (최종) |
|---|---|---|---|
| 서비스 단위 | 컨테이너 | Pod / Deployment | Pod(EKS) 또는 태스크(ECS) |
| 스케일 | 수동/compose scale | HPA·KEDA | HPA·KEDA + 노드 오토스케일 |
| 네트워크 | bridge/overlay | CNI + Service | VPC + SG + LB |
| 저장소 | 컨테이너/외부 VM | K8s 밖(하이브리드) | 관리형(RDS 등) 검토 |

→ 그래서 이 애플리케이션 아키텍처가 오래 사는 소스오브트루스이고, 배포 관심사(네트워크·스케일)는 각 단계의 별도 그림으로 관리한다.
