food-budget-app 팀 백업 및 재해복구 전략
작성일: 2026-07-16
상태: 팀 검토용 제안서(아직 인프라에 적용되지 않음)

======================================================================
1. 서비스 특장점과 백업이 필요한 이유
======================================================================

food-budget-app은 20~30대 1인 가구가 월 식비 예산 안에서 식단을 계획하고,
냉장고 재고를 소진하며, 마켓컬리·오아시스 가격을 비교하는 서비스다.

핵심 사용자 흐름:
1) 사용자가 예산, 지출, 냉장고 재고와 식단을 기록한다.
2) 만개의레시피와 사용자가 등록한 레시피에서 재료를 추출한다.
3) 재료를 자체 CRF NER와 품목 마스터로 표준화한다.
4) 마켓컬리·오아시스 상품 가격과 연결하여 장보기 비용을 계산한다.
5) 남은 예산, 보유 재료와 소비기한을 고려해 레시피와 식단을 추천한다.

서비스의 백업 관점 특장점:
- 개인화의 핵심은 사용자가 직접 만든 예산·지출·냉장고·식단·레시피북 데이터다.
  이 데이터는 외부에서 다시 수집할 수 없으므로 가장 짧은 RPO/RTO가 필요하다.
- 레시피·상품 가격 원본은 다시 크롤링할 수 있지만 복구에 시간이 걸린다.
  일부 손실은 허용하되 재수집 시간을 RTO에 반영한다.
- Elasticsearch 검색 인덱스와 Redis 캐시는 PostgreSQL 또는 원천 데이터에서
  재생성할 수 있다. 따라서 사용자 DB와 같은 수준으로 백업할 필요가 없다.
- Kafka는 크롤링 이벤트를 전달하는 중간 계층이다. 영구 정본으로 취급하지 않고
  마지막 적재 지점 이후를 재수집하는 방식으로 복구한다.
- 애플리케이션과 인프라 설정은 Git, Terraform, Ansible, Docker Compose로
  재현할 수 있다. 서버 전체 이미지보다 데이터 정본을 우선 백업한다.

결론적으로 데이터 종류별 백업 우선순위는 다음과 같다.

1순위: PostgreSQL의 사용자 생성 데이터
- 사용자가 입력한 예산, 지출, 냉장고 재고, 식단과 레시피북
- 외부에서 다시 가져올 수 없으므로 반드시 백업한다.

2순위: Elasticsearch 검색 인덱스와 Kafka 이벤트
- 레시피·상품 검색 데이터와 크롤링/폴링 중간 이벤트
- 원본에서 다시 수집하거나 재색인할 수 있지만 시간이 오래 걸리므로 보조 백업한다.

3순위: Redis 캐시와 모니터링 원시 데이터
- 현재가·추출 캐시, 메트릭, 로그와 트레이스
- 서비스 재가동 후 다시 생성되므로 기본적으로 백업하지 않는다.

2. 서비스 구조와 장애 범위
======================================================================

2.1 물리 구조

- 물리 서버: Proxmox 호스트 1대(192.168.0.12)
- 가상 서버: Ubuntu 24.04 VM 4대

  fb-data(192.168.0.8)
  - PostgreSQL 16: 앱 OLTP foodbudget + Terraform state
  - Elasticsearch 8: 레시피·상품 검색 인덱스
  - Redis 6379: 현재가·추출 캐시
  - Redis 6380: PGSync 체크포인트
  - Kafka KRaft: 크롤링/폴링 이벤트 전달

  fb-app-ai(192.168.0.9)
  - FastAPI 8개, React 프론트엔드, 크롤러·폴러
  - account, recipe, price, chat, pantry, recipebook, mealplan, notify

  fb-ci-harbor(192.168.0.10)
  - Harbor 이미지 레지스트리, GitHub Actions self-hosted runner

  fb-monitoring(192.168.0.11)
  - Prometheus, Loki, Tempo, Grafana, Alertmanager

VM은 4대지만 물리 서버는 1대다. Proxmox 호스트나 운영 SSD가 고장 나면 VM 4대가
동시에 중단될 수 있으므로 같은 Proxmox 안의 다른 VM에 복사하는 것은 독립 백업이 아니다.

볼륨 적용 계획:
- 전체 서비스에 필요한 영속 볼륨을 연결하고, 연결된 볼륨 전체를 공통 백업 대상으로
  포함할 예정이다.
- 현재 전 VM에는 /var/lib/docker 전용 디스크가 연결되어 있고 일부 데이터 서비스는
  Docker named volume으로 영속화되어 있다.
- 데이터 티어의 전체 볼륨 백업 연결은 아직 완료되지 않았으며 추후 적용 예정이다.
- 따라서 이 문서는 “전체 볼륨 백업 예정”을 기반 복구 수단으로 반영하되, 현재 완료된
  백업으로 표시하지 않는다.

2.2 데이터 흐름

  마켓컬리·오아시스 폴러 ─┐
                            ├→ Kafka → PostgreSQL + Elasticsearch + Redis
  만개의레시피 크롤러 ─────┘

  사용자 요청 → FastAPI → PostgreSQL(사용자 정본)
                         ├→ Elasticsearch(검색)
                         └→ Redis(캐시)

  GitHub → CI 빌드 → Harbor → fb-app-ai 배포
  전체 VM → Prometheus/Loki/Tempo → Grafana

2.3 데이터별 정본과 복구 원천

- PostgreSQL foodbudget: 사용자 데이터의 최종 정본. 백업 없이 재생성 불가
- PostgreSQL terraform_state: 인프라 상태 정본. 코드와 실제 자원으로 일부 재구성
  가능하지만 state import 작업이 필요하므로 백업하는 편이 빠름
- Elasticsearch: PostgreSQL·크롤링 원본으로 재색인 가능
- Redis 6379: 캐시이므로 비워진 상태로 재시작 가능
- Redis 6380: PostgreSQL 기준으로 PGSync 전체 재동기화 가능
- Kafka: 원천 크롤러·폴러 재실행과 PG 적재 지점 확인으로 복구
- 애플리케이션/IaC: GitHub 저장소에서 재배포
- Harbor 이미지: GitHub 소스로 CI 재빌드 가능
- 모니터링 원시 데이터: 서비스 운영에는 필수가 아니며 새로 수집 가능

3. 서비스 기준 RPO/RTO
======================================================================

RPO(Recovery Point Objective): 장애 시 최대 얼마 전 데이터까지 복구할 것인가
RTO(Recovery Time Objective): 장애 후 서비스를 몇 시간 안에 다시 사용할 것인가

[공통 복구 기반]

전체 서비스 영속 볼륨
- 목표 RPO: 24시간
- 목표 RTO: 4시간
- 근거: 모든 서비스의 볼륨을 한 번에 복원해 기본 실행 상태를 빠르게 재구성
- 주의: 이 목표는 볼륨 계층 기준이다. PostgreSQL은 아래의 WAL을 추가 적용하여
  사용자 데이터 RPO를 24시간에서 15분으로 줄인다.
- 현재 상태: 전체 볼륨 연결 방향은 예정되어 있고 데이터 티어 적용은 아직 미완료

[P0: 핵심 사용자 서비스]

1) PostgreSQL foodbudget
   - 포함: 사용자/인증, 예산/지출, 냉장고/재고, 식단, 레시피북
   - 목표 RPO: 15분
   - 목표 RTO: 2시간
   - 근거: 서비스 개인화의 핵심이며 외부에서 재생성할 수 없음
   - 달성 수단: 데이터 볼륨 전체 백업 + 주간 PG 전체 + 일일 차등 + 연속 WAL(PITR)

2) 사용자 API와 프론트엔드
   - 목표 RPO: 마지막 Git push/배포 버전
   - 목표 RTO: 2시간
   - 근거: PG가 복구되어도 로그인·냉장고·예산 기능이 열리지 않으면 서비스가 아님
   - 달성 수단: GitHub 소스 + Docker Compose 재배포, 필요 시 최근 이미지 사용

[P1: 검색·수집 서비스]

3) PostgreSQL terraform_state
   - 목표 RPO: 인프라 변경 직후(정기 기준 최대 24시간)
   - 목표 RTO: 4시간
   - 근거: 변경 빈도는 낮고 import로 재구성 가능하지만 복구 작업이 복잡함
   - 달성 수단: foodbudget과 동일한 PG 물리 백업 + 일일 논리 dump

4) Elasticsearch
   - 목표 RPO: 24시간
   - 목표 RTO: 4시간
   - 근거: 하루치 검색 인덱스는 다시 만들 수 있으나 전체 재색인 시간이 필요함
   - 달성 수단: 일일 snapshot 또는 PostgreSQL→ES 전체 재색인

5) Kafka와 크롤링/폴링 파이프라인
   - 목표 RPO: 최대 24시간 또는 마지막 PG 적재 지점
   - 목표 RTO: 4시간
   - 근거: 가격·레시피 이벤트는 다시 수집할 수 있으며 PG 적재 결과가 우선임
   - 달성 수단: 토픽 재생성 + 마지막 watermark 이후 크롤러·폴러 재실행

6) Redis PGSync(6380)
   - 목표 RPO: 24시간
   - 목표 RTO: 2시간
   - 근거: 체크포인트 손실 시 PostgreSQL에서 전체 재동기화 가능
   - 달성 수단: AOF 보조 백업 또는 PGSync 전체 재실행

[P2: 재생성 가능한 운영 보조 계층]

7) Redis 캐시(6379)
   - 목표 RPO: 적용하지 않음(백업 생략)
   - 목표 RTO: 30분
   - 근거: 현재가·추출 캐시는 원본 DB/API에서 자동 재생성됨

8) Harbor
   - 목표 RPO: 현재 운영 배포 버전 1개
   - 목표 RTO: 8시간
   - 근거: 전체 이미지 이력은 필요 없고 GitHub 소스에서 재빌드 가능

9) Prometheus·Loki·Tempo·Grafana
   - 목표 RPO: 원시 데이터에는 적용하지 않음
   - 목표 RTO: 8시간
   - 근거: 서비스 기능보다 우선순위가 낮고 설정은 Git/Ansible로 재배포 가능

10) ML 학습 데이터와 모델
   - 목표 RPO: 24시간
   - 목표 RTO: 8시간
   - 근거: 사람이 만든 gold set과 확정 모델은 재생성 비용이 크지만 실시간 서비스
     트랜잭션보다 복구 우선순위는 낮음

전체 서비스 복구 목표:
- 2시간 이내: PostgreSQL foodbudget + 사용자 핵심 API/프론트엔드
- 4시간 이내: 검색(ES) + 이벤트 수집(Kafka) + PGSync
- 8시간 이내: Harbor 재빌드 환경 + 모니터링 + ML 작업 환경


======================================================================
4. RPO/RTO 달성을 위한 백업 방식과 주기
======================================================================

4.1 방식 선택 기준

- 전체 백업: 선택한 데이터 전체를 저장. 복구가 단순하지만 저장 공간과 시간이 큼
- 증분 백업: 마지막 백업 이후 변경분만 저장. 작지만 복구 시 백업 체인이 길어짐
- 차등 백업: 마지막 전체 백업 이후 변경분 저장. 증분보다 크지만 복구가 단순함
- 스냅샷: 특정 시점의 볼륨/서비스 상태. 빠른 복구용이며 별도 매체로 내보내지
  않으면 독립 백업이 아님
- 트랜잭션 로그 백업: PostgreSQL WAL을 보관하여 특정 시점(PITR)까지 복구
- 복제(Replica): 가용성 향상 수단. 원본 삭제·손상도 복제되므로 백업으로 계산 안 함

전체 볼륨 백업 적용 원칙:
- 모든 서비스에 연결할 영속 볼륨 전체를 공통 백업 대상으로 삼는다.
- 전체 볼륨 백업은 컨테이너 설정, 서비스 상태 파일과 여러 볼륨을 한 번에 복구해
  RTO를 줄이는 기반 복구 계층이다.
- 실행 중인 PostgreSQL·Elasticsearch·Kafka 볼륨을 그대로 복사하면 특정 시점의
  쓰기가 덜 반영된 crash-consistent 사본일 수 있다.
- 따라서 데이터 티어는 가능한 서비스 checkpoint/flush 또는 일관된 snapshot 절차를
  사용하고, PostgreSQL은 별도 전체·차등·WAL 백업을 반드시 함께 사용한다.
- 전체 볼륨 백업의 목표 RPO는 24시간이며, PostgreSQL의 15분 RPO는 WAL이 담당한다.

우리 팀은 모든 방식을 무조건 쓰지 않고 다음 조합을 선택한다.
- 공통 기반: 전체 서비스 영속 볼륨 일일 전체 snapshot/백업
- 중요 PostgreSQL: 전체 + 차등 + 트랜잭션 로그(WAL) 조합
- Elasticsearch: 서비스 자체 증분 snapshot
- 변경이 적은 파일/ML 자산: 주간 전체 + 일일 증분
- 재생성 가능한 캐시·모니터링 원시 데이터: 백업 생략
- 복제: 현재 단일 물리 호스트 환경에서는 구축하지 않으며 백업 대체로 보지 않음

4.2 대상별 “무엇을·어떤 방식으로·어디까지” 백업하는가

[0] 전체 서비스 영속 볼륨
- 포함 범위: fb-data, fb-app-ai, fb-ci-harbor, fb-monitoring에서 서비스에 연결된
  Docker named volume과 상태 보존용 bind-mount 디렉터리 전체
- 방식: 일일 볼륨 전체 snapshot/백업
- 목표 RPO: 24시간
- 목표 RTO: 4시간(볼륨 복원 후 서비스별 검증 시간 포함)
- 역할: 서버 또는 Docker 볼륨 손상 시 서비스 실행 기반을 빠르게 되돌림
- 한계: PG의 15분 RPO와 시점 복구, DB 정합성을 단독으로 보장하지 않음
- 현재 상태(2026-07-16): 전체 서비스에 볼륨을 연결하는 방향은 예정되어 있으나,
  데이터 티어까지 포함한 전체 볼륨 백업은 아직 미구축

[1] PostgreSQL foodbudget
- 포함 범위: 사용자/인증, 냉장고/재고, 예산/지출, 식단, 레시피북 등 전체 스키마,
  DB role과 권한, schema migration에 필요한 메타데이터
- 방식: 주간 전체 물리 백업 + 일일 차등 백업 + 연속 WAL + 일일 논리 전체 dump
- 보관: 일일 7일, 주간 4주, 월간 6개월
- 제외: 실행 중 데이터 디렉터리의 단순 파일 복사
- 현재 상태(2026-07-16): PG named volume 영속화는 되어 있으나 전체 볼륨 백업과
  PG 전용 전체·차등·WAL 백업은 아직 미구축

[2] PostgreSQL terraform_state
- 포함 범위: terraform_state DB 전체, state 및 잠금 관련 테이블, 접속 복구에 필요한
  role/권한. 같은 PostgreSQL 클러스터의 물리 백업에 foodbudget과 함께 포함
- 방식/저장: foodbudget과 동일한 전체 + 차등 + WAL + 일일 논리 dump
- 현재 상태(2026-07-16): 미구축. PG 원격 backend 사용은 백업이 아님

[3] Elasticsearch
- 포함 범위: 레시피·상품 인덱스, index template/mapping. 장기 정본은 PostgreSQL
- 방식: 일일 증분 snapshot. 실패 시 PG와 크롤링 원본에서 전체 재색인
- 보관: 일일 snapshot 7일, 주간 snapshot 4주
- 현재 상태(2026-07-16): 미구축. single-node 실행 중이며 replica 없음

[4] Redis
- 캐시 Redis 6379: 백업하지 않음. 현재가/추출 캐시는 원본에서 재생성
- PGSync Redis 6380: AOF 파일을 일일 파일 백업에 포함하되 최종 복구는 PG 기준
  전체 재동기화
- 보관: PGSync AOF 일일 백업 7일
- 현재 상태(2026-07-16): 6379는 의도적으로 비영속, 6380은 AOF 볼륨만 영속화.
  외부 백업은 미구축

[5] Kafka
- 포함 범위: 토픽 이름/partition/retention 설정, consumer group 운용 정보,
  마지막 PG 적재 watermark와 재수집 절차
- 방식: 설정은 Git 전체 백업, watermark는 일일 파일 백업. Kafka 라이브 로그
  디렉터리는 백업하지 않고 크롤러·폴러 재실행으로 복구
- 보관: 토픽 설정은 Git 이력, watermark는 일일분 7일
- 현재 상태(2026-07-16): 코드/IaC는 Git에 있음. watermark 백업·재수집 runbook은 미구축

[6] 애플리케이션 코드·IaC·설정
- 포함 범위: Git 추적 소스, Dockerfile/Compose, Ansible, Terraform 코드, Alembic,
  운영 문서와 대시보드 JSON
- 방식: Git 전체 이력을 GitHub에 유지
- 현재 상태(2026-07-16): GitHub와 로컬 clone으로 백업 중

[7] Harbor 및 CI
- 포함 범위: Harbor 설정/인증서, 프로젝트와 태그 목록, 현재 운영 IMAGE_TAG,
  최근 정상 운영 이미지 1개(OCI archive)
- 제외: GitHub runner 작업 디렉터리, 재빌드 가능한 전체 이미지 이력
- 방식: 설정은 주간 전체, 운영 이미지 OCI archive는 월간 snapshot 성격의 내보내기
- 보관: 설정 주간 4주, 운영 이미지 OCI archive 월간 1개
- 현재 상태(2026-07-16): 이미지/설정 백업은 미구축. 소스 기반 재빌드는 가능

[8] 모니터링
- 포함 범위: Git/Ansible의 Prometheus·Loki·Tempo·Grafana 설정 및 대시보드.
  Grafana UI에서 직접 만든 항목이 있으면 grafana_data도 포함
- 제외: 기본적으로 Prometheus/Loki/Tempo 원시 시계열·로그·트레이스 데이터
- 방식: Git 전체 이력 + 필요 시 grafana_data 주간 snapshot
- 보관: 코드화된 설정은 Git 이력, grafana_data snapshot은 주간 4주
- 현재 상태(2026-07-16): 코드화된 설정은 Git에 있음. 런타임 볼륨 백업은 미구축

[9] ML 학습 데이터와 모델
- 포함 범위: 사람이 만든 gold set, 검수 결과, 재현 불가능한 학습 원본,
  확정 CRF/LightGBM 모델 artifact와 평가 결과
- 제외: 공개 원천에서 쉽게 다시 받을 수 있는 임시 캐시와 중간 산출물
- 방식: 주간 전체 + 일일 증분
- 보관: 일일 7일, 주간 4주, 월간 6개월
- 현재 상태(2026-07-16): Git 추적 파일만 GitHub에 있음. gitignore된 모델·대용량
  데이터의 외부 백업 여부는 미확인

[10] Proxmox VM
- 방식: 업그레이드/대규모 변경 직전 VM snapshot은 빠른 롤백용으로만 사용
- 범위: VM 전체 이미지 대신 각 서비스의 영속 볼륨 전체를 정기 백업의 기본 범위로 둠
- 복구: Terraform/Ansible/Compose로 VM을 재생성한 뒤 위 데이터 백업을 복원
- 현재 상태(2026-07-16): VM snapshot은 독립 백업으로 계산하지 않으며 전체 볼륨
  백업 연결은 적용 예정

4.3 상세 주기

전체 서비스 영속 볼륨
- 매일 01:00: 연결된 영속 볼륨 전체 snapshot/백업
- 매주: 최신 정상 볼륨 백업을 주간 보관본으로 지정
- 데이터 티어: checkpoint/flush 등 서비스별 일관성 절차 후 snapshot 실행
- 보관: 일일 7일, 주간 4주
- 검증: snapshot 목록, 파일 수/크기, checksum 및 임시 볼륨 복원 확인

PostgreSQL(두 DB를 동일 정책으로 보호)
- 연속: WAL 아카이빙, 최대 15분 단위로 외부 백업 저장소에 전송
- 매일 02:00: 차등 백업(마지막 전체 백업 이후 변경분)
- 매주 일요일 03:00: 전체 물리 백업
- 매일: foodbudget 및 terraform_state 논리 백업(pg_dump custom format) 1회
- 변경 전: Alembic migration, PG/Proxmox 업그레이드, 스토리지 작업 직전 수동 백업
- 권장 구현: pgBackRest 또는 동등한 무료 도구를 별도 컨테이너로 운영
- 보관: 일일 7일, 주간 4주, 월간 6개월
- 검증: 백업 도구 checksum + pg_restore 목록 검사 + 임시 DB 실제 복원

Elasticsearch
- 매일 03:30: snapshot repository에 증분 snapshot
- 보관: 일일 7일, 주간 4주
- PG에서 재생성 가능한 인덱스는 장기 보관하지 않음
- 복구 시험 시 nori 플러그인/버전을 먼저 맞춘 뒤 snapshot restore 또는 재색인

Redis
- 캐시 Redis(6379): 백업하지 않음
- PGSync Redis(6380): 매일 AOF 일관성 확인 후 1차 백업에 복사
- AOF 복구 실패 시 새 인스턴스를 띄우고 PGSync 전체 재동기화

Kafka
- 데이터 볼륨의 라이브 파일 복사 금지
- 토픽 이름, partition, retention 등 선언은 Git/IaC에 유지
- 수집 원본의 마지막 성공 시각과 PG 적재 watermark를 매일 기록
- 장애 시 마지막 정상 watermark 이후 크롤러/폴러를 재실행할 수 있게 runbook 유지
- 꼭 보존해야 하는 이벤트가 생기면 별도 객체/파일 아카이브를 설계한 뒤 P1로 승격

Harbor 및 CI
- 매주: Harbor 설정, 프로젝트/이미지 태그 목록, 인증서 백업
- 배포마다: 현재 운영 IMAGE_TAG를 복구 기록에 남김
- GitHub runner는 재등록 가능하므로 runner 작업 디렉터리 전체는 백업하지 않음
- 최근 정상 운영 이미지 하나는 OCI archive로 월 1회 보관 권장

모니터링
- Git/Ansible에 있는 설정·대시보드는 별도 데이터 백업 생략
- Grafana UI 직접 변경분이 존재할 때만 주 1회 grafana_data 보호
- Prometheus/Loki/Tempo 원시 데이터는 기본 백업 대상에서 제외

파일·설정·ML 자산
- Git 추적 코드/IaC/문서: GitHub와 개발자 clone으로 보호
- 직접 생성한 CRF 학습 원본, gold set, 모델 artifact 중 Git에 없는 대용량 파일:
  매일 변경분 + 주간 전체 백업, 월간 사본 6개월 보관
- 크롤링으로 다시 받을 수 있는 원본은 우선순위를 낮추되 데이터 출처 중단 가능성이
  있으면 월간 snapshot을 남김

5. 자동화, 감시 및 성공 기준
======================================================================

자동화 위치 권장:
- Ansible에 backup 역할을 추가하여 설치·설정·timer를 코드화
- 실행은 fb-data의 systemd timer 또는 전용 backup 컨테이너 사용

매 실행 확인 항목:
- 종료 코드 성공
- 생성 파일 크기 0 초과 및 예상 범위
- checksum 검증 성공
- 마지막 성공 시각이 각 RPO 안에 있음
- 저장소 여유 공간 20% 이상
- 보관 정책에 따른 오래된 사본 정리 성공

알림:
- P0 백업 1회 실패: 당일 담당자 확인
- P0 백업 2회 연속 실패 또는 마지막 정상 백업 15분 초과: 긴급 알림
- 저장소 여유 20% 미만, checksum 실패, WAL 전송 정지: 긴급 알림
- 기존 Prometheus/Alertmanager에 백업 성공 시각과 실패 횟수 metric 연동 권장

6. 복구 순서(runbook)
======================================================================

1) 장애 인지 및 쓰기 중지
   - 장애 시각, 영향 서비스, 의심 원인을 기록
   - 손상 확산 방지를 위해 앱/수집기의 DB 쓰기를 중지

2) 영향도 판단
   - 단일 컨테이너, 단일 VM, Proxmox 호스트, 데이터 손상 중 무엇인지 분류
   - 데이터 손상/삭제 시각을 추정하고 목표 복구 시점을 정함

3) 복구 대상 선택
   - 가장 최신이라는 이유만으로 선택하지 말고 checksum과 손상 이전 시점 확인
   - 운영 원본까지 손상되었으면 검증된 월간 백업본 사용

4) 깨끗한 기반 복원
   - Terraform/Ansible로 VM과 Docker 환경 재구성
   - 운영 볼륨에 바로 덮어쓰지 말고 별도 임시 볼륨/DB에 먼저 복원

5) 데이터 복원
   - PostgreSQL 전체 백업 복원 후 필요한 WAL 시점까지 PITR
   - 두 DB(foodbudget, terraform_state) 및 role/권한 검사
   - Redis 캐시는 비우고, PGSync는 필요 시 전체 재동기화
   - Elasticsearch는 snapshot restore 또는 PG→ES 재색인
   - Kafka 토픽을 재생성하고 PG watermark 이후 수집 작업 재실행

6) 검증
   - DB 제약조건, row count 표본, 최신 사용자 데이터 확인
   - 로그인→냉장고 조회→레시피 검색→식단/지출 조회 smoke test
   - ES 검색, Kafka consume, Redis PING, 모든 /health 확인

7) 서비스 재가동
   - 데이터 계층 → 앱 서비스 → 크롤러/폴러 순으로 단계적 시작
   - 오류율과 자원 사용량을 30분 이상 관찰

8) 사후 점검
   - 실제 RPO/RTO, 유실 범위, 원인, 개선 작업을 기록
   - 다음 복구 시험에 개선사항 반영


======================================================================
7. 복구 테스트 일정
======================================================================

- 매일 자동: checksum, 백업 목록, WAL/마지막 성공 시각 검증
- 매월: 격리된 임시 PostgreSQL에 최신 백업 복원 + 핵심 테이블 smoke test
- 분기별: 빈 VM/격리 네트워크에서 전체 재해복구 훈련
  (PG 복원 → ES 재색인 → 앱 기동 → 사용자 핵심 흐름 확인)
- 반기별: 월간 백업본만 사용한 전체 복구 훈련
- 스키마·스토리지·PG 메이저 버전 변경 전후: 추가 복구 시험

성공 기준:
- 정해진 RPO/RTO 충족
- checksum 오류 0건
- 복원 과정의 문서 누락 0건
- 사용자 핵심 흐름 smoke test 전부 통과
- 담당자가 원본 서버 도움 없이 문서만 보고 복구 가능
