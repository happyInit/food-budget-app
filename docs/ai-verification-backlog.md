# AI 파트 검증 백로그 — 미검증·검증부족 항목

> **왜 이 문서가 있나.** 2026-07-29 세션에서 "구현 → 총괄 검증" 방식으로 진행하기로 했다.
> 그 방식의 유일한 위험은 **미검증 항목을 잊는 것**이므로, 잊지 않기 위해 여기에 적는다.
>
> 갱신 규칙: 검증하면 ✅ 로 바꾸고 **근거(수치·명령)** 를 함께 적는다. 지우지 않는다 —
> "확인했다"의 이력이 남아야 다음 사람이 다시 안 판다.
>
> 작성 2026-07-29 · AI 파트

## 0. 왜 즉시 검증이 필요한 것과 미뤄도 되는 것이 갈리나

2026-07-29 하루에 드러난 결함 6건은 **전부 실물 대조에서** 나왔다. 그중 가장 비쌌던 것:

> **소비기한 커버리지 검증이 `item_id` 만 보고 `(item_id, storage)` 조합을 보지 않았다.**
> `lookup_shelf_life` 는 조합으로 조회하므로 "미커버 29 → 6건"이라는 보고가 틀렸고
> (실제로는 29건 그대로), **같은 잘못된 가정 위에 AI 초안 타게팅까지 지어서** 마이그레이션
> 4개(c·d·e·f)를 다시 써야 했다.

교훈은 "검증을 많이 하라"가 아니다. **가정 위에 다음 것을 짓기 전에 그 가정만 확인하라**는 것이다.
그 확인은 2분이고, 안 하면 재작업이 몇 시간이다.

| 성격 | 시점 | 근거 |
|---|---|---|
| **운영 DB 쓰기** · **유저 노출**(알림·소비기한) | **즉시** | 되돌리기 비싸거나 불가능. 유저 24명·재고 124건이 실재한다 |
| **다음 작업이 딛는 가정** | **즉시**(2분) | 위 사례. 틀리면 그 위 전부가 재작업 |
| 교차 기능 통합 · 부하 · 커버리지 · 문서 정합 | **총괄 단계** | 개별로 하면 오히려 놓친다 |

## 1. 미검증 — 총괄 단계에서 반드시 볼 것

### 1.1 🟡 `recipe_review_summary.review_count` 의미 불일치 — **측정 완료, 조치 대기**

집계 SQL 이 `recipe_review JOIN recipe_review_sentiment` 라 **분류된 리뷰만** 센다.
분류 누락이 있으면 `review_count` 가 실제 리뷰 수보다 적고, 유저에게 *"24개 중 91.7% 긍정"* 으로
보이는데 실제로는 30개일 수 있다.

**실측 2026-07-30 (운영 PG = `pg-rw.data.svc`)**

```
total_reviews 141,298 · scored 141,282 · unscored 16 · summed_in_summary 141,282
```

누락 16건은 **11개 레시피에 분산**되고 최대 집중도는 레시피 7738 의 **14.3%**(14건 중 2건 →
유저에게 "12건"으로 표시). 전체로는 0.011% 지만 그 레시피에서는 2건이 빠져 보인다.

**원인을 찾았다 — 빈 후기가 아니다.** 16건 중 15건이 33~216자의 정상 후기이고 1건만 `...`(3자)다.
그리고 **거의 전부 혼합 감정**이다(*"맛있어요! **근데** 손이 많이 가네요"*). `parse_labels()` 는
허용 라벨(`positive|negative|neutral`) 밖의 값을 버리므로, 모델이 혼합 후기에 다른 라벨을 붙이면
그 항목만 조용히 사라진다.

🔴 **재실행으로 낫지 않는다.** 스크립트 주석은 *"실패분은 다음 실행이 재시도"* 라고 가정하지만
`temperature=0` 이라 같은 입력은 같은 출력이다 — **재시도 설계가 이 실패 모드를 덮지 못한다.**

- **조치안**: ① 프롬프트에 "혼합이면 우세한 쪽" 규칙 명시 후 16건만 재처리 ② 그래도 남으면
  `neutral` 로 확정 기록(누락 0 달성) ③ 컬럼을 `scored_count` 로 개명해 의미를 정직하게.
- **잔여 블로커**: Bedrock 자격증명 + 파이프라인 이미지 재빌드(§1.13) 필요 — 로컬에서 못 돌린다.

### 1.2 ✅ AI_DRAFT 소비기한 전수 점검 — **완료·오류 4건 교정(2026-07-30)**

`source='AI_DRAFT'` 행은 표본만 눈으로 봤고 **전수 확인하지 않았다.** 식품안전 항목이다.

**전수 특성 (153건, 전부 FRIDGE)**

| 지표 | 값 |
|---|---|
| `days_min` | 1일 **121건** · 2일 5건 · 3일 27건 |
| `days_max` | 2일 76건 · 3일 42건 · 5일 18건 · 7일 17건 |
| 카테고리 | 수산물 56 · 육류 36 · 채소 36 · 과일 21 · 버섯 2 · 유제품 2 |

같은 FRIDGE 기준 비교 — **AI_DRAFT 만 극단적으로 짧다**: CURATED 평균 40일 · FOODKEEPER 43일 · **AI_DRAFT 1일**.
과대추정은 없다(상한 7일) — "구조적으로 막혀 있다"는 서술이 맞았다.

**확정 오류 4건 — 건조 해조류를 생물로 판정**

| 품목 | AI_DRAFT | 교정(CURATED) |
|---|---|---|
| 김 · 다시마 · 미역 · 톳 | FRIDGE **1~3일** | FRIDGE **150~180일** |

→ `2026-07-30j_shelf_life_dried_seaweed.sql` **적용 완료**.
매생이(1~2일)는 냉동·생 유통이 주류라 **값이 맞으므로 손대지 않았다** — 해조류라고 뭉뚱그리면 이쪽이 틀어진다.

🔴 **놓친 이유가 중요하다 — 같은 함정의 재발이다.** 네 품목은 **이미 CURATED ROOM·FREEZER 행을
갖고 있었고 `FRIDGE` 조합만 비어 있었다.** `2026-07-29c` 가 건조·발효 식품을 큐레이션할 때
`(item_id, storage)` **조합 단위**로 채우지 않아 생긴 구멍을 AI 초안이 메운 것이다. §0 이 기록한
바로 그 교훈이 다시 나타났다.

- **코드 후속(미조치)**: `draft_shelf_life.py` 의 `_FRESH_CATEGORIES` 가 `수산물` 을 신선으로
  취급하는데 건조 해조류도 수산물이다. 이름에 '건조·마른' 표기가 없어 `_DRIED_PATTERN` 도 비껴간다.
  → 재생성하면 같은 값이 다시 나온다. 해조류 예외 또는 품목명 패턴 추가 필요.
- **실질 노출**: 재고 124행 중 AI_DRAFT 근거 **7행**, 임박(7일) **2행**. 그 2행은 **양고기 냉장
  1~2일**로 생고기 기준 타당 — 오알림 아님(소비 측 조건 `(item_id, storage)` 로 확인).
- **잔여 149건**은 생선·육류·채소로, 값이 다소 짧지만(육류 1~3일 vs 통상 3~5일) 안전측이며
  "먹고 아픈" 위험은 없다. 백로그가 지목한 심각 케이스(건조식품)는 해소됐다.

### 1.4 ✅ NER 백필 미매칭 분석 — **완료(2026-07-30)**

12,662건 중 `item_id` 매칭 97.1%. **나머지 367건이 무엇인지 보지 않았다.**

**답: 둘 다이며, 비율이 갈린다.** 상위 25건을 분해하면 세 부류다.

| 부류 | 예시 | 판정 |
|---|---|---|
| 일반 범주어 | 채소(23) · 과일(5) · 크림(4) · 호박(4) · 해초(3) · 파스타(3) | **정상 미매칭** — 특정 품목이 아니다 |
| 🔴 CRF 오추출 | **노란색(4) · 빨간색(3)** | 재료가 아닌 색상어를 재료로 추출 |
| gazetteer 확장 대상 | 느타리 · 춘권피 · 깐밤 · 꼬막 · 단감 · 대두 · 들깨 · 북어 · 분유 · 생면 · 순무 · 젓갈 · 휘핑크림 | 실제 품목인데 사전에 없다 |

매칭 실패는 행으로 남아 손실이 없고(원문 보존) `item_id=null` 이라 재료비에 잡히지 않으므로
**오추출도 비용을 만들지 않는다.**

### ⏸️ gazetteer 확장은 **의도적으로 보류**한다 (2026-07-30)

착수하려다 **#130(매칭 정책 확립, 담당 Taylor5132)이 열려 있고** 본문이 명시적으로
*"개별 케이스 땜빵이 아니라 매칭 정책 확립"* 을 요청하고 있어 멈췄다.

**전수 측정(운영 PG)** — 위 표는 상위 25건 표본이고, 전체는 이렇다:

| 부류 | 고유명 | 행 |
|---|---|---|
| A. CRF 오추출(색상어) | 2 | 7 |
| B. 일반 범주어 | 4 | 35 |
| C. 기존 품목의 접미 확장 | **0** | 0 |
| **D. 신규 품목 후보** | **258** | **325** |
| 합계 | **264** | **367** |

> **C 가 0인 것이 시사적이다.** 기존 `canonical_name`(2자 이상)으로 끝나는 이름은 매처의 접미
> 단계가 이미 해결해 `item_id` 가 붙는다 — 미매칭에 남은 것은 **어느 단계로도 못 풀린 것**이다.

🔴 **258개를 넣는 것은 granularity 결정을 258번 하는 것**이고, 그건 #130 §1.3 ⑤ 가 미뤄둔 항목이다.
단독으로 정하면 **정책이 데이터로 굳어져 나중에 되돌리기가 더 비싸진다.**

특히 `크림` 은 넣으면 안 되는 사례다 — 매처 접미 단계가 2자 이상을 잡으므로
(`classify.py:_make_matcher`) `사워크림`·`생크림`·`휘핑크림` 이 전부 `크림` 으로 흡수된다.
#130 이 지목한 *"짧은 별칭(≤2자) 323개 부분매칭 오탐"* 과 같은 유형이다.
`순무↔무` · `꼬막↔꼬막살` · `휘핑크림↔크림` 같은 층위 질문을 실측과 함께 **#130 에 코멘트로 전달**했다.

- **정책 무관하게 할 수 있는 것**: A 부류(색상어)는 재료가 아닌 스팬이라 **CRF 후처리에서 거르는
  것**이 맞다 — gazetteer 문제가 아니다(§1.14 로 분리).
- **판정 방법**: #130 정책 확정 → `curate_item_master.py` `CATS` 일괄 반영 → 미매칭 재측정.

### 1.5 ✅ `price_alert_sent` FK 엣지케이스 — **재현·수정·검증 완료(2026-07-30)**

**우려가 실재했다 — 운영 PG 에서 재현됨.**

```
ERROR:  insert or update on table "price_alert_sent" violates foreign key constraint
        "price_alert_sent_anomaly_id_fkey"
DETAIL: Key (anomaly_id)=(-999999) is not present in table "price_anomaly".
```

FK 는 `ON DELETE CASCADE` 라 **기존 행 삭제**는 처리하지만 **사라진 행을 참조하는 INSERT** 는
그대로 위반이다. Kafka retention(7일) > 이상치 정리 주기면 이 경로가 열리고, 컨슈머에 DLQ 가
없어(#252) 같은 메시지에서 **무한 크래시 루프**가 된다.

**수정**: `_FANOUT_SQL_TRACKED` 에 사전 가드 `AND EXISTS (SELECT 1 FROM price_anomaly pa WHERE pa.id = %(anomaly_db_id)s)`.
예외 처리로 잡지 않은 이유 — **FK 위반은 트랜잭션을 abort 시켜 같은 배치의 정상 이벤트까지 죽는다.**
사전 가드가 유일하게 안전한 위치다.

**검증(모듈 원문 SQL 을 운영 PG 에 그대로 실행, 트랜잭션 롤백)**

| 경로 | 결과 |
|---|---|
| (A) 이상치 존재 + 관심 등록자 1명 | `INSERT 0 1` — **알림 생성됨** ✅ |
| (B) 이상치 삭제 후 같은 id 참조 | `INSERT 0 0` · **에러 없음** ✅ |

가드가 크래시만 막고 정상 경로는 살렸다. 회귀 테스트 1건 추가.

> 🎁 **덤으로 §1.6 이 전진했다** — (A) 는 fan-out 이 **실제로 알림 행을 만든다**는 첫 실증이다
> (그전까지 "발행 경로는 실 데이터로 검증된 적 없음"이었다). 다만 이는 SQL 계층 증명이고,
> 탐지→Kafka→컨슈머 전 구간은 여전히 미검증이다.

### 1.6 🟡 성숙도 게이트 — **탐지·게이트 산술 검증 완료 · 발행 경로만 미검증(2026-07-30)**

`MATURE_SAMPLES=28` 은 **2026-08-18 에 처음 풀린다.** 그 전까지는 "발행 0건" 경로만 실행되고,
**실제로 발행이 일어나는 경로는 실 데이터로 검증된 적이 없다**(`--allow-immature` 로만 확인).

**실측 2026-07-30 — 배포 이미지·운영 데이터로 dry-run 실행**(K8s Job · `--emit`/`--persist` 없음
= DB 쓰기 0 · Kafka 발행 0):

```
시계열 523개 · 스캔 6,055행 (window=30 · z<=-2.0 · drop>=8% · N>=7) · 조건 충족 4건
  [oasis] 딸기     ▼47%  z=-9.7   N=15  🔻역대최저
  [oasis] 치커리   ▼27%  z=-2.39  N=14
  [kurly] 블루베리 ▼19%  z=-3.39  N=9   🔻역대최저 · 할인 13%
  [oasis] 양파     ▼8%   z=-3.74  N=15  🔻역대최저
```

✅ **탐지는 실제로 동작한다** — 근거(품목·가격·z·평균)까지 정상 산출된다.
✅ **게이트 산술도 맞다** — 최대 표본이 15일이라 4건 전부 28일 기준에 막힌다(발행 0건).

**게이트 해제 시점(실데이터 계산)**

| 소스 | 수집 일수 | 결손 | 28일까지 | 예상 |
|---|---|---|---|---|
| oasis | 16 | 2 | +12일 | ~2026-08-11 |
| kurly | **10** | **8** | +18일 | ~2026-08-17 |

문서의 **2026-08-18** 추정이 맞다 — 컬리가 지각생이다(결손 8일 중 7일은 07-14~07-20 과거
공백, 1일은 07-29 `_topics.py` 장애).

🔴 **여전히 미검증인 것: 발행 경로 자체.** 성숙도 게이트 코드가 `if args.emit:` **블록 안에**
있어 dry-run 으로는 그 분기를 밟지 못한다. `--emit` 은 ① Kafka 토픽 `price.anomaly.detected`
가 필요한데 **아직 없고**(#381 요청 5) ② `--persist` 를 함의해 운영 DB 에 쓰며 ③ 알림은
되돌릴 수 없다. → **토픽 생성 후에 검증 가능**하다.

- **판정 방법(토픽 생성 후)**: `--mature-samples 8 --emit` 1회 → Kafka 메시지 4건 확인 →

### 1.9 ✅ `expire_at` 재계산 구조 — **도입 완료(2026-07-30)**

`pantry_item.expire_at` 은 **등록 시점에 한 번만** 계산되고 참조표가 나중에 채워져도
재계산되지 않는다. 2026-07-29 에 12건을 소급했으나(`2026-07-29g`) **이는 패치이지 수정이 아니다.**
AI_DRAFT 검수 승격·큐레이션 추가 때마다 그 사이 등록분이 또 NULL 로 남는다.

→ **주기 배치로 결정**했다. `pipelines/ingest/recompute_pantry_expire.py` +
CronJob `mp-pantry-expire-recompute`(주 1회 일 05:30 KST, `deploy/k8s/pantry-expire-recompute.yaml`).
사람이 기억해서 돌리지 않아도 참조표 갱신을 따라잡는다.

**안전규칙 3개**(회귀 테스트 6건으로 고정):
1. `expire_at IS NULL` 만 — 이미 있는 값은 유저가 본 날짜다(유저 입력일 수도)
2. **결과가 미래인 것만**
3. 멱등 — 대상 없으면 무동작

🔴 **2번이 핵심이다.** 실측: 채울 수 있는 2건이 **전부 이미 지난 날짜**가 된다. 그대로 넣으면
"기한 없음"이던 재고가 "지남"으로 바뀌어 임박 목록에 들어간다(`expire_at <= current_date + 7`
은 **과거도 잡는다**) → 26 → 28. 정보로는 정확하나 **행동 가능성이 없고** 알림 신뢰만 깎는다.
팀 결정(*"모르면 표시하지 않고 포장 표기 안내"*)과도 일관된다 — NULL 은 "모름"이라는 정직한 상태다.

**검증(운영 PG, 모듈 원문 SQL)**: 재계산 대상 **0건** · 남는 NULL 25(참조표 없음 23 + 과거 제외 2) ·
임박 **26 불변** · 대조군(규칙 없었다면) **2건이 과거로 채워짐**.
**오늘 아무것도 바꾸지 않는 것이 정상이자 안전 속성**이다 — 검수 승격이 일어나면 그때부터 잡는다.

### 1.10 ✅ 접근 불가 영상(삭제·비공개) 전용 실패 사유 — **해결(2026-07-29)**

Vertex PoC 중 발견(2026-07-29). 삭제된 YouTube URL(oEmbed 404)에서 두 백엔드가 다르게 죽는다.

| 경로 | 동작 | 문제 |
|---|---|---|
| api_key | 1초 만에 `is_recipe=false` | 유저에게 **"요리 영상이 아닙니다"** 로 오안내 |
| vertex | `500 INTERNAL` (3/3 재현) | 잡 실패 · 원인 불명 메시지 |

유저는 삭제·비공개·연령제한 URL 을 반드시 붙여넣는다. 지금은 **"영상을 못 읽었다"와
"요리 영상이 아니다"가 구분되지 않는다.**

**조치**: `pipeline.check_availability()` 추가 — 모델 호출 **전** oEmbed 확인(무료·수백ms).
불가면 `stage="unavailable"` + *"영상을 불러올 수 없어요. 삭제됐거나 비공개·연령제한…"* 로 즉시 반환.
헛된 모델 호출이 없으니 **비용도 아낀다.**

설계 요점 3가지:
- **캐시 뒤·모델 앞**에 둔다 — 캐시 히트는 이미 뽑아둔 결과라 영상이 내려가도 쓸모가 있다.
- **`None`(네트워크 오류)이면 막지 않는다** — 선점검이 새로운 실패 지점이 되면 안 된다.
- **주입식**(`availability_fn`) — 파이프라인은 순수 유지, 네트워크 I/O 는 `services/video` 가 넘긴다.
  (처음에 기본값으로 실호출을 넣었더니 단위테스트 10개가 외부망을 타며 깨졌다 — 규약 위반이었다.)

**검증**: 실 URL 3종 — 정상 `True` · 삭제 `False` · 없는ID `False`. 회귀 테스트 3건 추가
(모델 미호출·판정불가 통과·캐시히트 선점검 생략).

원문 `파프리카(빨간색, 노란색)` 에서 CRF 가 색상 수식어를 별도 스팬으로 뽑은 것이다.

**조치 2가지**
1. **재생산 차단** — `backfill_ner_raw_ingredients.py` 에 `_COLOR_ONLY` 필터(회귀 테스트 3건).
2. **기존 행 정리** — `2026-07-30k` 마이그레이션으로 7행 삭제.

🔴 **완전일치만 거른다.** `%색%` 로 지우면 실제 재료가 대량으로 날아간다 — 실측:
자색양파(6)·갈색설탕(5)·자색고구마(4)·대파 녹색부분(2)·적색 파프리카(2)·노란색 파프리카(2)·
삼색파프리카(1) 는 **전부 매칭에 성공한 정상 재료**다. 삭제 조건에 `ner_status='NER_PARSED'` 와
`item_id IS NULL` 도 함께 걸었다.

**검증(운영 PG)**: 색상어 잔존 **0** · 실제 재료 **16행 전부 매칭 유지** · 미매칭 총계 367 → **360**
(정확히 −7) · 재실행 멱등 0행 · 레시피 16875 화면에서 색상 행 사라짐 확인.

⚠️ **버리기만 하고 앞 재료에 되붙이지는 않았다.** `파프리카` 에 색을 붙이는 편이 데이터로는
낫지만 스팬 순서·괄호 구조를 추정해야 해서 **잘못 붙으면 멀쩡한 재료명을 오염시킨다.**
버리는 쪽은 최악이어도 정보가 줄 뿐이다(색상은 원문 `ingredient_raw` 에 그대로 남는다).

### 1.15 ✅ RAW 빈 이름 행 노출 — **해결(2026-07-30)**

§1.14 작업 중 발견. 규모가 훨씬 크다.

```
RAW 행 1,143 · 전부 ingredient_name 이 빈 값 · 영향 레시피 1,143
그중 1,142 개는 NER_PARSED(구조화 결과)도 함께 가진다
```

RAW 행은 원문 덩어리를 `ingredient_raw` 에 담고 `ingredient_name` 은 비어 있다. 그런데 상세 API 가
필터 없이 전 행을 반환하므로 **레시피마다 재료 목록에 빈 줄이 하나씩 뜬다.**
(백필 이전에는 그 빈 줄이 **유일한** 재료였다 — 백필로 실재료가 채워졌지만 빈 줄은 남았다.)

**조치**: 데이터를 지우지 않고 **조회에서 거른다** — `services/recipe/app/queries.py` 상세
쿼리에 `AND coalesce(btrim(ingredient_name), '') <> ''`. `ingredient_raw` 원문은 재백필·감사에
필요하므로 행 삭제는 옳지 않다.

**사전 위험분석에서 확인한 것**
- 빈 이름 행은 **RAW 전용**이다 — 1,143건 전부이며 CRAWLER·LABELED·NER_PARSED 는 **0건**.
  즉 필터가 의도한 집합만 정확히 잡는다.
- **재료비는 불변**이다. 빈 행은 `item_id IS NULL`(예외 0건)이라 단가 조회 대상(`item_ids`)에
  안 들어가고, 루프에서도 `low_price=None` → `basis='no_price'` 로 `total` 에 누적되지 않는다.
  이 쿼리가 표시와 비용 계산에 **함께** 쓰이므로 반드시 확인해야 했던 지점이다.

**검증(운영 PG · 모듈 원문 SQL 대조)**

| 항목 | 결과 |
|---|---|
| 레시피 16875 | **10행 → 9행** (빈 줄만 사라지고 실재료 9개 유지) |
| 전체 영향 | 1,143행 숨김 · 1,143 레시피 |
| 숨겨지는 행 중 `item_id` 보유 | **0건** → `ingredient_cost_total` 불변 |
| 재료 0건이 되는 레시피 | **1개**(17251) |

레시피 17251 은 RAW 원문이 **1글자**라 애초에 재료 정보가 없다. 빈 줄 1개 vs 0개는 실질
차이가 없고 **0 쪽이 정직하다**(있지도 않은 재료가 있는 것처럼 보이지 않는다).

회귀 테스트 1건 추가 — 필터가 사라지면 즉시 깨진다. recipe 서비스 **7 passed**.
