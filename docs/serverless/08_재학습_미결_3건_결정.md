## ① 온프렘 랭킹 스위치 — 🔴 **켜지 않는다**

**현황.** 온프렘에는 모델이 있고(`model_loaded: true`) `RANKING_ML_ENABLED=false` 라 안 쓰인다.

**결정 = 그대로 둔다.** 이유가 «아직 검증이 덜 됐다» 가 아니라 **켜면 더 나빠지기 때문**이다:

- 08-07 모델은 **실제 라벨로 학습된 것이 아니다.** 켜면 규칙 랭킹(재고·임박·예산 적합)을
  **근거 없는 재정렬로 덮는다.**
- 🔴 그리고 규칙 랭킹은 지금 **잘 돌고 있다.** 계정마다 추천이 다르게 나오는 것을 브라우저로
  확인했다(2026-08-16) — 재고·임박·예산이 유저별로 반영되고 있다는 뜻이다.
  즉 켜서 얻을 것은 없고 잃을 것은 그 개인화다.
- ⚠️ 그리고 이건 **되돌려도 흔적이 남는 종류**다. 그 사이 유저가 본 잘못된 순서가
  `recipe_impression` 에 라벨로 쌓이고, 그 라벨로 다음 모델을 학습하게 된다.

**언제 켜나** = ①라벨이 실제로 쌓이고 ②그 라벨로 학습한 모델이 ③오프라인 평가에서 규칙
baseline 을 이겼을 때. 셋 다 아직 아니다. 첫 번째부터가 막혀 있다(→ `GRANT` 건).

## ② 합성 라벨 — 🔵 **쓴다. 단 «배관 검증» 에만 쓰고, 그 모델을 서빙에 올리지 않는다.**

### 실제로 돌려 봤다 (2026-08-17 · 로컬 · PG 무관)

`synth.py` → `to_matrix` → `train` → `save_model` → `pickle.load` → `predict` 를
**serve.py 가 읽는 것과 같은 방식**으로 끝까지 태웠다.

```
① 라벨 생성   3,200행 / 400그룹 · 라벨 분포 {0: 2000, 1: 800, 2: 400}
② 학습        _SklearnRanker  (이 환경에 lightgbm 이 없어 폴백 경로)
③ 저장→로드   133,436 B · 언피클 성공
④ 평가        ML  ndcg@k 0.9310 · map 0.9292 · mrr 0.9850
              규칙 baseline  0.6970 · 0.6478 · 0.7732      →  ndcg_lift +33.6%
```

🔴 **평가는 그룹 경계로 잘랐다.** row 로 자르면 같은 세션이 학습·평가에 걸쳐 들어가
점수가 부풀고, 그걸 «잘 된다» 로 읽게 된다.

### 이 숫자가 말하는 것과 말하지 않는 것

| | |
|---|---|
| 🟢 말한다 | **배관이 끊긴 데가 없다** — 라벨→학습→저장→로드→예측이 전부 이어진다 |
| 🟢 말한다 | 피처·모델이 **심어 둔 신호를 찾아낼 능력은 있다**(못 찾았다면 실 라벨을 기다릴 문제가 아니라 피처 설계 문제였다) |
| 🔴 **말하지 않는다** | **개인화가 실제로 나아진다** — 신호를 우리가 심어 놓고 그걸 찾았다고 말하는 것이다 |

### 결정

- **쓴다** — 2단계(CronJob) 구현을 라벨이 쌓이기 전에 **미리 검증**하는 용도로. 그러면
  라벨이 도착했을 때 «배관도 처음 돌려 보는» 상태가 아니게 된다.
- 🔴 **그 모델을 `ranker.pkl` 로 올리지 않는다.** 올리면 ①과 같은 사고가 된다 —
  근거 없는 재정렬이 규칙 랭킹을 덮고, 그 결과가 다시 라벨이 된다.
- 🔴 **보고에서 섞지 않는다.** *"재학습 파이프라인이 돈다"* 와 *"개인화가 나아졌다"* 는
  다른 문장이다. 발표·데모에서 후자로 말하면 그건 사실이 아니다.

## ③ 전용 이미지 베이스 — 🔵 **`rank-serve` 와 공유한다**

**왜 이미지가 필요한가** = `lightgbm` 이 `libgomp.so.1` 을 요구하는데 그건 **OS 패키지**다.
`mp-data-pipeline` 이미지에는 없고, zip Lambda 번들에도 넣을 자리가 없다.

**결정 = 하나의 베이스를 둘이 쓴다.** 지금 그 비용을 두 번 낼 이유가 없다:

```
   베이스 (libgomp + numpy·scikit-learn·lightgbm)
     ├─ mp-ai-rank-serve      서빙 (+ mangum · serve.py · ranker.pkl)
     └─ mp-ai-ranking-retrain 재학습 (+ psycopg · retrain.py · boto3[S3 업로드])
```

근거:
1. **libgomp 배선이 한 곳**이 된다. 두 벌이면 한쪽만 고쳐지고, 그 실패는 `import lightgbm`
   시점 = **첫 호출**에서야 난다.
2. **언피클 호환이 저절로 맞는다.** 🔴 이게 진짜 이유다 — 학습 이미지의 sklearn/lightgbm 버전과
   서빙 이미지의 버전이 갈리면 `pickle.load` 가 조용히 다르게 동작하거나 죽는다.
   같은 베이스면 그 축이 사라진다.
3. 이미지 캐시·빌드 시간·ECR 저장량이 절반이다(학생 예산).

⚠️ **주의** — 베이스를 공유하면 **한쪽 사정으로 올린 버전이 다른 쪽에 그대로 간다.**
재학습에 새 lightgbm 이 필요해 올리면 서빙도 같이 올라가고, 그러면 **기존 `ranker.pkl` 을
못 읽을 수 있다.** ⇒ 베이스를 올릴 때는 **모델 재학습·재배포를 한 세트로** 본다.

### 재학습은 Lambda 가 아니라 **EKS CronJob** 이다

11종 서버리스 목록에 재학습은 **없다.** 재학습은 AI *기능*이 아니라 모델을 만드는 배치이고,
`ml/recipe-ranking/Dockerfile` 이 이미 그 이미지를 만든다. 설계서 §3.3 대로
`pipeline` ns 의 CronJob(`0 18 * * 0` = 일 03:00 KST)으로 둔다.
