# G-06 결정 — 영수증 이미지를 어떻게 Lambda 까지 나르나

**작성 2026-08-17 · AI 파트 · 실측 기반**
결정 = **클라이언트 다운스케일 + 인라인 업로드(정본)** · **presigned S3 PUT(폴백, 이미 구현됨)**

---

## 0. 왜 결정이 필요해졌나 — 숫자 하나

| | 값 | 출처 |
|---|---|---|
| **ALB → Lambda 요청 본문 상한** | **1 MB** | AWS 공식 문서 "Limits"(2026-08-17 직접 확인) |
| OCR 업로드 상한 `max_image_bytes` | 8 MB | `services/ocr/app/config.py` |
| 휴대폰 영수증 사진 통상 | 2 ~ 5 MB | — |

⇒ **현행 `POST /api/pantry/ocr` 를 그대로 Lambda 에 붙이면 대부분의 사진이 함수에 닿지도 못한다.**
ALB 가 부르기 전에 끊는다. 🔴 **튜닝으로 올릴 수 있는 값이 아니다** — ALB-Lambda 통합의 고정 상한이다.
파드(Envoy)에서는 안 나던 문제라, 이관 전에는 존재하지 않던 제약이다.

---

## 1. 🔵 그런데 결정을 쉽게 만드는 사실이 있다 — **서버가 이미 축소하고 있다**

`services/ocr/app/pipeline/backend/vision.py`:

```python
def _downscale(image: bytes, max_side: int) -> bytes:
    """큰 사진 축소 — 업로드·처리시간·비용↓(영수증 텍스트는 ~1600px면 충분)."""
    ...
    im.save(buf, "JPEG", quality=85)
```

`image_max_side = 1600` (config.py). ⇒ **모델이 보는 그림은 지금도 최장변 1600px JPEG q85** 다.
8MB 원본을 ALB 로 밀어 넣는 것은 **전송 낭비**일 뿐, 인식 품질에 기여하는 바가 **0** 이다.

🔴 **이게 결정을 바꾼다.** *"클라이언트에서 줄이면 품질이 떨어진다"* 는 걱정이 통상 맞지만,
**여기서는 틀리다** — 클라이언트가 같은 1600px 로 줄이면 모델은 **오늘과 똑같은 것**을 본다.
품질 트레이드오프가 아니라 **같은 일을 더 일찍 하는 것**이다.

---

## 2. 어떤 경우에도 S3 는 필요하다 (선택지가 아니다)

접수 함수와 워커 함수는 **다른 프로세스**다. 그 사이는 SQS 인데:

```
SQS 메시지 본문 상한 = 256 KB   <   1600px JPEG q85 (통상 200~500 KB)
```

⇒ **이미지를 큐에 실을 수 없다.** 접수가 S3 에 두고 큐에는 좌표(`bucket`/`key`)만 흘린다.
즉 **영수증 업로드 버킷은 어느 안을 고르든 만들어야 한다.** G-06 이 정하는 것은 그게 아니라
**«브라우저가 어디로 올리는가»** 뿐이다.

---

## 3. 선택지

### A. 클라이언트 다운스케일 + 인라인 ← **권고**

```
브라우저: 사진 → canvas 로 1600px 축소 → JPEG q85 (200~500KB)
        → POST /api/pantry/ocr  (multipart, 지금과 같은 모양)
Lambda:  받은 바이트 → S3 put → SQS → 202
```

- 🟢 **프론트 API 계약이 안 바뀐다.** `submitOcr(file)` 이 보내는 파일만 작아진다.
- 🟢 **왕복이 1회 그대로.** presigned 는 3회(URL 발급 → S3 PUT → 접수)다.
- 🟢 **버킷 CORS 설정이 불필요**하다. 브라우저가 S3 를 직접 안 친다.
- 🟢 **지금 파드에도 그대로 통한다** — 서버가 어차피 1600px 로 줄이므로 **동작 변화 0**.
  ⇒ 프론트 변경을 **Lambda 이관과 분리해서** 먼저 넣어도 안전하다.
- ⚠️ 축소해도 700KB 를 넘는 사진(아주 긴 영수증 등)은 이 경로로 못 간다 → **B 로 떨어진다.**

### B. presigned S3 PUT (폴백 · **이미 구현돼 있음**)

```
브라우저: POST /api/pantry/ocr/upload-url → {job_id, upload_url}
        → PUT upload_url  (S3 직결 · ALB 를 안 지남 → 상한 없음)
        → POST /api/pantry/ocr {"job_id"}
```

- 🟢 **크기 상한이 없다.** A 가 못 넘기는 사진의 안전망.
- 🔴 왕복 3회 · 버킷 CORS 필요 · 프론트 업로드 로직 재작성.
- 🔵 `serverless/ai_ocr_api/app.py` 에 **이미 들어 있다.** 추가 작업은 프론트뿐이다.

### C. OCR 만 파드에 남긴다

- 🟢 지금 아무것도 안 바뀐다.
- 🔴 **AI 기능을 서버리스로 옮긴다는 이 작업의 목적과 정면으로 어긋난다.** 그리고 1MB 는
  OCR 만의 문제가 아니라 **ALB 뒤 Lambda 전부의 성질**이라, 여기서 피해도 다시 만난다.
- ⇒ 기각.

## 4. 결정과 근거

> ### 🔵 **A 를 정본으로, B 를 폴백으로 간다.**
> 접수 함수는 이미 둘 다 받는다 — 인라인이 700KB 를 넘으면 **413 과 함께 upload-url 을 안내**한다.
> 그래서 «둘 중 하나» 가 아니라 **«기본은 A, 안 되면 B»** 가 코드 수정 없이 성립한다.

판단 축은 **품질이 아니라 부품 수**였다. 서버가 이미 1600px 로 줄이고 있어서 A 는 품질을
전혀 잃지 않는다(§1). 그러면 남는 비교는 «왕복 1회 · CORS 없음 · 계약 불변» 대 «왕복 3회 ·
CORS · 프론트 재작성» 이고, 답이 하나다.

🔴 그리고 A 에는 **B 에 없는 성질**이 있다 — **Lambda 이관과 분리해서 지금 넣어도 안전하다.**
파드가 어차피 축소하므로 오늘 배포해도 동작이 안 바뀌고, 나중에 OCR 이 Lambda 로 갈 때
**프론트는 이미 준비돼 있는** 상태가 된다. 이관 당일에 프론트까지 같이 바꾸는 것보다 훨씬 낫다.

## 5. 🔴 구현할 때 반드시 처리할 것 — EXIF 회전

`services/ocr/` 어디에도 EXIF 처리가 **없다**(`ImageOps.exif_transpose` 호출 0건, 확인함).
그래서 지금 동작은 크기에 따라 갈린다:

| 원본 | 지금 벌어지는 일 |
|---|---|
| 최장변 ≤ 1600px | 원본 바이트 그대로 전달 → **EXIF 회전 태그가 남아 있다** |
| 최장변 > 1600px | 재인코딩 → **EXIF 가 통째로 사라진다**(휴대폰 사진 대부분이 여기) |

⇒ 클라이언트에서 줄이면 **위 두 번째 경우와 같은 상태**로 통일된다 — 회귀가 아니다.
🟢 오히려 개선할 기회다: `createImageBitmap(blob, { imageOrientation: 'from-image' })` 로
그리면 **회전을 픽셀에 구워서** 보낼 수 있다. 지금 세로로 찍은 영수증이 모델에 눕혀서
들어가고 있을 가능성이 있고, 그건 **아무 에러도 없이 인식률만 떨어뜨린다.**

⚠️ 구형 iOS Safari 는 `imageOrientation` 을 무시한다 — 그때는 **원본을 그대로 보내는 폴백**을
둘 것. 줄이지 못한 사진은 §3-A 의 413 → B 경로로 자연히 흘러간다.

## 6. 남는 요청 사항 (인프라)

| | 무엇 | 비고 |
|---|---|---|
| S3 버킷 | 영수증 업로드용 (예: `mp-ai-uploads-ap2`) | 🔴 **수명주기 규칙 필수** — 개인정보다. 워커가 성공 시 즉시 삭제하지만 실패 잔여물이 남는다. 1일 만료 권장 |
| | 퍼블릭 차단 · SSE-S3 | `mp-crawl-ap2` 와 같은 형상 |
| | CORS | **A 만 쓰면 불필요.** B 를 켤 때 추가 |
| SQS | `mp-ai-ocr-jobs` + DLQ(maxReceiveCount 3) | `mp-crawl-*` 와 같은 형상 |

🔵 버킷·큐는 **G-06 결정과 무관하게 필요**하다(§2). 결정을 기다릴 필요가 없는 항목이다.
