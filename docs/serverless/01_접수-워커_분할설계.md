# 접수·워커 분할 설계 — `ocr` · `video` (2026-08-14)

> **범위** AI 12함수 중 접수 2 + 워커 2. 나머지(배치 5 · 이벤트 1 · 동기 2)는 별건이다.
> **전제** 실측은 전부 2026-08-14 · 레포와 라이브 클러스터 기준이다.

## 0. 결론 먼저

| | `video` | `ocr` |
|---|---|---|
| 분할 난이도 | 🟢 **바로 가능** | 🔴 **선행 결정 1건**(G-06) |
| 이유 | 입력이 **URL 한 줄** | 입력이 **최대 8MB 이미지** |
| 막는 것 | 없음 | ALB→Lambda 요청 **1MB** · SQS 메시지 **256KB** |

**`video` 부터 하고 `ocr` 은 결정을 받은 뒤에 한다.** 계약(잡 상태·락·큐)은 공유하므로 `video` 가 본이 된다.

## 1. 지금 어떻게 도는가 (실측)

두 서비스 **모두 이미 202 + 폴링** 구조다. 바꿀 것은 **일이 도는 자리**뿐이다.

```
POST /api/recipes/extract   →  202 {job_id}      GET .../{job_id} → 상태
POST /api/pantry/ocr        →  202 {job_id}      GET .../{job_id} → 상태
```

**일이 도는 자리**가 문제다.

| | 현행 | Lambda 에서 |
|---|---|---|
| `video` | `bg.add_task(_run_job, ...)` — FastAPI BackgroundTasks | 🔴 **안 돈다.** 응답 직후 실행 환경이 얼어붙는다 |
| `ocr` | `asyncio.create_task(_run_job, job_id, data)` | 🔴 **안 돈다.** 같은 이유 |

🟢 `ocr` 코드에 이미 예고돼 있다 — `# TODO(백엔드): BackgroundTasks/큐 + ocr_receipt PENDING row 생성`.

### 이미 있는 것 — 재설계하지 않는다

`video` 의 `store.py` 가 **워커 분할에 필요한 계약을 이미 갖고 있다.** Valkey 키로 전부 표현된다.

| 계약 | 구현 | TTL | 분할 후 |
|---|---|---:|---|
| 잡 상태 | `put_job` / `get_job` | 1h | **그대로** — 접수가 쓰고 워커가 갱신 |
| 결과 캐시 | `get_cached` / `put_cached` | 30일 | **그대로** — 접수 단계에서 히트하면 워커를 안 부른다(비용 0) |
| 단일비행 락 | `acquire` = `SET key 1 NX EX 180` | 180s | **그대로** — 아래 §3 주의 |

## 2. 목표 형상 — `video`

```
사용자 → ALB → ai-video-api          (접수 · 타임아웃 10s)
                 ├ URL 정규화·검증
                 ├ 캐시 히트?  → 202 {status:DONE, from_cache:true}   ← 워커 안 부름
                 ├ 락 획득 실패? → 409
                 ├ put_job(PENDING)
                 └ SQS 워커큐로 {job_id, url} 전송  → 202 {job_id}

SQS mp-ai-video-jobs ──→ ai-video-worker   (처리 · 타임아웃 300s)
        │                   ├ Vertex 호출 → 추출
        │                   ├ put_job(DONE|FAILED) · put_cached
        │                   └ release(락)
        └ 3회 실패 → mp-ai-video-jobs-dlq

사용자 → ALB → ai-video-api  GET /{job_id}  → Valkey 조회
```

**메시지 본문** = `{"job_id": "...", "url": "https://..."}` — 200바이트 수준. SQS 상한(256KB)에 여유가 크다.

## 3. 🔴 분할하면서 새로 생기는 것 4건

### ① 락이 워커 죽음을 못 견딘다 → **TTL 이 유일한 방어선**

지금은 같은 프로세스라 `finally` 로 `release` 가 보장된다. 분할하면 **워커가 죽으면 락이 남는다.**
🟢 `EX 180` 이 있어 **3분 뒤 자동 해제**된다 — 구조적으로 이미 막혀 있다.
🔴 **다만 워커 타임아웃을 180초 아래로 둬야 한다.** 300초로 잡으면 *"락은 풀렸는데 워커는 아직 도는"* 구간이 120초 생기고, 그 사이 같은 URL 이 중복 분석된다(비용 2배).
→ **워커 타임아웃 ≤ `lock_ttl_s`.** 둘 중 하나를 바꾸면 다른 하나도 같이 본다.

### ② SQS 는 **중복 전달**이 가능하다 (V-03)

표준 큐는 최소 1회 전달이라 **같은 메시지가 두 번 올 수 있다.**
🟢 우리는 이미 막혀 있다 — 워커가 시작할 때 `get_cached` 를 다시 보면 두 번째는 캐시 히트로 끝난다.
🔴 **단 워커 진입부에 그 체크를 넣어야 한다.** 지금은 접수 쪽에만 있다.

### ③ 실패가 조용해진다

BackgroundTasks 는 같은 프로세스라 예외가 로그에 남았다. 분할하면 **워커의 실패는 큐 재시도 뒤 DLQ 로 간다.**
🔴 **DLQ 에 쌓여도 사용자 잡 상태는 `PENDING` 그대로**다 — 영원히 기다린다.
→ 워커가 **마지막 시도에서 `put_job(FAILED)`** 를 남겨야 한다. `approximateReceiveCount` 로 판단한다.

### ④ 접수 함수가 Valkey 와 SQS 둘 다 쓴다

지금 `ocr`·`video` 는 Valkey 만 쓴다. 분할하면 **접수가 SQS 에도 써야** 한다 → 실행 역할에 `sqs:SendMessage`(`mp-ai-*`) 필요.
🟢 권한 안내문의 `mp-ai-api` 역할에 이미 들어 있다.

## 4. 🔴 `ocr` — 선행 결정 1건 (G-06)

**이미지가 워커까지 갈 길이 없다.**

| 경로 | 상한 | 8MB 이미지 |
|---|---:|:--:|
| ALB → Lambda 요청 본문 | **1 MB** | ❌ |
| SQS 메시지 본문 | **256 KB** | ❌ |
| Lambda 동기 호출 payload | 6 MB | ❌ |

현행 상한은 `settings.max_image_bytes = 8MB` 다. **어느 경로로도 안 들어간다.**

### 선택지

| | 방식 | 대가 |
|---|---|---|
| **A** | **프리사인드 S3 PUT** — 접수가 URL 을 주고 **클라이언트가 S3 에 직접 올린다**. 업로드 완료 후 접수 호출 또는 S3 이벤트로 워커 기동 | 🔴 **프론트 계약이 바뀐다**(1단계 → 2단계) · 🔴 **«원본 미저장» 원칙 변경** — 수명주기 규칙(예: 1일 만료)이 함께 필요 |
| **B** | **상한을 1MB 로 낮춘다** | 🔴 영수증 사진이 대개 1MB 를 넘는다. 프론트에서 축소해야 하는데 **품질이 OCR 정확도에 직결**된다 |
| **C** | **ocr 만 EKS 에 남긴다** | 🟢 오늘 당장 됨 · 🔴 AI 12함수 중 2개가 안 넘어감 |

**의견 — A 가 정답이나 결정 사항이 둘 붙는다**(프론트 계약 · 원본 저장 정책). **둘 다 제 소관이 아니다.**
🟢 참고 — `image_max_side = 1600px` 축소가 이미 파이프라인에 있다. 그걸 **클라이언트로 옮기면** B 가 현실성이 생긴다.
