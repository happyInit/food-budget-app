# 랭킹 재학습 경로 설계 (2026-08-17)

> 발단 = 리뷰 지적 *"모델을 만드는 주체가 어디에도 없다"*. 맞습니다. 그런데 조사해 보니
> **끊긴 곳이 하나가 아니라 셋**이고, 위에서부터 풀지 않으면 아래를 고쳐도 소용이 없습니다.

| 층 | 상태 | 이걸 안 풀면 |
|---|---|---|
| ① **라벨** | 🔴 **조인 가능한 양성 라벨 0건** | 재학습을 돌려도 **학습할 것이 없다** |
| ② **실행 주체** | 🔴 양 사이트 CronJob 0개 · 온프렘 모델은 08-07 수동 산출물 | 모델이 영원히 안 바뀐다 |
| ③ **전달 경로** | 🔴 EKS 는 `readOnlyRootFilesystem` + 모델이 **이미지 안**(C-20) | 새 모델을 만들어도 **넣을 자리가 없다** |

## 1. 실측 — 지금 무엇이 있고 없나

### 1.1 라벨 (2026-08-17 · 양 사이트 동일)

```
activity.user_event         37건   session_id 전부 NULL   2026-07-22 하루치
activity.recipe_impression 320건   session_id 전부 있음   2026-07-21~22
조인 가능한 양성 라벨         0건
```

🔵 **프론트는 이미 고쳐져 있습니다.** `1aa85a3`(#637)이 `session_id` 를 보내고, 배포 이미지에도
들어 있습니다. 위 37건은 **그 수정 이전(7/22)** 데이터라 NULL 인 것이고, 그 뒤로 새 데이터가
없어서 검증된 적이 없습니다.

🔴 그리고 **노출 기록이 조용히 실패하고 있습니다**(2026-08-16 확인). 추천 3건이 화면에 떴는데
`recipe_impression` 은 0건이었습니다. 설정·권한·스키마·프론트 전부 정상이라 원인 미상이고,
관측을 붙였습니다(MR !40). **이게 안 풀리면 트래픽이 생겨도 라벨이 안 쌓입니다.**

### 1.2 재학습 기계 — **이미 다 있습니다**

`ml/recipe-ranking/retrain.py`:
```
extract(피처행) → to_matrix → train → save_model(RANKING_MODEL_PATH) → /reload 호출
게이트: RETRAIN_MIN_ROWS=200 · RETRAIN_MIN_GROUPS=20 · RETRAIN_DAYS=90
```
`serve.py` 의 `POST /reload` 가 **떠 있는 채로 모델만 교체**합니다(재기동 불요, 실패 시 기존 유지).

⇒ **새로 만들 로직이 없습니다.** 문제는 *"이걸 어디서 돌리고, 결과를 어떻게 EKS 로 옮기느냐"* 뿐입니다.

### 1.3 전달 경로가 사이트마다 다릅니다 — 여기가 핵심

| | 온프렘 | EKS |
|---|---|---|
| 모델 자리 | **PVC** `/models/ranker.pkl` | **이미지 안** `/app/ranker.pkl` (C-20) |
| 루트FS | 쓰기 가능 | **`readOnlyRootFilesystem: true`** |
| `/reload` | 🟢 쓸 수 있다 (PVC 에 새 파일 쓰고 호출) | 🔴 **쓸 수 없다** — 쓸 자리가 없다 |

🔴 **이것이 설계의 제약입니다.** 온프렘식 루프(파일 쓰기 + `/reload`)를 EKS 에 그대로 옮길 수
없습니다. EKS 에서 모델을 바꾸려면 **이미지를 다시 굽는 것 말고는 방법이 없습니다.**

## 2. 방안 4가지

### A. 재학습을 EKS CronJob 으로 + 결과를 S3 → CI 재빌드
```
CronJob(주 1회) → retrain → ranker.pkl → S3(mp-ai-model-ap2)
                → GitLab 파이프라인 트리거 → 이미지 재빌드 → ArgoCD 배포
```
- 🟢 C-20 형상과 정합. 모델이 **이미지 신원과 함께** 버전 관리된다(롤백 = 이미지 태그 하나)
- 🔴 모델 반영에 **빌드+배포 한 사이클**이 걸린다(수분~십수분). 랭킹 모델에는 문제가 안 된다
- 🔴 CronJob 이 CI 를 트리거해야 한다 — 파이프라인 토큰이 클러스터 안에 생긴다

### B. 재학습 후 S3 에 두고, 파드가 기동 시 받아 오기(initContainer)
```
CronJob → retrain → S3 → (파드 재시작 시) initContainer 가 S3 에서 받아 emptyDir 에
```
- 🟢 재빌드 불요. 모델 교체가 **rollout restart 한 번**
- 🔴 **C-20 을 뒤집는다**(PVC 소거의 취지가 "굽는다"였다). 그리고 `mp-ranking-serving` SA 에
  **IRSA 가 없어** 새 롤이 필요하다 — 권한 작업이 A 보다 크다
- 🔴 이미지와 모델의 신원이 갈린다 — *"어느 모델로 돌고 있었나"* 를 이미지 태그로 못 답한다

### C. 온프렘에서만 재학습하고 산출물을 S3 로 올리기
```
온프렘 CronJob → retrain(PVC 에 쓰기 + /reload) → 같은 파일을 S3 에 업로드
                → EKS 는 A 와 같은 경로로 이미지에 굽는다
```
- 🟢 온프렘은 **기존 루프를 그대로** 쓴다(무중단 교체가 살아 있다)
- 🟢 EKS 는 S3 만 보면 된다
- 🔴 **온프렘 의존이 영구화**된다. C-70 이 온프렘을 축소 대상으로 두는 방향과 어긋난다
- 🔴 학습 데이터가 **온프렘 PG** 기준이 된다 — EKS 가 프로덕션이 되면 데이터가 반대편에 있다

### D. Lambda 로 재학습
- 🔴 **부적합.** LightGBM 학습은 CPU·메모리를 오래 쓰고, `rank-serve` 와 같은 이유로
  libgomp 때문에 zip 이 안 된다(컨테이너 이미지 강제). 15분 상한도 위험하다.
  **배치 학습은 Lambda 의 모양이 아닙니다.**

## 3. 🟢 권고 — **A안**, 단 ①이 풀린 뒤에

### 3.1 왜 A인가

1. **C-20 과 싸우지 않습니다.** 모델이 이미지 안에 있다는 형상이 유지되고, *"어느 모델로 돌았나"* 가
   **이미지 태그 하나로** 답해집니다. B는 그 성질을 깨고, 그 대가로 사고 조사 때 비쌉니다.
2. **새 IAM 이 가장 적습니다.** A 는 이미 요청해 둔 `mp-ci-job` 의 S3 읽기를 그대로 씁니다.
   B 는 파드용 IRSA 롤을 **새로** 만들어야 합니다(현재 `mp-ranking-serving` SA 에 롤 없음).
3. **반영 지연이 문제가 안 됩니다.** 랭킹 모델은 주 1회 갱신이면 충분합니다(현행 게이트도
   `RETRAIN_DAYS=90`). 초 단위 반영이 필요한 종류가 아닙니다.
4. C 는 **온프렘 의존을 영구화**합니다. 지금 온프렘이 꺼져 있어 Harbor 조차 못 쓰는 상황
   (2026-08-17 실측)을 보면, 학습 경로를 거기 묶는 것은 위험합니다.

### 3.2 단계 — 순서가 중요합니다

```
0단계 (선행 · 지금)   임프레션 조용한 실패 해소 → 라벨이 실제로 쌓이는지 확인   ← MR !40 배포 후 관측
1단계                 라벨 게이트 도달 대기 (200행 · 20그룹)                    ← 사용량이 필요하다
2단계                 EKS CronJob `mp-ai-ranking-retrain` 신설 (주 1회)
3단계                 산출물 → S3 `mp-ai-model-ap2/models/ranking/ranker.pkl`
4단계                 CI 트리거 → 이미지 재빌드 → ArgoCD 배포
```

🔴 **0·1단계를 건너뛰고 2단계부터 만들면 «돌지만 아무것도 안 하는 CronJob»** 이 생깁니다.
그건 초록으로 보여서 더 나쁩니다 — 오늘 임프레션이 정확히 그 모양이었습니다.

### 3.3 2단계의 구체

| | |
|---|---|
| 이름 | `mp-ai-ranking-retrain` (pipeline ns) |
| 스케줄 | `0 18 * * 0` (일 03:00 KST) — 리뷰 배치와 겹치지 않게 |
| 이미지 | `mp-data-pipeline` **아님** — lightgbm+libgomp 가 필요해 **전용 이미지**가 있어야 한다 |
| 롤 | `svc_pipeline`(PG 읽기) + S3 쓰기용 IRSA |
| 게이트 | 기존 `RETRAIN_MIN_ROWS`·`MIN_GROUPS` 그대로 — 미달이면 **아무것도 안 하고 끝난다** |
| 실패 | 조용하면 안 된다 — 로그에 사유·행수를 남긴다(임프레션 사고의 교훈) |

🔴 **전용 이미지가 필요하다는 것이 A안의 유일한 새 비용**입니다. `rank-serve` 도 같은 이유로
이미지가 강제되므로(설계서 §패키징), **두 개가 베이스를 공유**하게 만들면 한 번만 지불합니다.

## 5. 미결 — 결정이 필요한 것

1. **온프렘 랭킹 스위치** — 모델은 있는데(`model_loaded: true`) `RANKING_ML_ENABLED=false` 라
   안 쓰입니다. 08-07 모델은 실제 라벨로 학습된 것이 아니므로, 켜면 **규칙 랭킹(재고·임박·예산)을
   근거 없는 재정렬로 덮습니다.** 권고 = **켜지 않는다.**
2. **합성 라벨 사용 여부** — §4 의 단서와 함께 팀 판단.
3. **전용 이미지 베이스** — `rank-serve` 와 공유할지.
