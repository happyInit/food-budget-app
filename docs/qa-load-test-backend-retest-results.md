# 백엔드 성능 개선 재검증 결과서

> 작성일: 2026-07-20
>
> 대상: Food Budget App 백엔드 개발팀
>
> 목적: `qa-load-test-backend-handoff.md`(2026-07-19)에서 전달한 개선 요청에 대해 백엔드가 코드 수정을 완료했다는 보고를 받고, **동일 조건으로 재검증**한 결과를 공유한다. 무엇이 실제로 해결됐고 무엇이 남아있는지, 그리고 예상하지 못했던 회귀(regression)를 함께 정리한다.

## 1. 요약

1. **Price는 해결됨** — 개선 전 초 단위였던 응답시간이 ms 단위로 떨어졌다.
2. **MealPlan은 부분 해결** — 100VU 단일 지점 응답시간은 개선됐지만(2,314ms→841ms), 계단식(50/100/150/200VU) 재검증 결과 커넥션 풀(`max_size=10`, 하드코딩)이 **50VU부터 이미 포화** 상태다. 이번 개선 작업에서 mealplan만 풀 크기 env 조정 대상에서 빠져있었다. (§3.3 참고)
3. **Login은 두 차례 재검증 끝에 30VU는 해결, 50VU 이상은 CPU 포화가 남아있다** — bcrypt 오프로드는 코드상 해결됐지만(커밋 `04de7ff`) 1차 재검증에서 CPU 쿼터(`cpus: 0.75`) 문제가 드러났고, 이후 백엔드가 `cpus: 0.75→2.0` 상향 + signup/login 레이스 수정(커밋 `053fbd9`, `098d3ba`)을 반영했다. 2차 재검증 결과 **30VU(원본 조건)는 3,493ms→497ms로 실질 해결**됐지만, **100VU 이상에서는 여전히 CPU가 병목**이다 — 런타임 메트릭으로 직접 확인한 결과 account CPU가 한도(2.0코어)의 98%까지 포화되고, PG active 커넥션은 0이라 DB 풀 문제가 아님을 확인했다(최초엔 DB 풀 문제로 잘못 추정했으나 정정). (§3.1 참고)
4. **Chat은 예상 밖으로 악화(regression)됐고, 원인도 확인됨** — 다른 서비스는 다 좋아졌는데 Chat만 응답시간이 약 2배로 늘었다. 트레이스 분석 결과 미계측·미인덱스 쿼리(`PgRecipeNameSource`의 ILIKE 검색)가 원인 후보로 특정됐다. (§3.4 참고)
5. **혼합·피크 시나리오는 극적으로 개선**됐지만, 이 결과를 "전체 시스템이 좋아졌다"로 해석하면 안 된다 — 재검증 스크립트가 Login 병목을 의도적으로 우회하는 구조라, Login 미해결 문제가 이 결과에 반영되지 않았다. (§4.4 참고)
6. **MealPlan의 "커넥션 풀 확장" 요청은 재검토했다** — PostgreSQL `max_connections`(기본값 100)를 8개 앱 서비스가 나눠 쓰는데 이미 합계 60개를 쓰고 있어, "VUser 수만큼 풀을 늘려라"는 처방은 예산을 넘길 위험이 있다. "먼저 실제 필요한 규모를 판단하고, DB 전체 예산 안에서 조정하라"는 형태로 요청을 다시 구성했다. (§6.0 참고) Login은 런타임 증거로 DB 풀이 원인이 아님을 확인해 이 예산 문제와 무관하다 — 대신 CPU/rate limiting 관점으로 재구성했다(§3.1·§6 참고).
7. **모든 서비스에 대해 nGrinder 평균값만으로 판정하지 않고, P95/P99(Tempo)·컨테이너 CPU(Prometheus)까지 재확인했다** — Price·혼합(300VU)·피크(500VU)는 P95/P99도 낮고(각각 6ms/28ms/12ms) CPU도 여유(18.7% 이하)로 확인돼 기존 "해결" 판정이 더 탄탄해졌다. Login만 CPU 근거로 결론이 바뀌었다.

## 2. 재검증 방법

### 2.1 원칙 — 동일 조건 재현

기준값을 만들어낸 원본 테스트와 **VUser 수, 스크립트, duration을 동일하게** 맞춰야 개선 여부를 공정하게 판단할 수 있다. 조건이 다르면 "좋아졌다"는 게 실제 개선인지 테스트 조건 차이인지 구분할 수 없다.

### 2.2 축소 재검증 — 전체 재실행 대신 병목 지점만

3단계·4단계 전체를 다시 계단식으로 돌리면 시간이 지나치게 오래 걸려, **원래 병목이 확인됐던 지점만** 골라 재검증했다.

### 2.3 관찰 지표

원본과 동일하게 nGrinder TPS·평균 응답시간·오류 수를 기본으로 사용했다. Login은 nGrinder 자체가 중단되어, 원인 확인을 위해 **nGrinder 밖에서 직접 curl로 동시 요청을 재현**하는 방식을 추가했다(§3.1 참고).

## 3. 서비스별 단독 재검증 결과

### 3.1 Login (원본 P1)

| 구분 | VUser | 평균 응답시간 | 오류 |
|---|---:|---:|---|
| 개선 전(기준값) | 30 | 약 3,493ms | 약 1.4% |
| 1차 재검증(CPU 0.75, 수정 전) | 30 | 측정 불가 — nGrinder가 **"Too many errors"로 자동 중단**(약 20초 경과 시점, 18건 시도 중 30건 오류) | — |

**1차 재검증 — 직접 재현 결과**: nGrinder 밖에서 동일 계정으로 로그인 요청 30개를 동시에 발사했다.

```text
200 응답 14건 — 응답시간 1.9초~5.7초 (전부 원본 기준값 3.5초보다 느리거나 비슷한 수준)
타임아웃(6초) 16건 — 절반 이상이 아예 응답을 받지 못함
```

**1차 판정: 1차 병목 해결, 2차 병목(CPU 쿼터) 노출.** 코드를 직접 확인한 결과 `services/account/app/routers.py`에 이미 `asyncio.to_thread`로 bcrypt를 오프로드하는 수정이 적용돼 있었다(커밋 `04de7ff`, "로그인 bcrypt를 asyncio.to_thread로 오프로드 — 이벤트루프 블로킹 제거"). 즉 원래 진단이던 "이벤트 루프 블로킹"은 실제로 해결된 코드다.

그런데도 부하테스트에서 여전히(혹은 더 심하게) 타임아웃이 나는 이유는, `deploy/app/docker-compose.yml`의 `x-svc-common` 공통 설정에서 account를 포함한 전 서비스가 **`cpus: 0.75`로 제한**돼 있기 때문으로 보였다. 스레드 오프로드는 "이벤트 루프가 안 막히게" 할 뿐 CPU 자체를 늘려주지 않으므로, bcrypt처럼 CPU를 실제로 많이 쓰는 연산은 스레드로 돌려도 결국 같은 0.75 CPU 쿼터 안에서 대기하게 된다.

#### 2차 재검증 — happyinit의 후속 수정 반영 후

이후 백엔드에서 관련 커밋 2개가 추가로 들어왔다.

- `053fbd9 perf(account): 로그인 병목 대응 — account CPU 0.75→2.0·mem 512m 상향`
- `098d3ba fix(account): signup 직후 login 401 레이스 — 풀 커넥션 autocommit`

동일 조건(30VU) + 추가로 50/100/200VU 계단식까지 재검증했다.

| VUser | 성공(tests) | 오류 | 평균 응답시간 | TPS |
|---:|---:|---:|---:|---:|
| 30(원본 조건) | 415 | 8 | **497.38ms** | 7.97 |
| 50 | 427 | 0 | 2,972.16ms | 8.37 |
| 100 | 17 | **528** | 5,663.0ms | 0.33 |
| 200 | 25 | **1,045** | 5,348.2ms | 0.49 |

**30VU(원본과 동일 조건) 비교**: 3,493ms → **497.38ms**(약 86% 감소), 오류율 1.4%→1.89%(비슷한 수준, 유의미한 악화 아님). **CPU 상향이 30VU 기준으로는 실질적으로 해결됐다.**

**그러나 50VU를 넘어가면 완전히 새로운 병목이 나타난다.** 100VU에서 성공(17건)보다 오류(528건)가 30배 이상 많고, 200VU도 마찬가지(25 성공 vs 1,045 오류)다. 응답시간도 5,3~5,7초로 스크립트의 6초 타임아웃에 바짝 붙어있다 — 사실상 대부분의 요청이 타임아웃 직전까지 대기하다 실패하는 것으로 보인다.

**최초 원인 추정(코드만 보고 추론, 이후 정정됨)**: `services/account/app/config.py`의 `pg_pool_max` 기본값이 여전히 10이라 §3.3 MealPlan과 같은 DB 풀 부족 패턴일 것으로 추정했었다.

**실제 런타임 증거로 재확인한 결과, 이 추정은 틀렸다.** 100VU 구간의 Prometheus 메트릭을 직접 확인했다.

| 지표 | 값 |
|---|---|
| account 컨테이너 CPU (최대) | **195.8%** (한도 `cpus: 2.0`=200%의 약 98%) |
| account 컨테이너 CPU (평균) | 129.6% |
| PG `active`(쿼리 실행 중) 커넥션 | **0** |
| PG `idle in transaction` 커넥션 | 0 |

**PG 커넥션은 전혀 바쁘지 않다(active 0건) — DB 풀은 병목이 아니다.** 반면 account CPU는 한도(2.0코어)의 98%까지 완전히 포화돼 있다. 즉 **여전히 순수 CPU 문제**다 — bcrypt 연산이 100명 이상 동시 요청에서는 2.0코어로도 부족한 것으로 확인됐다.

**판정: 30VU 기준 해결(런타임 증거로 재확인 완료), 50VU 이상에서 CPU 포화로 인한 병목 지속.** DB 풀 확장은 근거가 없어 요청에서 제외한다.

**해결 방향** (팀장 피드백 반영 — "동시접속자 수만큼 무작정 늘리는" 처방 지양, §6.0 참고):
1. **먼저**: 실제 동시 로그인 피크가 현실적으로 얼마나 되는지부터 판단(DAU 500 기준 추정). 그 값이 50 이하라면 **지금 상태(CPU 2.0코어)로 이미 충분** — 추가 조치 불필요
2. 그래도 100VU 이상 동시 로그인 대응이 필요하다는 결론이면, 아래 중 검토:
   - **로그인 rate limiting/계정 잠금 도입** — `design/mp_k8s_security_design.md` P0 항목이자 미구현 상태. 브루트포스 방어와 동시에 비현실적인 동시 로그인 폭주로부터 서버도 보호하는 효과
   - **account 수평 확장(replica)** — CPU를 한 컨테이너에 더 몰아주는 것보다, 여러 인스턴스로 bcrypt 연산을 분산하는 게 호스트 전체 코어(6코어) 활용 관점에서 더 합리적일 수 있음
3. bcrypt 비용 인자를 낮추는 방식은 이번에도 개선안으로 인정하지 않는다
4. 조치 후 동일 계단식(30/50/100/200VU)으로 재검증 필요

### 3.2 Price (원본 P0)

| 구분 | VUser | TPS | 평균 응답시간 | 오류 |
|---|---:|---:|---:|---|
| 개선 전(기준값) | 200 | 58.2 | 1,407ms | 0 |
| 재검증 | 200 | **94.98** | **4.48ms** | 0 |

peak TPS 116, 총 9,984건 처리, 오류 0건.

**추가 검증(3층 기준 전부 확인)**: 평균값만이 아니라 Tempo 트레이스로 percentile을, Prometheus로 컨테이너 CPU를 직접 확인했다.
- P50 **1ms**, P95 **2ms**, P99 **6ms** (샘플 500건)
- price 컨테이너 CPU: 최대 **18.7%**, 평균 7.4% (한도 대비 여유 큼)

**판정: 해결.** 응답시간이 약 99.7% 감소했고, percentile·CPU 둘 다 여유로워 재발 우려도 낮다. §8에서 요청한 DB 인덱스·연결 풀·캐싱 개선 중 하나 이상이 실제로 적용된 것으로 보인다. **완료 확인**.

### 3.3 MealPlan (원본 P1)

| 구분 | VUser | 평균 응답시간 | 오류 |
|---|---:|---:|---|
| 개선 전(기준값) | 100 | 약 2,314ms | — |
| 재검증(1차) | 100 | **840.97ms** | 0 |

peak TPS 189, TPS 119.57, 총 9,811건 처리, 오류 0건.

**1차 판정(100VU 단일 지점만 봤을 때): 해결.** 응답시간이 약 64% 감소했다.

**그러나 계단식(50/100/150/200VU) 재검증 결과, 완전히 해결된 게 아니라 구조적 한계가 남아있는 것으로 확인됐다.**

| VUser | TPS | 평균 응답시간 | 오류 |
|---:|---:|---:|---:|
| 50 | 116.96 | 427.33ms | 0 |
| 100 | 114.89 | 879.47ms | 0 |
| 150 | 111.49 | 1,326.45ms | 15 |
| 200 | 105.76 | 1,887.05ms | 0 |

TPS가 **50VU 시점부터 이미 110~117 사이에서 고정**되고(VUser를 4배 늘려도 TPS는 오히려 소폭 감소), 응답시간은 **VUser에 거의 비례해서 계속 증가**한다(427ms→1,887ms). 이는 처리량은 늘지 않고 대기시간만 쌓이는 전형적인 커넥션 풀 포화 패턴이다.

코드 확인 결과 `services/mealplan/app/db.py`의 PostgreSQL 커넥션 풀이 `min_size=1, max_size=10`으로 **하드코딩**돼 있었다. 이번 개선 작업(커밋 `04de7ff`)에서 account·chat·notify·price 4개 서비스는 풀 크기를 env로 조정 가능하게 바꿨는데, **mealplan은 그 대상에서 빠져있다.**

트레이스로도 확인된다. 계단식 재검증 중(100VU) 관측된 트레이스 하나를 span 단위로 분해하면:

| Span | 소요시간 |
|---|---:|
| `GET /api/expenses/summary` (전체) | 896.8ms |
| `GET`(budget 조회, client) | 12.6ms |
| `GET`(pantry 조회, client) | 11.1ms |
| `select`(month_spent) | 6.4ms |
| `foodbudget` | 3.7ms |
| `pantry GET /api/pantry/stats`(서버측) | 1.9ms |
| `account GET /api/users/budget`(서버측) | 1.6ms |
| 기타 | <1ms |

식별 가능한 하위 span 합계는 38.5ms뿐이고, 나머지 858ms(96%)는 트레이스에 안 잡히는 구간이다. 커넥션 풀 체크아웃 대기 시간은 쿼리 실행 전에 발생해 span으로 안 잡히므로, 이 수치와 정확히 부합한다.

**판정: 부분 해결.** 100VU 단일 지점 응답시간은 개선됐지만, **50VU 이상에서는 구조적으로 포화 상태**다. 완료 확인 아님 — 커넥션 풀 크기 자체를 늘려야 한다.

### 3.4 Chat (원본 P1) — 회귀(regression) 발견

| 구분 | VUser | TPS | 평균 응답시간 | 오류 |
|---|---:|---:|---:|---|
| 개선 전(기준값) | 150 | 38.7 | 623ms | 0 |
| 재검증 | 150 | **32.7** | **1,364.94ms** | 0 |

Chat 스크립트는 로그인을 전혀 사용하지 않고 `/api/mealplan/assistant/chat`만 순수 호출하므로, Login 미해결 문제가 섞여서 나온 결과가 아니다.

**원인을 Tempo 트레이스로 특정했다.** 재검증 중 가장 느린 트레이스(2,393ms)를 span 단위로 분해한 결과:

| Span | 소요시간 |
|---|---:|
| `POST /api/mealplan/assistant/chat` (전체) | 2,393.0ms |
| `chat.search` | 2,387.0ms |
| ├ `select` | 202.8ms |
| ├ `elasticsearch.recipe` | 2.8ms |
| └ (기타 Redis 등) | <2ms |

`chat.search`의 하위 span 합계는 208ms뿐인데, 전체는 2,387ms다. **약 2,179ms(91%)가 트레이스에 안 잡히는 구간**이다.

코드(`services/chat/app/pipeline/search.py`)를 확인하니, `chat.search`는 5개 검색 소스를 병렬 호출하는데(`asyncio.gather`) 그중 `PgRecipeNameSource`(레시피 이름 폴백 검색)만 유일하게 `start_span`으로 트레이싱되어 있지 않다. 이 소스의 쿼리는:

```sql
where name ilike '%단어%'   -- 양쪽 와일드카드
```

양쪽 와일드카드 `ILIKE`는 일반 B-tree 인덱스를 사용할 수 없어 테이블이 커질수록 전체 스캔 비용이 늘어난다. 최근 레시피 관련 데이터가 계속 추가되고 있어(git 이력 확인), 회귀 시점과 맞물릴 가능성이 있다.

**판정: 악화(회귀), 원인 확인됨.** `PgRecipeNameSource`의 미계측·미인덱스 쿼리가 유력한 원인이다.

**요청**:
1. `recipe.name`에 `ILIKE '%word%'` 패턴 검색용 인덱스(`pg_trgm` extension + GIN 인덱스 등) 적용 검토
2. `PgRecipeNameSource.search()`에 `start_span("postgres.recipe_name")` 계측 추가(재발 방지 — 지금까지 이 문제가 트레이스에 안 보였던 이유)
3. 조치 후 동일 조건(150VU)으로 재검증

### 3.5 Recipebook (원본 미포함 — 신규 단독 계단식)

원본 문서(§4.1 전체 요약)에는 Recipebook 단독 테스트가 없었고, 300VU 혼합 시나리오에 낮은 비중으로만 포함돼 있었다. 9개 서비스 전수 점검 과정에서 단독 계단식 테스트가 없다는 게 확인돼, 이번에 처음으로 30/50/100/150/200VU 계단식을 새로 실행했다(`baseline-recipebook.groovy` 신규 작성, `GET /api/recipes/book` 대상).

| VUser | TPS | 평균 응답시간 | 오류 |
|---:|---:|---:|---:|
| 30 | 302.72 | 98.95ms | 0 |
| 50 | 303.1 | 164.79ms | 0 |
| 100 | 303.41 | 328.77ms | 0 |

3층 판정 기준을 전부 확인했다.

1. **사용자 증상**: 오류 0건. 200VU 구간 Tempo 트레이스 500건 샘플 기준 P50 72ms, **P95 261ms, P99 539ms**, 최대 638ms — 초 단위로 튀는 값 없음(Chat·MealPlan·Login 대비 훨씬 양호).

**혼합 시나리오(300VU, id=70) 추가 확인**: 같은 창구에서 Tempo로 recipebook 트레이스 50건 샘플 확인 — 평균 2.94ms, 최대 9ms로 혼합 부하에서는 전혀 병목이 아니다(원본 문서 300VU 수치 9.04ms와도 일관됨).

**판정**: Pantry·Notify와 동일한 **P2(낮은 우선순위) 병목**. 오류·P95/P99가 위험 수준은 아니라 급한 조치는 불필요하지만, "완전히 문제없음"은 아니다 — CPU 쿼터 근접으로 인한 처리량 한계가 3층 기준 전부로 확인됨.

**요청**: 급한 조치 불필요. 목표 트래픽이 300 TPS 이상으로 커지면 CPU limit 상향 검토(원본 문서 §4.6 Pantry 판정과 동일한 기준 적용).

### 4.3 Kafka·Redis — 핫딜 시나리오 (DB개발자 요청 대응)

nGrinder가 아니라 `confluent_kafka`/`redis` 라이브러리를 직접 사용하는 Python 스크립트로 실행했다(HTTP 요청이 아니라 Kafka 메시지 발행이라 nGrinder 대상이 아님).

#### 4.3.1 1차: 딜 데이터 순수 적재 (100/500/1,000건)

오아시스를 직접 호출하지 않고, 실제 크롤 스키마(`crawler/oasis/output/*.jsonl`)를 그대로 따르는 합성 테스트 메시지만 사용했다. 흐름: `테스트 딜 메시지 → Kafka(retail.deal.raw) → deal-notifier → PostgreSQL·Redis`.

| 배치 | Produce | Consume(success) | Consumer Lag | 처리시간 |
|---|---:|---:|---:|---:|
| 1차 | 100 | 100 | 0으로 즉시 복귀 | <5초 |
| 2차 | 500 | 500(누적 600) | 0으로 즉시 복귀 | <4초 |
| 3차 | 1,000 | 1,000(누적 1,600) | 0으로 즉시 복귀 | <4초 |

Redis 정합성을 직접 조회해 확인했다 — `retail:deals:detail`(hash) 1,600건, `retail:deals:active`(zset) 1,600건, 전부 테스트 태그(`TEST-`)와 정확히 일치. **손실·중복 없음.** PostgreSQL은 직접 접속 권한이 없어(§8 참고) `fb_pipeline_records_total{result="success"}` 메트릭(PG 커밋 성공 후에만 증가)으로 간접 확인했다.

**판정: 문제 없음.** 원본 문서의 "딜=저볼륨"(파티션 2개) 가정이 최소 1,000건 규모에서는 유효한 것으로 보인다.

참고로 실제 오아시스 딜(`timeSale`/`closeSale`) 건수를 크롤 데이터에서 확인하려 했으나, 보유한 크롤 파일(`oasis_products_20260713.jsonl`, 1,930건)에 딜 타입 레코드가 0건이라 **실제 운영 규모는 미실측**이다. 딜 크롤 시각(15시/17시)에 맞춰 별도로 실측이 필요하다.

#### 4.3.2 2차: 딜 적재(쓰기) + 사용자 조회(읽기) 동시 스파이크

**설계 근거**: 딜 데이터는 정해진 시각에 한 번에 폴링되고(지속 유입 아님) Redis에 저장돼 다음 폴링까지 서빙만 되는 구조다. 따라서 실제로 부하가 겹치는 순간은 "딜이 올라온 직후 사용자들이 몰려 새로고침하는 짧은 구간"이다. 이를 재현하기 위해 **Kafka 딜 버스트(1,000건)** 와 **Price hotdeals 읽기 스파이크(nGrinder, `baseline-price.groovy`, 400VU)** 를 같은 순간(nGrinder가 `TESTING` 상태로 진입한 직후)에 발사했다.

| 구분 | 단독 읽기(200VU, §3.2 기준) | **동시(400VU 읽기 + 1,000건 쓰기 겹침)** |
|---|---:|---:|
| TPS | 94.98 | **199.03** |
| 평균 응답시간 | 4.48ms | **4.28ms** |
| 오류 | 0 | 0 |
| Kafka Consumer Lag | — | 겹치는 구간 내내 0 |

VUser를 2배(200→400)로 늘리고 동시에 Kafka 딜 1,000건을 겹쳐 밀어넣었는데도 응답시간이 오히려 소폭 더 빨랐다. Redis 상태도 여유로웠다: `connected_clients` 7, `used_memory` 2.64MB(한도 256MB의 약 1%), `evicted_keys` 0, 캐시 히트율 약 69%.

**판정: 문제 없음.** 순수 적재(4.3.1)와 read+write 동시(4.3.2) 두 각도 모두에서 Kafka·Redis 튜닝이 필요하다는 증거를 찾지 못했다.

**DB개발자에게 줄 결론**: 지금 규모(딜 1,000건, 동시 읽기 400VU)에서는 Kafka·Redis 둘 다 튜닝 권고를 낼 근거가 없다. 대신 예방적 권고만 제시한다.
1. Kafka: 실제 딜 건수를 15시/17시 크롤 시점에 실측해, 1,000건에 근접하면 파티션(현재 2개) 증설 검토
2. Redis: 지금 당장 조정 불필요하나 `evicted_keys` 지표에 알람을 걸어 실제 운영에서 축출이 시작되면 즉시 인지할 수 있게 할 것
3. 더 높은 규모(수만 건, 수천 VUser)에서의 진짜 임계점은 확인되지 않았음 — 필요 시 추가 테스트

### 4.4 ⚠️ 해석 시 반드시 주의할 점 — Login 우회

4.1·4.2에 쓰인 `mixed-capacity-journey.groovy` 스크립트는 **테스트 시작 시 토큰을 딱 한 번만 발급받고, 측정 구간에는 로그인을 아예 포함하지 않는다** (원본 handoff 문서 §3.1에도 "인증이 필요한 서비스는 로그인 병목이 섞이지 않도록 미리 발급한 공유 토큰을 사용했다"고 명시). 즉 이 스크립트는 **Login 병목을 의도적으로 우회하도록 설계**돼 있다.

따라서 4.1·4.2의 극적인 개선 결과는 **"Login도 포함해서 전체 시스템이 좋아졌다"는 뜻이 아니다.** §3.1에서 확인했듯 30VU는 해결됐지만 100VU 이상에서는 CPU 포화 병목이 남아있어서, 실제 서비스에서 사용자가 몰리는 시간대(예: 명절, 피크타임)에 로그인이 100명 이상 동시에 몰리면 여전히 문제가 발생할 수 있다.

| Kafka·Redis(핫딜) | 1,000건 + 400VU 동시 | ✅ 문제 없음 | 순수 적재·read+write 동시 두 각도 다 이상 없음. 단, 실제 딜 건수 미실측 — §4.3 참고 |
| Recipebook | 30~200VU(계단식, 신규) | ⚠️ P2 병목(경미) | 오류 0건, P95 261ms·P99 539ms로 심각하지 않지만, TPS가 30VU부터 ~300에서 고정되고 컨테이너 CPU가 최대 68.1%(한도 75%)까지 도달 — Pantry·Notify와 동급의 낮은 우선순위 병목으로 확인 |

## 6. 백엔드에 다시 요청하는 사항

### 6.0 ⚠️ 먼저 확인할 것 — 커넥션 풀은 "동시접속자 수만큼" 늘리는 게 아니다

MealPlan·Login 둘 다 원인이 "PG 커넥션 풀 부족"으로 나왔다고 해서, 곧바로 "VUser 수만큼 풀을 키워라"는 요청은 **잘못된 처방**이다. PostgreSQL 자체의 `max_connections`가 무한하지 않고(설정을 따로 안 올려서 기본값 100 그대로), 이미 여러 서비스가 같은 PG 인스턴스를 나눠 쓰고 있다.

**현재 서비스별 pool_max 합계**:

| 서비스 | pool_max |
|---|---:|
| account | 10 |
| mealplan | 10(하드코딩) |
| pantry | 10(하드코딩) |
| recipe | 10(하드코딩) |
| chat | 5 |
| notify | 5 |
| price | 5 |
| recipebook | 5(하드코딩) |
| **앱 서비스 합계** | **60** |

여기에 데이터 파이프라인 컨슈머 4개(retail-refiner·deal-notifier·recipe-refiner·deal-pruner), PGSync 복제 슬롯, postgres-exporter까지 더하면 **100개 한도에 이미 근접한 상태다.** 이 상태에서 account나 mealplan 하나만 "VUser 200명 감당하게 풀 200개로" 요청하면, 다른 서비스 몫까지 합쳐 한도를 넘기거나 서로의 여유분을 갉아먹는다. **커넥션 예산은 서비스 각자가 아니라 DB담당이 전체를 보고 배분해야 한다.**

따라서 Login·MealPlan 요청은 "풀을 늘려라"가 아니라, 아래처럼 **먼저 판단부터 요청**하는 형태로 재구성한다.

### P0: Chat — 미계측·미인덱스 쿼리 수정

이 건은 위 커넥션 예산 문제와 무관하다. "리소스를 늘려라"가 아니라 **"느린 쿼리(인덱스 없는 ILIKE) 자체를 고쳐라"**는 근본 원인 수정 요청이라, 재판단해도 결론이 바뀌지 않는다. 원인이 `PgRecipeNameSource`(레시피 이름 ILIKE 폴백 쿼리)로 특정됨(§3.4 참고).

1. `recipe.name`에 `ILIKE '%word%'` 검색용 인덱스(`pg_trgm` + GIN) 적용 검토
2. `PgRecipeNameSource.search()`에 `start_span("postgres.recipe_name")` 계측 추가
3. 조치 후 동일 조건(150VU)으로 재검증

### P1: MealPlan — 커넥션 풀 확장 (단, 예산 안에서 판단 필요)

원인이 `services/mealplan/app/db.py`의 하드코딩된 `max_size=10`으로 특정됨(§3.3 참고). 50VU부터 이미 포화(TPS 고정, 응답시간만 VUser에 비례 증가).

MealPlan은 로그인과 달리 앱을 켤 때마다 반복 호출되는 핵심 기능이라, 피크타임(11-12시·17-18시)에 실제로 동시 접근이 몰릴 가능성이 있다. 그래서 "풀 확장"이라는 방향 자체는 유효하다고 판단한다. 다만:

1. **먼저** — mealplan에 실제로 얼마나 배정 가능한지, 위 커넥션 예산(§6.0) 안에서 DB담당이 산정
2. mealplan도 account·chat·notify·price와 동일하게 풀 크기를 env로 조정 가능하게 코드 변경(현재 하드코딩)
3. 위에서 산정된 값으로 실제 상향
4. PgBouncer 같은 커넥션 풀러 도입도 대안으로 함께 검토(앱 레벨 풀 크기와 실제 PG 커넥션 수를 분리해 예산 압박을 줄이는 방법)
5. 조치 후 동일 계단식(50/100/150/200VU)으로 재검증

### ✅ 완료 확인: Login — CPU 쿼터 병목 (30VU 기준)

- bcrypt 오프로드(`asyncio.to_thread`) + `cpus: 0.75→2.0`·`mem_limit: 512m` 상향(커밋 `053fbd9`) 반영 확인
- 30VU(원본 조건) 응답시간 3,493ms→497.38ms — **실질 해결**

### P2(재검토 필요): Login — 100VU 이상은 "CPU 증설/rate limit" 전에 현실성부터 판단

100VU 이상에서 성공보다 오류가 30배 이상 많은 건 사실이지만(§3.1 참고), 이걸 곧바로 "account CPU를 더 늘려라"로 요청하지 않는다. **런타임 증거로 원인은 확인됐다** — account CPU가 한도(2.0코어)의 98%까지 포화되고, PG active 커넥션은 0이라 DB 풀 문제가 아니다(§3.1 참고, 이전 버전에서 DB 풀 문제로 잘못 추정했던 것을 정정함).

로그인은 사용자가 세션당 1번만 하는 행동이라 **API 조회처럼 지속적으로 몰리는 트래픽이 아니다.** 100~200명이 정확히 같은 순간에 로그인하는 상황이 현실적인지부터 의문이다.

1. **먼저** — DAU(설계 문서상 500) 기준으로 실제 동시 로그인 피크가 얼마나 되는지 추정 요청. 이 추정치가 30~50 수준이면 **지금 상태(30VU 해결됨)로 이미 충분할 수 있다** — 추가 조치 불필요.
2. 만약 실제로 높은 동시 로그인 대응이 필요하다고 판단되면:
   - **로그인 rate limiting/계정 잠금 도입**(`design/mp_k8s_security_design.md` P0, 미구현) — 브루트포스 방어와 동시에 비현실적 동시 로그인 폭주로부터 서버 보호
   - **account 수평 확장(replica)** — CPU를 한 컨테이너에 계속 몰아주기보다 여러 인스턴스로 분산하는 게 호스트 전체 코어(6코어) 활용 관점에서 더 합리적일 수 있음
3. bcrypt 비용 인자를 낮추는 방식은 이번에도 개선안으로 인정하지 않는다
4. 결론과 무관하게 재검증은 추정된 "현실적 피크" 수치를 기준으로 진행(원본 문서의 30VU가 아니라, 실제 근거가 있는 숫자로)

### P2: Kafka·Redis — 예방적 모니터링 (튜닝 아님)

핫딜 시나리오(§4.3)에서 문제를 못 찾아 "지금 고쳐라"는 요청은 아니다. 대신:

1. 실제 오아시스 딜(`timeSale`/`closeSale`) 크롤 시각(15시/17시)에 실제 건수를 로그로 남겨, 1,000건에 근접하는지 확인
2. Redis `evicted_keys` 지표에 알람 설정(운영에서 캐시 축출 시작 시 조기 감지용)

### 완료 확인 요청: Price

- 재배포된 이미지 태그·커밋 SHA 공유 요청 (어떤 변경이 이 개선을 만들었는지 기록용)

## 7. 결과 해석 시 주의사항

1. 이번 재검증도 nGrinder 요약 화면의 응답시간은 P95가 아니라 평균값이다. Chat 회귀와 Login 미해결 확정 판정을 위해서는 P95·P99 재확인이 필요하다.
2. 혼합·피크 시나리오는 §4.4에서 설명한 대로 Login을 우회한 조건이므로, 이 결과만으로 "일반 피크 시나리오 통과"라고 발표하면 안 된다.
3. Login 재현 실험은 nGrinder가 아니라 순수 curl 동시 요청으로 진행했다 — nGrinder 자체가 "Too many errors"로 자동 중단되어 정식 지표(TPS 등)를 얻지 못했기 때문이다. 정식 지표가 필요하면 `ignoreTooManyError` 옵션을 조정한 재시험이 별도로 필요하다.

## 8. 이번에 시도했지만 실행하지 못한 것

- **Login DB 레벨 확인(EXPLAIN ANALYZE)**: 사용자 조회 SQL의 인덱스 사용 여부를 직접 확인하려 했으나, PostgreSQL 접속 정보(비밀번호)를 로컬에서 구할 수 없고 fb-data(192.168.0.8) SSH도 호스트 키 불일치 경고로 접속을 보류했다. DB 접속 권한이 확보되면 추가 확인 필요.
- **Kafka·Redis 진짜 임계점 확인**: §4.3에서 1,000건·400VU까지는 문제가 없었지만, 그 이상(수만 건, 수천 VUser)에서 실제로 어디가 깨지는지는 확인하지 못했다. 지금 규모에서 문제가 없다는 것과 "한계가 어디인지 모른다"는 것은 다른 이야기라, 필요하면 규모를 계속 올려가는 별도 테스트가 필요하다.
- **테스트 데이터 정리**: §4.3에서 생성한 합성 딜 데이터(`TEST-` 접두사, 총 2,600건)가 fb-data의 Redis(`retail:deals:active` 등)에 남아있다. PostgreSQL 쪽(`crawl_raw`, `retail_product`, `retail_price`)도 DB 접속 권한이 없어 정리하지 못했다.
