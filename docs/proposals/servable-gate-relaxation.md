# 제안: servable 게이트 완화 — 실재료 미매칭 허용치

**상태: 미결정 (팀 결정 대기).** 이 문서는 측정치와 선택지를 정리한 것이고, 아직 채택된 정책이 아니다.
정본 정책은 확정 후 `docs/design.md`에 반영한다.

- **측정일: 2026-07-21 (재측정)**, 10K(만개의레시피) 레시피 **6,547건** 기준 (프로덕션 PG 실측)
- 선행 변경 2건이 **이미 적용**되어 있다(아래 §1) — 이 문서는 **그 다음** 단계를 다룬다
- 관련: `pipelines/ingest/index_recipes_es.py`(배치 게이트) · `deploy/pgsync/plugins/recipe_servable.py`(CDC 게이트) · [gazetteer-matching-policy.md](gazetteer-matching-policy.md)

> ⚠️ **숫자는 빨리 낡는다.** 이 문서의 초판(같은 날 오전)은 B=5,556 / 미매칭1개=837 이었는데,
> 반나절 만에 B=5,425 / 905 로 바뀌었다(§1-b 참조). 크롤·파서·큐레이션이 움직이면 재측정해야 한다.
> 재현 SQL은 부록에 있다.

## 1. 배경 — 이미 처리한 것과 남은 것

게이트는 "레시피의 모든 재료에 가격을 매길 수 있나"를 묻는다. 못 매기면 재료비가 틀리므로 검색에서 뺀다.

### 1-a. 비-재료를 매칭 실패로 세던 정의 오류 (수정 완료)

`gazetteer.STOP` 품목(물·얼음·이쑤시개…)은 "가정이 식비 재료로 사서 가격비교할 가치가 없는 이름"(`CONTEXT.md` 비-재료)이라 **일부러** `item_id`를 안 붙인다. 그런데 게이트가 `item_id IS NULL`을 매칭 실패로 세는 바람에 **물이 들어갔다는 이유로 레시피가 통째로 빠졌다** — 단독 최대 요인이 '물' 1,520건이었다.

가격을 **안 매기기로 한** 것들이라 실패로 세면 안 된다. 완화가 아니라 버그였고, `recipe_ingredient.is_non_ingredient` 컬럼으로 분리해 수정했다. **servable 3,787 → 5,556.**

### 1-b. 재료명이 '구매'로 덮이던 크롤 파싱 버그 (수정 + 백필 완료)

만개는 **재료 정보 페이지가 있는 재료만** 이름을 `<a>`로 감싸는데, 파서가 첫 `<a>`를 이름으로 써서 정보 페이지가 없는 재료(=흔치 않은 재료)의 이름이 구매 버튼 텍스트 **'구매'로 덮였다**. 446 레시피 / 510행.

`구매`가 `STOP`에 있어 **비-재료로 분류**됐고, 그래서 1-a의 게이트가 그 레시피들을 **통과시키고 있었다.** 즉 재료 하나가 통째로 가려진 채 그 값이 재료비에서 조용히 빠졌고, 게이트는 "전 재료 매칭됨"으로 판정했다.

파서 수정 + 446건 백필로 실제 이름(모닝빵·오레오·통팥조림 등)을 복구하자 이들이 **실재료 미매칭**이 되어 정직하게 막혔다. **servable 5,556 → 5,425 (−131).** 숫자는 줄었지만 **이전 5,556이 부풀려진 값**이었다.

### 1-c. 남은 것 = 이 문서의 주제

현재 차단 **1,122건**의 분해:

| 원인 | 건수 | 비중 |
|---|---:|---:|
| 실재료 미매칭 1개 | 905 | 80.7% |
| 실재료 미매칭 2~3개 | 197 | 17.6% |
| 실재료 미매칭 4개 이상 | 20 | 1.8% |

## 2. 선택지

| 옵션 | 정의 | servable | 노출률 | 기준선(B) 대비 |
|---|---|---:|---:|---:|
| **B (현행)** | 실재료 미매칭 0 | 5,425 | 82.9% | — |
| **C** | 실재료 미매칭 **≤1** 허용 | 6,330 | 96.7% | +905 |
| **D** | 실재료 **매칭률 ≥80%** | 6,335 | 96.8% | +910 |
| **E** | C ∪ D | 6,427 | 98.2% | +1,002 |

## 3. 트레이드오프 — 무엇을 잃나

완화하면 **재료비가 과소추정된 레시피가 검색에 노출된다.** 크기를 재보면:

- C 대상 905건은 평균 재료 **9.3개**, 그중 1개 미반영 → **평균 13.3%의 재료비가 빠진다**
- 단, 앱은 이미 이 상황을 숨기지 않는다 — `services/recipe/app/queries.py`가 재료별 `cost_basis`(`no_price`/`no_convert`/`excluded_liquid`/`capped`/`usage`)를 반환하고, 프론트(`IngredientPanels.tsx`)는 값이 없는 재료를 회색 `-`/`미매칭` 칩으로 표시하며 푸터에 "재료비 산정 N/M개"를 명시한다. 설계상 "정직한 과소추정"으로 문서화돼 있다(`recipe_cost.py` 주석). 즉 **새로운 거짓말을 만드는 건 아니고, 기존의 과소추정 노출 범위가 넓어지는 것**이다.
- D는 재료가 많은 레시피에 관대하다(20개 중 4개 미매칭 통과). C는 재료 수와 무관하게 절대 1개. 어느 쪽이 예산 신뢰도에 맞는지는 제품 판단.
- **1-b의 교훈**: 게이트를 느슨하게 할수록 "가려진 재료" 같은 데이터 결함이 지표에 안 잡힌다. C/D를 택한다면 미매칭 재료의 **절대 건수를 별도 모니터링**하는 편이 안전하다.

## 4. 대안으로 검토한 것 — 사전 큐레이션(비추천 근거)

"게이트를 건드리지 말고 `item_master`를 채우자"는 대안은 **효율이 낮다.** 미매칭 실재료는 롱테일이다:

| 미매칭 실재료 | 차단 레시피 |
|---|---:|
| 호박 | 45 |
| 모닝빵 | 24 |
| 오레오 | 13 |
| 죽염 / 불닭소스 | 각 10 |
| 에스프레소 / 간마늘 20g / 화이트 발사믹 / 김칫국물 / 조청 | 각 8 |
| 메이플시럽 / 깨가루 | 각 7 |

상위 12개를 전부 매핑해도 회수는 **150건 남짓**이다(C의 905건 대비). 큐레이션은 계속 하되 **게이트 정책과는 분리해서** 판단하는 편이 낫다.

참고로 `간마늘 20g`처럼 수량이 이름에 붙어 들어온 잔재도 섞여 있어, 일부는 큐레이션이 아니라 **크롤/정규화 개선 대상**이다(1-b 같은 사례가 더 있을 수 있다).

## 5. 결정이 필요한 것

1. B 유지 / C / D / E 중 무엇인가
2. (완화 시) 과소추정 레시피를 UI에서 표시할 것인가 — `cost_basis`가 이미 있으니 배지 하나로 가능
3. (완화 시) 미매칭 재료 절대건수 모니터링을 같이 붙일 것인가 (§3 마지막 항목)
4. 재측정 주기 — §서두 경고 참조

## 6. 구현 시 주의

게이트는 **두 곳에 중복 구현**돼 있다. 한쪽만 고치면 두 인덱스가 어긋난다.

| 위치 | 대상 인덱스 | 형태 |
|---|---|---|
| `pipelines/ingest/index_recipes_es.py` | `recipes` (배치 · DR 폴백) | SQL `HAVING` |
| `deploy/pgsync/plugins/recipe_servable.py` | `recipes_pgsync` (**CDC · 실제 서빙**) | Python |

앱이 실제로 읽는 것은 `recipes_pgsync`다(`.9` recipe 컨테이너 `ES_INDEX=recipes_pgsync`). 플러그인은 pgsync 컨테이너에서 돌아 `pipelines/ingest/gazetteer.py`를 import할 수 없으므로, 판정에 필요한 정보는 **적재 시점에 컬럼으로 남겨** 양쪽이 같은 값을 읽게 해야 한다(§1-a의 `is_non_ingredient`가 그 방식).

**게이트 로직(플러그인)을 바꾸면 PGSync 전량 재동기가 필요하다** — 이미 색인된 문서는 자동 재변환되지 않는다. 반면 컬럼 **값**만 바뀌는 경우(예: 1-b 백필)는 트리거 CDC가 알아서 따라온다.

## 부록 — 재현 방법

```sql
with ing as (
  select r.id rid, ri.item_id, ri.is_non_ingredient
  from recipe r join recipe_ingredient ri on ri.recipe_id = r.id
  where r.source = '10K'
),
per as (
  select rid,
         count(*) filter (where not is_non_ingredient)                          tot_real,
         count(*) filter (where item_id is null and not is_non_ingredient)      unm_real
  from ing group by rid
)
select
  count(*) filter (where unm_real = 0)                                          as "B",
  count(*) filter (where unm_real <= 1)                                         as "C",
  count(*) filter (where tot_real > 0
                     and (tot_real - unm_real)::float / tot_real >= 0.8)        as "D"
from per where tot_real > 0;
```
