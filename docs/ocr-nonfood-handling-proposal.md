# 제안 — 비재료 식품 처리(2축 라우팅 + 식품 카테고리)

> **작성:** 건우 (AI 담당) · 2026-07-16
> **수신:** 제품/기획 · 데이터 담당(Taylor, item_master 범위)
> **상태:** 제안(팀 결정 필요) · 근거: OCR 데모 **실물 영수증 실사용** (`ocr-devlog.md §9.3`)

## 1. 발견 (실사용 근거)

OCR 데모에 **실물 마트 영수증**을 넣어보니, 구매 품목의 상당수가 **"깨끗한 요리 재료"가 아니었다** — 가공식품·즉석식·간식·음료가 많음. 예(실측 1장, 17품목):

| 유형 | 실측 품목 예 | 재료? |
|---|---|---|
| 신선재료 | 삼겹살·대파·애호박·부추·새송이버섯·바나나 | ✅ |
| 가공/양념재료 | 백설콩식용유·곰표튀김가루·사누끼우동면·광천돌자반 | 🟡 경계 |
| 즉석/간편식 | 알탕(소스포함)·해물탕(소스포함) | ❌ |
| 간식·음료 | 고래밥볶음·예감오리·미닛메이드감귤·(허니도넛) | ❌ |

현재 시스템은 `is_food`(식품 vs 봉투)만 구분해, **가운데(식품이지만 비재료)를 재료와 똑같이 취급** → item_master(재료 카탈로그)에 억지로 매칭하려다 전부 미매칭. **"실패"처럼 보이지만 실은 설계 사각지대.**

## 2. 재프레이밍 — 앱엔 축이 2개다

| 축 | 대상 | 비재료(도넛·음료·즉석식) |
|---|---|---|
| **식비(expense)** | **모든 식품 구매** | ✅ **전부 포함**(먹는 데 쓴 돈) |
| **재고/레시피(pantry)** | **재료만** | ❌ (레시피 못 돌림) |

→ 비재료는 **노이즈가 아니라 식비축에 100% 속하는 정상 데이터**. **거부가 아니라 "올바른 축으로 라우팅"** 이 답.

## 3. 제안

1. **식비축**: 모든 식품 계상 + **Gemini가 식품 카테고리 분류**(신선재료/가공재료/즉석·간편식/간식·음료/기타).
   → **"문제"를 기능으로**: "이번 달 신선재료 X원 / 간식·음료 Y원" **지출 분석** — 예산앱의 실질 가치.
2. **재고/레시피축**: **재료(신선+가공)만** 매칭·적재. 비재료는 식비만, 재고엔 안 넣음 → **미매칭 = 정상 종착**.
3. **HITL**: 비재료 카테고리는 **매칭을 강요하지 않음**(도넛에 재료코드 안 붙임).
4. **레시피 추천 영향 없음**: 비재료가 많아도, 영수증의 재료 부분집합(삼겹살·양파·대파…)만으로 추천 성립.

## 4. 팀 결정 필요 항목

1. **item_master 범위** — "재료 전용" 유지 vs 가공/즉석식 포함? (재료 전용이면 비재료 영구 미매칭=식비 전용 처리가 설계상 정합) — **Taylor/제품**
2. **식품 카테고리 taxonomy** — 몇 단계로? (위 5분류 안 or 조정) — **제품/기획**
3. 카테고리 → **식비 화면 표시/집계** 방식 — 제품
4. `expense.category`(현재 GROCERY/DINING/DELIVERY/ETC)와의 관계 — 식품 하위 카테고리를 어디에 둘지

## 5. 담당 경계

- **카테고리 정의·화면·집계** = 제품/백엔드

## 7. 확정 결정 — 라우팅·자동화·비용 전략 (건우, 2026-07-16)

> §1~6은 최초 제안(2축 재프레이밍). §7은 그 위에서 팀 논의로 **확정된 설계**다. 이후 구현·문서는 §7을 SoT로 삼는다.

### 7.0 대원칙
1. **OCR 엔진 동결** — Gemini Vision(`flash-lite`, thinking OFF)은 현 상태 유지. **분류를 OCR 프롬프트에 넣지 않는다**(엔진에 추론 부담 X).
2. **분류·라우팅 = 다운스트림 별도 단계** — OCR은 텍스트만, 그 뒤 단계가 품목을 라우팅.
3. **신규 대용량 데이터 저술 0** — 이미 레포에 있는 자산만 재사용(`is_food`·`food_nutrition`·레시피 재료·`oasis_products`·`kr_shelf_life_seed`·`dict_item_master` 1,054). 새 데이터셋을 찾고·검증하고·인제스트하지 않는다.
4. **생성형 AI는 정말 필요할 때만** — 캐스케이드에서 싼 방법이 다 실패한 **미해결 품목만** LLM. 결과는 DB화되어 재사용(품목당 생애 1회).

### 7.1 전체 흐름
```
영수증 사진 → OCR(Gemini vision, 장당 1콜)
  → 품목마다 분류 캐스케이드(7.2)  → 라우팅 4갈래(7.3)
  → HITL 확정 화면(7.6: 대부분 자동 채움, 저신뢰만 하이라이트)
  → 식재료→pantry(+검토큐) / 식품→식비 / 비식품→식비 제외
```

### 7.2 분류 캐스케이드 (싼 것부터, 맞으면 멈춤)
| 단계 | 판정 | 비용 |
|---|---|---|
| 0. **경계정책 참조표**(7.7) | 생수·얼음·홍삼정 등 정책 확정어 | 0 |
| 1. `is_food=false` | 비식품(봉투·할인·포인트) | 0 |
| 2. `item_master` 정규화 정확매칭(7.5) | 식재료 + `item_id`(+보관법 있으면) | 0 |
| 3. 레시피재료·`food_nutrition` 소속 파생 | 식품/식재료 여부 | 0 |
| 4. `oasis` 상품 카테고리 매핑 | category | 0 |
| 5. `kr_shelf_life_seed` 조회 / 규칙셋(코드) | 보관법 | 0 |
| 6. 기존 1,054 문자 n-gram 유사도 상속 | 최근접 품목 속성 | 0(로컬) |
| 7. **미해결** → LLM(실시간·동기, 영수증 내 미지 1콜 묶음) | category 분류 | **여기만 과금** |

- **7단계 LLM = 실시간 즉시 반영**(일일 배치 아님) — 사용자가 스캔 직후 확정 화면에서 결과 확인. 결과는 **DB화**(별도 캐시 아님) → 다음 등장부턴 2단계에서 공짜.
- LLM은 **강제 추측 금지** — 애매하면 "모르겠음" 반환 → 미해결 처리(7.6).

### 7.3 품목 라우팅 (5갈래)
1. **식재료**: `item_master` 있으면 `item_id` 매핑 / 없으면 **후보 제안 → 검토큐(7.10)**. **pantry 추가 + 식품.**
2. **가공식품**: **식품.** pantry는 **조리재료성만** 후보(식용유·간장 등), 간식·음료는 식비만.
3. **비식품 '상품'**(세제·봉투·화장지 등): 산 물건이지만 음식 아님 → **식비에서 차감**, pantry X.
4. **조정**(할인·쿠폰·포인트·음수 라인): **품목 아님** → pantry X, **식비 차감 대상 아님**(총액에 이미 반영). ↓ 7.3.5.
5. **미지(미해결)**: 식품으로 취급 + **"확인" 플래그**(마트 구매는 음식 확률↑). 사용자가 비식품이면 뺌.

#### 7.3.5 식비 계산 — **total 앵커** (2026-07-16 개정)
> **`식비 = total_amount − Σ(비식품 '상품' 금액)`.** (구 "식품 품목합"에서 개정.)

- **왜 개정**: 품목합 방식은 (a) 할인/쿠폰 라인, (b) **OCR 가격-품목 오정렬**에 취약. 예) 맥도날드 영수증에서 Gemini가 스낵랩값 3,000을 쿠폰에, 할인 -1,200을 스낵랩에 오배치 → 품목합이면 식비 = **-1,200**(오류). `total`(=할인 반영된 실지불액)을 앵커로 하면 오정렬·할인에 안 흔들림.
- **조정은 차감 안 함** — 할인·쿠폰은 `total`에 이미 반영됨. 이걸 "비식품 상품"으로 오취급해 또 빼면 이중차감(맥도날드 케이스의 근본 결함이 이거였음). → 조정과 비식품상품을 **분리**. 맥도날드: 조정만 있고 비식품상품 0 → **식비 = total 1,800 ✓**.
- **부호-종류 불일치 → HITL 플래그**(7.6): 식품인데 음수 / 할인·쿠폰인데 양수 = 오정렬 의심. (⚠️ `Σ라인=total` 정합체크는 이 **스왑을 못 잡음** — 합이 불변이라. 부호 플래그가 실질 안전망.)
- **약점(정직)**: `total_amount` 신뢰도에 의존 — 영수증에 합계가 여러 개(소계·과세표준)면 Gemini가 **할인 전 소계**를 집을 수 있음 → 식비 과대. **완화**: `total` 없거나 `Σ라인≠total`이면 자동 식비 대신 **HITL**. 완벽 자동해결은 없음 — messy 영수증은 조용히 틀리지 말고 플래그.

### 7.4 보관법 (냉장/냉동/실온)
- **기본값 = 냉장(FRIDGE)** — 상하는 걸 실온 방치하는 실수가 최악이라 안전측.
- 확실한 건 규칙/시드로 자동 배치(냉동*·아이스→냉동, 우유·두부→냉장, 라면·통조림→실온).
- ⚠️ **보관법은 학습·개인화·전역변경하지 않는다.** 삼겹살은 같은 사람도 상태·의도에 따라 냉장/냉동이 갈려 — per-user 학습도, 공용 기본 변경도 오류. **인스턴스별 사용자 선택만**, 어디에도 "기본"으로 저장 안 함. (DB화 대상은 category뿐, 보관법 아님.)

### 7.5 정규화·매칭·조인 (기존 자산 재사용)
품목명 구조 = 브랜드+수식어+핵심명+용량("돈생삼겹살500g"). 파이프라인:
```
OCR명 → ① 정규화(기존 index PR#69/74 재사용: 브랜드·용량·단위 제거)
      → ② NER로 핵심 재료명 추출("돈생삼겹살"→"삼겹살")
      → ③ 정규화 표준명 정확매칭 → ④ 실패시 문자 n-gram 유사도 → ⑤ 미해결→LLM
```
- **조인 키 = 정규화 표준명(canonical name)** — 모든 소스(item_master·nutrition·레시피·oasis)를 같은 정규화로 맞춰 조인(외부 ID 의존 X). oasis 카테고리→3분류는 작은 매핑표(코드).

### 7.6 사용자 상호작용 (자동화 우선)
- **자동 배치 + 사후 수정** — "질문 팝업" 아니라, 최선 추측값으로 배치 후 틀린 것만 수정.
- **확정 화면**: **고신뢰**=값 다 채워진 채(훑고 넘김) / **저신뢰**=노란 하이라이트+"자동 추정" 배지+프리필(그 줄만 수정).
- **선택지 제시 기준 3축**: ① 신뢰도(카탈로그 확정=자동) ② 금전·되돌리기(식비 걸리면 확인) ③ 애매성(결정적이면 자동). 물어도 원탭·배치.
- **OCR 깨짐**: 줄 단위 손상=그 줄만 "인식 실패—삭제/수동입력" 플래그(나머지 유지). 전체 손상(파싱률·합계정합 임계 초과)=**"재촬영" 알림 → 2회차도 실패 시 "손상도가 심해 자동 인식이 어려울 것 같아요. 직접 입력해주시겠어요?" → 수동 입력.**
- **브랜드명만 찍힌 경우**: "브랜드다"를 양성 분류하지 않는다(브랜드 사전=새 데이터, 지양). 대신 **캐스케이드가 확정 못 한 "미해결"을 신호로** — 미해결 품목에 **"상품명을 확인/입력해주세요"**(원문 프리필). 브랜드명만은 자동으로 이 그물의 부분집합. 최종 안전망=HITL.
- **부호-종류 불일치(오정렬 탐지, 7.3.5)**: **식품 이름인데 음수 가격 / 할인·쿠폰 이름인데 양수 가격** = OCR 가격-품목 오배치 의심 → 해당 줄 `needs_review`(노란 하이라이트). `total` 없거나 `Σ라인≠total`이면 자동 식비 대신 확인 요청.

### 7.7 경계정책 참조표 (정의 애매 품목)
- **저장**: `pipelines/ingest/data/` 에 **repo CSV(SoT)** → DB 참조 테이블 적재(기존 `shelf_life_ref`·`food_nutrition` 패턴 재사용). 컬럼 `term, 식비취급(포함/제외), 사유`. **단어 추가는 PR로**(거버넌스—식비에 영향, git 이력 추적). 규모 작으면 MVP는 기동 시 메모리 로드 → 커지면 DB 승격.
- **초기 확정**: `생수→식비 포함`, `얼음→식비 포함`, `홍삼정(건기식)→식비 제외`. (사료·종이컵 등은 추후 PR로 추가.)

### 7.8 비용 모델
- OCR: 장당 **~0.45원**(flash-lite, 변동 없음).
- 분류: 캐스케이드 0~6단계는 **0원**. 7단계 LLM만 과금 — 품목당 **<0.05원**, **정규화 품목당 생애 1회**(DB화). 비용은 영수증·사용자 수가 아니라 **"등장한 고유 품목 수"에만** 비례 → 넉넉히 5,000종이라도 평생 **~250원**, 앞에 몰릴 뿐 총액 사소. 정상상태 0 수렴.
- **월 상한 캡 없음** — 사용 중 LLM이 갑자기 멈추면 안 됨. 장애 시 **기본값(식비 포함+냉장+확인) 폴백**으로 흐름 유지(차단 아님).
- 이미지 썸네일은 **별개 트랙**(아래), 이 비용에 미포함.

### 7.9 이미지 썸네일 (별개 결정)
- 실사진 아닌 **작고 단순한 그림**(생성형 고려 중). **오프라인 1회·품목당 생애 1회.** 저품질 티어 ~15~60원/장, 로컬 SD면 ~0원. 카탈로그 캐시 + category 아이콘 폴백(실시간 생성·웹검색 안 함). → 분류 전략과 분리, 별도 확정 필요.

### 7.10 ⚠️ item_master 자동 추가 거버넌스 (핵심)
새 식재료를 **공용 카탈로그에 무분별 insert하면 데이터 품질 붕괴**(중복·비표준명·OCR 오탐). → **바로 추가 금지.** 흐름: **"새 식재료 후보" 제안 → 검토큐(표준명·중복 검사) → 승인 후 추가.** **Taylor(데이터 오너) 소관.**

### 7.11 담당 경계
| 항목 | 담당 |
|---|---|
| 분류 캐스케이드·정규화·NER·미해결 LLM·category 산출 | **AI(건우)** |
| `item_master`(category 컬럼)·pantry 저장·식비 계산(식품만)·예산 차감 제외·검토큐·경계정책 DB | 백엔드/데이터(Taylor) |
| HITL 선택지·확정 UX·"직접입력"·"상품명 입력" 화면·아이콘 세트 | 제품/프론트 |

### 7.12 남은 결정 필요 항목
1. **경계정책 초기 목록 확장** — 사료·종이컵·주류·담배 등 식비 취급(추후 PR).
2. **이미지 썸네일**(7.9) — 생성형 여부·모델·품목 범위·로컬 vs API.
3. **손상도 임계값** — 전체 재촬영 트리거 기준(파싱률·합계정합 컷).
4. **per-instance 보관 수정 UX** — 사용자가 냉장/냉동 옮기는 화면(제품).
