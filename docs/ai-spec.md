## 1. 재료 NER — 표준 품목코드 정규화 (P0 · 자체 학습)

**문제**: "다진 마늘 한 스푼"(레시피), "농협 깐마늘 200G"(영수증), "마늘 좀 있는데"(챗봇)를 기계는 같은 것으로 못 잇는다.
**해법**: 시퀀스 라벨링으로 재료명·분량·단위를 추출하고 품목 마스터(design.md §6.3, 식약처 식품코드 앵커·300~500 품목)의 표준 코드로 정규화.

- **모델**: CRF (sklearn-crfsuite) · CPU 학습/서빙, GPU 불필요
- **학습 데이터**: 농교원 EPIS 3종(재료 **정형** — 1재료=1행 `IRDNT_NM`+`IRDNT_CPCTY` = **gold label**) + 식약처 COOKRCP01(~1,000건, 재료 자유텍스트 = NER 적용 대상 겸 보조 라벨). `recipe_ingredient.ner_status`로 라벨/대상 구분이 이미 스키마에 반영됨(`prd/schema-public-data.sql`의 NER seam). 만개의레시피 크롤 텍스트는 **레시피 DB용으로만** 사용, 학습 코퍼스에서는 제외(TDM 옵트아웃 존중)
- **파이프라인**: 수집 → 자동 라벨 → Argo Workflows 학습 Job → MLflow 버전 관리 → S3 → ML Serving(FastAPI, `/ner` endpoint, HPA)
- **소비처(4)**: ① 레시피 적재 시 재료 정규화 ② F5 영수증 품목 매칭 ③ F13 유튜브 추출 결과 정규화 ④ F18 어시스턴트 질문 분석
- **평가**: 재료명 span F1 ≥ 0.85 목표 · 품목코드 매칭률 실측(마스터 PoC와 연동)

## 2. 최저가 이상탐지 (P0 · 자체 통계)

**문제**: "지금이 살 때"를 유저가 알 수 없다.
**해법**: 컬리·오아시스 **2축** 가격 경량 이력의 30일 이동평균 대비 z-score로 급락 감지(보조 신호: 역대 최저 갱신·할인율) → 관심 품목 Push(F21). 소스 2축이라 baseline이 2배 속도로 축적 — §4.1 "4주 미만 오탐" 구간 단축.

- 라벨 불필요 → 콜드스타트 강점(서비스 첫날부터 동작). 단 baseline 4주 미만 구간은 오탐↑(design.md §4.1)
- 품목별 σ 기반이라 "원래 출렁이는 품목"과 "진짜 이상 급락" 구분
- 배치: 가격 폴링 주기에 맞춘 K8s CronJob · 코드 몇십 줄 수준, 외부 API 비용 0
- 발송: 이상탐지 컨슈머 → **관심 등록 유저 fan-out** (KEDA, design.md §7.1·§8.2) → 알림 탭 "싼 재료 담기"
- ⚠️ **"관심 등록 유저" 기준 미정(정본 빈칸)**: 후보 = ⓐ 품목 직접 관심 등록(위시) ⓑ 레시피북 저장 레시피의 재료 자동 등록 ⓒ 장보기 목록의 부족 재료 자동 등록. 담당 의견: ⓐ 명시 등록을 기본으로 하되 ⓑ·ⓒ는 "자동 등록 + 해제 가능" 옵션 — 알림 피로도 제어가 관건

## 3. 개인화 레시피 랭킹 (규칙 P0 → LightGBM P1 · 자체 학습)

**2단계 설계** — 콜드스타트와 개인화를 모두 잡는다.

- **1단계(P0, 규칙)**: 점수 = 재고 활용률 + 임박 재료 사용 + 저비용 (F11·F16 현행 명세 그대로)
- **2단계(P1, ML)**: 클릭스트림 축적 후 LightGBM 랭킹 모델로 교체. 피처 = 규칙 점수 3종 + 유저 행동 이력 + 레시피 인기도
- **학습 데이터 = 클릭스트림**: Kafka `events.user.activity` 토픽, 액션 6종(레시피 조회/담기/조리완료/좋아요/폐기/알림클릭), user_id 스코프, 수집 동의 고지 — ⚠️ **P0 편입 팀 승인 대기**
- 학습·서빙은 NER과 동일 인프라 재사용(Argo·MLflow·S3·ML Serving)

## 4. 유튜브 영상→레시피 추출 (P1 · Gemini)

상세: `video-recipe-ai.md`. 요약:

```
URL 제출 → 사전필터(Data API·무료: 20분 초과/비요리 거절) → URL 정규화·Redis 캐시(TTL 30일, 히트=비용 0)
→ 단일비행 락(SETNX) → Gemini Flash-Lite 영상 추출($0.047, JSON+타임스탬프) → 규칙 검증 H1~H5
→ (실패 1회) 3 Flash 재분석 → 3.5 Flash 정제 → [공용] NER 품목코드 정규화 → ES 매핑 → 레시피북 저장
```

- 비용: 평균 **$0.063/건**, 캐싱 반영 월 2천 건 ≈ $44 (유료 API 예외 승인 완료 범위)
- 운영: 온디맨드(유저 트리거)만 · 배치 소진 없음 · 실패 시 "레시피를 읽지 못했어요" + 수동 입력 유도
- NER은 이 파이프라인의 마지막 정규화 단계로 **호출**된다(#1의 소비처 — 포함 관계 아님)

## 5. 대화형 어시스턴트 (P1 · RAG) — 요약

**차별점**: 범용 챗봇은 내 냉장고·예산·오늘 시세를 모른다. 답의 근거를 전부 자체 데이터에서 검색해 주입하는 RAG. 용도는 3층 — A 기능 프록시(의도적 겹침) / B 조합·해석(UI 제공 불가) / C 생성(레시피 변형, 챗봇 전용).

**구성**: ① NER 질문 분석 → ② 저장소 4종 병렬 검색(ES 레시피·PG 개인상태·컬리/오아시스 가격·영양 DB) → ③ 품목코드 조인 컨텍스트 조립 → ④ 생성(**Generator 인터페이스, 교체 가능 1개 층**) → ⑤ 근거 태그 + 액션 버튼. 5단계 중 4단계가 자체 구현.

**생성 백엔드 — 확정(2026-07-13, 팀 최종)**: 1차 **TemplateGenerator**(무료·승인 불필요)로 출시. 실사용 품질을 실측해 부족하다고 판단되면 그때 유료 전환(Bedrock Nova Lite → 옵션 Gemini, 월 $10 캡)을 재검토. design.md §9의 Gemini 재승인 패키지(OCR+유통기한갭)와는 별개이며, 챗봇이 유료 전환되는 시점이 오면 그때 별도 승인 필요.

> **상세 전체(구성·가드레일 4층·운영·비용 분석·템플릿 품질 한계와 개선안·구현 계획): [`chat-assistant-ai.md`](chat-assistant-ai.md)**

## 6. 유통기한 산출 (P0 기능 · 방식 확정 — 2026-07-14, design.md §9 반영)

기능 자체(F5 유통기한 파싱→F8 임박 알림)는 P0 확정. **✅ 산출 방식 확정: A안(검수 테이블 하이브리드).** `pipelines/ingest/`에 `shelf_life_ref` 테이블·FoodKeeper 적재·한국 시드가 이미 구현 착수됐고(2026-07-14 확인 시점 DB 실측 1,264행), B안(런타임 AI 직조회)은 채택 안 함.

| | A. 검수 테이블 하이브리드 (채택) | B. AI 검색(런타임 Gemini/검색 직조회) — 미채택 |
|---|---|---|
| 구조 | Gemini 배치로 품목 마스터 300~500개 초안 → 사람이 식약처 소비기한 참고값과 대조 검수 → 확정 테이블 → 런타임은 조회만. 미등재 신품목만 Gemini 온디맨드 산출 후 'AI 추정' 플래그로 테이블 자동 편입(캐시) | 재고 등록 시마다 AI가 실시간 산출 |
| 장점 | 식품안전 항목의 환각 차단 · 런타임 비용 0 · 응답 일관성 | 구현 단순 · 검수 공수 0 |
| 단점 | 초기 검수 공수(1회) · 식약처 소비기한 데이터 확보 여부 🧪 미검증 | 같은 품목에 다른 답 가능 · 식품안전 정보 환각 리스크 · 호출 비용 상시 |

**확정 근거**: 유통기한은 틀리면 유저가 상한 음식을 먹는 안전 항목이라 정적 검수 테이블이 원칙. **AI(Gemini)는 일회성이 아니라 ① 초기 초안 생성 ② 신품목 온디맨드 산출, 두 용도로 상시 사용**한다 — "AI 안 쓰는 방식"으로 오독하지 말 것.

⚠️ **검수 소스 현실 (prd/public-data-ingest §4 실측)**: KFIA 소비기한은 정형 데이터가 아니라 **품목별 PDF뿐**(대표 샘플 수기 입력만 가능), FoodKeeper는 CC0이나 US 기준이라 한식 매칭률 낮음. → 참고 테이블의 커버리지 갭이 예상보다 커서 **Gemini 초안 생성의 역할이 오히려 확대**됨: 초안은 Gemini 배치, 검수 앵커는 KFIA 수기 샘플+FoodKeeper+오아시스 상품페이지 소비기한(크롤 필드) 교차 대조. 보조 검증 소스로 오아시스 상품정보고시 테이블(소비기한·보관방법) 활용 가능.

**남은 절차**: AGENTS.md Gemini 유료예외 재승인(§8 승인 2) — 팀장 승인 대기.

## 7. 영수증 인식 OCR/Vision (P0 · 방식 검토중 — PoC 대기, design.md §9 등재)

F5(재고 등록)·F17(식비 기록)의 입구. design.md §9에 **"Tesseract → Gemini Vision-first(저빈도·감열지 약함, 합계 자가검증 + HITL)"** 방향이 검토중으로 등재 — 아래 ③안으로 수렴 중. **3안 비교**:

| | ① Tesseract 단독 | ② Tesseract + 실패 시 Vision 폴백 | ③ Gemini Vision 단독 |
|---|---|---|---|
| 비용 | 0 | 폴백 건만 (~장당 1원 미만) | 장당 1원 미만 |
| 공수 | 좌표 파서 1.5~2주 | 파서 + 실패판정 + Vision 경로 (최대) | 프롬프트+JSON 파싱 (최소) |
| 리스크 | 한국어 감열지 오류율 높음 | 복잡도 최대 | API 의존·오프라인 불가 |

②의 실패 판정 기준(안): ⑴ 파싱 품목 0건 ⑵ 품목 금액 합 ≠ 영수증 합계 ⑶ NER 품목 매칭률 임계 미달 ⑷ OCR confidence 저하.

담당 의견: 비용이 아니라 **개발 공수 vs 정확도**가 진짜 변수. 실물 영수증 20장으로 Tesseract vs Vision 정확도 비교 PoC 후 결정 권장(수 시간짜리 PoC). 어느 안이든 출력은 동일하게 NER로 넘어가므로 뒷단 설계는 영향 없음.

**(2026-07-14 추가) 실물 영수증 확보 제약으로 외부 공개 벤치마크 조사 — PoC 대체 아님, 방향성 참고용:**
- Gemini 2.5 Pro가 스캔 영수증 정확도 87.46%로 프론티어 VLM 중 최고, **저품질/저대비/감열지 퇴색 문서에서 Tesseract 대비 우세폭이 크게 벌어짐**. 반대로 깨끗한 인쇄 문서에선 격차가 줄어듦(출처: [dev.to 벤치마크](https://dev.to/gabrielanhaia/vision-models-for-ocr-when-they-beat-tesseract-and-when-they-dont-54a6), [arXiv:2509.04469](https://arxiv.org/pdf/2509.04469)).
- Tesseract는 한국어(한글) 인식이 영어보다 학습데이터 부족으로 약함 — 조명 균일한 인쇄문서 기준 85~90%, 그림자·구겨짐 있으면 급락(출처: [한국어 OCR 비교](https://www.lido.app/kr/hangugeo-ocr)).
- **단, 한국어 감열지 특화 정량 벤치마크는 공개자료 부재** — 일반 벤치마크가 design.md §9 방향(Vision-first)과는 일치하나, 최종 확정엔 여전히 국내 실물 PoC가 가장 정확. 실물 확보가 어려우면 팀원 지갑의 감열지 영수증 소수(수 장)라도 확보해 최소 PoC 권장.
- **결론: 방식은 아직 미확정 유지.** 위 조사는 참고자료일 뿐 PoC를 대체하지 않음.
