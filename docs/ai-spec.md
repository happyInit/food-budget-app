## 1. 재료 NER — 표준 품목코드 정규화 (P0 · 자체 학습)

**문제**: "다진 마늘 한 스푼"(레시피), "농협 깐마늘 200G"(영수증), "마늘 좀 있는데"(챗봇)를 기계는 같은 것으로 못 잇는다.
**해법**: 시퀀스 라벨링으로 재료명·분량·단위를 추출하고 품목 마스터(design.md §6.3, 식약처 식품코드 앵커·300~500 품목)의 표준 코드로 정규화.

- **모델**: CRF (sklearn-crfsuite) · CPU 학습/서빙, GPU 불필요
- **학습 데이터**: 농교원 EPIS 3종(재료 **정형** — 1재료=1행 `IRDNT_NM`+`IRDNT_CPCTY` = **gold label**) + 식약처 COOKRCP01(~1,000건, 재료 자유텍스트 = NER 적용 대상 겸 보조 라벨). `recipe_ingredient.ner_status`로 라벨/대상 구분이 이미 스키마에 반영됨(`prd/schema-public-data.sql`의 NER seam). 만개의레시피 크롤 텍스트는 **레시피 DB용으로만** 사용, 학습 코퍼스에서는 제외(TDM 옵트아웃 존중)
- **파이프라인**: 수집 → 자동 라벨 → Argo Workflows 학습 Job → MLflow 버전 관리 → S3 → ML Serving(FastAPI, `/ner` endpoint, HPA)
  - *(1차는 오프라인 경로: OLTP에서 **1회 스냅샷 export → 로컬 CPU 학습 → git 아티팩트**(모델 X). Argo/MLflow/S3는 AWS 이전 후 승격 목표. 근거 `prd/ner-training-data-spec.md` §1)*
- **소비처(4)**: ① 레시피 적재 시 재료 정규화 ② F5 영수증 품목 매칭 ③ F13 유튜브 추출 결과 정규화 ④ F18 어시스턴트 질문 분석
  - ⚠️ **④는 현재 rule 기반이 기본**(`extractor_backend="rule"`): CRF는 레시피 분포로 학습돼 짧은 채팅 문장에 **과다추출** → 챗 스왑 금지가 방침. CRF는 챗에 **옵트인 옵션**(`extractor_backend="ner"`)일 뿐 기본 아님. ①②③은 CRF 사용.
- **평가**: 재료명 span F1 ≥ 0.85 목표 · 품목코드 매칭률 실측(마스터 PoC와 연동)

## 2. 최저가 이상탐지 (P0 · 자체 통계)

**문제**: "지금이 살 때"를 유저가 알 수 없다.
**해법**: 컬리·오아시스 **2축** 가격 경량 이력의 30일 이동평균 대비 z-score로 급락 감지(보조 신호: 역대 최저 갱신·할인율) → 관심 품목 Push(F21). 소스 2축이라 baseline이 2배 속도로 축적 — §4.1 "4주 미만 오탐" 구간 단축.

- 라벨 불필요 → 콜드스타트 강점(서비스 첫날부터 동작). 단 baseline 4주 미만 구간은 오탐↑(design.md §4.1)
- 품목별 σ 기반이라 "원래 출렁이는 품목"과 "진짜 이상 급락" 구분
- 배치: 가격 폴링 주기에 맞춘 배치(**1차 host cron**, 목표 K8s CronJob) · 코드 몇십 줄 수준, 외부 API 비용 0
- 발송: 이상탐지 컨슈머 → **관심 등록 유저 fan-out** (1차 컨슈머, 목표 KEDA; design.md §7.1·§8.2) → 알림 탭 "싼 재료 담기"
- ✅ **"관심 등록 유저" 기준 = ⓐ 명시 등록으로 스키마 확정**: `price.price_watch`(user_id, item_id) 테이블 존재. ⓑ 레시피북 기반·ⓒ 장보기 기반 자동 등록은 "자동 등록 + 해제 가능" 옵션으로 후속(알림 피로도 제어가 관건).
- ✅ **탐지 로직(z-score 배치) 구현 완료** (2026-07-28) — `pipelines/ingest/detect_price_anomaly.py`. 실데이터 캘리브레이션으로 임계 확정(z 분포 p5=-2.45 → **z≤-2.0**), 실행 시 12건 감지(낙지 -19%·고구마 -18% 등 전부 역대최저 갱신).
  - ⚠️ **z 단독으로는 부족했다**: `item=95`가 z=-16.95인데 실제 하락은 -7%뿐(σ=7원으로 극소) → "안 움직이던 품목이 조금 움직인 것"이 상위를 차지한다. **z + 최소 하락률(8%) 동시 충족**을 요구하고 정렬도 **체감(하락률) 순**으로 한다.
  - ⚠️ **baseline은 적응형**: 스펙의 30일 이동평균에 이력이 미달(14일치)이라 고정 30일이면 전부 스킵된다. **상한 30일·최소 표본 7일·표본 수 노출**로 두고, 이력이 쌓이면 파라미터만 조인다.
- ✅ **노출 정책 확정** (2026-07-28, 팀 결정) — 조건 충족 품목이 많을 때의 기준:
  | # | 정책 | 값 | 근거 | 구현 단계 |
  |---|---|---|---|---|
  | ① | 배치 채택 상한 | **상위 20건**(체감 순) | 평상시 12건이라 걸리지 않는 **안전판** — 크롤 이상·품목 확대 시 무한 증식 방지 | ✅ 탐지 배치 |
  | ② | 유저당 일일 상한 | **미적용** | 알림은 **유저가 직접 관심 등록한 품목에만** 나가므로 원치 않는 알림이 구조적으로 없다. 인위적 상한은 오히려 "등록했는데 알림이 안 오는" 손실을 만든다 | — |
  | ③ | 재알림 쿨다운 | **7일** (동일 user×item) | 급락이 며칠 지속될 때 매일 같은 알림이 가는 것을 방지 | ✅ fan-out(C) |
- ✅ **발행(B)·fan-out(C) 구현 완료** (2026-07-29) — 실 Kafka·실 운영 PG로 엔드투엔드 검증(롤백).
  - **B 발행**: `pipelines/stream/produce_price_anomaly.py` → 토픽 `price.anomaly.detected`(key=item_id, 멱등키 `anomaly_id={item_id}:{source}:{observed_at}`). 배치는 `detect_price_anomaly.py --emit` 으로만 발행 — **기본은 dry-run**(알림은 되돌릴 수 없다).
  - **C fan-out**: `pipelines/stream/consume_price_anomaly.py` → `notify.notification(type='LOW_PRICE')`. **이 컨슈머가 `notify.notification` 의 첫 writer** — 그전까지는 알림 목록 API만 있고 알림을 만드는 주체가 없었다.
  - **수신자 3조건**(INSERT..SELECT 한 방 — 조회·삽입 경쟁 없음): 관심 등록(`price.price_watch`) **AND** 알림설정 ON(`notification_setting.low_price`, 행 없으면 기본 수신) **AND** 7일 쿨다운 경과. 실측 검증: 설정OFF·쿨다운중·미등록 유저는 각각 제외, 8일 경과 후 재수신.
  - 쿨다운이 **멱등성도 겸한다** — 배치 재실행·오프셋 되감기로 같은 메시지를 다시 읽어도 중복 발송되지 않는다(at-least-once 전제).
  - **관심 등록 API**: price `POST/GET /api/prices/watch`, `DELETE /api/prices/watch/{item_id}` (api-spec #29·#30). user_id는 **JWT에서만**(A01) — price 서비스에 검증 전용 `security.py` 추가.
  - ⚠️ **토픽은 반드시 사전 생성** — 브로커 `auto.create.topics.enable=false` 라 토픽이 없으면 produce 가 성공한 듯 보이고 flush 만 타임아웃해 알림이 통째로 유실된다(실측). 발행기가 `DeliveryIncomplete` 로 즉시 실패하도록 했고, `create_topics.py`(Docker)·Strimzi `KafkaTopic`(k8s, `deploy/k8s/price-anomaly.yaml`) 양쪽에 등록했다.
  - ⚠️ **인덱스 필요** — 쿨다운 조회가 `payload->>'item_id'` 표현식이라 부분 인덱스 `notification_lowprice_cooldown_idx` 가 없으면 알림 누적에 따라 순차 스캔이 된다. 운영 적용: `python pipelines/ingest/migrate_lowprice_cooldown_idx.py`(멱등).
- ✅ **탐지 근거 영속 + 기준선 소스별 교정** (2026-07-29, 실측 판정) — `price_baseline`·`price_anomaly`·`price_alert_sent` 3테이블을 실제로 사용한다.
  - ⚠️ **기준선은 (품목, 소스)별이다.** 원설계는 두 소매를 한 기준선에 합쳤으나(100g 정규화로 "2배 축적"), 실측상 두 소매의 100g 단가가 **중앙값 41.9%** 다르고 합치면 σ가 **중앙값 2.08배** 부푼다. z=(x−μ)/σ이므로 σ 2배면 z가 절반이 되어 **z≤−2.0 임계에서 실제 급락이 탐지되지 않는다.** 표본 2배의 이득은 정밀도에 그치고 σ 부풀림은 탐지를 무력화하므로 교환이 성립하지 않는다. → `migrations/2026-07-29b_price_baseline_per_source.sql`(PK를 `(item_id, source, as_of)`로).
  - **`--persist`** 로 기준선·이상치를 기록하고, **`--emit` 이 이를 함의**한다 — 근거 없이 알림만 나가면 "왜 급락인가"에 답할 수 없고 오탐률도 사후 측정할 수 없다. Kafka 발행 성공 후에만 `published_at` 을 찍어 미발행분이 재시도 대상으로 남는다.
  - **근거 스냅샷 무손실** — 탐지 SQL이 `row_number() … rn=1` 로 최저가를 만든 **실제 상품 행**(`retail_product_id`·`crawled_at`·`price`)을 함께 가져온다(roadmap §6 "합성금액 금지"를 스키마가 NOT NULL 로 강제).
  - **발송 멱등 2중** — `price_alert_sent(anomaly_id,user_id)` PK가 **같은 이상치의 재전달**(at-least-once)을, 7일 쿨다운이 **같은 품목의 반복 알림**(피로도)을 막는다. 둘은 겹치지 않는다. 컨슈머는 알림 생성과 이력 기록을 **한 문장(CTE)** 으로 처리 — 나누면 사이에서 죽었을 때 알림만 남고 이력이 비어 재처리 시 중복 발송된다.
  - 실 DB 검증: 기준선 491건(2소스) · 이상치 7건 · 발행 7건 · 재전달 시 알림 불변(전부 롤백).

## 3. 개인화 레시피 랭킹 (규칙 P0 → LightGBM P1 · 자체 학습)

**2단계 설계** — 콜드스타트와 개인화를 모두 잡는다. **AI측 코드는 전 구간 구현 완료**(flag OFF·데이터/스키마/배포 대기). 상세 서빙 계약·블렌딩: `ml/recipe-ranking/SERVING.md`.

- **1단계(P0, 규칙)**: 점수 = 재고 활용률 + 임박 재료 사용 + 저비용 (F11·F16 현행 명세 그대로). ✅ mealplan `ranking.py`.
- **2단계(P1, ML)**: 규칙 후보를 LightGBM(LambdaMART) **재랭킹**. 피처 = 규칙 점수 3종 + 유저 행동 이력 + 레시피 인기도 + 재료 선호. 콜드스타트·장애·데이터부족은 **규칙순 폴백**. ✅ `ml/recipe-ranking/`(serve.py :8009 · mealplan `/rank/personalize` 호출).
- **학습 데이터 = 클릭스트림**: Kafka `events.user.activity` 토픽, **구현 액션 3종**(`VIEW`·`ADD_CART`·`NOTIF_CLICK` — 조리완료/좋아요/폐기는 미구현), user_id 스코프, 수집 동의 고지 — ⚠️ **P0 편입 팀 승인 대기(코드는 구현됨)**.
- **재학습 자동화**: `retrain.py`가 activity 축적분으로 주기 재학습 → 공유볼륨 모델 저장 → 서빙 반영(무인). ✅ `ranking-retrain` 서비스.
- 학습·서빙 인프라: **1차 = docker compose**(serve 컨테이너 :8009 + retrain 배치 + host cron). 목표(AWS 이전 후) = Argo·MLflow·S3·ML Serving.
- **구현 이력**: 노출로깅·발행(#160·168·170) → 피처/학습/평가(#158·166) → 서빙(#172) → ML 재랭킹 호출(#171) → 재학습 자동화(#178) → CI 자동배포 등록(이슈 #180).

## 5. 대화형 어시스턴트 (P1 · RAG) — 요약

**차별점**: 범용 챗봇은 내 냉장고·예산·오늘 시세를 모른다. 답의 근거를 전부 자체 데이터에서 검색해 주입하는 RAG. 용도는 3층 — A 기능 프록시(의도적 겹침) / B 조합·해석(UI 제공 불가) / C 생성(레시피 변형, 챗봇 전용).

**구성**: ① NER 질문 분석 → ② 저장소 4종 병렬 검색(ES 레시피·PG 개인상태·컬리/오아시스 가격·영양 DB) → ③ 품목코드 조인 컨텍스트 조립 → ④ 생성(**Generator 인터페이스, 교체 가능 1개 층**) → ⑤ 근거 태그 + 액션 버튼. 5단계 중 4단계가 자체 구현.

**생성 백엔드 — 1차 template 확정(2026-07-13) → 이후 Gemini prod 전환(2026-07-18)**: 1차 **TemplateGenerator**(무료)로 출시 후, 실사용 품질 실측을 거쳐 **Gemini 생성 백엔드를 prod 활성**(`generator_backend=gemini`, `gemini-flash-lite`). 유료 전환 비용 방어로 **월 예산 상한(#155, 7,200원 = Google billing cap 8,000원의 90%)**을 배선 — 초과 시 template 자동 강등. 가드레일 4층·커버리지 절벽 방어(#174)·기능안내 딥링크 등 상세는 `chat-assistant-ai.md`. design.md §9의 Gemini 재승인 패키지(OCR+소비기한갭)와는 **별개 트랙**.

> **RAG 추가 구현 로드맵**(prep-ahead, chat_message 쓰기경로 #127 열리면 가동): 대화 분석 **리포트 생성기**(데이터 담당 전달, `reports/chat/`) · **장기 개인화 선호 신호 추출**(랭킹 피처 환류) · **FastText 의도분류**(무응답 로그 학습). 분석 LLM = Gemini Flash(비용 격리 전용 키).

> **상세 전체(구성·가드레일 4층·운영·비용 분석·템플릿 품질 한계와 개선안·구현 계획): [`chat-assistant-ai.md`](chat-assistant-ai.md)**

## 6. 소비기한 산출 (P0 기능 · 방식 확정 — 2026-07-14, design.md §9 반영)

기능 자체(F5 소비기한 파싱→F8 임박 알림)는 P0 확정. **✅ 산출 방식 확정: A안(검수 테이블 하이브리드).** `pipelines/ingest/`의 `shelf_life_ref` 테이블·FoodKeeper 적재·한국 시드 + pantry `estimate.py` 조회 경로가 **구현됨**(2026-07-14 확인 시점 DB 실측 1,264행), B안(런타임 AI 직조회)은 채택 안 함.

| | A. 검수 테이블 하이브리드 (채택) | B. AI 검색(런타임 Gemini/검색 직조회) — 미채택 |
|---|---|---|
| 구조 | Gemini 배치로 품목 마스터 300~500개 초안 → 사람이 식약처 소비기한 참고값과 대조 검수 → 확정 테이블 → 런타임은 조회만. 미등재 신품목만 Gemini 온디맨드 산출 후 'AI 추정' 플래그로 테이블 자동 편입(캐시) | 재고 등록 시마다 AI가 실시간 산출 |
| 장점 | 식품안전 항목의 환각 차단 · 런타임 비용 0 · 응답 일관성 | 구현 단순 · 검수 공수 0 |
| 단점 | 초기 검수 공수(1회) · 식약처 소비기한 데이터 확보 여부 🧪 미검증 | 같은 품목에 다른 답 가능 · 식품안전 정보 환각 리스크 · 호출 비용 상시 |

**확정 근거**: 소비기한은 틀리면 유저가 상한 음식을 먹는 안전 항목이라 정적 검수 테이블이 원칙. **AI(Gemini)는 일회성이 아니라 ① 초기 초안 생성 ② 신품목 온디맨드 산출, 두 용도로 상시 사용**한다 — "AI 안 쓰는 방식"으로 오독하지 말 것.

⚠️ **검수 소스 현실 (prd/public-data-ingest §4 실측)**: KFIA 소비기한은 정형 데이터가 아니라 **품목별 PDF뿐**(대표 샘플 수기 입력만 가능), FoodKeeper는 CC0이나 US 기준이라 한식 매칭률 낮음. → 참고 테이블의 커버리지 갭이 예상보다 커서 **Gemini 초안 생성의 역할이 오히려 확대**됨: 초안은 Gemini 배치, 검수 앵커는 KFIA 수기 샘플+FoodKeeper+오아시스 상품페이지 소비기한(크롤 필드) 교차 대조. 보조 검증 소스로 오아시스 상품정보고시 테이블(소비기한·보관방법) 활용 가능.

**남은 절차**: AGENTS.md Gemini 유료예외 재승인(§8 승인 2) — 팀장 승인 대기.

## 7. 영수증 인식 OCR/Vision (P0 · 방식 검토중 — PoC 대기, design.md §9 등재)

F5(재고 등록)·F17(식비 기록)의 입구. design.md §9에 **"Tesseract → Gemini Vision-first(저빈도·감열지 약함, 합계 자가검증 + HITL)"** 방향이 검토중으로 등재 — 아래 ③안으로 수렴 중. **3안 비교**:

| | ① Tesseract 단독 | ② Tesseract + 실패 시 Vision 폴백 | ③ Gemini Vision 단독 |
|---|---|---|---|
| 비용 | 0 | 폴백 건만 (~장당 1원 미만) | 장당 1원 미만 |
| 공수 | 좌표 파서 1.5~2주 | 파서 + 실패판정 + Vision 경로 (최대) | 프롬프트+JSON 파싱 (최소) |
| 리스크 | 한국어 감열지 오류율 높음 | 복잡도 최대 | API 의존·오프라인 불가 |

②의 실패 판정 기준(안): ⑴ 파싱 품목 0건 ⑵ 품목 금액 합 ≠ 영수증 합계 ⑶ NER 품목 매칭률 임계 미달 ⑷ OCR confidence 저하.

담당 의견: 비용이 아니라 **개발 공수 vs 정확도**가 진짜 변수. 실물 영수증 20장으로 Tesseract vs Vision 정확도 비교 PoC 후 결정 권장(수 시간짜리 PoC). 어느 안이든 출력은 동일하게 NER로 넘어가므로 뒷단 설계는 영향 없음.

**(2026-07-14 추가) 실물 영수증 확보 제약으로 외부 공개 벤치마크 조사 — PoC 대체 아님, 방향성 참고용:**
- Gemini 2.5 Pro가 스캔 영수증 정확도 87.46%로 프론티어 VLM 중 최고, **저품질/저대비/감열지 퇴색 문서에서 Tesseract 대비 우세폭이 크게 벌어짐**. 반대로 깨끗한 인쇄 문서에선 격차가 줄어듦(출처: [dev.to 벤치마크](https://dev.to/gabrielanhaia/vision-models-for-ocr-when-they-beat-tesseract-and-when-they-dont-54a6), [arXiv:2509.04469](https://arxiv.org/pdf/2509.04469)).
- Tesseract는 한국어(한글) 인식이 영어보다 학습데이터 부족으로 약함 — 조명 균일한 인쇄문서 기준 85~90%, 그림자·구겨짐 있으면 급락(출처: [한국어 OCR 비교](https://www.lido.app/kr/hangugeo-ocr)).
- **단, 한국어 감열지 특화 정량 벤치마크는 공개자료 부재** — 일반 벤치마크가 design.md §9 방향(Vision-first)과는 일치하나, 최종 확정엔 여전히 국내 실물 PoC가 가장 정확. 실물 확보가 어려우면 팀원 지갑의 감열지 영수증 소수(수 장)라도 확보해 최소 PoC 권장.
- **결론(갱신 2026-07-19): 구현은 ③ Gemini Vision(flash-lite)으로 수렴·구현됨**(`services/ocr/`). 형식상 실물 20장 PoC 검증은 여전히 잔여지만, 실제 서비스는 **Vision-first로 동작**(카테고리 라우팅 + item_master 거버넌스 포함). 위 외부 벤치마크가 이 방향(Vision-first)의 근거. PoC는 사후 정량 검증 위상으로 조정.
