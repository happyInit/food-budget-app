# 마켓컬리 신선식품 크롤러

월 식비 예산 앱(food-budget-app)의 **가격·상품 메타 수집기**. Playwright로 마켓컬리
카테고리 페이지를 순회해 상품 정보를 JSON으로 저장한다. (전체 설계 정본은 `docs/design.md`
— 이 프로토타입은 §3.4 크롤링 정책의 "마켓컬리 핵심 SKU 폴링" 방향을 검증하기 위한
파이프라인 프로토타입이다. 오아시스 크롤러[`../oasis`]와 같은 소비처를 겨냥한 병행 소스.)

## 실행 방법

```bash
cd crawler/kurly
python -m venv venv
./venv/bin/pip install -r requirements.txt
./venv/bin/playwright install chromium
./venv/bin/python prototype.py
```

결과는 `output/kurly_products_{수집시각}.json`에 저장된다 (실행할 때마다 새 파일로 쌓임).

## 수집 대상

`prototype.py`의 `CATEGORIES`에 정의된 마켓컬리 신선식품 4개 카테고리:

| 코드 | 카테고리 |
|---|---|
| 907 | 채소 |
| 908 | 과일·견과·쌀 |
| 909 | 수산·해산·건어물 |
| 910 | 정육·가공육·달걀 |

`https://www.kurly.com/categories/{코드}?page={N}` 페이지를 페이지당 96건씩, 빈 페이지가
나올 때까지 순회한다. (`api.kurly.com`의 내부 REST API가 더 빠르고 깨끗하지만
`robots.txt`상 일반 크롤러(`User-agent: *`)에게는 Disallow라 — Googlebot에만 허용 —
브라우저 기반으로 사람이 보는 페이지만 긁는다.)

가공식품 카테고리(간편식·밀키트 등)는 아직 포함하지 않았다 — design.md는 "신선+가공" 둘 다
대상으로 명시하지만, 이 프로토타입은 신선식품만 다룬다.

## 출력 스키마

상품 1건당 아래 필드를 갖는 JSON 객체:

| 필드 | 설명 |
|---|---|
| `product_id` | 마켓컬리 상품 번호 |
| `detail_url` | 상품 상세페이지 URL |
| `image_url` | 상품 이미지 URL |
| `name` | 상품명 (원문 그대로) |
| `original_price` | 정가 (할인 없으면 `null`) |
| `sale_price` | 판매가 — **쿠폰 미반영, 사이트 표시가 그대로** (아래 "전처리 결정" 참고) |
| `discount_rate` | 할인율 (%) |
| `delivery_info` | 배송 타입 (예: "샛별배송") |
| `quantity_raw` | 상품명에서 뽑은 중량/용량 원문 (예: `"1kg"`, `"300g X 2개입"`) |
| `weight_grams` | 정규화된 중량(g). 개수 단위(개/입/마리 등)만 있고 무게가 없으면 `null` |
| `volume_ml` | 정규화된 부피(mL). 무게 단위 상품이면 `null` |
| `is_variant_selection` | `true`면 "(택1)"/"N종"처럼 여러 변형 중 하나를 고르는 상품이라 무게를 특정할 수 없음 |
| `category_code` / `category_name` | 수집 카테고리 |
| `crawled_at` | 수집 시각 (UTC ISO 8601) |

## 전처리 결정 사항

- **품절 상품 제외**: "담기" 버튼이 없는 카드(품절/재입고대기, "Coming Soon"으로 표시)는
  수집 대상에서 뺀다. 예산 앱에서 살 수 없는 상품은 의미가 없다고 판단해 의도적으로 제외했다
  (`parsers/kurly.py`의 `parse_item` 참고). 카테고리별로 사이트 표시 총건수 대비 6~14% 적게
  나오는 게 정상이다.
- **쿠폰가 아닌 판매가 기준**: "+10%쿠폰" 같은 조건부 뱃지는 파싱하지 않고 버린다. 쿠폰은
  회원등급·최초가입 등 조건부라 로그인 없는 크롤러가 적용 여부를 알 수 없고, "시세" 신호로
  보기도 어렵다. `sale_price`는 항상 사이트에 표시된 판매가(할인가) 그대로다.
- **중량/용량 정규화까지만, 재료 매칭(item_code)은 범위 밖**: `weight_grams`로 "감자 500g"과
  "감자 1kg"의 100g당 가격은 계산할 수 있지만, 이 둘을 "같은 감자"로 묶어주는 로직은 없다.
  품종명(수미/두백 등)은 무시해도 되지만 부위명(돼지고기 앞다리 vs 오겹살, 100g당 최대
  12.7배 가격차 확인)은 절대 무시하면 안 되는 등 재료마다 판단이 달라서, 이건 규칙 기반
  일반화가 안 되고 design.md §6.3 "표준 품목 마스터" PoC(식약처 코드 앵커링 + 팀 큐레이션
  ~300~500 품목 + CRF NER)로 별도로 다뤄야 한다.

## 알려진 한계

- **크롤 속도**: 4개 카테고리 전체(~3,300건, 페이지 로드 약 45회) 수집에 약 8분 소요.
  카테고리 페이지 로드 직후 스크롤 없이 바로 파싱해서, 상품 이미지가 아직 lazy-load 안 된
  카드마다 `_get_card_image_url`의 개별 폴백(스크롤+500ms 대기)이 걸리는 것으로 추정된다.
  페이지 로드 후 스크롤 1회를 넣으면 상당히 줄어들 것으로 보이나 아직 적용 전이다.
- **가공식품 카테고리 미포함**: 위 "수집 대상" 참고.
